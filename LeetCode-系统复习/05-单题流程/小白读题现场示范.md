## 1. 原题事实

原题里有这些词：

> 之后、第一个、严格更高、几天后。

我把它们逐个圈出来，先只写能指回原句的事实。

### 题目给了我什么

- `temperatures` 是一个按日期排列的温度数组；
- 第 `i` 个位置就是第 `i` 天；
- 每个位置有一个温度；
- 对第 `i` 天，要向右看未来的日期。

### 要我交回什么

- 一个与输入等长的答案数组；
- 第 `i` 个答案表示相隔几天；
- 如果未来没有严格更高温，第 `i` 个答案为 `0`。

### 示例提供了什么

示例只能说明输入怎样走到输出，不能替我补完一般规则。

### 明确保证和明确禁止

- 保证：需要找的是未来；
- 保证：必须是第一个严格更高；
- 保证：找不到时交回 `0`；
- 禁止：不能把相等温度当成更高；
- 禁止：不能把温度差当成相隔天数。

### 现在还不知道

```text
题目确认的输入：按日期排列的温度数组。
题目要求交回：每一天到未来第一次严格更高温的日期差。
题目保证：之后、第一个、严格更高；找不到为 0。
题目禁止：相等不算更高；交回的不是温度差。
我现在还不知道：一个普通人具体怎样逐天检查，日期和温度怎样绑定。
```

## 2. 人话扩写

我现在不优化，只把题目改写成一个人能照着做的动作。

| 原句 | 新增规则 | 忽略后具体会错在哪 | 来源 |
| --- | --- | --- | --- |
| 之后 | 只能看未来日期 | 可能向左看到更高温 | 事实 |
| 第一个 | 遇到第一个满足条件就停止 | 可能继续找到更远或更高的日期 | 事实 |
| 严格更高 | 相等不能停 | 两个 `70` 会互相结算 | 事实 |
| 几天后 | 交回两个日期的下标差 | 可能写成温度差或日期值 | 事实 |

合成后的过程：

```text
我手里有：第 i 天和它的温度。
我从：第 i + 1 天开始。
我反复做：向右逐日看温度。
条件“严格更高”意味着我不能：在相等温度时停下。
当：第一次遇到严格更高温时停止。
我最后要交出：两个日期的下标差；找不到就写 0。
```

别人现在可以照着这段文字演算，但还不知道“日期”和“温度”是不是应该分开。

## 3. 对象

我卡在一个很小的点：两个温度都写成 `70` 时，它们算不算同一个东西？

这不是凭空问的。人话过程里同时出现了“天数”和“温度”，但还没有证据说明它们怎样绑定。

### 纸上动作

我写：

```text
日期 0：70
日期 1：70
```

同一个数字 `70` 写在两个位置。题目要求交回两个日期之间的距离，所以这两个 `70` 的身份不能相同。

新增证据：

```text
值可以相同；
位置不同；
答案属于日期，不是数值本身；
温度绑定在某一天。
```

### 对象表

| 题目对象 | 值和状态 | 身份由什么决定 | 位置或时间 | 和谁发生关系 | 最终要得到什么 |
| --- | --- | --- | --- | --- | --- |
| 日期 | 等待或已结算 | 原数组下标 | 从旧到新的时间位置 | 与右侧未来日期比较 | 第一次严格更高日期与它的距离 |
| 温度 | 当天数值 | 绑定在具体日期上 | 跟随该日期 | 可与同日和未来日期的温度比较 | 判断是否严格更高 |
| 答案 | 未写入或已写入 | 每个日期各有一份 | 放在该日期的结果位置 | 由未来事件写入 | 相隔天数，找不到为 `0` |

## 5. 第一次变化与答案确定时刻

看着刚才的过程，我第一次看见“答案已经确定”的动作发生在第 2 天：

```text
变化前：第 0 天还没有答案，未来游标在它右边。
触发事件：游标第一次遇到严格更高的 71。
变化后：第 0 天得到 2，不再向右看。
答案产生时刻：写下两个日期下标差时。
```

这里不想保存什么，也不讨论优化。只确认过程事实：

> 一个起始日期，在第一次遇到严格更高的未来温度时，从等待状态变成已结算状态。

### 为什么这也适用于后面的日期

第 1 天同样在第一次看到 `71` 时确定答案。第 2 天没有未来日期，所以保持 `0`。

我第一次看出：

```text

```

但这句话只说明过程中的重复现象，仍然不知道它是否超出预算。

## 6. 数据范围与慢过程预算

现在才看完整约束，不只抄 `n`。

```text
1 <= temperatures.length <= 10^5
30 <= temperatures[i] <= 100
```

### 最坏输入

如果温度单调不升，比如：

```text
[100, 99, 98, ...]
```

每个日期都找不到更高温，因此都要向右看到末尾。

第 0 天比较 `n - 1` 次，第 1 天比较 `n - 2` 次，依此类推：

```text
(n - 1) + (n - 2) + ... + 1
= n(n - 1) / 2
```

`n = 10^5` 时约为五十亿次比较。

### 范围只说明什么

```text
小白此刻真正的原话疑问：这份逐日重扫到底有多慢，题目容得下吗？
为什么这个疑问现在才出现：现在已有完整慢过程，才有资格数它的重复。
纸上实际做了什么：取单调不升的最坏输入，逐轮相加比较次数。
做完后新增了什么证据：官方约束、约五十亿次比较、不能稳定承受的复杂度家族。
这份证据只能说明什么：每个日期完整重扫的平方级过程不可靠。
它还不能说明什么：具体应该保存什么，更不能用某个方法名替代证据。
因此下一问只能是什么：带着这份代价重看，哪份信息真的被重复读取？
回答它需要什么证据：同一条人工过程上的最小重复例子。
如果答不出，退回哪里：交接 4 和交接 5。
```

这一步只说“平方级过程不稳妥”，不报任何具体结构。

## 7. 第二次变化

我带着预算回到同一条过程，换一种观察方式：不再从每个起始日期向右扫，而是从左到右看每一天到来时发生了什么。

用：

```text
[75, 71, 69, 72]
```

从左到右走：

```text
75 到来：
没有更早的等待项，75 进入等待。

71 到来：
不高于 75，不能结算 75；71 进入等待。

69 到来：
不高于 71，不能结算 71；69 进入等待。

72 到来：
高于 69，结算日期 2；
高于 71，结算日期 1；
不高于 75，75 继续等待；
72 进入等待。
```

### 这次我看见了什么

#### 重复查询

原来的慢过程里，`72` 会被很多更早日期向右重新检查。

最小证据：日期 2 和日期 1 都在向右检查时遇到同一个 `72`。

#### 候选失效

`72` 到来后，日期 2 和日期 1 已经找到第一次严格更高温，不再等待。

最小证据：`69 < 72`、`71 < 72`，两者在同一事件中被结算。

#### 子问题复用

这道题里，当前现场没有形成独立的子问题复用现象。相同未来事件会被重复查看，但不需要写“没有证据也硬填一个复用”。

#### 顺序约束

日期从最近一端加入，也先从最近的一端检查。

为什么能连续删除？

假设仍在等待的两个日期是 `i < j`，且：

```text
temperatures[i] < temperatures[j]
```

那么第 `j` 天到来时已经严格高于第 `i` 天，第 `i` 天早在当时就会被结算，不可能还留在等待集合里。

所以仍有等待日期时：

```text
从旧到新，温度不增。
```

因此新温度从最近端检查，遇到第一个不低于今天的等待日期就可以停止。

### 翻译成操作

```text
需要从最近端加入今天；
需要读取最近端等待日期；
需要从最近端连续删除已经结算的日期；
加入和删除必须保持日期的时间顺序。
```

这时仍然只知道操作，不知道具体容器。

### 交接 7

## 8. 候选比较与方向确认

现在才允许具体结构名进入。

### 交接 8

```text

为什么这个疑问现在才出现：操作需求刚刚具体，候选才有可比对象。
纸上实际做了什么：比较继续重扫、只记数值和保存等待日期三种真实候选。
做完后新增了什么证据：支持、缺口、失效条件和代价。
这份证据只能说明什么：保存等待日期能承担当前操作和预算。
它还不能说明什么：状态变量、更新顺序和代码怎样落地。
因此下一问只能是什么：怎样把等待日期变成状态并保证更新顺序？
回答它需要什么证据：状态、转移、不变量和反例。
如果答不出，退回哪里：交接 7 的操作需求。
```

### 真实候选

| 候选 | 支持哪些操作 | 缺少什么 | 何时失效 | 代价 |
| --- | --- | --- | --- | --- |
| 每个日期继续向右重扫 | 能正确找到答案 | 不能避免重复读取未来 | 最大输入约五十亿次比较 | 时间不可接受 |
| 只记录温度的某个值 | 能知道数值出现过 | 不能保存日期身份和等待顺序 | 相同温度或需要日期差时失效 | 丢失位置关系 |
| 保存尚未结算的日期 | 最近端加入、读取、连续删除 | 需要证明停止条件和更新顺序 | 相等温度不能删除，必须先结算再加入 | 每个日期最多进出一次 |

我真正比较了三种方向，不是临时补一个衬托答案的候选。

### 完整方向确认句

> 逐日向右重扫会让同一未来温度被很多日期重复检查，最坏约五十亿次。第二次变化证明，新温度需要从最近的等待日期开始连续结算，日期还要从最近端加入和删除。保存尚未结算的日期正好支持最近端加入、读取和连续删除；每个日期只在第一次遇到严格更高温时删除，所以这个方向能承担过程提出的全部操作。

这时可以说明：这种“最近端加入、读取、连续删除”的结构是栈，Java 里可以用 `ArrayDeque` 承担。

2. 再用对象证据把温度与日期分开；
3. 再手算最笨过程；

5. 读范围后确认逐日重扫太慢；
6. 带代价重看，发现连续结算和最近端顺序；

### 状态定义

```text
answer[i]：第 i 天第一次遇到严格更高温还要等几天。
waiting：尚未结算的日期下标，按进入时间排列。
```

### 初始状态

```text
answer 全部为 0。
waiting 为空。
```

### 一次转移

```text
读取今天的日期 i 和温度 current。

当 waiting 非空，并且 current 严格高于最近等待日期的温度：
    弹出最近等待日期 previous
    answer[previous] = i - previous

把 i 加入 waiting。
```

### 为什么更新顺序不能交换

最小反例：`[70, 70]`。

如果遇到相等温度也弹出，第 0 天会被错误结算。因此删除条件必须是严格更高。

另一个顺序反例：如果先把今天加入，再检查是否需要结算今天，今天可能和自己比较。状态范围会从“过去的未结算日期”变成“包含当前的混合集合”。

### 不变量

```text
waiting 中只有已经出现、仍未结算的日期；
下标从旧到新递增；
温度从旧到新不增。
```

为什么不会漏？

每个日期在第一次遇到严格更高温时被删除，删除时写下当前日期差。

为什么不会错？

只删除严格低于今天的等待日期；相等温度继续等待。

为什么可以提前停止？

等待温度从旧到新不增。遇到第一个不低于今天的等待日期后，更早的等待日期只会更高，也不可能被今天结算。

### 伪代码

```text
answer = new int[n]
waiting = empty

for i from 0 to n - 1:
    while waiting is not empty and temperatures[i] > temperatures[top]:
        previous = remove top
        answer[previous] = i - previous
    add i to top

return answer
```

### Java

```java
class Solution {
    public int[] dailyTemperatures(int[] temperatures) {
        int n = temperatures.length;
        int[] answer = new int[n];
        ArrayDeque<Integer> waiting = new ArrayDeque<>();

        for (int i = 0; i < n; i++) {
            while (!waiting.isEmpty()
                    && temperatures[i] > temperatures[waiting.peek()]) {
                int previous = waiting.pop();
                answer[previous] = i - previous;
            }
            waiting.push(i);
        }

        return answer;
    }
}
```
