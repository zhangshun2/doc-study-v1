# 小白读题现场示范：每日温度

> 这不是标准答案摘要，也不是要求你照抄的独白。它是一份第一人称的学习现场，用来看清一个不知道单调栈的人，怎样从字面题意走到可验证的算法方向。
>
> 示范中的犹豫、暂时错误候选和“我还不知道”都是流程的一部分。前六段不写完整代码，方向确认之后才进入第二层推导链。
>
> 下面的“我一开始以为”是这份真实示范里出现过的心理现场，不是每题必须补上的固定台词。换一道题时，如果没有形成初始方向，就写“没有形成候选”；如果已经知道答案，就标记为“事后校验”，不能把记忆倒写成新手直觉。

题目来源：[LeetCode 739. 每日温度](https://leetcode.cn/problems/daily-temperatures/)。

## 0. 开始前：我只允许自己做什么

我现在的真实状态是：

- 我知道数组、下标和循环。
- 我记得有些题会用栈，但还不知道这道题为什么要用。
- 我不能从“每日温度是单调栈题”开始，因为这会跳过题目怎样产生等待和结算。

我先留下真实的现场状态：

| 项目 | 当前内容 |
| --- | --- |
| 我一开始以为 | 每一天各扫一遍右边，应该就能得到答案 |
| 哪条事实暂时支持它 | 题目要求“之后”的日子，逐天向右看符合这个方向 |
| 哪条事实让我保留疑问 | 题目不只要任意更高温，而要“下一个”更高温；很多日期可能重复看同一段未来 |
| 我现在还不知道 | 多个日期等待时，能不能让一个新温度同时结算它们 |
| 下一个最小问题 | 先按最直接的办法走一个例子，看看哪些检查被重复 |
| 什么证据会改变判断 | 如果同一个未来温度被多个起点重复读取，并且范围不允许平方级重扫，就必须重新考虑保存什么 |

本次现场只按下面的顺序走：

```text
读原题
-> 扩写成生活过程
-> 清点对象
-> 手工走最小例子
-> 第一次观察变化
-> 读数据范围并估算预算
-> 生成候选，但不选结论
-> 第二次观察变化
-> 比较候选，确认方向
-> 才进入状态、更新、不变量和代码
```

如果某一段只能说出“感觉应该这样”，我就把它记成暂时卡住的地方，而不是假装已经推导完成。

## 1. 先只读题：我到底被要求交出什么

我先把官方题面原句放在这里，不把它改写成算法摘要：

> 给定一个整数数组 `temperatures`，表示每天的温度，返回一个数组 `answer`，其中 `answer[i]` 是指对于第 `i` 天，下一个更高温度出现在几天后。如果气温在这之后都不会升高，请在该位置用 `0` 来代替。

我逐句确认它新增了什么：

| 原句 | 我读到的事实 | 来源 | 我暂时不能补上的假设 |
| --- | --- | --- | --- |
| 整数数组 `temperatures`，表示每天的温度 | 每个数组位置是一天，位置上的数是当天温度 | 事实 | 温度会不会先升后降、是否只有一种变化趋势 |
| 返回一个数组 `answer` | 每一天都必须有对应答案，输出长度与输入相同 | 推导 | 答案是否只保留有更高温的日期 |
| `answer[i]` 是第 `i` 天“下一个更高温度”出现在几天后 | 对固定日期，要找一个未来日期；取第一个满足条件者；输出两天位置差 | 事实 | “下一个”是否指紧挨着的下一天 |
| 之后都不会升高时用 `0` | 找不到未来更高温时保留 `0` | 事实 | 是否存在其他表示“没有答案”的特殊值 |

这里最容易被脑补的一条是“日期会明显持续升温”。题目没有这个保证。另一个是我最早想直接看“有没有更高温”，但原句要的是**第一个**更高温，所以仅仅知道未来存在更高温还不够。

我先不写算法，再把事实、推导和未知分开记录：

| 项目 | 我现在确定的内容 |
| --- | --- |
| 输入 | 一个整数数组 `temperatures`，每个位置代表一天，数值代表当天温度 |
| 输出 | 一个与输入等长的整数数组 `answer` |
| 单格答案 | 对第 `i` 天，如果有未来的更高温度，答案为“第一个这样的未来日期与 `i` 的距离” |
| 找不到时 | 对应位置为 `0` |
| 方向 | 只能看当前日期的右边，也就是下标更大的位置 |
| 比较 | “更高”表示严格大于，相等不算 |
| 最近性 | 要第一个满足条件的未来日期，不是未来最高温所在日期 |

我现在还不知道：

- 一个普通人拿到 `temperatures` 后，第一天具体看哪里、什么时候记答案、什么时候停？
- “下一个”和“更高”这两个词，分别在逐日动作里阻止哪一种错误？

我刚刚已经确认题目要什么和不能假设什么，因此现在最早缺的不是优化方向，而是人的动作顺序。下一问只问：“如果只用最直接的办法，一个人会怎样处理每一天？”能回答它的是逐句扩写和一个最小例子。此时任何“用栈”“用数组”“用线段树”的想法都只是记忆，不是由题目事实得到的结论。

最小事实例子：

```text
temperatures = [70, 71]
第 0 天后面第一个更高温是第 1 天，所以 answer[0] = 1 - 0 = 1
第 1 天没有未来日期，所以 answer[1] = 0
结果 = [1, 0]
```

## 2. 把题干扩写成一个人能看见的过程

先逐句把压缩事实变成人的动作。下表中的“新增动作”不是题面外的设定，而是把原句本来承载的关系展开：

| 原句事实 | 它在人的过程里新增了什么 | 如果忽略会错在哪 | 来源 |
| --- | --- | --- | --- |
| 每个位置代表一天 | 每一天是一个有身份的任务，不能只留下一个温度值 | 丢掉日期身份后，无法计算相隔几天 | 推导 |
| 要找右侧之后的日子 | 人的目光只能向未来移动 | 向左找可能把更早的日期误当答案 | 事实 |
| 是“下一个更高温度” | 第一个严格超过当天的未来日期到来时就停止 | 继续找到未来最高温，输出错误日期 | 推导 |
| “更高”不是“不低于” | 相等温度出现时仍要继续等 | `[70,70,71]` 会在第二个 `70` 错误停止 | 推导 |
| 答案是出现“几天后” | 最终写下两个日期位置之差 | 写温度差、日期本身或温度值都会错 | 事实 |
| 之后不会升高时用 `0` | 走到末尾仍没有成功时停止，并保留默认值 | 把“没有答案”误写成最后一个日期或负数 | 事实 |

这些片段按时间顺序合起来，才是完整的人话过程：

> 我站在每一天，手里拿着当天的温度和日期。我向右一天一天看。第一次看到比当天更热的日子时，我记下两个日期相差几天，然后这一天的任务结束。如果走到最后也没有更热的日子，就记 `0`。所有日期都要各自得到答案。

这里每个新增解释都能回到题面：

- “站在每一天”来自每个下标都要有一个答案。
- “向右看”来自题目说的是之后的日子。
- “第一次”来自题目要下一个更高温度。
- “严格更热”来自“更高”，所以相等不能停止。
- “记 `0`”来自题目明确给出的不存在时规则。

扩写完成后，我仍然不知道怎样加速。此时我还不知道“等待日期”是否会成为后面的模型；它甚至还没有出现在这段人工过程中。我刚刚已经知道人会怎样执行，但最早缺的是对象身份和过程里真正发生的变化，所以下一问只问：“走一个最小例子时，哪一刻谁的状态变了，答案何时确定？”能回答它的是一个完整小例子的手算。

## 3. 清点对象、走人工过程、第一次观察变化

### 3.1 对象

题目世界里的对象不是抽象容器，而是：

- **日期：** 序列中的一个位置，用来计算相隔几天。
- **当天温度：** 这个日期携带的比较属性。
- **未来日期：** 当前日期右边仍待检查的位置。
- **等待关系：** 一个较早日期正在等待未来某天超过它。
- **答案：** 每个日期对应的等待天数，找不到更高温时为 `0`。

日期和温度必须绑定。两个日期可能都是 `70` 度，但它们的答案可以不同，所以只保存温度会丢失“这是哪一天”的身份。

### 3.2 最直接的人工过程

如果完全不考虑效率，我会这样做：

```text
从第 0 天开始
-> 看第 1 天是否比第 0 天热
-> 不满足就继续向右看
-> 第一次满足时，记下距离
-> 回到第 1 天，重新向右找
-> 一直处理到最后一天
```

用 `[70, 70, 71]` 手算：

| 起始日期 | 向右看到什么 | 什么时候停止 | 答案 |
| --- | --- | --- | --- |
| 第 0 天，`70` | 第 1 天也是 `70`，不更高；第 2 天是 `71` | 第 2 天第一次严格更高 | `2` |
| 第 1 天，`70` | 第 2 天是 `71` | 第 2 天第一次严格更高 | `1` |
| 第 2 天，`71` | 右边没有日期 | 走到末尾仍不满足 | `0` |

结果应为 `[2, 1, 0]`。

这个例子确认了三件事：

1. 相等温度不能结束等待。
2. 答案是下标差，不是温度差。
3. 默认值 `0` 正好表示没有找到。

### 3.3 第一次变化

我只观察过程里真实发生的变化，不急着优化：

```text
变化前：当前起始日期还没有答案，未来游标在它右边
触发事件：未来游标遇到一个严格更高的温度
变化后：当前起始日期得到答案，未来游标停止
```

用 `[75, 71, 69, 72]` 看：

- 第 0 天的 `75` 向右看到 `71`、`69`、`72`，都不更高，最后没有答案。
- 第 1 天的 `71` 向右看到 `69`，再看到 `72`，在第 3 天停止，答案是 `2`。
- 第 2 天的 `69` 看到第 3 天的 `72` 就停止，答案是 `1`。
- 第 3 天没有未来日期，答案是 `0`。

结果应为 `[0, 2, 1, 0]`。

我注意到第 3 天的 `72` 在第 1 天和第 2 天的向右扫描里都出现过。现在我只记录这个过程事实：同一个未来日期会出现在多次扫描中。

这里我故意不把“用栈”写进第一次变化。第一次变化只回答“什么事件让某个起始日期不再需要向右看”；它还没有回答“哪些日期值得同时保存”“保存到什么程度”“什么时候删除”。这些问题属于第二次变化。

我刚刚已经看见同一段未来会被多次检查，但还不知道这份重复究竟值不值得处理。因此现在最早缺的是代价证据，下一问只问：“最慢的人工过程在这个范围里大约重复多少次？”能回答它的是官方约束和最坏情况的手算。

## 4. 读数据范围，只用来缩小候选

官方约束：

```text
1 <= temperatures.length <= 10^5
30 <= temperatures[i] <= 100
```

我先估算最直接的人工过程。

最坏情况可以取单调不升的温度，例如：

```text
[100, 99, 98, 97, 96]
```

每个日期都要一直向右看到末尾，仍然找不到更高温。比较次数是：

```text
(n-1) + (n-2) + ... + 1
= n(n-1)/2
```

当 `n = 10^5` 时，约为：

```text
100000 * 99999 / 2
约等于 50 亿次
```

这个数量不能作为稳定实现的依据。但“太大”仍然没有告诉我应该用什么。范围只完成两件事：

- 排除仍然对每个日期完整向右重扫的方向。
- 保留能够减少重复检查、并且每步操作足够少的候选。

温度值只有 `30` 到 `100`，这是一个额外的可利用事实，但不能把它误写成“官方要求使用某个算法”。

我从范围只得到下面四行：

```text
官方约束：n <= 10^5，温度只取 30..100
慢过程最坏大约重复：n(n-1)/2，约五十亿次比较
因此首先不能稳定依赖：每个日期都完整向右重扫的平方级过程
结合过程需要的操作，仍待验证的候选是：减少重复扫描的共享结构、利用小值域记录最近位置、其他范围查询结构
```

“温度只有 71 种”让我保留了另一种候选，但它不能反过来证明题目一定该用栈。范围负责排除和保留，不负责点名。

### 4.1 从慢过程生成候选，而不是从题目标签猜

慢过程真正反复做的事情是：

> 对很多起始日期，重复查看同一批未来温度，判断未来是否第一次超过起始温度。

我根据“需要什么操作”列出功能候选。下面的“排序”“区间”等词只是我借熟悉的说法帮助自己描述需求，不代表现在已经确定具体方法；具体结构名留到第六段比较。

| 候选方向 | 它能利用什么 | 现在还缺什么 | 暂不采用的原因 |
| --- | --- | --- | --- |
| 每个日期继续完整向右扫描 | 直接、不会漏 | 没有任何共享 | 最坏约五十亿次 |
| 只保存未来最高温 | 能知道未来是否存在更高温 | 不知道第一个更高温在哪里 | `[70,71,100]` 中最高温是 `100`，但答案应由 `71` 产生 |
| 先排序温度 | 容易比较大小 | 丢失原始日期先后 | 仍然需要恢复“右侧最近”的关系 |
| 保存尚未得到答案的日期，让新温度到来时处理 | 同一未来温度可能一次结算多个旧日期 | 还不清楚保留顺序 | 需要继续观察等待对象怎样失效 |
| 从右向左记录每种温度最近出现的位置 | 温度值只有 `71` 种 | 每次要检查更高温度范围 | 这是合法候选，但依赖小值域 |
| 按温度范围查询更高温度中的最近日期 | 能表达数值范围和最近位置 | 需要范围维护，结构还没确定 | 范围可行，但目前看不出比更简单的候选更必要 |

到这一步，我只知道自己不应该继续完整重扫。还不能说“所以用栈”。

我刚刚已经有了操作预算和功能候选，但还不知道未来到底要保留哪份信息、它何时失效。因此下一问只问：“带着这个预算重看，哪批等待对象会在同一个事件后一起结算，处理应当从哪一端开始？”能回答它的是第二次变化。

## 5. 第二次观察变化：等待日期怎样产生和失效

我把视角从“每个日期主动向右找”换成“我按时间从左向右经过每个日期”。这仍然是在观察同一个题目，只是换看在某一刻谁已经出现。

用 `[75, 71, 69, 72]` 走一遍：

```text
第 0 天，75 到来
-> 它暂时没有答案，进入等待

第 1 天，71 到来
-> 71 不高于 75，不能结算第 0 天
-> 71 自己也没有答案，进入等待

第 2 天，69 到来
-> 69 不高于 71，不能结算第 1 天
-> 69 自己也没有答案，进入等待

第 3 天，72 到来
-> 72 高于 69，第 2 天结算，答案 3 - 2 = 1
-> 72 高于 71，第 1 天结算，答案 3 - 1 = 2
-> 72 不高于 75，第 0 天继续等待
-> 72 自己进入等待
```

这里的变化类型是：

- **对象产生：** 一个日期到来时，通常先进入等待。
- **对象失效：** 未来某天严格更高时，日期不再等待。
- **批量结算：** 一个新温度可能连续解决多个更早的等待日期。
- **阻挡：** 遇到不低于今天温度的等待日期时，今天不能继续解决它。

### 5.1 我还不知道具体结构，也能先问出需要哪些操作

现在我只知道要保存“尚未结算的日期”。我还需要回答：

1. 新日期应该从哪一端加入等待集合？
2. 新温度应该从哪一端开始检查旧日期？
3. 检查到什么时候必须停止？
4. 已经结算的日期为什么可以删除？

等待日期按时间到来，所以我自然把它们按从左到右的顺序记住。新日期加入最右端。新温度到来时，先检查最近进入等待的日期，因为最近日期还没得到答案；如果它也不能被今天解决，更早的日期是否还有可能被解决？

这里不能靠感觉。我要证明等待日期之间的温度有什么关系。

假设两个尚未结算的日期是 `i < j`，并且：

```text
temperatures[i] < temperatures[j]
```

那么第 `j` 天到来时，它已经严格高于第 `i` 天，第 `i` 天应该在那一刻被结算，不可能还留在等待集合里。

所以，任意两个仍在等待的日期，只可能满足：

```text
较早日期的温度 >= 较晚日期的温度
```

也就是说，等待集合从旧到新的温度不会上升。这个关系不是题目标签给的，是从“为什么还没被结算”推出来的。

新温度到来时：

- 如果它高于最近等待日期，那个日期第一次遇到更高温，可以结算。
- 结算后，再检查它前面一个等待日期。
- 一旦遇到温度不低于今天的等待日期，今天无法解决它；更早的等待日期温度还更高，今天同样无法解决。

这自然产生了“最近端加入、最近端检查、最近端连续删除”的操作需求。到这里，等待模型才开始支持这类操作；具体结构仍然只是候选，不是题目事实。

我刚刚已经知道需要哪些操作和等待关系，但还没有比较具体候选。因此下一问只问：“哪个候选能承担最近端加入、检查和连续删除，代价又符合当前范围？”能回答它的是候选比较；在方向确认句写出之前，不能把“栈”当成已经证明的答案。

## 6. 比较候选并确认算法方向

现在比较几个真正可行的方向：

| 候选 | 消除哪份重复劳动 | 需要什么操作 | 代价或限制 |
| --- | --- | --- | --- |
| 每个日期向右重扫 | 不消除 | 每个日期重新访问未来 | 最坏约 `O(n^2)`，当前规模不可靠 |
| 从右向左记录每种温度最近位置 | 避免每个日期扫描所有未来日期 | 对当前温度检查更高温度的最近位置 | 时间约 `O(100n)`，合法但依赖值域很小 |
| 保存等待日期，并从最新一端连续结算 | 新温度只处理当前仍可结算的旧日期 | 最近端加入、检查、删除 | 需要证明等待顺序和停止条件，结算后每个日期只处理一次 |
| 区间查询结构 | 快速找更高温度中的最近位置 | 建结构、更新位置、范围查询 | 可实现，但当前生命周期模型更简单 |

方向确认句：

> 直接过程会让同一批未来温度被很多起始日期重复扫描，最坏约五十亿次。一个新的更高温到来时，可以同时解决多个仍在等待且温度更低的旧日期，而遇到不低于它温度的等待日期后就可以停止。因此我需要保存尚未结算的日期，并支持在最近端加入、连续比较和删除。等待日期从旧到新的温度不会上升，所以一个只在末端操作的结构就足够完成结算，每个日期最多加入一次、删除一次。当前方向选择这种等待结算模型。

注意，这句话里：

- “约五十亿次”是我的操作预算，不是官方推荐复杂度。
- “温度不会上升”是从等待状态推出的关系。
- “只在末端操作”是从加入和结算顺序推出的操作需求。
- “栈”可以不写在句尾；即使写了，它也必须由前面的需求支持。

方向确认后，才进入下面的第二层推导链。

## 7. 方向确认后的思维链

### 7.1 状态定义

```text
answer[i]：第 i 天第一次遇到严格更高温还要等几天；没有答案时保持 0
waiting：尚未结算的日期下标
```

`waiting` 从底部到顶部对应从旧到新的日期。它们当前没有答案，并且温度从底部到顶部不会上升。

### 7.2 初始状态、停止和答案时机

- 开始时还没有处理任何日期，`waiting` 为空。
- `answer` 全部初始化为 `0`，因为“没有更高温”正是题目要求的默认答案。
- 每处理到 `today`，用它结算仍能结算的旧日期。
- 处理完最后一天后，仍然留在 `waiting` 的日期都没有更高温，答案保持 `0`。

### 7.3 一次转移

读取今天 `today`：

```text
while waiting 非空
      且 temperatures[today] > temperatures[waiting 顶端]:
    previous = 弹出顶端
    answer[previous] = today - previous
把 today 加入 waiting
```

这条转移回答的问题是：

> 今天这个新事件能让哪些旧日期第一次得到确定答案？

### 7.4 更新顺序

必须先处理旧日期，再把今天加入等待集合。

如果先把今天加入：

- 今天会出现在本应只包含过去日期的等待集合里。
- 后续比较会混入“今天结算自己”的错误语义。
- 即使额外加条件避开自己，也会让状态定义从“已经过去且尚未结算的日期”变成不一致。

因此顺序是：

```text
读取今天
-> 结算被今天超过的旧等待项
-> 今天进入等待
```

### 7.5 不变量与正确性

每一轮结束后：

1. `waiting` 中只有已经出现、仍未结算的日期。
2. 下标从底部到顶部递增。
3. 对应温度从底部到顶部不增。

为什么不会漏：

- 一个日期进入等待后，只会在遇到第一个严格更高的未来日期时被删除。
- 删除时写下的是当前下标差，所以不会错过更近的更高温。

为什么不会错结算：

- 只有 `temperatures[today] > temperatures[waiting 顶端]` 才删除。
- 相等温度不会触发，符合“严格更高”。

为什么某个旧日期不会在更早的更高温出现时仍被留下：

- 那个更高温到来时，会从最近端连续结算所有更低的等待日期。
- 如果它被一个不低于当前事件的温度挡住，说明当前事件也无法超过那个更早日期。

### 7.6 结构与操作

需要的操作是：

- 在最近端加入今天。
- 读取最近端日期。
- 连续删除最近端已经结算的日期。

普通数组也能完成，但删除末尾以外的位置会带来移动；队列处理的是最早加入的一端，不符合“先结算最近等待项”的顺序。双端队列或栈都支持最近端操作。本题只需要在一端加入、读取和删除，因此使用栈语义最直接。

Java 中 `ArrayDeque` 可以作为栈使用：

```java
Deque<Integer> waiting = new ArrayDeque<>();
waiting.push(today);
int previous = waiting.pop();
int recent = waiting.peek();
```

这里保存下标而不是温度，因为结算答案要计算 `today - previous`；温度可以从原数组按下标读取。

### 7.7 伪代码

```text
answer = all 0
waiting = empty stack

for today from 0 to n - 1:
    while waiting is not empty
          and temperatures[today] > temperatures[waiting.top]:
        previous = waiting.pop()
        answer[previous] = today - previous
    waiting.push(today)

return answer
```

### 7.8 Java 基准实现

```java
import java.util.ArrayDeque;
import java.util.Deque;

class Solution {
    public int[] dailyTemperatures(int[] temperatures) {
        int[] answer = new int[temperatures.length];
        Deque<Integer> waiting = new ArrayDeque<>();

        for (int today = 0; today < temperatures.length; today++) {
            while (!waiting.isEmpty()
                    && temperatures[today] > temperatures[waiting.peek()]) {
                int previous = waiting.pop();
                answer[previous] = today - previous;
            }
            waiting.push(today);
        }

        return answer;
    }
}
```

### 7.9 反例和边界

| 输入 | 应得结果 | 检查点 |
| --- | --- | --- |
| `[70, 70, 71]` | `[2, 1, 0]` | 相等不结算，两个 `70` 都等 `71` |
| `[30, 40, 50, 60]` | `[1, 1, 1, 0]` | 每天的下一天都结算当天 |
| `[90, 80, 70]` | `[0, 0, 0]` | 所有日期最终留在等待集合中 |
| `[75, 71, 69, 72]` | `[0, 2, 1, 0]` | 一次新温度连续结算两个旧日期后停止 |

最容易写错的地方：

- 用 `>=` 代替 `>`，会把相等温度错误当更高温。
- 用 `if` 代替 `while`，一次新温度只能结算一个日期。
- 栈中保存温度而不是下标，无法计算天数差。
- 先压入今天再弹出，状态含义会被打乱。

### 7.10 闭卷重建

闭卷时我不先背代码，而是按下面的路径重建：

```text
每个日期向右找很慢
-> 新日期到来时可以先等待
-> 新温度可能同时结算多个更低旧日期
-> 等待日期从旧到新温度不会上升
-> 新温度从最近端连续结算，遇到不低于自己的温度就停
-> 用栈保存尚未结算的日期下标
-> 今天是第一个更高温时，答案等于下标差
-> 最后仍留在栈中的日期保持 0
```

只有这条路径能重新生成，代码里的 `while`、`push`、`pop` 和 `answer[previous] = today - previous` 才有可解释的来源。

## 8. 这份现场最后留下的标准

以后遇到新题，我会按下面的顺序想，而不是一上来先报方法名：

```text
第一段读题：哪些是原题事实，哪些是我还不知道的
第二段扩写：谁拿着什么，从哪开始，重复做什么，何时停止
第三段对象、过程与第一次变化：有哪些对象和关系，人最直接会怎样做，
  第一次变化前后是什么，答案何时产生
第四段范围与候选：官方约束是什么，慢过程大约做多少操作，
  范围排除了哪些量级，由实际操作生成了哪些待验证方向
第五段第二次变化：重复查询、候选失效还是子问题复用，
  哪份信息值得留下，需要支持什么操作
第六段方向确认：比较具体候选，说明为什么当前条件选择它
第七段推导链：状态、初始、转移、更新顺序、不变量，
  再到结构、伪代码、Java、反例、闭卷重建
```

这套顺序不是每段都要填一张审核表。思路还在产生新内容时，可以连续往下走；真正卡住时，统一记录五件事：

```text
我现在已经能确认：______
我现在还不能确定：______
这个空缺正在阻碍：______
因此下一个最小问题是：______
哪一种具体输入、例子、约束或手算结果能回答它：______
```

复盘时也要保留现场，而不是只留下最后一条正确路径：

- 如果当时确实形成过初始方向，我原来以为可能是哪个方向；如果没有，哪里最能说明我还没有形成候选？
- 哪个题目事实或小例子让这个方向成立、失效或暂时保留？
- 哪一个最早出现的重复、失效或顺序关系，使我开始想到当前方向？
- 方向确认以后，哪一处状态或更新顺序还不能用题目语言解释？

前六段只负责从题面走到算法方向，第七段才把已确认的方向变成模型和代码。能继续往下走，不是因为我记住了某条规则，而是因为当前问题已经自然变成下一段要回答的问题；如果这个变化还没有发生，就保留真实卡点，不跳到代码里寻找熟悉感。
