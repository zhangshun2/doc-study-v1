# 人类读题与算法确认

> 这是单题学习、题解扩写、AI 讲解和网站复习中心共同使用的人类思考标准。它回答的不是“这题用什么算法”，而是“一个不知道答案的人，怎样从题面一步步想到并确认这个算法”。

## 为什么需要这条流程

“先理解题意，再选择算法”听起来正确，但对新手没有可执行性。题面通常把动作、条件后果和过程压缩成几句话；如果直接跳到“用哈希表”“用滑动窗口”，真正被跳过的正是从人话到算法的那段桥。

本项目采用下面这条连续路径：

```text
第一层：从题面走到算法方向
01 只读原题事实
02 把题干扩写成完整生活过程
03 清点对象
04 手工走最小例子
05 第一次捕捉变化
06 读数据范围，估算操作预算，并生成候选算法池
07 第二次捕捉变化，寻找重复劳动
08 比较候选并确认算法方向

第二层：方向确认后的模型链
-> 状态、更新、不变量、结构、代码、反例
-> 闭卷重建
```

第一层是 **8 个连续判断入口**，不是 13 个彼此独立的待填表格。读范围、预算和候选池同属第 6 入口：范围先排除明显不够用的量级，再由过程的重复操作生成待验证方向。第二次变化和候选比较不能提前到这之前。

第二层只有通过第 8 入口后才能开始。没有通过方向闸门之前，不写完整 Java。

这里的关键不是“像专家一样一眼前看出答案”，而是允许自己只知道眼前这一小步。新手不需要同时想清楚对象、复杂度、数据结构和代码；他只需要不断问：**我现在确定的事实是什么？我还不明白什么？为了排除这个不明白，下一个最小问题是什么？**

## 小白在每个阶段实际会怎么想

下表不是需要勾选的任务清单，而是帮助理解“为什么要从上一段走到下一段”。如果某一段只剩方法名，没有这里的疑问和回答，就说明推导被压缩了。

| 阶段 | 新手此时知道什么 | 真实卡点 | 下一个最小问题 | 此时不能做什么 |
| --- | --- | --- | --- | --- |
| 读原题 | 每个字都认识，但不知道哪些条件重要 | 例子看懂了，却分不清事实和脑补 | 输入、输出、保证、禁止、未知分别是什么？ | 不能先猜算法 |
| 扩写题干 | 能复述零散条件，但脑中还没有完整过程 | 题目压缩了动作和停止时机 | 谁拿着什么，从哪里开始，重复做什么，何时停止？ | 不能加入题面没有的条件 |
| 对象、过程、变化 | 能举一个例子，但说不清到底是什么在变 | 不知道哪里是“对象”，哪里只是代码变量 | 人按时间顺序会先做什么，什么因此改变？ | 不能直接使用高级方法 |
| 数据范围 | 看到了 `n`、值域和特殊保证，但不知道意味着什么 | 容易把范围当成算法暗号 | 最慢的过程要做多少次操作，哪些量级不够用？ | 不能仅凭范围点名算法 |
| 候选算法池 | 知道要更快，但脑中只有一两个熟悉名词 | 不知道还有哪些方向值得比较 | 当前操作像“查历史、等结果、缩范围、复用子问题”中的哪一种？ | 不能把候选当成结论 |
| 第二次变化 | 能说慢过程，但还没找到可消除的浪费 | 不知道应该保存什么，或为什么会想到那个结构 | 哪件事重复最多，哪批候选一旦发生什么就永远没用了？ | 不能因为标签匹配就停止分析 |
| 方向确认 | 有一两个候选，但无法判断为什么选它 | 方法能运行不等于它由当前过程自然推出 | 每个候选是否支持真正需要的操作，为什么符合预算？ | 不能跳过比较写完整 Java |
| 推导链 | 方向基本确定，但状态和更新顺序还容易凭记忆 | 模板顺序记住了，却不知道交换后错在哪里 | 每个变量表示什么，哪一步先读，哪一步后写？ | 不能把运行通过当作理解完成 |

## 一、只读原题事实

第一次读题时先关闭题解、标签、讨论区和记忆中的标准做法。目标不是马上“想出来”，而是建立一张事实卡：

| 项目 | 要记录什么 |
| --- | --- |
| 输入 | 有哪些数据，各自代表什么，是否允许重复、空、负数或特殊符号 |
| 输出 | 返回长度、下标还是值，顺序是否重要，没有答案时怎么办 |
| 示例 | 从输入到输出的过程，以及示例没有覆盖的部分 |
| 约束 | 规模、值域、关系数量、已排序、唯一性等 |
| 禁止 | 不能重复使用、不能修改输入、不能交换顺序等限制 |
| 未知 | 还不能判断的问题，明确留空，不靠猜测补全 |

每句话都要贴一个来源标签：

- **事实：** 原题直接写了。
- **推导：** 根据原题条件必然得到。
- **推测：** 目前没有证据，只是我认为可能如此。

这一步的产物不是算法方向，而是一张不混入猜测的题面事实卡。

## 二、把题干扩写成完整生活过程

扩写不是把题面改写得更高深，也不是添加题目没有的条件。扩写是把压缩句子展开成“谁拿着什么，从哪里开始，按什么顺序动作，什么事件改变什么，什么时候停止，最后交出什么”。

逐句问六个问题：

1. **谁或什么在被处理？**
2. **现在手里已经有什么？**
3. **下一步具体做什么动作？**
4. **这个动作使什么发生变化？**
5. **什么时候可以停止？**
6. **停止时题目要的是哪一个结果？**

可以先用这个骨架：

> 我手里有 ______；我从 ______ 开始；我反复 ______；条件“______”意味着我不能 ______；当 ______ 时停止；题目最后要交出的不是 ______，而是 ______。

每条扩写都要能指回原句。比如“只能使用一次”不能只抄一遍，而要写出它阻止的具体错误：当前元素不能在查询历史时已经被自己写入。

## 三、按对象、过程、变化做第一次分析

### 1. 对象

先列题目世界里的对象，而不是代码容器：

- 元素：单个数字、字符、节点或状态。
- 位置：下标、坐标、区间端点或层数。
- 关系：前后、相邻、包含、依赖、可达或对应。
- 目标：需要找到、构造、判断或返回的对象。
- 结果：路径、数量、布尔值、下标、区间或整个结构。

对象需要说明身份和关系。例如“数组里有两个 3”不够，必须知道它们分别是不同下标上的元素，否则无法解释“不能重复使用”。

### 2. 过程

先让一个普通人按最直接的方法做，即使这样做很慢。过程必须按时间顺序，每一步只做一个动作：

```text
看到什么
-> 决定处理谁
-> 做一次什么动作
-> 得到什么中间结果
-> 下一步从哪里继续
```

不要在这里先说“可以用双指针”。如果当前过程已经是高级方法的结论，就无法判断你是否真的知道普通做法为什么不够。

### 3. 第一次捕捉变化

对关键信息写清变化：

```text
变化前：……
触发事件：……
变化后：……
```

至少检查五类变化：

- 当前处理对象是否移动。
- 可选候选是否增加、减少或失效。
- 历史信息是否累积。
- 临时结果是否被更新或覆盖。
- 答案在哪一个事件发生后成为确定结果。

第一次捕捉变化只回答“过程里发生了什么”，还不急着决定保存什么。

## 四、读数据范围，估算操作预算

约束不只有 n 的大小。需要一起读：

- 元素数量、字符串长度、节点数、边数或矩阵尺寸。
- 值域是否允许负数、溢出、重复或稀疏。
- 输入是否已经有序。
- 答案是否唯一、是否保证存在。
- 输出是否保留原位置。
- 是否要求原地修改。

范围可以用来排除明显不可能的复杂度，但只能作为门槛，不能单独决定算法。

| 常见上限 | 通常需要优先考虑的量级 | 不能直接推出 |
| --- | --- | --- |
| `n <= 10` | 指数枚举、全排列可能可以接受 | 一定要回溯 |
| `n <= 20` | 子集枚举、状态压缩可能进入候选 | 一定要位运算 |
| `n <= 100` | `O(n^3)` 可能可以接受 | 一定要三重循环 |
| `n <= 1,000` | `O(n^2)` 可能可以接受 | 一定要动态规划 |
| `n <= 10^5` | 通常优先考虑 `O(n)` 或 `O(n log n)` | 一定要排序、哈希或双指针 |
| `n <= 10^6` | 通常只剩接近 `O(n)` 的做法 | 一定要一次遍历 |

这张表不是规则证明。实际还要看常数、Java 实现、图的关系数量以及是否每一层都扫描全部对象。正确写法是：

> 如果每轮都重新检查全部对象，大约要做 ______ 次操作；这个规模是否还允许我保留这种重复计算？

这里必须区分三类信息，不能混写成一句“题目要求某复杂度”：

| 信息类型 | 例子 | 能否当作题目事实 |
| --- | --- | --- |
| 官方约束 | `n <= 10^5`、`30 <= temperatures[i] <= 100` | 可以；这是题目原文或结构化事实 |
| 操作量推导 | 每天向未来扫描，最坏约检查 `n(n-1)/2` 对 | 不可以；这是学习者根据过程做的估算 |
| 算法候选 | “可以考虑单调栈、按温度记录最近位置或线段树” | 不可以；候选必须在第二次变化后继续排除 |

数据范围只回答“大预算下哪些做法首先不够”，不回答“哪个算法正确”。官方题面通常也没有“推荐复杂度”这一项。

### 从范围走到候选算法池

新手看到范围后仍然不会做题，常见的缺失桥是：**范围只排除了复杂度等级，还没有产生可以比较的方法。** 候选算法池必须同时来自两边：

```text
慢过程反复需要什么操作
+ 当前预算最多允许多少这类操作
+ 题目保证或特殊限制会淘汰什么方向
= 一小组待验证的候选方向
```

可以先写下这张候选池卡：

| 项目 | 本次答案 |
| --- | --- |
| 慢过程在重复什么 | 例如：为每个当前值重新向后寻找补数 |
| 完成后最想立即得到什么 | 例如：以前是否出现过某个值，以及它的位置 |
| 直接重复大约多少操作 | 例如：`n=10^4` 时约五千万次配对检查 |
| 范围排除了什么 | 例如：不适合再为每个位置完整扫描一次 |
| 仍允许哪些量级 | 例如：`O(n)`、`O(n log n)` 仍值得继续比较 |
| 由操作特征产生的候选 | 例如：排序记录位置、历史查询结构、一次扫描维护候选 |
| 此刻仍不能决定什么 | 例如：到底该排序还是保存历史映射 |

再按“过程中的操作形态”扩充候选池，而不是按题目标签猜：

| 慢过程中观察到的操作 | 可以进入候选池的方向 | 还不能直接断定 |
| --- | --- | --- |
| 反复问以前是否出现、出现几次、对应哪个位置 | 哈希查询、计数表、位置表、前缀记录 | 用哪种历史结构，是否需要保留全部历史 |
| 有对象已经出现，但要等未来事件才结算 | 栈、队列、堆、按值索引 | 谁先结算，哪些候选可以同时丢弃 |
| 连续区间扩张、收缩后仍能增量维护 | 滑动窗口、前缀和、差分 | 窗口条件是否单调，边界移动是否安全 |
| 一批候选能被证明永远不再最优 | 双指针、单调栈、贪心淘汰 | 淘汰条件是否真的覆盖所有情况 |
| 同一小问题会从多条路径再次遇到 | 记忆化、动态规划、图上的最短步数 | 状态是否完整，按什么顺序复用 |
| 每一步有多个选择，且需要撤回 | DFS、回溯、搜索 | 完成条件、去重和恢复状态是什么 |
| 输入有序，或答案具有可判定的单调性 | 二分、双指针 | 判定函数是否单调，边界代表什么 |

候选池中的名字只是待验证假设。此时可以写“可能需要按过去信息查询”，但还不能写“所以用哈希表”。下一节必须继续回答：真正丢掉的是哪份重复劳动，候选在什么事件后失效，要求的操作和结构是否一一对应。

## 五、第二次捕捉变化，寻找重复劳动

第一次变化分析描述过程，第二次要找出优化入口。带着操作预算重新检查人工过程：

1. 哪个动作被反复执行？
2. 每次重复时，有多少信息其实可以从上一轮继续使用？
3. 当前这一步真正需要查询什么？
4. 哪份历史信息如果保存下来，就能避免重新扫描？
5. 哪批候选在某个事件后已经不可能产生答案？
6. 哪个状态只需要保留最近一份，哪个必须保留全部历史？
7. 当前更新是否会被后续步骤读取？

第二次变化通常不是一种，而是三类：

| 第二层变化 | 新手要问的问题 | 典型入口 |
| --- | --- | --- |
| 重复查询 | 同一个问题是否被反复问，历史答案能否保留？ | 哈希、前缀和、计数 |
| 候选失效 | 某个事件发生后，哪一批候选已经不可能更优？ | 双指针、单调栈、贪心 |
| 子问题复用 | 不同路径是否到达同一个更小问题？ | 记忆化、动态规划、BFS 状态图 |

然后把重复劳动翻译成操作需求：

| 观察到的变化 | 先问需要什么操作 | 可能进入候选的方向 |
| --- | --- | --- |
| 反复问“以前是否出现/出现了几次/对应哪个位置” | 快速查询和写入历史 | 哈希、计数表、前缀记录 |
| 只关心最近一个尚未完成的项 | 后进先出 | 栈 |
| 只关心最早发现的项 | 先进先出 | 队列、BFS |
| 每次只取当前最大或最小候选 | 插入后快速取极值 | 堆、有序结构 |
| 连续区间的统计可以增量维护 | 加入右端、删除左端 | 滑动窗口、前缀和 |
| 两端候选具有可证明的淘汰关系 | 安全移动边界 | 双指针、二分 |
| 对象之间存在边或依赖 | 按关系遍历 | DFS、BFS、拓扑排序 |
| 小问题被大量重复求解 | 保存子问题结果 | 动态规划、记忆化 |
| 每一步有多个选择且需要撤销 | 路径共享与恢复 | 回溯 |

最后两列只是候选方向。必须继续回答“所需操作为什么真的匹配”和“为什么不会漏掉候选”，才能确认算法。

### 新手在这一步为什么会卡住

新手常常已经能看出“有重复”，却不知道应该保存什么。原因通常不是不会某个数据结构，而是还没问清下面三件事：

1. **这份信息未来还会不会被读取？** 如果不会，就不需要保存。
2. **未来读取时需要知道哪几个字段？** 只判断出现过，和还要知道位置、次数、有效期，对应不同状态。
3. **它什么时候失效？** 不会失效的历史、只需最近一份的历史、只要最优候选的历史，维护方式完全不同。

因此不要从容器出发找用途。先写：

> 未来第 ______ 步会回来问：______？为了回答它，我现在至少要留下 ______。当 ______ 发生后，这份信息可以消失。

如果这句话还写不出来，说明重复劳动或候选寿命尚未确认，候选池也还不能收缩成实现方案。

## 六、确认算法方向

方向确认要比较候选，而不是报出最熟悉的名字。每个候选至少写四项：

| 候选方案 | 能消除哪份重复劳动 | 需要的数据和操作 | 代价或失效条件 |
| --- | --- | --- | --- |
| 方案 A | …… | …… | …… |
| 方案 B | …… | …… | …… |

只有同时满足下面五项，才算通过方向闸门：

1. 能从手工过程指出必须避免的重复计算。
2. 能列出算法每一步需要支持的查询或修改。
3. 能说明所选结构或策略为什么正好支持这些操作。
4. 能说明数据范围为什么允许当前复杂度。
5. 能说出一个替代方案为什么可行或不优先。

方向确认句必须包含因果，而不只是名称：

> 当前过程反复需要 ______；如果每次重新扫描会做 ______ 次操作；因此我需要支持 ______；方案 A 能提供 ______，而方案 B 在 ______ 条件下会失效；所以我选择 A。

没有这句话，不进入完整代码。可以把代码当参考观察，但不能把抄写当成学习完成。

## 七、方向确认后的八段推导链

| 确认点 | 必须回答 | 通过证据 |
| --- | --- | --- |
| 1. 状态定义 | 每个变量在题目世界里表示什么，覆盖哪个范围 | 不看代码也能用完整句子定义 |
| 2. 初始、停止与答案时机 | 从哪里开始，何时停止，结果何时确定 | 最小例子能对应到每个初始值 |
| 3. 一次状态转移 | 当前事件读取什么、计算什么、写入什么 | 能手算至少三轮并预测下一轮 |
| 4. 更新顺序 | 查询、写入、删除、覆盖为什么按这个顺序 | 交换顺序能指出具体错误结果 |
| 5. 不变量与正确性 | 为什么不会漏、不会多、不会误删 | 证明依赖的条件能逐条指出 |
| 6. 结构与操作 | 所需操作与结构代价是否真正匹配 | 能与更简单结构作具体比较 |
| 7. 伪代码与 Java | 每段代码对应哪个对象和动作 | 关键行位置和变量含义可解释 |
| 8. 反例与闭卷重建 | 模型何时失效，能否独立重来 | 有反例、手算、代码和自测证据 |

## 八、新手完整示例：两数之和

下面展示一个不知道哈希解法的学习者，怎样从题面一步步想到它。这里最重要的是中间判断，不是最后几行代码。

### 1. 只读事实

使用例子 `nums = [2,7,11,15]`、`target = 26`。

事实卡：

- 输入是一个整数数组和一个目标整数。
- 要找到两个整数，使它们的和等于目标值。
- 返回的是这两个整数的数组下标，不是数值本身。
- 每种输入只有一个有效答案。
- 同一个元素不能使用两次。
- 返回顺序任意。
- 数组长度最大为 `10^4`。

未知：数组是否有序？题目没有保证。是否允许重复值？从“整数数组”和“不能使用同一元素”可以推导出可以出现重复值，但不能重复使用同一位置。

### 2. 人话扩写

> 我手里有一排带位置的数字，还有一个目标和。我要从这排数字里找两个不同位置，使它们相加正好等于目标和，然后把两个位置交出去。题目保证答案只有一组，所以第一次找到有效位置对时可以停止。因为不能使用同一个元素两次，检查当前数字时，不能把它自己当成另一个数。

这段扩写没有出现哈希表。它只补全了动作、停止条件和“不能重复使用”的实际含义。

### 3. 对象、过程、变化

对象是数字、下标、目标和答案下标对。数字与下标绑定，因为最后返回的是位置；目标和是判断依据；答案是两个不同下标。

最直接的人工过程是枚举每一对：

| 固定第一个位置 | 依次检查后面位置 | 计算结果 |
| --- | --- | --- |
| `i=0`，值 `2` | `j=1`，值 `7` | `9`，不是 26 |
| 保持 `i=0` | `j=2`，值 `11` | `13`，不是 26 |
| 保持 `i=0` | `j=3`，值 `15` | `17`，不是 26 |
| `i=1`，值 `7` | `j=2`，值 `11` | `18`，不是 26 |
| 保持 `i=1` | `j=3`，值 `15` | `22`，不是 26 |
| `i=2`，值 `11` | `j=3`，值 `15` | `26`，找到答案 `[2,3]` |

第一次捕捉变化：固定的 `i` 不变时，`j` 不断向后移动，当前两个位置和每次重新计算；只有当前和等于 `target` 时，答案才产生。

### 4. 数据范围

最坏情况下，每一对都要比较一次。`n=10^4` 时大约有 `n(n-1)/2`，接近五千万对。这个数量不能只凭“O(n^2)”几个字判断，但至少说明：如果能在一次推进中避免反复检查全部后续元素，会显著减少工作。

范围只告诉我们“需要更好的重复利用”，没有直接说“使用哈希表”。

### 5. 第二次捕捉变化

仔细观察慢过程，真正的重复劳动不是加法，而是：每遇到一个当前数字，都要重新向后寻找能与它配成目标的数字。

换一个视角：

> 如果当前数字是答案中的右边那个数，那么答案中的左边那个数必须已经在我之前出现过，而且它的值必须是 `target - 当前值`。

例如当前值是 `15`，目标和是 `26`，那么之前必须出现过 `11`。所以我不需要保存所有未检查的数，只需要保存已经出现过的“值到位置”的历史。

所需操作变成：

- 查询某个补数以前是否出现。
- 如果出现，还要取回它的原下标。
- 把当前值和下标加入历史。

### 6. 比较候选方向

| 候选 | 优点 | 问题或代价 |
| --- | --- | --- |
| 枚举所有数对 | 直接、容易证明 | 反复扫描，约 `O(n^2)` |
| 排序后双指针 | 可以用两端和调整方向，`O(n log n)` | 会打乱原下标，需要额外保存值和原位；还要处理排序和指针逻辑 |
| 哈希记录历史 | 平均 `O(1)` 查询补数和取下标，一遍扫描 | 需要 `O(n)` 额外空间；哈希查询是平均复杂度 |

这里不选排序双指针，不是因为它“错误”，而是当前题要求原下标、答案唯一，而哈希可以把值与位置一起保存，一遍完成。对新手的自然推导也更直接。

方向确认：

> 慢过程反复向后寻找配对值；如果按右端点扫描，左边只需记录出现过的值及其下标。因此我需要补数查询和位置读取。哈希表平均能常数时间完成这两件事，代价是保存最多 n 条历史，符合当前约束，所以我选择一次遍历加历史表。

### 7. 进入推导链

状态定义：

> 哈希表 `seen` 保存“已经处理过的位置中，数值到下标”的对应关系。

循环准备处理下标 `i` 时，`seen` 只覆盖区间 `[0, i)`。这意味着它不包含当前元素，正好表达“不能重复使用同一元素”。

每一轮：

1. 计算 `need = target - nums[i]`。
2. 查询 `seen` 中是否已有 `need`。
3. 如果存在，说明历史位置与当前 `i` 构成答案。
4. 如果不存在，再把当前值和下标写入 `seen`。

更新顺序必须是先查后写。若先写当前值，当 `target = 6`、当前值也是 `3` 时，查询可能立刻拿到当前下标，返回两个相同位置，违反“不能使用同一个元素两次”。

不变量：

> 每一轮开始处理 `i` 时，`seen` 恰好保存 `[0, i)` 内每个已出现数值的一个下标。

不会漏：如果答案的右端点是 `i`，左端点一定已经出现在 `[0, i)` 中，因而补数查询能命中。

不会多：只有历史值与当前值之和等于目标时才返回，而且两个下标来自不同位置。

结构与操作：哈希表支持按键查询补数、插入当前值和读取历史下标。数组若只保存值，仍然需要线性扫描；若要保存“值到下标”，普通数组又无法直接处理任意整数键。这里哈希表与所需操作匹配。

伪代码：

```text
seen = empty map
for i from 0 to n - 1:
    need = target - nums[i]
    if need exists in seen:
        return [seen[need], i]
    seen[nums[i]] = i
```

Java 基准实现：

```java
class Solution {
    public int[] twoSum(int[] nums, int target) {
        Map<Integer, Integer> seen = new HashMap<>();

        for (int i = 0; i < nums.length; i++) {
            int need = target - nums[i];
            Integer previousIndex = seen.get(need);
            if (previousIndex != null) {
                return new int[]{previousIndex, i};
            }
            seen.put(nums[i], i);
        }

        throw new IllegalArgumentException("No valid pair");
    }
}
```

反例和边界：

- `[3,3], target=6`：第一个 3 先写入，第二个 3 查询时命中。不能跳过重复值。
- `[3,2,4], target=6`：如果先写后查，当前 3 可能匹配自己；先查后写可以排除。
- 如果题目不保证唯一答案，当前“命中即返回”仍然有效，但它只返回其中一组，需要按新的输出要求重新确认。
- 如果题目要求返回值而不是下标，历史表可以只存值；当前题目要求原下标，所以必须存位置。

闭卷重建时，先重走“朴素枚举 -> 五千万级检查 -> 历史补数查询 -> 先查后写”的路径，再写代码。只背 `Map<Integer,Integer>` 不能通过。

## 九、新手最容易卡住的地方

### 1. 先看到题目标签，再假装自己推导出来

标签可以作为事后检查，不能作为第一步。看到“哈希表”后说“因为要查补数”，是沿答案向前解释，不是从题面生成答案。

### 2. 只说“暴力太慢”，不说慢在哪里

必须指出哪一个动作被重复。慢的是“每轮重新寻找配对值”，不是笼统的“复杂度高”。

### 3. 看到数据范围就报算法名

`10^5` 只说明可能要 `O(n log n)` 或 `O(n)`，不能区分排序、双指针、哈希、滑动窗口或单调栈。要看变化方式。

### 4. 先写状态，再问它代表什么

变量名不是状态定义。必须用题目语言说明状态覆盖哪些对象、发生什么事件时更新、未来哪一步会读取它。

### 5. 用代码运行通过代替过程确认

运行只能证明某个输入下输出一致。它不能证明你知道为什么不会漏、为什么更新顺序正确，也不能证明几天后还能重建。

### 6. 数据范围之后没有生成候选池

只知道 `n=10^5` 不够，只知道“要用 O(n)”也不够。必须进一步说出慢过程反复要求的是历史查询、候选淘汰、区间维护还是子问题复用。否则范围只会变成新的算法暗号。

### 7. 候选池生成后立刻选定方法

候选池的作用是保留少量可能性，第二次变化才负责排除。比如“需要快速查询历史”仍可能对应排序后二分、位置哈希或前缀记录；不继续问位置、顺序、重复和失效条件，就仍然是在凭熟悉程度选择。

## 十、统一验收标准

### 单段通过

只有同时满足三点才算通过：

1. 产出该段要求的可核对内容，而不是口头说“知道了”。
2. 能说明它与上一段的因果关系。
3. 换一个小例子后仍能重新生成，而不是背刚才的原话。

### 候选池通过

- 能把官方范围、自己推导的操作量和候选算法分开标注。
- 能说清慢过程需要的主要操作形态。
- 能列出至少两个后续可比较的方向；如果没有真实歧义，能说明为什么只保留一个。
- 不把候选名写成结论，也不把官方题面没有的“推荐复杂度”当事实。

### 方向通过

- 能说出朴素过程中真正的重复劳动。
- 能说出数据范围允许和排除的复杂度。
- 能列出算法需要的具体操作。
- 至少比较两个候选，并说出选择或排除条件。
- 能指出所选算法依赖的题目保证。

只说出方法名不通过。

### 本轮通过

- 能用原题事实完成人话扩写，不偷偷添加条件。
- 能手工走最小例子并解释每轮变化。
- 能明确区分两次变化：第一次说明“过程里发生了什么”，第二次说明“哪里可以优化或复用”；两次不能混写成同一段。
- 能从第二次变化分析推出算法方向。
- 能闭卷写出状态、更新顺序和不变量。
- 能把关键代码映射回过程，并手算出至少一个反例。
- 能独立写伪代码、Java 和自测输入。

### 长期掌握

过一段时间后重新开始时，可以忘记某个 Java API，但不能忘记：

- 题目对象和过程。
- 为什么需要保存这类信息。
- 状态的真实含义。
- 更新顺序的理由。
- 不变量的作用。
- 什么条件改变后模型会失效。

如果只记得方法名，长期掌握尚未成立。

## 十一、AI 讲解必须遵守的标准

AI 不按这些规则输出时，讲解就不合格：

1. 不先给方法名、代码或“关键观察”。
2. 先复述题面事实，再明确哪些是扩写、哪些是推测。
3. 用最小例子按时间顺序展开，一次只引入一个动作。
4. 第一次变化分析之后，必须单独读规模和约束，不能跳过预算。
5. 第一次变化只说明过程中发生了什么；第二次变化必须指出哪里可以优化或复用、重复劳动和所需操作，不能把两者合并成一句“优化暴力”。
6. 进入代码前，先比较候选方向并说明选择条件。
7. 每个公式都展开到对象、事件和状态，不用“显然”“直接套”代替。
8. 代码只在使用者的过程模型稳定后给出；用户主动要求直接看代码时，也要标出它跳过了哪些判断。
9. 卡住时只补最早缺失的一段，不顺手扩展成多套完整解法。
10. 最后必须要求使用者闭卷重建，并区分“看懂参考”与“自己生成”。
