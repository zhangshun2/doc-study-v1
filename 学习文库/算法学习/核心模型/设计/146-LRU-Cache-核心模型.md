# 146. LRU 缓存：核心模型

> **双轨阅读：** [[题目/设计/146-LRU-Cache.md|标准题解]]

## 一句话本质

缓存同时需要两种能力：按键直接定位，以及维护随访问变化的时间顺序。单个容器无法同时优雅满足二者，因此组合： HashMap 负责定位节点。 双向链表按新旧排序：靠近头部的是最近使用，靠近尾部的是最久未使用。

## 直观画面与扩题

像同时维护目录和最近使用顺序，不同结构各负责一种查询能力。

在本题中，对象是 **哈希索引与按访问顺序变化的链表**；把它从“枚举全部可能”改写为“只维护影响下一步的最少信息”。

## 关系重写

把题目翻译成一条可执行关系：缓存同时需要两种能力：按键直接定位，以及维护随访问变化的时间顺序。单个容器无法同时优雅满足二者，因此组合： HashMap 负责定位节点。 双向链表按新旧排序：靠近头部的是最近使用，靠近尾部的是最久未使用。

## 最小演算

官方首例输入：`["LRUCache", "put", "put", "get", "put", "get", "put", "get", "get", "get"] [[2], [1, 1], [2, 2], [1], [3, 3], [2], [4, 4], [1], [3], [4]]`，输出：`[null, null, null, 1, null, -1, null, -1, 3, 4]`。

1. **初始状态：** 维护虚拟节点 head 和 tail： head <-> 最近使用节点 <-> 中间节点 <-> 最久未使用节点 <-> tail
2. **触发事件：** put 更新：修改值并移到头部。
3. **结束条件：** 命中的 get 和成功的 put 都把对应节点放到头部，故顺序不变量成立。
4. **核对首例：** 按上述状态与事件逐步更新，最终应得到题面给出的输出；若结果不符，优先检查状态初始化、更新先后顺序和边界收缩方向。

## 为什么成立

每次公开操作结束后保持： map 中的键与链表中的真实节点一一对应。

## 代码映射

```text
1. 维护虚拟节点 head 和 tail：
2. put 更新：修改值并移到头部。
3. 维护虚拟节点 head 和 tail： head <-> 最近使用节点 <-> 中间节点 <-> 最久未使用节点 <-> tail
```

## 复杂度

- 时间复杂度：增加时间戳/最小堆或时间轮，淘汰策略不再只有容量。
- 空间复杂度：O(capacity)。

## 30 秒识别信号

- 主题型：`设计`
- 切入点：哈希表能 O(1) 找节点，却不能 O(1) 找出最久未使用项。

## 最小反例与易错点

- 更新已有键不能增加缓存大小。
- 淘汰链表节点时必须同步从 map 删除，反之亦然。
