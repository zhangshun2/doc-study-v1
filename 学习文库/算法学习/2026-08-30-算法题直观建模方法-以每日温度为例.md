# 算法题的直观建模方法：以 739. 每日温度为例

日期：2026-08-30  
定位：算法建模方法笔记，不替代单题标准题解  
配套材料：[每日温度：从“记不住”到“宏观建模”的完整拆解](./2026-08-30-每日温度单调栈与宏观建模.md)

## 1. 先给结论：建模不是猜数据结构

做算法题时，最容易走偏的一步，是刚读完题就问：

> 这题是不是单调栈？

更稳的顺序应该是：

```text
题目在问什么关系
-> 暴力怎样直接得到答案
-> 暴力重复做了什么
-> 哪些对象还没有答案
-> 什么事件会让它们得到答案
-> 用什么结构维护这些对象
```

数据结构是最后长出来的，不是第一步猜出来的。

把这个过程压缩成一句话：

> 算法建模，就是把故事翻译成“对象、关系、状态、事件和结果”。

在“每日温度”里，它们分别是：

| 建模要素 | 本题中的含义 |
| --- | --- |
| 对象 | 每一天，使用下标 `i` 表示 |
| 关系 | 右边第一个温度严格更高的日子 |
| 状态 | 已经见过、但还没有等到更高温度的日子 |
| 事件 | 新的一天到来，温度高于某些等待者 |
| 结果 | 当前下标减去等待者下标，即等待天数 |

一旦这五项说清楚，单调栈只是“等待名单”的一种高效实现。

## 2. 跨来源检索后，哪些观点最值得保留

不同资料的讲法不同，但对这道题的核心认识高度一致。

| 来源 | 最值得吸收的观点 | 在本文中的落地 |
| --- | --- | --- |
| LeetCode 题目与官方题解 | 题目本质是寻找右侧第一个严格更大元素；官方同时利用了温度范围有限和单调栈两种模型 | 不把单调栈当作唯一思路，先比较模型 |
| OI Wiki 单调栈 | 单调栈适合在线性序列中寻找前后第一个更大或更小的元素 | 提炼“方向 + 第一个 + 大小关系”识别指纹 |

| AlgoMonster 739 | 栈保存尚未解决的下标；当前温度可以一次解决多个更冷的历史下标 | 使用“未结算任务”解释 `while`，而不是背代码 |
| USACO Guide | 弹出栈顶正是维护单调性的动作；单调性不是额外规定，而是更新规则产生的结果 | 先写弹出条件，再描述栈内不变量 |

综合这些资料后，一个更实用的认识是：

> “题型识别”只能帮助提出候选结构；真正决定结构的是状态、不变量和结算事件。

## 3. 第一步：把题目压缩成一个关系

原题可以压缩为：

> 对每个位置 `i`，寻找最小的 `j`，满足 `j > i` 且 `temperatures[j] > temperatures[i]`；答案是 `j - i`，不存在则为 `0`。

这里有四个不能漏掉的词：

| 题目词语 | 建模含义 | 代码影响 |
| --- | --- | --- |
| 之后 | 只看 `i` 的右侧 | `j > i` |
| 第一个 | 要满足条件的最小下标 | 不能找任意一个更高温度 |
| 更高 | 严格大于 | 相等温度不能结算 |
| 几天后 | 求下标差 | 保存下标，而不只是温度值 |

这一步先不要想栈。只要能把题目说成“右侧第一个严格更大元素的距离”，建模就已经完成了一半。

## 4. 第二步：先写绝对正确的暴力模型

暴力思路很自然：固定一天 `i`，从 `i + 1` 开始向右找，第一个更高温度就是答案。

```java
for (int i = 0; i < temperatures.length; i++) {
    for (int j = i + 1; j < temperatures.length; j++) {
        if (temperatures[j] > temperatures[i]) {
            answer[i] = j - i;
            break;
        }
    }
}
```

这不是“没想出算法”，而是在建立三个重要事实：

1. 什么条件下产生答案：`temperatures[j] > temperatures[i]`。
2. 答案是什么：`j - i`。
3. 为什么慢：不同的 `i` 会反复扫描同一批未来位置。

若数组长度为 `n`，最坏情况下比较次数约为：

```text
(n - 1) + (n - 2) + ... + 1 = n(n - 1) / 2
```

时间复杂度是 `O(n^2)`，空间复杂度是 `O(1)`（不计返回数组）。`n` 表示天数。

优化的目标由此变得具体：

> 不要让每个历史日子各自重新扫描未来。

## 5. 第三步：把“向未来查询”翻转成“到来时结算”

暴力模型是“拉取答案”：

```text
每个旧日子主动去未来寻找答案
```

换一个观察方向：

```text
每个新日子到来时，主动给更冷的旧日子发答案
```

例如温度 `72` 到来时，它可以同时结算前面仍在等待的 `69` 和 `71`：

```text
75, 71, 69, 72
        ^   ^   69 等了 1 天
    ^       ^   71 等了 2 天
```

这次视角翻转非常关键。很多线性扫描题的优化都来自它：

| 原始视角 | 优化视角 |
| --- | --- |
| 每个对象去寻找未来答案 | 新事件到来时批量结算旧对象 |
| 对每个起点重复扫描 | 整体只扫描一次 |
| 关注“我要去哪里找” | 关注“谁还在等待” |

此时已经自然出现了一个状态：

> 维护所有已经出现、但尚未找到更高温度的日子。

## 6. 第四步：只保存完成任务所需的最小状态

等待名单里应该保存温度，还是下标？

最终答案需要 `当前下标 - 旧下标`，同时比较温度时又能通过原数组取得 `temperatures[旧下标]`。因此只保存下标就够了：

```text
保存下标 i
-> 比较时读取 temperatures[i]
-> 结算时计算 currentIndex - i
```

如果只保存温度 `73`，便无法知道这个 `73` 是哪一天，也就算不出等待天数。

最小状态设计原则：

> 优先保存能回到原始数据的位置或标识；不要把可以随时查回的信息重复存一份。

本题的栈不是“温度栈”，而是“尚未结算的天数下标栈”。

## 7. 第五步：写出不变量，再选择数据结构

从左向右扫描，在处理第 `i` 天之前，栈必须始终满足：

1. 栈中每个下标都小于 `i`，即它们都是已经出现的日子。
2. 栈中每个下标都还没有找到右侧第一个更高温度。
3. 下标从栈底到栈顶递增，符合时间先后顺序。
4. 对应温度从栈底到栈顶单调不升，即下面较热，上面较冷或相等。

假设栈中是：

```text
栈底 [75, 71, 69] 栈顶
```

今天是 `72`：

```text
69 < 72，69 得到答案并出栈
71 < 72，71 得到答案并出栈
75 >= 72，停止
72 自己入栈等待未来
```

为什么遇到 `75` 就能停止？因为 `75` 下面的元素只会比它更热或相等，更不可能被今天的 `72` 结算。

所以我们不需要搜索整份等待名单，只要不断检查栈顶。这正是选择栈的理由。

不要死记“递增栈”或“递减栈”的名字，不同资料对观察方向和命名可能不同。直接记清下面两件事更可靠：

```text
栈底到栈顶：温度不升
弹出条件：栈顶温度 < 当前温度
```

## 8. 第六步：把模型写成三个动作

每来一个新日子，只做三个动作：

```text
1. 能结算就结算：当前温度更高时，反复弹出栈顶
2. 弹出时写答案：answer[old] = current - old
3. 当前日子入栈：等待未来更高温度
```

对应代码骨架：

```java
for (int current = 0; current < temperatures.length; current++) {
    while (!pending.isEmpty()
            && temperatures[pending.peek()] < temperatures[current]) {
        int old = pending.pop();
        answer[old] = current - old;
    }
    pending.push(current);
}
```

`while` 不是技巧，它表达的是“同一个新日子可以结算多个等待者”。当前日子也不是只有在没有弹栈时才入栈，所以 `push` 不能写在 `else` 里。

## 9. 完整演算：只看等待名单如何变化

输入：

```text
[73, 74, 75, 71, 69, 72, 76, 73]
```

栈中写成 `下标:温度`，左边是栈底，右边是栈顶。

| 当前日 | 当前温度 | 结算动作 | 入栈后的等待名单 | 新写入答案 |
| ---: | ---: | --- | --- | --- |
| 0 | 73 | 无 | `[0:73]` | 无 |
| 1 | 74 | 弹出 `0:73` | `[1:74]` | `answer[0] = 1` |
| 2 | 75 | 弹出 `1:74` | `[2:75]` | `answer[1] = 1` |
| 3 | 71 | 无 | `[2:75, 3:71]` | 无 |
| 4 | 69 | 无 | `[2:75, 3:71, 4:69]` | 无 |
| 5 | 72 | 依次弹出 `4:69`、`3:71` | `[2:75, 5:72]` | `answer[4] = 1`，`answer[3] = 2` |
| 6 | 76 | 依次弹出 `5:72`、`2:75` | `[6:76]` | `answer[5] = 1`，`answer[2] = 4` |
| 7 | 73 | 无 | `[6:76, 7:73]` | 无 |

遍历结束后，栈里的 `6` 和 `7` 没有等到更高温度。结果数组初始值本来就是 `0`，不需要额外处理：

```text
[1, 1, 4, 2, 1, 1, 0, 0]
```

## 10. 为什么弹出时得到的一定是“第一个”更高温度

设旧日子下标为 `old`，它在当前下标 `current` 被弹出。

需要证明两件事：

1. `temperatures[current] > temperatures[old]`，这是进入 `while` 的条件，所以当前日确实更热。
2. `old` 从入栈到现在一直没有被弹出，说明在 `(old, current)` 之间没有任何一个已经处理过的日子比它更热；否则它早已在那一天被结算。

因此，`current` 不只是一个更高温度的位置，还是右侧第一个更高温度的位置。

这是一种很通用的正确性证明方式：

```text
当前事件满足答案条件
+
此前一直未触发，说明没有更早答案
=
当前事件就是第一个答案
```

## 11. `while` 看起来嵌套，为什么仍是 O(n)

不能只看到 `for` 里面有 `while` 就判断为 `O(n^2)`。应该数每个下标一生能被操作几次：

```text
每个下标入栈一次
每个下标最多出栈一次
```

即使某一天一次弹出很多元素，这些元素以后也不会再次入栈或弹出。全部 `while` 加起来最多弹出 `n` 次。

- 时间复杂度：`O(n)`。
- 空间复杂度：`O(n)`，最坏情况下温度单调不升，所有下标都留在栈中。
- `n` 表示温度数组的长度。

这叫均摊分析。判断复杂度时，应统计元素在整个算法生命周期中的总操作次数，而不是只看代码嵌套层数。

## 12. 一个更直白但不够通用的模型：有限温度表

题目给出温度范围 `30 <= temperatures[i] <= 100`。由于取值只有 71 种，还可以从右向左维护每个温度最近出现的位置：

```text
next[t] = 右侧最近一次出现温度 t 的下标
```

处理当前温度 `x` 时，检查 `x + 1` 到 `100` 的所有温度，取其中最小的下标。然后更新 `next[x]`。

```text
从右向左处理 i：
    warmerIndex = 所有 next[x + 1 ... 100] 中的最小值
    如果 warmerIndex 存在：answer[i] = warmerIndex - i
    next[x] = i
```

若把温度种类数记为 `R`：

- 时间复杂度：`O(nR)`。
- 空间复杂度：`O(R)`。
- 本题中 `R = 71` 是固定小常数，因此实际运行也近似线性。

两种模型没有绝对的高下：

| 比较项 | 有限温度表 | 单调栈 |
| --- | --- | --- |
| 最初直觉 | 很直白：记录每种温度最近在哪 | 需要理解等待名单和不变量 |
| 对本题约束 | 完全可用 | 完全可用 |
| 时间 | `O(nR)` | `O(n)` |
| 空间 | `O(R)` | `O(n)` |
| 对值域的依赖 | 强，值域大时不可取 | 不依赖温度取值范围 |
| 可迁移性 | 较弱 | 可迁移到大量 Next Greater/Smaller 问题 |

如果目标只是快速做对这道题，有限温度表可能更容易想到；如果目标是建立可迁移的算法模型，单调栈更值得掌握。

## 13. 可直接运行的 Java 17 实现

```java
import java.util.ArrayDeque;
import java.util.Arrays;
import java.util.Deque;

class Solution {
    public int[] dailyTemperatures(int[] temperatures) {
        int n = temperatures.length;
        int[] answer = new int[n];
        Deque<Integer> pending = new ArrayDeque<>();

        for (int current = 0; current < n; current++) {
            while (!pending.isEmpty()
                    && temperatures[pending.peek()] < temperatures[current]) {
                int old = pending.pop();
                answer[old] = current - old;
            }
            pending.push(current);
        }

        return answer;
    }

    public static void main(String[] args) {
        Solution solution = new Solution();
        int[] temperatures = {73, 74, 75, 71, 69, 72, 76, 73};
        int[] answer = solution.dailyTemperatures(temperatures);
        System.out.println(Arrays.toString(answer));
    }
}
```

预期输出：

```text
[1, 1, 4, 2, 1, 1, 0, 0]
```

变量名 `pending` 比 `stack` 更能保留模型含义：它是一份尚未结算的等待名单，栈只是实现方式。

## 14. 写代码前，强制自己说清四句话

如果下面四句话说不完整，先不要写代码：

```text
1. 栈里存什么？
   存还没找到更高温度的日子下标。

2. 栈保持什么性质？
   从栈底到栈顶，下标递增、温度不升。

3. 什么时候弹出？
   当前温度严格高于栈顶下标对应的温度时。

4. 弹出时算什么？
   当前下标减去弹出下标，得到等待天数。
```

这四句话分别对应状态、不变量、事件和结果。能独立回答它们，才算真的完成了建模。

## 15. 单调栈题的识别指纹

同时出现下面多个特征时，可以把单调栈列为候选模型：

- 数据是一条有先后顺序的一维序列。
- 对每个位置，都要寻找左边或右边的某个元素。
- 关键词包含“第一个”“最近”“下一个”。
- 比较条件是“大于”“小于”“不大于”或“不小于”。
- 输出通常是目标值、目标下标、下标距离或左右边界。
- 某个新元素到来后，可以让一批旧候选永久失效或立即得到答案。

识别后仍然要回答：

```text
扫描方向是什么？
栈里存值还是下标？
栈顶满足什么条件时被淘汰或结算？
相等元素应该保留还是弹出？
答案在入栈、看栈顶还是出栈时产生？
```

这些问题比背“单调递增栈模板”更可靠。

## 16. 最常见的建模和编码错误

### 16.1 把严格更高写成大于等于

错误条件：

```java
temperatures[pending.peek()] <= temperatures[current]
```

相同温度不算升高，正确条件必须是 `<`。

### 16.2 栈里只存温度

只存温度无法计算等待天数。保存下标即可同时取得温度和位置。

### 16.3 用 `if` 代替 `while`

一个高温日可能同时结算多个旧日子，必须持续弹出，直到栈顶不能被结算。

### 16.4 把 `push` 放进 `else`

当前日子无论结算了多少旧日子，最后都要进入等待名单，因为它自己也可能需要等待未来。

### 16.5 把代码嵌套直接等同于平方复杂度

复杂度要按全部元素的总入栈、出栈次数计算。本题每个下标最多各一次，所以是 `O(n)`。

### 16.6 只记“递增栈”这个名字

命名会随遍历方向、栈顶观察方向而引起歧义。调试时直接打印栈中实际温度，并检查“栈底到栈顶温度不升”。

## 17. 一套可以迁移到其他题的建模清单

拿到新题后，依次填写下面这张表：

| 问题 | 要写出的内容 |
| --- | --- |
| 输入对象是什么 | 数组元素、下标、节点、区间还是状态 |
| 要找的关系是什么 | 第一个、最近、最大、最小、可达或计数 |
| 方向是什么 | 左到右、右到左、上下游或图上的邻接 |
| 暴力怎样做 | 给出一个一定正确的小规模算法 |
| 暴力重复了什么 | 重复扫描、重复计算子问题、重复维护统计量 |
| 谁还没有答案 | 明确定义“待处理对象” |
| 什么事件产生答案 | 新元素到达、边界移动、状态转移、节点出队 |
| 最少要保存什么 | 值、下标、计数、前驱、边界或最优状态 |
| 哪些候选可永久丢弃 | 写出支配关系或淘汰条件 |
| 数据结构保持什么不变量 | 不要只写结构名称 |
| 为什么是第一个或最优 | 证明此前不可能已经出现更好答案 |
| 总操作次数是多少 | 按元素生命周期做复杂度分析 |

每日温度只是这张表的一次具体填写。真正需要练习的是“填表过程”，不是最后十几行代码。

## 18. 建议的练习顺序

不要直接跳到柱状图最大矩形。按模型增量练习更容易形成迁移能力：

1. `496. 下一个更大元素 I`：先练“下一个更大元素”的关系。
2. `739. 每日温度`：在关系上增加下标距离。
3. `901. 股票价格跨度`：把方向改成左侧，并在栈中压缩跨度。
4. `42. 接雨水`：弹栈时同时使用左边界和右边界。
5. `84. 柱状图中最大的矩形`：寻找左右第一个更小元素形成边界。

每做一道题，只对比三项：

```text
弹出条件变了什么？
栈中保存的信息变了什么？
答案在哪个瞬间产生？
```

## 19. 最终记忆卡

```text
先找关系，不猜结构。
先写暴力，定位重复。
把“主动找未来”翻成“未来到来时结算”。
维护尚未得到答案的对象。
用不变量决定保留和淘汰谁。
在状态变化的瞬间捕捉答案。
最后用元素的一生证明复杂度。
```

“每日温度”的一句话模型：

> 从左向右扫描，把尚未等到更高温度的日子下标放进等待栈；新温度到来时，反复结算所有更冷的栈顶，弹出时用下标差写答案，最后让今天入栈继续等待。
