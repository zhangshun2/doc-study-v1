# 每日温度中的过程建模：从题意、状态到结果

日期：2026-08-30  
关联题目：LeetCode 739. Daily Temperatures  
关联记录：[每日温度：从“记不住”到“宏观建模”的完整拆解](./2026-08-30-每日温度单调栈与宏观建模.md)

## 1. 这篇只回答一个问题：什么叫“建模”

在算法题里，建模不是给题目换一个更抽象的名字，也不是先猜“这题用栈”。

建模是把自然语言问题改写成一套可以稳定执行的规则：

```text
现实描述
  -> 谁在变化
  -> 哪些信息必须被记住
  -> 什么事件会触发变化
  -> 变化前后必须保持什么性质
  -> 在哪个瞬间可以确定答案
```

对“每日温度”来说，最终模型可以压缩成一句话：

> 按时间接收新温度，维护一份尚未等到更高温度的日期列表；新温度到来时，结算列表末端所有比它低的日期。

这里已经包含了模型的五个部件：

| 部件 | 每日温度中的含义 |
| --- | --- |
| 输入流 | 按日期依次到来的温度 |
| 状态 | 还没有答案的日期 |
| 事件 | 新的一天到来 |
| 状态转移 | 较冷日期被结算并离开，今天进入等待 |
| 输出 | 被结算日期等待的天数 |

单调栈只是实现这套模型的合适工具，不是建模的起点。

## 2. 公式、代码和模型不是一回事

假设第 `j` 天在等待，第 `i` 天出现了第一个更高温度，那么：

```text
answer[j] = i - j
```

这个公式只说明“答案确定后怎么算”，却没有回答三个更难的问题：

1. 怎样高效找到这个 `i`？
2. 怎样保证它是第一个更高温度，而不是后面的任意一个？
3. 在扫描到 `i` 时，怎样知道哪些 `j` 正在等它？

所以，公式是模型中的一个结果规则，而不是完整模型。

同样，下面这段代码也不是模型本身：

```java
while (!stack.isEmpty()
        && temperatures[stack.peek()] < temperatures[i]) {
    int j = stack.pop();
    answer[j] = i - j;
}
stack.push(i);
```

代码只是模型的实现。真正可迁移的理解是：

```text
保留未决对象
  -> 新事件到来
  -> 从最容易被解决的对象开始检查
  -> 能解决就连续结算
  -> 不能解决时停止
  -> 新对象成为未决状态的一部分
```

## 3. 第一步：先定义问题边界

建模前先把自然语言中的约束钉死：

- 对每一天，只寻找它右侧的日期。
- 要找第一个满足条件的日期。
- 温度必须严格更高，相等不算。
- 输出是日期距离，不是温度差。
- 扫描结束仍没有答案时保留 `0`。

这些限制决定了模型不能只记“右边最大温度”，因为最大值没有保留“第一个”的位置信息；也不能只记温度，因为结果需要下标差。

这一步的普遍意义是：

> 先判断结果依赖哪些信息，再决定状态里必须保存什么。

## 4. 第二步：从“逐个查找”换成“统一结算”

### 4.1 请求者主动查找

最自然的暴力思路是：

```text
第 0 天向右找自己的答案
第 1 天向右找自己的答案
第 2 天向右找自己的答案
...
```

这是“每个请求者主动搜索”的模型。它正确，但不同日期会反复扫描同一段未来。

### 4.2 事件到来时统一结算

换一个观察方向：

```text
今天的温度到来后，它能成为哪些过去日期的答案？
```

于是处理方式变为：

```text
过去还没有答案的日期先等待
新温度是一次事件
事件一次性结算所有能被它解决的等待者
```

这不是为了迎合单调栈而编故事，而是在消除暴力中的重复工作。原来“许多过去日期反复查看今天”，现在变成“今天只到达一次，并主动处理相关的过去日期”。

这种视角转换在工程中也很常见：

| 原视角 | 转换后的视角 |
| --- | --- |
| 每个订单反复查询支付状态 | 支付事件到达后更新相关订单 |
| 每个订阅者轮询新消息 | 新消息到达后通知订阅者 |
| 每个任务不断检查前置条件 | 条件完成事件触发任务推进 |

算法里的转换，本质上是从重复查询变为事件驱动。

## 5. 第三步：状态只保存“未来仍可能需要的信息”

扫描到第 `i` 天时，过去的日期分成两类：

1. 已找到第一个更高温度，答案已经确定，以后不再需要。
2. 尚未找到更高温度，必须继续等待。

因此状态中只需要保存第二类。

又因为输出需要 `i - j`，并且比较温度需要 `temperatures[j]`，最小且充分的信息就是日期下标 `j`：

```text
栈中存下标
下标既能取回温度，也能计算日期差
```

这是一个重要的建模原则：

> 状态不是把历史全部保存下来，而是只保存仍会影响未来决策的最小信息。

如果只存温度，会丢失日期距离；如果把日期、温度和答案包装成复杂对象，又保存了可以由下标取回的冗余信息。

## 6. 第四步：设计一个可以持续维护的不变量

“栈里都是未决日期”还不够，因为如果这些日期完全无序，新温度到来时仍要把全部状态扫一遍。

我们还需要一个顺序性质：

```text
从栈底到栈顶，对应温度单调不升。
```

例如：

```text
栈底 [75, 72, 72, 69] 栈顶
```

栈顶是最容易被当前温度解决的等待者。若当前温度连栈顶都不比它高，那么栈顶下面的温度只会更高，也不可能被解决，因此可以立即停止。

这个“能停止”的性质，才是单调性的真正价值。它不是为了让数据看起来整齐，而是让我们不用扫描全部未决状态。

不变量可以完整写成：

> 每轮开始前，栈中下标按日期递增；这些日期都还没有答案；它们对应的温度从栈底到栈顶单调不升。

## 7. 第五步：把每次变化写成状态转移

第 `i` 天到来时只做两件事。

### 7.1 结算能够被今天解决的等待者

```text
只要栈顶温度 < 今天温度：
    弹出栈顶 j
    answer[j] = i - j
```

必须使用 `while`，因为同一个新温度可能同时解决多个过去日期。

必须使用严格小于 `<`，因为相同温度不满足“更高”。

### 7.2 今天进入等待状态

```text
把 i 压入栈
```

即使今天刚刚解决了别人，也不代表今天自己已经有答案。它仍然要等待未来第一个比自己高的温度，所以入栈不是 `else` 分支，而是每一天的固定动作。

## 8. 用一个小例子看模型，而不是背操作

使用温度序列：

```text
[75, 71, 69, 72, 76]
```

| 今天 | 事件发生前的等待状态 | 本次结算 | 事件后的等待状态 |
| --- | --- | --- | --- |
| `0:75` | 空 | 无 | `[0:75]` |
| `1:71` | `[0:75]` | 无 | `[0:75, 1:71]` |
| `2:69` | `[0:75, 1:71]` | 无 | `[0:75, 1:71, 2:69]` |
| `3:72` | `[0:75, 1:71, 2:69]` | 结算 `2`、`1` | `[0:75, 3:72]` |
| `4:76` | `[0:75, 3:72]` | 结算 `3`、`0` | `[4:76]` |

在第 3 天，`72` 依次解决 `69` 和 `71`，遇到 `75` 后停止。停止不是碰巧，而是由单调性保证：既然栈顶的 `75` 不低于 `72`，栈底方向不会再有能被 `72` 解决的日期。

最终仍留在栈中的第 4 天没有更高温度，答案数组初始化的 `0` 就是它的正确结果。

## 9. 为什么这个模型一定正确

### 9.1 弹出的日期一定满足“更高”

只有 `temperatures[j] < temperatures[i]` 时才弹出，所以第 `i` 天温度严格更高。

### 9.2 第 `i` 天一定是第一个更高温度

日期按从左到右扫描。如果 `j` 和 `i` 之间曾出现更高温度，`j` 在那个更早的日期到来时就已经被弹出，不会一直留到 `i`。

### 9.3 没弹出的日期不能由今天结算

弹出所有较冷栈顶后，新的栈顶温度大于等于今天。由于栈内温度从底到顶单调不升，新的栈顶之下只会更高，所以今天不能解决剩余任何日期。

### 9.4 单调性会被持续保持

今天入栈前，所有比今天冷的栈顶都已经弹出。剩余栈顶大于等于今天，压入今天后仍然单调不升。

## 10. 复杂度来自“生命周期”，不是看见 while 就猜平方

代码里有 `for` 套 `while`，但每个日期的完整生命周期只有：

```text
入栈一次
最多出栈一次
```

因此所有 `while` 加起来最多弹出 `n` 次：

- 时间复杂度：`O(n)`，`n` 是温度数组长度。
- 空间复杂度：`O(n)`，最坏情况下所有日期都在等待。

这种分析叫摊还分析。判断复杂度时，应计算一个对象在整个过程里能被处理几次，而不是只看循环的书写层数。

## 11. 它和 OOP、DDD 建模有什么不同

熟悉 OOP 或 DDD 后，遇到算法题容易先找名词：`Day`、`Temperature`、`Forecast`，再考虑对象关系。但这道题的困难不在对象结构，而在时间推进中的状态变化。

可以这样对照：

| 对象或领域建模常问 | 过程建模常问 |
| --- | --- |
| 世界里有哪些实体和值对象？ | 哪些状态会随时间变化？ |
| 对象之间是什么关系？ | 什么事件触发状态变化？ |
| 哪个聚合保护一致性？ | 每一步必须保持什么不变量？ |
| 哪个对象拥有这个行为？ | 结果在哪个状态转移瞬间产生？ |

两者并不冲突。把每日温度写成领域语言，也可以得到：

```text
事件：NewTemperatureArrived(i, temperature)
当前状态：UnresolvedDays
规则：结算所有温度更低且位于栈顶的等待日
不变量：等待日未被结算，温度单调不升
产出：WaitingDaysResolved(j, i - j)
```

区别在于，这里最重要的不是设计类，而是找到状态转移和不变量。

## 12. 一套可复用的过程建模步骤

以后遇到算法题，可以按下面顺序，而不是先猜数据结构：

### 第一步：定义输出

- 最终要返回什么？
- 每个结果在什么条件下才算确定？
- 要的是值、位置、距离、数量，还是最优方案？

### 第二步：写出暴力过程

- 谁在反复查找？
- 哪一段数据被重复访问？
- 暴力为什么慢？用具体最坏输入说明。

### 第三步：寻找未决状态

- 扫描到当前位置时，过去哪些对象已经没用了？
- 哪些对象仍可能被未来影响？
- 为未来决策，最少需要保存什么信息？

### 第四步：确定事件与转移

- 新元素到来会改变哪些旧状态？
- 是逐个查询，还是新事件统一结算？
- 结果在哪个变化瞬间出现？

### 第五步：设计不变量

- 为了快速判断，状态需要保持什么顺序或统计性质？
- 为什么只检查边界、栈顶或窗口端点就够？
- 每次修改后，性质怎样继续成立？

### 第六步：验证与证明

- 用最小例子走一遍。
- 用相等、递增、递减和无答案情况验证边界。
- 证明不会漏、不会错、不会重复。
- 按对象完整生命周期计算复杂度。

## 13. 怎样识别相似模型

看到下面这些语言信号，可以考虑“未决对象 + 未来事件结算”的模型：

- 下一个更大或更小元素
- 左边或右边第一个满足条件的位置
- 要等待多久才发生某事
- 某个新事件能一次解决多个旧请求
- 暴力方案让每个旧对象反复查看未来

但不要见到“下一个”就机械套栈。还要继续问：

1. 未决对象能否按某种单调关系排列？
2. 新事件是否只需从一个端点开始结算？
3. 遇到第一个无法结算的对象时，后面的对象是否也都无法结算？

三个问题都成立，单调栈才有充分理由出现。

## 14. 最后压缩成四句话

```text
公式回答“已知对应关系后怎么算”。
模型回答“对应关系怎样在过程中被发现”。
不变量回答“为什么只看局部就足够”。
代码回答“怎样把状态转移准确实现出来”。
```

真正值得记住的不是 `push` 和 `pop`，而是：

> 把尚未解决的过去压缩成最小状态，让新的事件在恰当的瞬间统一结算它们。
