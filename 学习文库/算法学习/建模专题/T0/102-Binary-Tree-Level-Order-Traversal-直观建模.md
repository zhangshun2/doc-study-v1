# 102. 二叉树的层序遍历：把“这一层”冻结成一次前沿批次

> **双轨入口：** [[题目/二叉树/102-Binary-Tree-Level-Order-Traversal.md|标准题解]] · [[核心模型/二叉树/102-Binary-Tree-Level-Order-Traversal-核心模型.md|核心模型]]

| 核心建模问题 | 如何保存“已经发现但还没有展开”的当前前沿，并准确切开相邻两层 |

这道题真正容易卡住的地方，不是“如何访问所有节点”。递归、栈、队列都能让我们见到每个节点。困难在于输出不是一条扁平序列，而是 `[[第一层], [第二层], [第三层]]`：程序必须知道一层在哪里结束，下一层从哪里开始。

本篇从一个故意笨但一定正确的“按深度反复查树”模型开始。我们先看清它重复了什么，再把“每次从根重新寻找某层”改成“保留下一批等待展开的节点”。直到状态、不变量和边界都明确之后，才给这种结构命名。目标不是背下几行层序遍历代码，而是理解三个以后可以反复迁移的角色：**当前前沿、下一前沿、冻结的批次边界**。

## 2. 完整题目

给定一棵二叉树的根节点 `root`，按层输出整棵树的节点值。层的定义来自节点到根的距离：根节点是第 `0` 层，根的孩子是第 `1` 层，依次类推。同一层内必须按照从左到右的顺序输出；不同层要分别放入不同的列表中。

输入是根节点 `root`。它可能指向一棵非空二叉树，也可能为 `null`，表示空树。输出类型是 `List<List<Integer>>`：外层列表按从上到下的顺序保存各层，内层列表按从左到右的顺序保存本层节点值。

**示例 1：普通且不完全对称的树**

```text
输入：root = [3,9,20,null,null,15,7]
输出：[[3],[9,20],[15,7]]

树形：
        3
       / \
      9  20
        /  \
       15   7
```

根 `3` 单独形成第一层；`9` 和 `20` 同为根的孩子，按左到右形成第二层；`15` 和 `7` 是下一层。空孩子只表示连接不存在，不进入输出。

**示例 2：只有根节点**

```text
输入：root = [1]
输出：[[1]]
```

根既是第一层，也是最后一层。结果仍然是两层列表结构，而不是 `[1]`。

**示例 3：空树**

```text
输入：root = []
输出：[]
```

没有根，就没有任何层；不能输出 `[[]]`，因为后者表示“存在一层，只是该层没有节点”，这不符合树层的定义。

官方约束与提示如下：

- 树中节点数 `n` 的范围为 `[0, 2000]`。
- 每个节点值满足 `-1000 <= Node.val <= 1000`。
- 官方接口额外提示可以使用队列完成广度优先搜索，但本文不会把提示当作推导起点。
- Java 方法入口为：

```java
public List<List<Integer>> levelOrder(TreeNode root)
```

`n` 允许为 `0`，所以空树必须在模型入口处有明确语义。节点值可以重复且可以为负数，因此数值不能用来判断节点是否访问过，也不能代表节点身份。`n` 最大为 `2000`，平方级做法在最坏形状下会进行约四百万数量级的重复访问；线性访问每个节点一次更符合这道题要训练的模型。

## 3. 先把题目说成人话

**一句话生活化复述：**从负责人开始，一批一批点名；先完整点完当前批次，再点由这批人带来的下一批人，每批内部保持从左到右的登记顺序。

**一句话关系化复述：**把与根节点边数距离相同的节点归入同一组，按距离从小到大输出各组，并在组内保持父节点次序和左孩子优先所诱导出的顺序。

先看“层”到底是什么。对示例中的节点 `15`，从根到它的路径是 `3 -> 20 -> 15`，走过两条边，所以深度为 `2`。节点 `7` 也要走两条边，因此它与 `15` 同层。题目不是按值大小分组，也不是按数组中的位置分组，而是按**从根出发需要走几步**分组。

| 要素 | 本题的关系化含义 |
| --- | --- |
| 对象 | 二叉树中的节点对象，不只是节点值 |
| 关系 | 父节点通过左、右引用连接孩子；层由到根的边数决定 |
| 方向 | 从根向下，每个父节点先看左孩子，再看右孩子 |
| 目标 | 每个节点恰好输出一次；同深度同组，组从浅到深，组内从左到右 |
| 限制 | 树可能为空；形状可能很偏；值可重复，空孩子不是节点 |
| 需要持续保存的信息 | 已经被上层发现、但其孩子尚未展开的节点，以及当前层有多少个这样的节点 |

题目关系图可以压缩成：

```text
根（距离 0）
  |
  | 展开孩子，距离统一加 1
  v
第 1 层当前前沿
  |
  | 完整处理这一批，再统一进入下一批
  v
第 2 层当前前沿 -> 第 3 层当前前沿 -> 直到前沿为空

同一批内部：父节点从左到右；每个父节点的孩子也是左后右。
```

这里最重要的不是“树”这个名词，而是“同距离对象构成一批”。只要后续问题也要求按从起点的步数分批处理，当前前沿与下一前沿的模型就可能出现。

## 4. 第一切入点：读题时先看什么

读题第一分钟，先圈出三个决定模型的词：**逐层**、**从上到下**、**从左到右**。

“逐层”说明输出存在批次边界，不能只得到访问顺序；“从上到下”说明在处理更深节点之前必须先处理完所有更浅节点；“从左到右”说明发现和保存同层节点时不能打乱顺序。题名里的“二叉树”告诉我们每个节点最多产生两个下一批对象，但它不是最关键的限制。节点值的正负、大小也只是数据内容，对分层没有作用。

可以暂时忽略的故事包装包括：节点值具体是多少、示例为何用数组表示树、空位写成几个 `null`。真正参与模型的是节点引用关系。数组 `[3,9,20,null,null,15,7]` 只是平台展示和构造树的方式，算法收到的是 `TreeNode root`，不是这个数组。

人工看最小非平凡例子：

```text
      A
     / \
    B   C
       /
      D
```

人会先写 `[A]`，再写 `[B,C]`，最后写 `[D]`。仔细观察这个动作：写下 `A` 时，我们同时看见了 `B、C`；但不能马上把 `B` 写进 `[A]`，而是把它们留给下一批。写下 `B、C` 时，又看见 `D`，继续留给更后一批。于是第一个可迁移问题自然出现：

> 当处理当前层时，怎样暂存刚刚发现的孩子，并保证它们只在下一层被处理？

数据范围给出的性能信号是：每个节点最好只展开一次。更关键的结构信号是：孩子总在父节点之后处理，而先被发现的父节点所产生的孩子，也应排在后被发现父节点所产生的孩子之前。现在先记住这个先后要求，不急着给容器起名字。

## 5. 最直接的人工或暴力模型

最贴近题目字面的做法，是把问题理解成多个独立查询：先问“深度 `0` 有哪些节点”，再问“深度 `1` 有哪些节点”，然后问“深度 `2` 有哪些节点”。每次查询都从根重新出发。

完整步骤如下：

1. 先遍历一次树，算出最大高度 `h`，于是层号范围是 `0` 到 `h - 1`。
2. 对每个目标深度 `targetDepth`，创建一个新的本层列表。
3. 从根递归向下，同时记录还要走多少层。
4. 剩余深度为 `0` 时，把当前节点值加入这一层；否则继续先访问左孩子、再访问右孩子。
5. 把本层列表加入结果，然后从根重新查询下一深度。

伪代码的含义可以写成：

```text
height = 计算整棵树高度(root)
for targetDepth = 0 到 height - 1:
    level = 空列表
    从 root 出发收集 targetDepth 深度的节点到 level
    result 加入 level
```

这个模型一定正确。对于任意目标深度，它枚举了从根往下的所有实际路径，只在走了恰好 `targetDepth` 条边时收集节点；先左后右的递归顺序也保证同层从左到右。它很有价值，因为它直接把题目翻译成“按深度查询”，让我们明确了正确性的基线。

设 `n` 为节点数，`h` 为树的层数。每一层都可能重新访问从根到该层之间的大量节点，总时间上界为 `O(nh)`。在只有单侧孩子的链状树中，查询第 `d` 层要经过前 `d` 个祖先，总访问次数为 `1 + 2 + ... + n`，达到 `O(n^2)`。递归工作空间由树高决定，为 `O(h)`；返回结果本身保存全部 `n` 个值，占 `O(n)`。

这不是“逻辑错误”的暴力。它的问题是：已经知道的父子关系没有被带到下一轮，每问一个更深层，就把上轮到达的地方忘掉并重新从根出发。

## 6. 暴力到底浪费在哪里

仍看示例树：

```text
        3
       / \
      9  20
        /  \
       15   7
```

按深度反复查询时，访问轨迹近似如下：

```text
查询第 0 层：3                         -> 得到 [3]
查询第 1 层：3, 9, 20                  -> 得到 [9,20]
查询第 2 层：3, 9, 20, 15, 7           -> 得到 [15,7]

重复次数：
3  被看了 3 次
9  被看了 2 次
20 被看了 2 次
15、7 各被看 1 次
```

第一次处理 `3` 时，我们其实已经知道下一层是 `9、20`；但暴力模型只把 `[3]` 留在结果中，把“下一步应该从 `9、20` 继续”这个中间结论丢掉。第二次处理 `9、20` 时，我们又已经知道再下一层是 `15、7`，它仍然被丢掉。下一轮只好再次经过 `3、20` 才抵达它们。

在链状树中浪费更明显：

```text
1 -> 2 -> 3 -> 4

找第 0 层：1
找第 1 层：1 -> 2
找第 2 层：1 -> 2 -> 3
找第 3 层：1 -> 2 -> 3 -> 4
```

越靠近根的节点被重复经过得越多。问题并不在递归语法，而在状态生命周期：本轮发现的下一层节点没有被保存到下一轮。

因此优化目标可以明确成一句话：

> 不要为了查询每一层反复从根出发；处理当前层时就保存它发现的全部孩子，让这些孩子直接成为下一轮的起点，并让每个节点只被展开一次。

还有一类可以永久丢弃的信息：一个节点的值已经写入当前层、它的非空孩子也已经交给下一批后，这个父节点以后不会再影响任何输出。继续保存它没有价值。模型需要的是“尚未展开的前沿”，而不是完整访问历史。

## 7. 容易想到但走不通的方向

### 方向一：只保留一条扁平的从上到下访问序列

我们很容易写出一种遍历，让结果成为 `[3,9,20,15,7]`。它保存了节点被发现的先后顺序，却丢失了层边界。处理完成后，仅凭这个扁平列表和节点值，不能可靠恢复哪几个值属于一层，尤其当树不完全、节点值重复时更不可能。

这个方向不是访问顺序错误，而是**输出模型不完整**。它提醒我们：除了等待处理的节点，还要知道当前批次的数量或明确维护两批容器。

### 方向二：让内层循环不断读取正在变化的容器大小

下面这种直觉很自然：“这一层有多少个，就循环多少次”，于是把条件直接写成 `i < pending.size()`。问题在于每次取出父节点后又会加入孩子，`size()` 同时受出队和入队影响，它不再代表循环开始时的当前层节点数。

以根 `3` 有两个孩子 `9、20` 为例：开始时大小为 `1`；处理 `3` 后，容器中变为 `[9,20]`，大小为 `2`；此时 `i` 变为 `1`，条件 `1 < 2` 仍成立，于是 `9` 被错误地并进根这一层。若某个节点没有孩子，大小又可能快速缩小，导致本层后面的节点反而没处理完。动态大小既可能吞入下一层，也可能提前停止。

从这个失败中得到的条件是：**批次边界必须是进入本轮时的快照，不能由本轮正在修改的状态实时决定。**

### 方向三：递归时携带深度，把值放进对应桶

深度优先搜索可以在一次遍历内完成：递归函数携带 `depth`，当结果中还没有该层时创建列表，再把当前值放入 `result.get(depth)`。先左后右递归时，它同样能得到正确顺序，时间也是 `O(n)`。

这个方向并没有走不通，它是本题的另一套正确最优模型。但它保存的是“当前路径 + 深度编号”，层的节点并不同时存在于一个当前前沿中。对于“每层平均值”“每层最后一个节点”仍然可以扩展，但对于无权图最短路、按距离向外扩散等任务，逐层前沿更直接；在极度偏斜的树上，递归还会有 `O(h)` 调用栈风险。我们选择前沿模型，是为了训练更通用的按距离分批处理能力，而不是声称 DFS 错误。

### 方向四：只保存节点值

如果等待区只保存 `3、9、20` 这些整数，取出 `20` 时便不知道它的左、右孩子是谁。节点值只够输出，不够继续展开关系；而且值可以重复，不能充当节点身份。因此等待状态必须保存 `TreeNode` 对象，输出时才读取其中的 `val`。

## 8. 关键视角转换

暴力模型是在“主动查询某个深度”：每次从根出发，走到指定距离。新模型改成“按距离推进前沿”：当前距离的所有节点已经在手中，处理它们时自然产生距离加一的节点。

> **小白追问：** “前沿”到底指谁，为什么一轮开始时等待区里的节点恰好属于同一层？
>
> **先给短答：** 前沿就是已经被上一层发现、但还没有展开孩子的那一批节点；上一轮只会把当前节点的孩子放入等待区，所以轮次结束后留下的节点深度统一加一。
>
> **最小例子：** 根 `A` 是第 `0` 层。处理 `A` 只会发现孩子 `B、C`，因此下一轮开始时等待区为 `[B,C]`，两者到根都走一条边，不可能混入孙节点。
>
> **回到模型/代码：** 外层 `while` 的一次循环就是一轮前沿推进；轮次开始时的 `pendingFrontier` 才整体代表当前层，内层加入的孩子则属于下一层。

| 转换前 | 转换后 |
| --- | --- |
| 每一层都从根重新查找 | 下一层直接继承当前层发现的孩子 |
| 深度是一次查询参数 | 深度由外层轮次自然推进 |
| 处理完节点就丢掉所有中间关系 | 丢掉父节点前先保存它的孩子 |
| 一轮中反复判断节点是否达到目标深度 | 一轮开始时就知道在手中的节点都属于当前深度 |
| 把“访问顺序”和“层分组”混在一起 | 用固定批次边界分开当前层与下一层 |

视角转换后，最小过程是：

```text
当前前沿 = [根]

只要当前前沿不空：
    冻结当前前沿人数
    恰好处理这些节点
    处理时发现的孩子追加到等待区尾部
    当前批处理结束后，剩余等待者正好构成下一前沿
```

> **小白追问：** 为什么必须在一轮开始时冻结人数，不能在循环条件里随时读取等待区大小？
>
> **先给短答：** 因为本轮一边取出当前层节点，一边加入下一层节点，实时大小描述的是混合状态，不再是当前层原有数量。
>
> **最小例子：** 开始只有根 `A`，大小为 `1`。处理 `A` 后加入 `B、C`，实时大小变成 `2`；若此时继续按动态大小循环，`B` 就会被错误放进 `A` 所在层。
>
> **回到模型/代码：** `currentLevelSize = pendingFrontier.size()` 必须位于内层 `for` 之前，并且 `processed` 始终与这个固定整数比较。

为什么减少重复？一个非根节点只会在其唯一父节点被处理时被发现一次，之后进入等待区一次、被展开一次。根也只进入一次。我们不再为了确定深度重复穿过祖先，层号由“经历了多少轮前沿推进”隐含表达。

这里还有一个细微但关键的认识：当前层和下一层在内层循环进行到一半时，可以共存在同一个物理容器中。它们不需要真的分成两个容器，只需有一个冻结的整数告诉我们本轮还应该取出多少个旧节点。物理状态会变化，逻辑边界保持不变。

## 9. 正式建立模型

| 建模项 | 本题结论 |
| --- | --- |
| 对象 | `TreeNode` 节点对象；它同时携带值和向孩子继续展开的引用 |
| 关系 | 父节点的非空左、右孩子属于父节点下一层；到根距离相同的节点同组 |
| 状态 | 按发现顺序保存的“已发现但尚未展开”节点，以及本轮开始时冻结的 `currentLevelSize` |
| 事件 | 从等待区头部取出一个当前层节点，输出其值，并在尾部加入其左、右孩子 |
| 不变量 | 每轮开始时，等待区从头到尾恰好是当前层全部节点，顺序为从左到右 |
| 结果时机 | 恰好处理完冻结数量的节点后，当前 `level` 才成为一个完整层并加入 `result` |

> **小白追问：** 孩子为什么要在父节点出队时立刻入队，不能等整层结束后再找吗？
>
> **先给短答：** 父节点出队时正好握有孩子引用，这是把关系交给下一轮的唯一直接时机；若延后，就必须额外保存父节点或另建下一层列表。
>
> **最小例子：** 节点 `A` 只有孩子 `B`。取出 `A` 后若既不加入 `B`、也不保留 `A`，等待区马上为空，`B` 便永久丢失。
>
> **回到模型/代码：** `poll()` 得到 `current` 后，先读取 `current.left`、`current.right` 并 `offer()` 非空孩子，然后才结束这次父节点处理。

### 为什么这些状态足够

等待区中的节点对象能让我们继续找到孩子；先进者先处理能保存同层顺序；冻结数量能区分本轮旧节点与本轮新加入的孩子。层号本身不是输出内容，所以无需额外在每个节点旁保存深度。访问历史也不需要，因为输入是树：除根外每个节点只有一个父节点，不会从两条路径被重复发现。

### 状态是否保存了多余信息

容器保存完整节点，而不是只保存值，看起来信息更多，但左右引用正是产生下一前沿所必需的。相反，已经完成展开的父节点可以永久删除：它的值已进入结果，孩子已进入等待区，之后没有任何规则需要再次查看它。

### 遍历方向为什么是从根向下

题目先要浅层，再要深层；根是唯一已知入口。由父节点可以直接找到孩子，而普通 `TreeNode` 没有父引用，反向从叶子找根既没有入口，也不利于分层。因此从根向下是与数据可达方向和输出顺序同时一致的方向。

> **小白追问：** 只保证先处理左父节点，就一定能让整层保持从左到右吗？
>
> **先给短答：** 还要同时保证每个父节点先登记左孩子、再登记右孩子；父节点顺序和孩子顺序共同决定下一层顺序。
>
> **最小例子：** 当前层是 `[A,B]`，`A` 的孩子是 `C、D`，`B` 的左孩子是 `E`。依次处理 `A、B` 并按左后右加入，下一层只能是 `[C,D,E]`。
>
> **回到模型/代码：** 队头 `poll()` 保证父节点顺序；两个独立判断必须按 `current.left`、`current.right` 的次序执行 `offer()`。

### 相等值和空引用如何处理

两个节点值相等仍是两个独立节点，都必须输出。模型按对象引用处理身份，不做值去重。空孩子表示没有待展开对象，不能进入等待区；否则取出 `null` 后既不能访问 `val`，`ArrayDeque` 也明确不允许保存 `null`。

### 运行中最关键的混合状态

若某轮开始时等待区是 `[9,20]`，冻结大小为 `2`。处理 `9` 后，区内可能是 `[20]`；处理 `20` 并加入孩子后，区内是 `[15,7]`。更一般地，在一轮尚未结束时可以把容器理解成：

```text
队头 -> [尚未处理的当前层节点 | 已发现的下一层节点] -> 队尾
          数量由冻结边界控制       只追加，不在本轮展开
```

这个逻辑分隔符不真实存储在容器里，`currentLevelSize` 和内层已处理计数共同确定它的位置。

> **小白追问：** 一个队列中途明明同时有两层节点，为什么仍能说它表示“当前前沿”？
>
> **先给短答：** “整个队列就是当前层”只在外层轮次开始时成立；轮次中途，冻结数量把队头尚未处理的旧节点和队尾新发现的孩子逻辑分开。
>
> **最小例子：** 本轮从 `[A,B]` 开始并冻结为 `2`。处理 `A` 加入 `C` 后变成 `[B | C]`，竖线左边还属于本轮，右边已经属于下一轮。
>
> **回到模型/代码：** `processed < currentLevelSize` 决定还要从队头取多少个旧节点；代码不需要真的保存竖线，也不会在本轮取出 `C`。

## 10. 所需数据结构详解

现在模型已经要求一种结构：新发现的节点从尾部加入，等待最久的节点从头部取出；先发现的父节点必须先展开。这个“先进先出”的结构才被命名为**队列（Queue）**。算法整体按与根的距离从小到大扩展，称为**广度优先搜索（Breadth-First Search，BFS）**。

### 队列是什么

队列有队头和队尾。新元素从队尾进入，旧元素从队头离开，因此进入顺序就是处理顺序。Java 中 `Queue<E>` 是接口，本题用 `ArrayDeque<TreeNode>` 作为具体实现：它内部使用可扩容的环形数组管理两端位置，不需要在每次队头操作时搬移其余元素。

| 本题操作 | Java 表达 | 含义 | 单次复杂度 |
| --- | --- | --- | --- |
| 加入待展开节点 | `queue.offer(node)` | 把新发现的孩子放到队尾 | 摊还 `O(1)` |
| 取出下一个节点 | `queue.poll()` | 从队头取得并删除等待最久的节点 | `O(1)` |
| 判断是否还有前沿 | `queue.isEmpty()` | 决定外层遍历是否继续 | `O(1)` |
| 冻结本层人数 | `queue.size()` | 只在一轮开始时读取快照 | `O(1)` |

`offer` 与 `poll` 比 `add` 与 `remove` 更适合表达普通队列操作：前一组通过特殊返回值表示失败或空，后一组可能抛异常。本题在 `poll` 前已有非空和固定计数保证，因此不会得到 `null`。`ArrayDeque` 不接收空元素，我们也只在孩子非空时调用 `offer`。

### 队列里为什么保存节点而不是值或深度

保存值无法继续展开孩子；保存“节点 + 深度”的复合对象当然可行，却不是本题最小状态。因为一轮开始时队列中所有节点深度相同，外层轮次已经表达深度，逐节点重复保存层号没有必要。队列最坏保存一整层附近的节点，设树最大宽度为 `w`，其规模为 `O(w)`，最坏可达 `O(n)`。

### BFS、层和队列到底是什么关系

BFS 的一般含义是从起点开始，先处理距离为 `0` 的对象，再处理距离为 `1` 的对象，然后是距离为 `2` 的对象。队列保证先发现的近距离对象先被处理。在树中，从根到每个节点只有唯一路径，因此边数距离就是节点深度，“相同 BFS 距离”与“同一树层”完全一致。

> **小白追问：** 为什么 BFS 天然保留层次，普通 DFS 却要额外携带深度？
>
> **先给短答：** BFS 的等待顺序保证较浅节点全部排在更深节点前面；DFS 会优先沿一条分支向下，访问顺序本身不能标出层边界。
>
> **最小例子：** 树中 `A` 的左孩子是 `B`、右孩子是 `C`，`B` 又有孩子 `D`。普通先序 DFS 是 `A,B,D,C`，深度为 `2` 的 `D` 会早于同层尚未访问的 `C` 出现。
>
> **回到模型/代码：** BFS 用 `pendingFrontier + currentLevelSize` 直接形成一层；DFS 若要正确分组，必须传入 `depth`，再写入 `result.get(depth)`。

单独使用队列只保证访问顺序按距离不下降，却不会自动替我们生成嵌套列表。**队列负责前沿顺序，冻结的 `queue.size()` 负责层边界。**少了前者会打乱发现与展开顺序，少了后者只能得到扁平 BFS。

### 为什么不使用其他常见结构

- 栈是后进先出。先加入左孩子再加入右孩子时，右孩子会先被处理；更本质地说，它会沿最新分支深入，形成深度优先行为，不自然地维持同距离批次。
- `ArrayList` 尾部加入很快，但反复 `remove(0)` 要移动剩余元素，单次为 `O(n)`，可能把整体退化到 `O(n^2)`。用额外头指针可以修正，却相当于自行实现队列语义。
- 两个列表 `currentLevel` 和 `nextLevel` 是完全正确的替代实现，层边界更显式；每轮交换列表即可。单队列加冻结大小保存的对象更少，且是图 BFS 中更常见的骨架。
- `LinkedList` 也实现 `Queue`，功能正确，但每个节点还要维护链表链接，局部性通常不如数组式双端队列；本题不需要在中间插入删除，`ArrayDeque` 更直接。

### 结果列表的职责

`List<List<Integer>> result` 不是搜索状态，而是已经完成的输出；`List<Integer> level` 是当前批次的输出缓冲。必须等冻结数量全部处理完再把 `level` 加入 `result`，这样“一个内层列表就是完整一层”的含义始终稳定。

## 11. 生活化类比及边界

把过程想成展馆按批次接待家庭。入口第一批只有一位家长。工作人员在本轮开始时先盖章确认“本批共有几人”，然后按排队顺序逐个接待。每位来访者可以登记自己的左侧孩子和右侧孩子；孩子排到队尾，领取的是下一批资格，不能因为已经站进队伍就混入当前批。当前盖章人数全部接待完，工作人员封存本批名单，再为此时队伍中的人开始下一轮。

| 生活对象或动作 | 算法中的对应物 |
| --- | --- |
| 一位来访者 | 一个 `TreeNode` 节点对象 |
| 来访者带来的左、右孩子 | 当前节点的 `left`、`right` 非空引用 |
| 等候队伍 | 保存尚未展开节点的 `queue` |
| 先来者先接待 | 队列先进先出，保持从左到右发现顺序 |
| 本轮开始时盖章确认人数 | `currentLevelSize = queue.size()` 的冻结快照 |
| 接待一人并登记其孩子 | `poll` 当前节点，记录值，再 `offer` 非空孩子 |
| 本批完整名单 | `level` |
| 所有批次档案 | `result` |
| 队伍最终为空 | 所有实际节点都已展开，遍历结束 |

这个类比最有用的地方，是区分“已经进入同一条物理队伍”和“属于同一个逻辑批次”。孩子可以在当前轮进入队尾，但批次资格由轮开始时的盖章人数决定。

类比到这里为止。现实队伍里可能有人迟到、插队、重复登记，也可能一个孩子被多个家庭带来；二叉树没有这些动态行为，每个非根节点只有一个父节点，结构在遍历期间不变化。现实批次常按时间切分，本题批次严格按到根的边数切分。类比帮助记忆状态变化，不能替代后面的不变量证明。

## 12. 典型输入的完整数据变化图

使用官方示例的树：

```text
深度 0：           3
                 /   \
深度 1：         9     20
                       / \
深度 2：             15   7

读取方向：上 -> 下
层内方向：左 -> 右
队列方向：队头 -> 队尾
```

初始时只知道根：

```text
queue = 队头 -> [3] -> 队尾
result = []
```

### 第 0 层：冻结 `currentLevelSize = 1`

| 快照字段 | 内容 |
| --- | --- |
| 当前输入 | 节点 `3` |
| 处理前状态 | `queue = [3]`，`level = []` |
| 判断依据 | 本轮冻结人数为 `1`，`3` 是唯一当前层节点 |
| 执行动作 | 取出 `3`，记录值；按左后右加入 `9、20` |
| 处理后状态 | `queue = [9,20]`，`level = [3]` |
| 新增结果 | 本轮已处理 `1/1`，封存 `[3]` |

```text
result = [[3]]
queue  = 队头 -> [9, 20] -> 队尾
                    全部属于下一层
```

### 第 1 层：冻结 `currentLevelSize = 2`

先处理 `9`：

| 快照字段 | 内容 |
| --- | --- |
| 当前输入 | 节点 `9` |
| 处理前状态 | `queue = [9,20]`，`level = []` |
| 判断依据 | 本轮冻结人数为 `2`，目前处理第 `1` 个 |
| 执行动作 | 取出 `9`，记录值；两个孩子均为空，不入队 |
| 处理后状态 | `queue = [20]`，`level = [9]` |
| 新增结果 | 本层尚未结束，不写入外层结果 |

再处理 `20`：

| 快照字段 | 内容 |
| --- | --- |
| 当前输入 | 节点 `20` |
| 处理前状态 | `queue = [20]`，`level = [9]` |
| 判断依据 | 本轮还剩第 `2` 个旧节点；动态大小虽然为 `1`，冻结边界仍为 `2` |
| 执行动作 | 取出 `20`，记录值；按左后右加入 `15、7` |
| 处理后状态 | `queue = [15,7]`，`level = [9,20]` |
| 新增结果 | 本轮已处理 `2/2`，封存 `[9,20]` |

```text
result = [[3], [9, 20]]
queue  = 队头 -> [15, 7] -> 队尾
                     它们只属于第 2 层
```

### 第 2 层：冻结 `currentLevelSize = 2`

```text
处理 15 前：queue = [15, 7]  level = []
取出 15：   queue = [7]      level = [15]      无孩子加入
取出 7：    queue = []       level = [15, 7]   无孩子加入
本轮结束：  result 加入 [15, 7]
```

最终：

```text
queue  = []
result = [[3], [9, 20], [15, 7]]
```

外层循环停止不是因为我们预先知道树有三层，而是因为当前前沿为空。层数由成功推进了多少轮自然得到。

### 看清一轮中的逻辑分界

再看一个节点都有孩子的局部状态。假设本轮开始为 `[A,B]`，大小冻结为 `2`：

```text
开始：队头 -> [A, B] -> 队尾
                当前层共 2 个

处理 A，加入 C、D：
      队头 -> [B | C, D] -> 队尾
                ^
                左边仍是本轮未处理对象；右边已是下一层

处理 B，加入 E：
      队头 -> [C, D, E] -> 队尾
                本轮计数已经达到 2，全部留给下一轮
```

分隔线会随当前层节点被取出而右移，但我们不需要真的维护分隔线；`for` 循环已经处理的次数与冻结大小共同表达它。

## 13. 边界场景的数据变化

### 场景一：空树

```text
root = null
result = []

入口判断发现没有首个前沿对象
-> 不执行 queue.offer(root)
-> 外层循环一次也不执行
-> 返回 []
```

这里必须先判断空根。`ArrayDeque` 不允许加入 `null`；即使换成能容纳空值的实现，把 `null` 当成真实节点也会在读取 `val` 时失败。空树没有层，因此不会创建空的 `level`。

### 场景二：只有一个节点

```text
root = 1
初始 queue = [1]
冻结大小 = 1
取出 1，左右孩子都为空
queue = []，level = [1]
result = [[1]]
```

本轮后等待区为空，遍历自然结束。循环既不会越界，也不需要特殊判断“叶子是不是最后一层”。叶子只是产生零个下一批对象的普通节点。

### 场景三：为什么动态 `size()` 会破坏层

设树为：

```text
      1
     / \
    2   3
```

错误循环条件是 `for (int i = 0; i < queue.size(); i++)`：

```text
开始：i = 0，queue = [1]，动态 size = 1，条件成立
处理 1：queue = [2,3]，level = [1]
i 变为 1：动态 size = 2，1 < 2 仍成立
错误处理 2：queue = [3]，level = [1,2]
i 变为 2：动态 size = 1，条件失败

错误首层：[1,2]
剩余队列：[3]
```

这不是固定地“多处理所有孩子”，而是结果取决于每个节点产生几个孩子，因而更危险。正确做法在开始时保存 `currentLevelSize = 1`，之后即使队列变为 `[2,3]`，内层也只执行一次。

### 场景四：重复值与极端值

```text
      -1000
      /   \
   -1000  1000

输出：[[-1000],[-1000,1000]]
```

相同的 `-1000` 不会被去重，因为它们是两个位置不同的节点。极端值只被读取和保存，不参与加减乘除，因此没有整数溢出风险。

## 14. 正确性与不变量

要证明的不是“队列通常能做 BFS”，而是这段具体过程确实生成了题目要求的每一层。核心循环不变量是：

> 每次外层循环开始时，队列从头到尾恰好保存尚未输出的当前深度全部节点，并且顺序是从左到右。

### 起点成立

非空树开始时，队列中只有根。根是深度 `0` 的全部节点，也是这一层从左到右唯一的节点，所以不变量成立。空树在入口直接返回，也符合“没有任何层需要处理”。

### 本轮输出为什么满足题意

进入一轮时先冻结 `currentLevelSize`。根据不变量，这个数字正好是当前层节点数。内层恰好从队头取出这么多个节点，得到的既不会少于当前层，也不会多到下一层。队列原本按从左到右排列，逐个从头取出并记录，因此 `level` 的顺序正确。

> **小白追问：** 冻结一个数字为什么就能保证既不少取，也不多取？
>
> **先给短答：** 冻结时队列中的每个节点都属于当前层，数量就是本层全集大小；之后只执行同样次数的出队，新加入的孩子没有机会增加执行次数。
>
> **最小例子：** 一轮从 `[B,C]` 开始，冻结为 `2`。即使处理 `B` 后加入 `D、E`，两次出队仍然只会取走 `B、C`，`D、E` 留在队中。
>
> **回到模型/代码：** 正确性依赖固定上界 `processed < currentLevelSize`，而不是依赖循环中不断变化的 `pendingFrontier.size()`。

### 为什么下一轮仍然成立

处理当前层每个父节点时，先加入左孩子，再加入右孩子。当前层父节点本身也是从左到右处理，所以所有孩子的总发现顺序是：最左父节点的左、右孩子，接着是下一个父节点的左、右孩子。树的平面顺序正是这样得到的。孩子全部追加到队尾，不会跑到尚未处理的当前层节点之前。

当冻结数量处理完后，所有当前层节点已删除；队列中只剩它们的非空孩子。每个下一层节点都有且只有一个当前层父节点，所以不会漏掉，也不会重复加入。于是队列恰好按从左到右保存下一层全部节点，不变量对下一轮继续成立。

> **小白追问：** 为什么“每个孩子跟着父节点入队”就足以证明下一层没有遗漏和重复？
>
> **先给短答：** 二叉树中除根外每个实际节点恰好有一个父节点；处理完当前层全部父节点，也就检查完了通向下一层的全部边，而且每条边只检查一次。
>
> **最小例子：** 当前层 `[B,C]` 的非空孩子分别是 `D` 和 `E、F`。处理完 `B、C` 后得到 `[D,E,F]`；不存在第三个入口再次发现 `D`，也不存在绕过父节点才能找到的孩子。
>
> **回到模型/代码：** 两个非空判断覆盖每个 `current` 的全部出边；树无需 `visited`，一般图因可能有多个前驱才必须增加首次发现标记。

### 删除父节点为什么安全

节点出队前后，我们完成了它对未来的全部贡献：值已加入当前层，左、右孩子已检查并将非空者加入等待区。后续层的生成只依赖那些孩子自己的引用，不再依赖父节点。删除父节点不会丢失未来所需信息。

### 为什么不会漏掉更深节点

任取一个非根节点 `x`。它有唯一父节点 `p`。根最终会被处理；若 `p` 被处理，`x` 就会被加入队列；加入的节点最终位于有限队列的队头并被处理。沿根到 `x` 的唯一路径逐层应用这个事实，`x` 一定会被发现和输出。不存在一个需要从其他方向才能找到的树节点。

### 为什么会终止并得到全部答案

每个实际节点至多入队一次、出队一次。树节点数有限，处理叶子不会加入新节点；当最后一层全部出队后，队列为空，外层循环结束。根据不变量，每一轮恰好生成一层；根据不遗漏论证，所有节点都已进入某一层。因此最终结果既没有多余节点，也没有缺失节点，层次和层内顺序均正确。

## 15. 时间与空间复杂度推导

定义变量：

- `n`：树中实际节点总数。
- `h`：树的层数，也就是树高；空树可视为 `0`。
- `w`：任意一层节点数的最大值，即最大宽度。
- 返回结果中共有 `n` 个整数，不论使用哪种正确方法，这部分输出空间都不可避免。

### 直接模型：逐层从根查询

先计算高度访问 `n` 个节点，成本为 `O(n)`。随后对每个目标深度重新从根出发。第 `d` 层查询要经过到该层为止的祖先。总访问量上界可写为 `O(nh)`。

在平衡树中，`h = O(log n)`，这种上界体现为 `O(n log n)` 量级；在单链形树中，`h = n`，实际访问次数是 `1 + 2 + ... + n = n(n+1)/2`，所以最坏时间为 `O(n^2)`。递归调用栈最多沿一条根叶路径，辅助空间为 `O(h)`；若把返回结果算入，总空间再加 `O(n)`。

### 推荐模型：按前沿逐层推进

每个节点的生命周期固定：

```text
被父节点发现并入队一次
-> 到达队头并出队一次
-> 值加入结果一次
-> 左孩子检查一次，右孩子检查一次
```

根省略“被父节点发现”，但也只入队一次。`offer` 和 `poll` 的摊还成本为 `O(1)`，`size` 与 `isEmpty` 为 `O(1)`。所有内层循环次数相加正好是 `n`，不是“外层乘内层”的 `O(n^2)`：每一轮处理不同的一批节点，各层大小之和为 `n`。因此总时间复杂度为 `O(n)`。

> **小白追问：** 代码有外层 `while` 和内层 `for`，为什么不是两层循环相乘得到 `O(n^2)`？
>
> **先给短答：** 内层不是每轮都遍历全部 `n` 个节点，而是把互不重叠的各层节点分批处理；所有批次的处理次数相加才是总次数。
>
> **最小例子：** 三层节点数分别为 `1、2、2` 时，内层总执行次数是 `1 + 2 + 2 = 5`，正好等于五个节点，而不是 `3 * 5`。
>
> **回到模型/代码：** 每个 `TreeNode` 只会对应一次 `offer`、一次 `poll` 和一次内层循环体，所以按节点生命周期汇总为 `O(n)`。

队列最多保存一层附近的前沿节点，规模用 `w` 表示，辅助空间为 `O(w)`，最坏为 `O(n)`。当前 `level` 最多也有 `w` 个值，但加入 `result` 后属于返回结果；若严格把输出排除在辅助空间外，搜索结构仍为 `O(w)`。完整返回结果保存 `n` 个值，输出空间为 `O(n)`。算法没有递归调用栈。

> **小白追问：** 队列中途可能混有当前层和下一层，为什么最大宽度 `w` 仍能决定空间？
>
> **先给短答：** 队列只可能包含“当前层尚未处理的部分”和“下一层已经发现的部分”，不会同时保留更早或更深的层，因此数量最多是两层宽度之和，不超过 `2w`。
>
> **最小例子：** 当前层 `[B,C]`，处理 `B` 后加入 `D、E`，队列变成 `[C,D,E]`。它暂时比任一已完成批次更长，但仍只是两层的局部，总量与 `w` 同阶。
>
> **回到模型/代码：** `poll()` 持续删除当前层，`offer()` 只加入直接孩子；常数因子 `2` 在大 O 中省略，所以辅助空间写作 `O(w)`，最坏 `w = O(n)`。

需要注意 `ArrayDeque` 的扩容使单次 `offer` 偶尔不是常数，但一个节点只导致有限次加入，扩容成本分摊到所有操作后仍为摊还 `O(1)`，整体结论不变。对本题 `n <= 2000`，线性模型也让性能不依赖树是平衡还是极端偏斜。

### 泛用模型骨架

下面先写不依赖二叉树字段名的“分层前沿”骨架。`childrenProvider` 表示如何从当前对象得到按期望顺序排列的下一层对象，`projector` 表示输出时从对象提取什么信息。骨架假设输入关系像树一样不会让同一对象被重复发现；若用于一般图，必须额外加入 `visited` 集合，并在首次发现节点时标记。

> **小白追问：** 空树为什么直接返回 `[]`，而不是先创建一个空层得到 `[[]]`？
>
> **先给短答：** 层必须由至少一个真实节点构成；没有根就没有第一个前沿，也就没有任何一次合法的批次处理。
>
> **最小例子：** `root = null` 时连深度 `0` 的节点都不存在。`[]` 表示零层，`[[]]` 却表示已经生成了一层但层中没有节点，两者语义不同。
>
> **回到模型/代码：** `if (start == null)` 或 `if (root == null)` 必须早于第一次 `offer` 和 `while`，直接返回尚未加入任何层的结果列表。

```java
import java.util.ArrayDeque;
import java.util.ArrayList;
import java.util.List;
import java.util.Queue;
import java.util.function.Function;

final class LayeredFrontierModel<T, R> {
    public List<List<R>> traverse(
            T start,
            Function<T, Iterable<T>> childrenProvider,
            Function<T, R> projector) {
        List<List<R>> layers = new ArrayList<>();
        if (start == null) {
            return layers;
        }

        Queue<T> pendingFrontier = new ArrayDeque<>();
        pendingFrontier.offer(start);

        while (!pendingFrontier.isEmpty()) {
            int currentLayerSize = pendingFrontier.size();
            List<R> currentLayer = new ArrayList<>(currentLayerSize);

            for (int processed = 0; processed < currentLayerSize; processed++) {
                T current = pendingFrontier.poll();
                currentLayer.add(projector.apply(current));

                for (T discovered : childrenProvider.apply(current)) {
                    if (discovered != null) {
                        pendingFrontier.offer(discovered);
                    }
                }
            }
            layers.add(currentLayer);
        }
        return layers;
    }
}
```

泛用骨架的稳定角色不是某个题号，而是：`pendingFrontier` 保存尚未展开的前沿，`currentLayerSize` 冻结批次，`childrenProvider` 产生下一前沿，`projector` 产生当前层输出。对二叉树，孩子顺序必须返回左、右；对组织层级，可以返回直属成员；对无权图，要在加入邻居前过滤已访问节点。

> **小白追问：** 代码中的读取和更新顺序为什么不能交换？
>
> **先给短答：** 必须先冻结旧前沿，再逐个取父节点并登记孩子，最后提交本层；提前提交会得到残缺层，延后冻结则会把新孩子算入旧批次。
>
> **最小例子：** 根 `A` 有孩子 `B、C`。先冻结为 `1` 才能只生成 `[A]`；若处理 `A`、加入孩子后才读取大小，读到的是 `2`，它描述的已经是下一层。
>
> **回到模型/代码：** 顺序固定为 `size()`、内层 `poll/project/offer`、`layers.add(currentLayer)`；这三段分别确定边界、推进状态和产生结果。

import java.util.ArrayDeque;
import java.util.ArrayList;
import java.util.List;
import java.util.Queue;

class Solution {
    public List<List<Integer>> levelOrder(TreeNode root) {
        List<List<Integer>> result = new ArrayList<>();
        if (root == null) {
            return result;

            for (int processed = 0; processed < currentLevelSize; processed++) {

                if (current.left != null) {
                    pendingFrontier.offer(current.left);
                }
                if (current.right != null) {

                }
            }
            result.add(currentLevel);
        }

}

### 模型角色到代码的映射

| 模型角色 | Java 变量或代码块 |
| --- | --- |
| 当前对象 | `TreeNode current` |
| 尚未展开的前沿 | `Queue<TreeNode> pendingFrontier` |
| 当前批次边界 | 外层轮次开始时的 `int currentLevelSize` |
| 当前层输出缓冲 | `List<Integer> currentLevel` |
| 触发下一层状态 | `current.left != null` 与 `current.right != null` |
| 状态变化 | 队头 `poll` 当前节点，队尾 `offer` 左、右孩子 |

代码里最值得记住的不是类名，而是读取 `size()` 的时机。它必须在内层循环之前执行一次；`processed` 与这个固定值比较，不能与动态队列大小比较。

## 17. 边界、常见错误与调试观察点

| 层次 | 常见问题 | 会出现的现象 | 修正依据 |
| --- | --- | --- | --- |
| 建模错误 | 只保存扁平访问顺序 | 得到 `[3,9,20,15,7]`，无法分层 | 输出要求包含批次，必须保存层边界 |
| 建模错误 | 等待区只保存节点值 | 取出值后无法发现孩子 | 状态必须足以推动下一步，所以保存节点对象 |
| 建模偏差 | 认为所有 BFS 都自动按层输出 | 访问顺序正确，但外层列表分组错误 | 队列保顺序，冻结大小保边界，两者职责不同 |
| 条件错误 | 内层写 `processed < queue.size()` | 当前层混入孩子或提前结束 | 一轮开始时冻结 `currentLevelSize` |
| 条件错误 | 左右孩子入队顺序颠倒 | 每层局部顺序变为从右到左 | 题目要求从左到右，必须先左后右 |
| 条件错误 | 把 `null` 孩子也入队 | `ArrayDeque` 抛异常或后续空指针 | 空引用不是节点，不属于任何前沿 |
| 实现错误 | 空树仍先 `offer(root)` | 入口直接失败 | `root == null` 时返回空结果 |
| 实现错误 | 每取出一个节点就把 `level` 加入结果 | 每个节点变成单独一层 | 结果时机是完整批次结束，不是单节点结束 |
| 实现错误 | 用栈替换队列但不调整顺序 | 搜索沿分支深入，层序被破坏 | 前沿要求先进先出 |
| 泛化错误 | 把树写法原样用于有环图 | 节点反复入队，可能无法终止 | 一般图需要首次发现时写入 `visited` |

调试时不要只打印最终结果。每轮打印以下稳定状态最有效：

```text
轮次开始：levelIndex、currentLevelSize、队列从队头到队尾的节点值
处理节点：current.val、processed/currentLevelSize
加入孩子后：队列内容
轮次结束：currentLevel、下一轮队列内容
```

对示例一，轮次开始快照应依次是：

```text
levelIndex=0, size=1, queue=[3]
levelIndex=1, size=2, queue=[9,20]
levelIndex=2, size=2, queue=[15,7]
```

如果某轮开始的队列同时出现不同深度节点，错误发生在上一轮边界控制；如果同层顺序反了，检查孩子入队次序；如果节点重复，先确认输入是否真是树，再检查是否重复加入同一孩子；如果空树报错，检查空判断是否早于第一次 `offer`。

还可以在开发期加入断言式观察：内层结束后 `currentLevel.size()` 必须等于冻结的 `currentLevelSize`。这个条件不能证明孩子一定正确，却能迅速暴露层循环次数被动态状态干扰的问题。

## 18. 最终模型卡

| 模型卡项目 | 结论 |
| --- | --- |
| 识别指纹 | 从一个起点出发，要求按距离、层级或传播轮次分组处理对象 |
| 一句话关系模型 | 当前距离的全部节点构成一批，它们发现的未访问孩子共同构成下一距离的一批 |
| 实际保存什么 | 尚未展开的节点对象；不保存纯值，不重复保存每个节点的深度 |
| 状态何时变化 | 当前节点出队时完成展开，非空左、右孩子按顺序入队 |
| 答案何时产生 | 一轮开始时冻结的节点数全部处理完后，提交完整本层列表 |
| 核心不变量 | 每轮开始时，队列恰好按从左到右保存当前层全部节点 |
| 时间复杂度 | `O(n)`，每个节点入队、出队、输出各一次 |
| 辅助空间复杂度 | `O(w)`，`w` 为树的最大宽度；返回结果另为 `O(n)` |

**四句建模结论：**

```text
我正在处理的对象是：与根距离相同、属于当前层的一批树节点。
我必须持续保存的是：已经被发现但尚未展开的节点前沿，以及本轮开始时冻结的前沿大小。
当一个当前层节点出队时，我执行：记录它的值，并把非空左、右孩子按顺序加入队尾。
答案在本轮冻结数量的节点全部处理完时，由当前层值列表计算并写入外层结果。
```

**泛用控制模板：**

```text
起点进入等待区
while 等待区不空:
    冻结当前批次大小
    创建本批结果
    repeat 冻结大小次:
        取出当前对象
        记录当前对象的结果贡献
        按规则加入下一批对象
    提交本批结果
```

**迁移变式：**

| 题目 | 保持不变的模型 | 发生变化的部分 |
| --- | --- | --- |
| 103. 二叉树的锯齿形层序遍历 | 前沿与冻结层大小不变 | 结果写入方向随层号交替，变化的是层内输出规则 |
| 199. 二叉树的右视图 | 每轮仍处理完整当前前沿 | 只在 `processed == currentLevelSize - 1` 时记录，变化的是结果时机 |
| 637. 二叉树的层平均值 | 每轮边界和节点展开不变 | 本层状态改为总和与人数，变化的是聚合状态；总和宜用 `long` |
| 107. 二叉树的层序遍历 II | 发现和展开顺序不变 | 最终层列表反转或头插，变化的是层间输出顺序 |
| 无权图最短距离 | 按距离推进前沿不变 | 邻居可能重复到达，必须增加 `visited`，并用轮次或距离数组记录最短步数 |

以后看到“第几轮传播”“离起点几步”“每一层分别统计”时，不要先背“使用队列”。先问：当前批次是谁，下一批由什么事件产生，批次边界如何固定，旧对象在交出哪些信息后可以删除。回答完这四问，数据结构通常会自然浮现。
