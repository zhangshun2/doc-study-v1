# 739. 每日温度：从寻找未来到到来即结算

| 项目 | 内容 |

| 原清单优先级 | P0 |
| 原清单标签 | Monotonic Stack 单调栈 |
| 本专题的核心模型 | 新事件到来时，结算仍在等待且满足条件的旧对象 |

这道题的最终代码很短，真正困难的地方却不在 Java 语法，而在三个思维跳跃：为什么不再让每一天各自向右寻找，为什么等待名单只需从一端处理，以及为什么栈里保存的是下标而不是温度。很多人可以照着模板写出 `while + pop + push`，但换成“下一个更小”“左边最近更大”或“循环数组”就会再次失去方向，原因是记住了结构名称，却没有建立结构背后的状态语义。

本篇不会从“这是一道单调栈题”出发。我们会先忠实翻译题目关系，写出一定正确的直接模型，观察重复扫描，再把“旧日期主动查询未来”翻转为“新温度到来时主动结算旧日期”。等到状态、事件和不变量都明确后，栈才会作为合适的实现自然出现。

还要特别守住四个容易混淆的事实：题目要的是未来**第一个**更高温度；“更高”是严格大于，相等不算；结果是下标差而不是温度差；遍历结束仍然等待的日期答案就是 `0`。后文的每个判断都能回到这四个事实，而不是依赖一段孤立模板。

## 2. 完整题目：输入、输出、示例、约束与入口

给定一个整数数组 `temperatures`。数组下标代表日期，`temperatures[i]` 代表第 `i` 天的温度。需要返回一个同样长度的整数数组 `answer`：

- 如果第 `i` 天之后存在温度严格高于 `temperatures[i]` 的日子，那么 `answer[i]` 等于从第 `i` 天到其中最早那一天需要等待的天数。
- 如果第 `i` 天之后再也没有更高温度，那么 `answer[i]` 为 `0`。

换成精确关系，就是对每个下标 `i` 寻找最小的下标 `j`，使得：

```text
j > i
temperatures[j] > temperatures[i]
```

若这样的 `j` 存在，写入 `answer[i] = j - i`；否则保留 `answer[i] = 0`。

**示例 1：一次新温度会结算多个旧日期**

```text
输入：temperatures = [73, 74, 75, 71, 69, 72, 76, 73]
输出：[1, 1, 4, 2, 1, 1, 0, 0]
```

解释：第 `0` 天的 `73` 在第 `1` 天遇到 `74`，等了 `1` 天；第 `2` 天的 `75` 直到第 `6` 天的 `76` 才遇到严格更高温度，所以等了 `4` 天；最后两天右侧没有更高温度，答案为 `0`。

**示例 2：严格递增**

```text
输入：temperatures = [30, 40, 50, 60]
输出：[1, 1, 1, 0]
```

解释：前三天的下一天都更热，因此等待天数都是 `1`；最后一天没有未来日期。

**示例 3：跨度仍然取最早满足者**

```text
输入：temperatures = [30, 60, 90]
输出：[1, 1, 0]
```

虽然 `90` 也高于 `30`，但第 `0` 天的答案是第 `1` 天的 `60`，因为题目要的是第一个更高温度，而不是未来最高温度。

**补充示例：相等不算更高**

```text
输入：temperatures = [70, 70, 69, 71]
输出：[3, 2, 1, 0]
```

第 `0` 天不能被第 `1` 天相等的 `70` 结算，它与第 `1` 天都要等待第 `3` 天的 `71`。

**全部约束：**

- `1 <= temperatures.length <= 10^5`
- `30 <= temperatures[i] <= 100`

Java 方法入口为：

```java
public int[] dailyTemperatures(int[] temperatures)
```

长度上限 `10^5` 是重要的性能信号：平方级扫描在最坏情况下可能进行约五十亿次比较，不能作为推荐实现。温度范围只有 `30` 到 `100`，意味着还存在按固定值域记录最近位置的专用办法；这种办法对本题有效，但依赖值域很小。为了建立更可迁移的模型，本文主线选择不依赖温度范围的做法，同时会如实比较两者。

## 3. 先把题目说成人话：到底是谁在等谁

一句话生活化复述：每一天都拿着一张等待单，想知道还要过几天才第一次遇到一个比当天更热的日子。

一句话关系化复述：对序列中的每个位置，求它右侧第一个值严格更大的位置距离；不存在时输出 `0`。

题目里的“天气预报”可以先拿掉，留下的是一条有先后顺序的数值序列和一种方向明确的关系：

```text
旧日期 i --只向右等待--> 第一个满足 temperatures[j] > temperatures[i] 的日期 j
          --产生结果-->  j - i

下标：  0    1    2    3    4    5    6    7
温度： 73   74   75   71   69   72   76   73
                  |---------------->|
                  第 2 天等待到第 6 天，距离为 4
```

| 要素 | 从题目中提取出的结论 |
| --- | --- |
| 对象 | 每一天，但程序用日期下标表示它 |
| 关系 | 右侧第一个温度严格更高的日期 |
| 方向 | 只能从过去指向未来，也就是下标从小到大 |
| 目标 | 对每个日期求目标下标与当前下标之差 |
| 限制 | 相等不算更高；找最近而不是最高；找不到时为 `0` |

这里保存“下标”比保存“温度值”更接近真实对象。温度只是判断关系的属性，日期下标既能回到原数组读取温度，又是计算等待天数不可缺少的位置。两个日期都可能是 `70`，但它们等待的天数不同；只看温度无法区分这两个任务。

所以第一层模型还没有任何数据结构名称，只有一句关系：过去的每个下标，都在等待右边第一个严格更大的值，并在那一刻得到下标差。

## 4. 第一切入点：第一分钟先观察哪些词

读题时先圈出“之后”“下一个”“更高”“几天后”四组词。

1. “之后”确定方向，只能看当前下标右侧。
2. “下一个”不是指数组里紧挨着的下一项，而是指满足条件的最小未来下标。
3. “更高”确定严格比较，必须是 `>`，不能把相等当成成功。
4. “几天后”确定输出位置距离，所以最终状态必须能恢复日期下标。

“每天”“温度”“气温升高”是帮助理解的故事包装。它们可以先翻译成“位置”“数值”“严格更大”，这样更容易看见这道题和其他序列问题共享的关系。暂时不必考虑摄氏度、天气是否真实波动，也不用寻找未来最高温度；这些都不是答案定义的一部分。

接着看数据范围。`n` 最大为 `100000`，提示推荐模型应接近 `O(n)` 或 `O(n log n)`。如果每一天都扫描全部未来，最坏比较次数为 `n(n-1)/2`，数量级约为 `4,999,950,000`，已经明确暴露风险。另一方面，温度只有 `71` 种取值，这是一个可利用但专属于本题的信号，不应掩盖更一般的“右侧第一个更大”关系。

最小人工样例可以用 `[70, 71]`：第 `0` 天看到右边第 `1` 天更热，所以答案是 `1 - 0 = 1`；第 `1` 天没有未来，答案是 `0`。再用 `[70, 70, 71]` 检查严格性：第一个 `70` 不能在第二个 `70` 处停止，而要等到 `71`，答案为 `2`。这两个小例子已经决定了比较符号、结果公式和默认值。

第一分钟不需要猜“栈”。应该先写下这个问题：**怎样避免每个旧日期都重新扫描同一段未来，同时仍然保证得到第一个严格更高的位置？**这才是后续结构选择要回答的具体问题。

## 5. 最直接的人工或暴力模型：逐日起点向右找

最接近人工阅读的办法是固定一天 `startDay`，从下一天开始逐日向右看。一旦看到严格更高温度，就记录下标差并停止；如果扫描到数组结尾仍未找到，结果数组的默认 `0` 就是正确答案。

```java
class BruteForceDailyTemperatures {
    public int[] solve(int[] temperatures) {
        int[] answer = new int[temperatures.length];

        for (int startDay = 0; startDay < temperatures.length; startDay++) {
            for (int futureDay = startDay + 1;
                    futureDay < temperatures.length;
                    futureDay++) {
                if (temperatures[futureDay] > temperatures[startDay]) {
                    answer[startDay] = futureDay - startDay;
                    break;
                }
            }
        }
        return answer;
    }
}
```

它为什么一定正确？对固定的 `startDay`，内层循环严格按未来日期从近到远检查。第一次满足 `temperatures[futureDay] > temperatures[startDay]` 时，所有更靠前的未来日期已经被检查并且不满足，所以此时的 `futureDay` 必然就是“第一个”更高温度。若一个都没有，循环不写答案，默认 `0` 正好表达不存在。

设 `n` 为天数。最好情况下，许多日期的下一天就更热，每个起点只比较一次；最坏情况下温度单调不升，每个起点都会一直扫描到结尾，比较次数为：

```text
(n - 1) + (n - 2) + 逐项递减后的其余项 + 2 + 1
= n(n - 1) / 2
```

因此最坏时间复杂度是 `O(n^2)`。除了返回数组，只使用两个循环下标和少量变量，额外空间复杂度是 `O(1)`；若把必须返回的答案数组也计入总占用，则为 `O(n)`。

这个模型并不“低级”。它建立了后续优化必须保持的正确语义：按时间顺序找到第一个严格更高者、在找到时计算下标差、找不到时保留零。推荐模型只是压缩重复工作，不能改变这些规则。

## 6. 暴力到底浪费在哪里：同一未来被反复查看

用输入 `[75, 71, 69, 72, 76]` 逐个起点观察：

```text
下标：       0   1   2   3   4
温度：      75  71  69  72  76

处理第 0 天 75：查看 71、69、72、76 -> 到第 4 天才成功
处理第 1 天 71：查看 69、72         -> 到第 3 天成功
处理第 2 天 69：查看 72            -> 到第 3 天成功
处理第 3 天 72：查看 76            -> 到第 4 天成功
处理第 4 天 76：没有未来日期
```

第 `3` 天的 `72` 被第 `0`、第 `1`、第 `2` 天的扫描反复读取；第 `4` 天的 `76` 又被第 `0` 和第 `3` 天反复读取。更关键的是，每个起点扫描失败后，“这些未来温度还不够高”的中间结论全被丢弃，下一起点又从头建立关系。

在严格递减输入 `[100, 99, 98, 97, 96]` 中，任何日期都没有答案，但暴力仍会检查所有有序下标对：

```text
100 检查 99、98、97、96
 99 再检查 98、97、96
 98 再检查 97、96
 97 再检查 96
```

这些扫描没有产生任何答案，却做了十次比较。数组继续增长时，重复呈三角形累积。

换个角度看第 `3` 天的 `72`：它一到来，就已经足以同时回答两个问题，“第 `1` 天的 `71` 等了多久”和“第 `2` 天的 `69` 等了多久”。暴力却把同一个 `72` 分别交给两个起点查询。我们想保留的不是每个起点扫过的完整历史，而是那些**已经出现、目前还没有答案**的日期。

优化目标可以写成一个可执行的句子：

> 不要让每个旧日期重新扫描未来；让每个新温度只到达一次，并在到达时一次结算所有现在已经能够确定答案的等待日期。

这个目标将推动视角转换。此时仍未决定用栈，只确定了需要一份“未结算日期集合”，以及新事件应当主动处理旧状态。

## 7. 容易想到但受限或走不通的方向

### 7.1 只记录右侧最大温度

从右向左维护 `suffixMax` 很自然，因为它能回答“右边是否存在更高温度”。然而本题还要知道**第一个**更高温度在哪里。对 `[70, 71, 100]` 而言，右侧最大值是 `100`，但第 `0` 天的答案由更近的 `71` 产生。最大值摘要丢失了距离和最近位置，因此不足以直接求答案。失败给出的条件是：状态不仅要判断存在性，还必须保留能够定位最近满足者的信息。

> **小白追问：** 既然最终是找“更高”，为什么不能直接找未来最高温度？
>
> **先给短答：** “最高”回答谁的数值最大，“第一个更高”回答谁最早越过当前温度；这是两个不同问题。
>
> **最小例子：** 在 `[70,71,100]` 中，`100` 是未来最高温度，但第 `0` 天走到第 `1` 天的 `71` 时条件已经首次成立。正确等待天数是 `1`，若奔着 `100` 去会错误得到 `2`。
>
> **回到模型/代码：** 目标下标是满足条件的最小 `j`。左到右扫描时，`71` 到来便立即弹出下标 `0`；算法不维护 `suffixMax`，也不会让后来的 `100` 覆盖已经写好的 `answer[0]`。

### 7.2 排序后寻找更高值

“更高”容易让人想到排序或有序集合。排序确实能快速找到数值上更大的温度，却会破坏原始日期顺序；即使给每个值带上下标，仍需额外判断哪个更大值位于右侧且下标最小。问题的主约束是时间先后和最近位置，不是单纯的数值排名。排序不是逻辑上绝对不能做，但它没有直接压缩“为每个日期找右侧最近者”的困难，还会增加 `O(n log n)` 成本。

### 7.3 用普通队列保存所有等待日期

既然新日子要处理旧等待者，维护一个列表或队列看起来很合理。如果每次新温度到来都扫描整个等待队列，找出所有比它冷的日期，就仍可能达到 `O(n^2)`。如果只看队头，又不正确：最早等待的日期可能温度很高，暂时不能结算，但它后面更冷的日期可能应该被今天结算。由此得到新条件：需要从“最近且最容易被当前温度结算”的一端开始处理，并且一旦这一端都不能结算，其他候选也必须都不能结算。

### 7.4 按温度值记录右侧最近位置

官方约束给出温度范围 `30..100`，所以可以从右向左维护 `nextPosition[t]`，处理温度 `x` 时检查 `x+1..100` 的最近位置，取最小下标。这是**正确且在本题中实用**的办法，不应被误称为错误。设温度种类数为 `R`，它的时间复杂度是 `O(nR)`、空间复杂度是 `O(R)`；本题 `R=71`，可视为固定小常数。

它的限制是模型依赖小值域。若温度换成任意 32 位整数，或比较对象不再是有限枚举值，就不能再扫描全部更大取值。它带来的启发是：可以利用题目约束选择专用状态；但若目标是学习“右侧第一个更大元素”的通用关系，就应寻找只与元素个数有关的状态结构。

这些方向共同指出，推荐模型需要同时保留时间位置、严格大小关系和未结算状态，还要让一次新事件只访问真正会被它结算的候选。

## 8. 关键视角转换：旧日期不再主动找未来

暴力模型的叙事是“拉取答案”：

```text
第 i 天主动向右查询：我的第一个更高温度在哪里？
```

转换后的叙事是“事件结算”：

```text
第 current 天作为新事件到来：哪些旧日期第一次等到了我？
```

拿 `[75, 71, 69, 72]` 看这个转换：

```text
72 到来之前，75、71、69 都还在等待。
72 > 69：69 在今天结算，距离 1。
72 > 71：71 在今天结算，距离 2。
72 不大于 75：75 继续等待。
72 自己也还不知道未来，于是加入等待名单。
```

为什么可以按“最近等待者”向更早日期处理？我们希望等待名单从早到晚的温度保持不升，也就是较晚位置位于处理端，且它的温度不高于前面的等待者。当前温度若能超过处理端，就结算它并继续；若连处理端都不能超过，那么更深处只会更热或相等，也都不能结算，可以立刻停止。

这不是先规定“要保持单调”，而是从避免无效扫描得出的状态压缩：让最可能被当前事件解决的候选放在可直接访问的一端；当前事件解决不了它时，就能一次排除其余全部等待者。

| 转换前 | 转换后 |
| --- | --- |
| 每个旧日期重复扫描未来 | 每个新日期只到来一次 |
| 关注“我去哪里找答案” | 关注“谁还没有答案” |
| 同一未来位置被多个起点读取 | 当前事件批量结算一批等待者 |
| 扫描失败信息被丢弃 | 尚未满足条件的日期持续留在状态中 |
| 一次只求一个起点的答案 | 一次事件可能产生多个答案 |

转换后，答案不再在“查询结束”时产生，而是在旧日期从等待状态转为已结算状态的瞬间产生。这个瞬间同时拥有当前下标、旧下标和严格更高的比较结果，正好足以写出 `currentDay - pendingDay`。

旧日期被结算完，不代表当前日期也完成了。当前日期只知道自己比哪些过去日期热，却仍不知道未来是否会有一个比自己更热的日期。因此，每轮结算结束后都要把当前日期加入等待状态。

> **小白追问：** 今天已经把别人结算了，为什么今天自己还必须入栈？
>
> **先给短答：** “能回答过去的问题”和“自己的未来答案已确定”没有因果关系；今天仍是一个尚未看到未来的旧对象候选。
>
> **最小例子：** 在 `[69,72,73]` 中，第 `1` 天的 `72` 会结算第 `0` 天的 `69`。但第 `1` 天自己还要等第 `2` 天的 `73`，答案应为 `1`。若结算别人后不保存第 `1` 天，它的答案会错误保持 `0`。
>
> **回到模型/代码：** `pendingDays.push(currentDay)` 位于 `while` 之后且无条件执行，不能放进只在“没有弹栈”时才运行的 `else`。它建立的是当前日自己的等待状态。

## 9. 正式建立模型：先写状态与不变量

| 建模项 | 本题结论 |
| --- | --- |
| 对象 | 日期下标；温度是下标对应的比较属性 |
| 关系 | 旧下标右侧第一个温度严格更高的下标 |
| 状态 | 已经扫描过、但尚未遇到更高温度的日期下标 |
| 事件 | 一个新的当前日期从左向右到来 |
| 不变量 | 等待下标从早到晚排列；对应温度从处理结构底部到顶部单调不升；其中每个日期在已扫描范围内都还没有更高温度 |
| 结果时机 | 当前温度严格高于某个等待日期，使其离开等待状态时 |

处理第 `currentDay` 天之前，状态中所有日期都小于它，而且它们从加入状态到当前之前没有遇到严格更高温度。处理时不断查看最近的等待日期：只要当前温度更高，就把这个等待日期结算并写入下标差。直到等待状态为空，或最近等待者温度大于等于当前温度，再把当前日期加入等待状态。

这份状态是充分的。比较时，可用保存的下标回到 `temperatures[pendingDay]` 读取温度；结算时，又能直接计算 `currentDay - pendingDay`。不需要重复保存温度，也不需要保存等待期间见过的所有日期，因为“尚未遇到更高温度”已经概括了那些失败比较。

这份状态也没有保留已经完成的对象。某个下标一旦被当前日结算，它的答案已经由第一个更高温度确定，未来任何温度都不可能给它更近的答案，所以可以永久删除。未被当前温度结算的日期不能随意删除：它们可能等待将来的更高温度。

遍历必须从左向右，因为题目中的答案来自未来。这样当前事件第一次满足旧日期条件时，自然就是时间上最早的满足者。如果从右向左也能设计正确方法，但需要把“右侧候选的最近性”换成另一套状态语义；不能把两种方向的代码条件混合。

> **小白追问：** 等待者有很多，为什么当前温度只从栈顶开始检查，不去看看中间是否藏着更冷的日期？
>
> **先给短答：** 栈顶是最新且温度最低的一端；若当前温度连它都不超过，更靠栈底的日期只会更热或相等，也一定不能结算。
>
> **最小例子：** 等待栈从底到顶为 `[0:75,1:71,2:69]`，当前温度是 `68`。栈顶 `69` 已经不小于 `68`，下面的 `71` 和 `75` 更不可能小于 `68`。反过来，当前温度为 `72` 时，先弹 `69`，再弹 `71`，看到 `75` 才停止。
>
> **回到模型/代码：** “栈底到栈顶温度不升”使 `pendingDays.peek()` 成为唯一需要直接访问的位置。`while` 每弹出一个栈顶，才把下一名候选暴露出来；停止条件同时排除了整座栈。

相等温度必须保留。若栈顶温度等于当前温度，当前日不是“更高”，所以不能结算栈顶；当前日仍要加入等待名单。后来出现更高温度时，较晚的相等日期先结算，较早的相等日期后结算，各自得到不同下标差。比如 `[70,70,71]` 会先结算下标 `1` 得到 `1`，再结算下标 `0` 得到 `2`。

> **小白追问：** 两天温度相等，看起来作用一样，为什么不能弹掉较早那天，只保留较新的那天？
>
> **先给短答：** 两天虽然温度相同，却是两个都要输出答案的日期；相等既不满足“更高”，也不能合并两个不同的等待距离。
>
> **最小例子：** `[70,70,71]` 中，后一个 `70` 等 `1` 天，前一个 `70` 等 `2` 天。若第 `1` 天到来时弹掉第 `0` 天，就会把相等误当升温并写成 `answer[0]=1`。
>
> **回到模型/代码：** 弹出条件必须是 `temperatures[currentDay] > temperatures[pendingDays.peek()]`，不能改成 `>=`。因此温度序列是“单调不升”，允许相等下标同时留在栈中。

到这里，状态变化表现为“只从最近一端反复查看和删除，当前对象最后也从同一端加入”。这种后进先出的访问方式适合用栈实现；温度单调不升是上述更新规则维持的不变量。因此现在才可以给结构命名：保存未结算日期下标的单调栈。

## 10. 所需数据结构详解：下标栈、原数组与结果数组

### 10.1 栈为什么正好匹配状态变化

栈是一种只在同一端加入、查看和删除元素的线性结构，具有后进先出特征。本题把最新的未结算日期放在栈顶，因为它是当前事件首先检查的对象。使用 Java 的 `Deque<Integer>` 配合 `ArrayDeque`：

| 操作 | 本题语义 | 复杂度 |
| --- | --- | --- |
| `push(currentDay)` | 当前日期进入等待状态 | 均摊 `O(1)` |
| `peek()` | 查看最近的未结算日期，不删除 | `O(1)` |
| `pop()` | 取出已经被当前温度结算的日期 | `O(1)` |
| `isEmpty()` | 判断是否还有等待者 | `O(1)` |

`ArrayDeque` 内部使用可扩容的循环数组组织元素。单次扩容可能搬移多个元素，所以加入操作严格说是均摊 `O(1)`；在整个算法中仍保持线性总成本。相比旧的 `Stack` 类，`ArrayDeque` 更适合作为 Java 中的普通栈使用，也没有把“栈”与继承自 `Vector` 的历史接口混在一起。

### 10.2 栈里为什么必须保存下标

栈中保存 `Integer` 下标，而不是只保存温度值：

```text
下标 pendingDay
  -> temperatures[pendingDay] 用于比较是否能结算
  -> currentDay - pendingDay 用于计算等待天数
```

如果只保存 `70`，既分不清数组里多个 `70` 分别是哪一天，也无法计算距离。保存“下标 + 温度”的对象当然也能做，但温度可通过原数组随机访问，重复保存会增加状态和实现复杂度，没有必要。

> **小白追问：** 比较时明明用的是温度，栈里为什么偏偏保存下标而不是温度？
>
> **先给短答：** 下标同时承担“找到自己的温度”和“找到自己的答案位置”两项职责；单独温度只能比较，不能定位输出。
>
> **最小例子：** `[70,70,71]` 中有两份数值相同的 `70`，但它们要写入 `answer[0]=2` 和 `answer[1]=1`。栈里若只有两个无法区分来源的 `70`，弹出时不知道该写哪个位置，也算不出 `2-0` 或 `2-1`。
>
> **回到模型/代码：** `pendingDays.peek()` 取得日期下标，再用它读取 `temperatures[...]`；`pendingDays.pop()` 得到 `settledDay`，随后写入 `answer[settledDay] = currentDay - settledDay`。一个下标连接了比较、距离和输出槽位。

### 10.3 单调性不是容器自动提供的

普通 `ArrayDeque` 不会自动排序。所谓“单调栈”是算法通过入栈前的反复结算维护出来的性质：从栈底到栈顶，下标严格递增，温度单调不升。当前温度严格大于栈顶温度时弹出；停止后，剩余栈顶温度大于等于当前温度，此时压入当前下标，单调不升仍然成立。

相等值被保留，所以这里是不升而不是严格下降。直接记住“从栈底到栈顶不升”和弹出条件 `<`，比争论它叫递增栈还是递减栈更可靠，因为不同资料可能按栈顶视角使用不同名称。

### 10.4 其他容器为何不如它贴合

- 普通数组列表可以保存等待日期，但若每次从中间查找或删除所有更冷者，可能重复扫描并产生移动成本。
- 队列只允许优先处理最早等待者；最早日期若很热，会挡住后面本可被结算的冷日期。
- 优先队列可以按温度找更冷者，但题目还要求每个日期的第一个未来满足者，且维护顺序与相等值会更复杂，操作成本也变成 `O(log n)`。
- 手写 `int[] pendingDays` 加一个 `top` 指针同样正确，还能避免装箱；但 `ArrayDeque` 更清晰地表达栈语义。需要极致常数性能时可选择数组栈。

### 10.5 三个数组或容器的职责

输入数组 `temperatures` 是只读事实库，按下标提供温度；`pendingDays` 只保存尚未结算的日期；`answer` 保存已经确定的距离，未写位置默认是 `0`。最坏情况下，如温度严格递减或全部相等，所有 `n` 个下标都会留在栈中，所以辅助空间上界为 `O(n)`。

## 11. 生活化类比及边界：一摞等待升温的日期单

可以把每个尚未等到升温的日期想成一张等待单。每张单子只写日期编号，原始温度仍可从天气记录表查到。等待单按日期到来顺序压成一摞，最新日期在最上面。新的一天到来时，工作人员先看最上面的单子：如果今天严格更热，就在单子上写“等了当前日期减原日期天”，取走它，再看下一张；如果最上面都不比今天冷，就停止处理，最后把今天自己的等待单放上去。

| 生活对象或动作 | 算法中的对应物 |
| --- | --- |
| 一张写着日期编号的等待单 | 一个尚未结算的下标 `pendingDay` |
| 原始天气记录表 | 输入数组 `temperatures` |
| 等待单从下到上按时间排列 | 栈底到栈顶下标递增 |
| 较冷或相等的单子放在更上方 | 栈底到栈顶温度单调不升 |
| 新的一天到来 | 扫描到 `currentDay` |
| 今天严格更热，可以结账 | `temperatures[currentDay] > temperatures[pendingDays.peek()]` |
| 取走最上方等待单 | `pop()`，该日期以后不再参与 |
| 写上等待天数 | `answer[pendingDay] = currentDay - pendingDay` |
| 今天也放一张新单 | `push(currentDay)` |
| 最后留在桌上的等待单 | 右侧没有更高温度，答案保持 `0` 的日期 |

“热的来，冷的走，今天自己最后加入”等价于每轮的完整动作。这里的“冷的走”必须理解为严格更冷；相等的等待单不会结账。

类比到这里为止。现实工作人员完全可以抽出中间任意一张单，也可以提前查看未来天气，但算法刻意只访问栈顶，并且不知道未扫描的未来。现实中的纸张物理顺序也不会自动保证温度单调；是“能结算就从顶部反复取走，不能结算就把今天压上去”这一规则维护了算法性质。类比帮助记住状态和动作，正确性仍需由“第一次触发”和不变量证明。

## 12. 典型输入的完整数据变化图

完整演算官方示例 `[73,74,75,71,69,72,76,73]`。下表统一把栈写成“栈底 -> 栈顶”，每项格式为 `下标:温度`。处理前状态只包含过去尚未结算的日期；新增结果只列本轮刚写入的位置。

```text
扫描方向：左 -> 右

下标：  0   1   2   3   4   5   6   7
温度： 73  74  75  71  69  72  76  73
        ^ currentDay 从这里逐步右移
```

| 当前输入 | 处理前状态（栈底 -> 栈顶） | 判断依据与执行动作 | 处理后状态 | 新增结果 |
| --- | --- | --- | --- | --- |
| `0:73` | `[]` | 空状态，无人可结算；压入 `0` | `[0:73]` | 无 |
| `1:74` | `[0:73]` | `74 > 73`，弹出 `0`；再压入 `1` | `[1:74]` | `answer[0]=1` |
| `2:75` | `[1:74]` | `75 > 74`，弹出 `1`；再压入 `2` | `[2:75]` | `answer[1]=1` |
| `3:71` | `[2:75]` | `71` 不大于 `75`，停止；压入 `3` | `[2:75, 3:71]` | 无 |
| `4:69` | `[2:75, 3:71]` | `69` 不大于 `71`；压入 `4` | `[2:75, 3:71, 4:69]` | 无 |
| `5:72` | `[2:75, 3:71, 4:69]` | `72>69` 弹 `4`；`72>71` 弹 `3`；`72` 不大于 `75`，停止；压入 `5` | `[2:75, 5:72]` | `answer[4]=1`，`answer[3]=2` |
| `6:76` | `[2:75, 5:72]` | `76>72` 弹 `5`；`76>75` 弹 `2`；栈空；压入 `6` | `[6:76]` | `answer[5]=1`，`answer[2]=4` |
| `7:73` | `[6:76]` | `73` 不大于 `76`；压入 `7` | `[6:76, 7:73]` | 无 |

第 `5` 天是核心状态转折，可以展开为连续快照：

```text
当前输入：currentDay=5，currentTemperature=72

处理前：栈底 [2:75, 3:71, 4:69] 栈顶
                              ^ 先看这里

72 > 69
执行：pop 4，answer[4] = 5 - 4 = 1
状态：栈底 [2:75, 3:71] 栈顶

72 > 71
执行：pop 3，answer[3] = 5 - 3 = 2
状态：栈底 [2:75] 栈顶

72 <= 75
执行：停止结算；下标 2 继续等待
最后：push 5
状态：栈底 [2:75, 5:72] 栈顶
```

处理结束后的完整结果和残留状态为：

```text
answer = [1, 1, 4, 2, 1, 1, 0, 0]
pendingDays = 栈底 [6:76, 7:73] 栈顶
```

下标 `6` 和 `7` 留在栈里不是算法漏做了工作，而是它们确实没有未来更高温度。Java 的 `int[]` 初始值为 `0`，所以不需要清空栈或再次写零。每轮压栈后，栈底到栈顶的温度仍然不升，这让下一轮只看栈顶就足够。

## 13. 边界场景的数据变化：相等、无答案和最小输入

### 13.1 相等温度不能结算

演算 `[70,70,69,71]`：

| 当前日 | 处理前状态（栈底 -> 栈顶） | 动作 | 处理后状态 | 新答案 |
| ---: | --- | --- | --- | --- |
| `0:70` | `[]` | 压入 `0` | `[0:70]` | 无 |
| `1:70` | `[0:70]` | `70` 不严格大于 `70`，保留 `0`；压入 `1` | `[0:70,1:70]` | 无 |
| `2:69` | `[0:70,1:70]` | `69` 不大于 `70`；压入 `2` | `[0:70,1:70,2:69]` | 无 |
| `3:71` | `[0:70,1:70,2:69]` | 依次弹出 `2`、`1`、`0`；压入 `3` | `[3:71]` | `answer[2]=1`，`answer[1]=2`，`answer[0]=3` |

最终为 `[3,2,1,0]`。如果误把弹出条件写成“小于等于当前温度”，第 `1` 天会错误结算第 `0` 天，得到 `1`；这直接违反“更高”要求。

### 13.2 严格递减：所有日期最终都未结算

```text
输入：[80, 70, 60]

0:80 -> [0:80]
1:70 -> [0:80, 1:70]
2:60 -> [0:80, 1:70, 2:60]

遍历结束，answer = [0, 0, 0]
```

每轮 `while` 都不执行，所有下标各入栈一次。最终栈残留三个元素，正好展示辅助空间最坏情况。算法不会越界，因为每次 `peek()` 前都先检查 `isEmpty()`；残留元素无需出栈，结果默认值已经正确。

### 13.3 只有一天：初始空状态与最后位置

```text
输入：[42]
初始：pendingDays=[]，answer=[0]
处理第 0 天：空栈，直接 push(0)
结束：pendingDays=[0:42]，answer=[0]
```

题目保证数组至少有一个元素，因此不需要为非法空输入设计题意答案。算法本身即使收到空数组也会返回空数组，但这不是官方约束要求。单元素场景同时验证了初始空状态、最后一个位置没有未来和结果默认值三个边界。

### 13.4 当天一次结算全部等待者

严格递增 `[30,40,50,60]` 中，每个新日都弹出前一天，然后自己入栈；栈长度始终为一，得到 `[1,1,1,0]`。这验证 `while` 可以执行一次。典型示例第 `5` 和第 `6` 天则验证 `while` 可以在同一轮执行多次，因此不能写成 `if`。

## 14. 正确性与不变量：为什么恰好是第一个更高日

证明对象是推荐模型返回的每个 `answer[pendingDay]`。需要说明写入的日期确实更高、它是最早满足者、没有答案的日期最终保持零，并且只看栈顶不会漏掉可以被当前日结算的人。

**循环不变量。**在开始处理第 `currentDay` 天之前，栈中下标都来自 `[0,currentDay-1]`，从栈底到栈顶严格递增；对应温度从栈底到栈顶单调不升；每个栈中日期在它之后到 `currentDay-1` 的已扫描范围内都没有出现严格更高温度，因此仍未结算。

初始时栈为空，三个性质自然成立。假设处理当前日前成立。只要当前温度严格高于栈顶日期温度，就弹出栈顶并写答案；弹出不会破坏剩余元素的下标顺序和温度顺序。停止时，如果栈非空，栈顶温度大于等于当前温度；由于更深处温度只会更高或相等，当前日也不能结算任何更深处日期。把当前下标压入后，下标比栈内所有下标大，温度又不高于停止时的栈顶，因此三个性质继续成立。若栈已空，直接压入也成立。

**写入结果满足严格更高。**某个 `pendingDay` 只有在 `temperatures[currentDay] > temperatures[pendingDay]` 时才被弹出，所以当前日期确实在其右边并且温度严格更高。下标差 `currentDay - pendingDay` 因而是正的等待天数。

**当前日一定是第一个更高日。**`pendingDay` 从入栈后一直保留到当前日。如果在两者之间存在更早下标 `earlierDay`，且温度已经严格高于 `temperatures[pendingDay]`，那么处理 `earlierDay` 时，`pendingDay` 应当已经满足结算条件并被弹出，不可能继续留到当前日。这与它仍在栈中矛盾。因此当前日不仅是一个更高日，还是右侧第一个更高日。

> **小白追问：** 弹出时只证明“今天更热”，凭什么还能断定今天恰好是第一个更热的日子？
>
> **先给短答：** 因为日期按从左到右到达，等待下标一旦遇到更高温度就立刻离栈；它能活到今天，已经说明中间没有任何更早的合格日期。
>
> **最小例子：** 在 `[70,69,71]` 中，下标 `0` 遇到第 `1` 天的 `69` 时不会弹出，所以继续等待；第 `2` 天的 `71` 是扫描过程中第一个让 `71>70` 成立的事件。若中间已有 `72`，下标 `0` 早就在那一天离栈，不可能留到第 `2` 天。
>
> **回到模型/代码：** `currentDay` 严格递增，触发条件一成立，`pop()` 和写入答案就在同一轮立即发生。每个 `settledDay` 只写一次，所以后来的更高温度没有机会把首次答案改成更远答案。

**只查看栈顶不会漏。**当栈顶温度大于等于当前温度时，栈底到栈顶温度不升意味着栈顶下面的日期温度也都大于等于栈顶，当然不会小于当前温度。所以当前日无法结算任何栈中日期，可以安全停止。若栈顶更冷，先结算它后才有必要检查下一项，这正是 `while` 的顺序。

**删除已经结算的候选是安全的。**弹出日期已经得到第一个更高日。未来日期下标更大，只可能产生更长距离，不可能推翻已经确定的最近答案；它也不再是其他日期寻找答案所需要的中间状态，因此可以永久删除。

> **小白追问：** 一个日期弹出后会不会还对别人的答案有用，永久删除会不会丢信息？
>
> **先给短答：** 栈保存的是“还欠自己一个答案的旧日期”，不是“供其他日期选择的未来温度”；自己的答案结清后，它就没有继续留栈的职责。
>
> **最小例子：** `[69,70,71]` 中，第 `1` 天到来时下标 `0` 已得到答案 `1` 并离栈。第 `2` 天只需结算仍在等待的下标 `1`。下标 `0` 的温度 `69` 既不能让更晚的日期把它当作未来，也不会改变下标 `1` 的答案。
>
> **回到模型/代码：** `pop()` 后只写 `answer[settledDay]`，不再压回 `settledDay`。下一轮状态只含未结算下标；这正是 `pendingDays` 的名称和不变量所限定的范围。

**遍历结束时结果完整。**所有曾被弹出的日期都得到正确答案。仍在栈中的日期直到数组末尾都没遇到严格更高温度，否则它们会在第一次满足时被弹出，所以它们应当输出 `0`。结果数组默认值正好覆盖这部分。由此每个日期要么被正确结算一次，要么被正确保留为零，没有遗漏。

> **小白追问：** 遍历结束后栈里还有日期，为什么不再清空并给它们计算答案？
>
> **先给短答：** 清空栈只能取出旧下标，却已经没有新的未来日期可与它比较；残留本身就表示题目要求的“右侧不存在更高温度”。
>
> **最小例子：** `[80,70]` 结束时栈中是 `[0:80,1:70]`。第 `1` 天右边没有日期，第 `0` 天右边只有更低的 `70`。无论按什么次序清空，都不存在可以形成正等待天数的更高日，因此两项都应为 `0`。
>
> **回到模型/代码：** `answer` 创建时所有位置已是 `0`，算法只在 `pop()` 由真实当前日触发时改写。遍历后不执行“清栈写值”，避免凭空制造一个不存在的 `currentDay`。

## 15. 时间与空间复杂度：按每个下标的一生计数

定义 `n = temperatures.length`，表示日期总数；若讨论固定温度表的替代模型，再定义 `R` 为可能温度值的种类数，本题 `R = 100 - 30 + 1 = 71`。

**直接模型。**外层为每个起点执行 `n` 次。内层最坏检查数量从 `n-1` 逐项递减到 `0`，总比较次数为 `n(n-1)/2`，所以最坏时间复杂度是 `O(n^2)`。它只使用循环变量，额外空间是 `O(1)`；返回数组自身为 `O(n)`。

**推荐模型的外层扫描。**每个下标作为 `currentDay` 恰好处理一次，外层基础工作为 `O(n)`。代码中有内层 `while`，但不能仅凭循环嵌套写成 `O(n^2)`，因为某个下标被弹出后永远不会再次回到栈中。

按一个下标从出现到结束的生命周期计数：

```text
第 i 天到来：入栈恰好 1 次
未来若遇到更高温度：出栈最多 1 次
若永远没有更高温度：不出栈
```

所有下标合计最多 `n` 次入栈、`n` 次出栈。某一天可能连续弹出很多元素，例如 `76` 一次结算多个日期，但这些弹出只是把过去各元素唯一的一次出栈集中在同一轮；后面不会重复。全部 `while` 的成功迭代总数至多为 `n`，失败检查也至多随每轮外层发生常数量级。因此总时间复杂度为 `O(n)`。这就是按元素生命周期进行的均摊分析。

这里的“均摊”不是说每一天都只做一次操作，而是把某些高温日集中完成的工作，分回到每个只会被处理有限次的下标身上。单轮可以很忙，总账仍然是线性的。

> **小白追问：** `for` 里面明明套着 `while`，为什么总时间不是 `O(n^2)`？
>
> **先给短答：** 两层循环没有独立地各走 `n` 次；内层每成功一次，就永久删除一个以后再也不会被内层处理的下标。
>
> **最小例子：** `[75,71,69,72,76]` 中，`72` 到来时弹出 `69、71`，`76` 到来时弹出 `72、75`。虽然两天各执行了两次 `while`，四个旧下标合计也只弹出四次，没有任何一个下标第二次出栈。
>
> **回到模型/代码：** 外层让每个 `currentDay` 执行一次 `push()`，共 `n` 次；内层的 `pop()` 对每个下标最多一次，总共不超过 `n` 次。把入栈与出栈总数相加仍是 `O(n)`，这就是此处的元素生命周期计数。

栈最坏保存全部 `n` 个下标，例如严格递减或全部相等输入，辅助空间复杂度为 `O(n)`。结果数组是题目必须返回的 `O(n)` 空间；若“额外空间”不计返回结果，仍因栈而为 `O(n)`。算法没有递归，不存在递归调用深度。

**固定温度表替代模型。**从右向左处理每一天，并扫描所有更高温度值，需要 `O(nR)` 时间和 `O(R)` 辅助空间。本题 `R=71` 是固定常数，从仅考虑 `n` 的渐进记号可写为 `O(n)`，但常数工作约为每个日期最多检查 70 个槽位，且模型依赖固定小值域。单调栈的 `O(n)` 不依赖数值范围，更容易迁移到任意整数序列。

> 本节代码用于串联模型与实现；可提交、可运行的权威版本见 [[题目/单调结构/739-Daily-Temperatures.md|标准题解 Java 实现]]。

先把业务动作抽成“未来第一个严格更强事件，结算仍在等待的旧位置”。下面不是天气专用类名，它可直接用于任何整数序列的“右侧第一个严格更大值距离”。抽象判断没有隐藏调用：当前测量值严格大于等待位置测量值时即可结算。

代码的关键不是 API，而是三个动作的固定顺序：先反复结算能被今天确定的旧日期，再在每次弹出时写答案，最后让今天进入等待状态。次序改变会直接改变模型语义。

> **小白追问：** 为什么结算条件必须写成 `while`，用一次 `if` 判断栈顶还不够吗？
>
> **先给短答：** 一个新温度可能同时是多个旧日期的第一个更高日；`if` 只结算最上面一个，会把同样满足条件的下一张等待单漏在栈里。
>
> **最小例子：** 处理 `[75,71,69,72]` 的最后一个 `72` 前，栈从底到顶是 `[75,71,69]`。`72` 先结算 `69`，弹出后又能结算 `71`，最后才被 `75` 挡住。若只执行一次 `if`，下标 `1` 的 `71` 会错过自己的第一个更高日。
>
> **回到模型/代码：** `while (!pendingIndices.isEmpty() && current > top)` 表示“结算后重新暴露下一名候选并继续判断”。循环停止后，才执行一次 `push(currentIndex)`，恢复等待栈的单调不升性质。

```java
import java.util.ArrayDeque;
import java.util.Deque;

final class PendingIndexSettlementModel {
    private PendingIndexSettlementModel() {
    }

    public static int[] distanceToFirstStrictlyLarger(int[] measurements) {
        int[] distanceUntilSettled = new int[measurements.length];
        Deque<Integer> pendingIndices = new ArrayDeque<>();

        for (int currentIndex = 0;
                currentIndex < measurements.length;
                currentIndex++) {
            while (!pendingIndices.isEmpty()
                    && measurements[currentIndex]
                    > measurements[pendingIndices.peek()]) {
                int settledIndex = pendingIndices.pop();
                distanceUntilSettled[settledIndex] = currentIndex - settledIndex;
            }

            pendingIndices.push(currentIndex);
        }

        return distanceUntilSettled;
    }
}
```

这个骨架中的稳定角色是：`currentIndex` 表示新事件，`pendingIndices` 表示未结算旧对象，严格大于表示触发条件，`pop` 表示状态从等待变为完成，下标差表示结果。换题时应优先检查比较方向、扫描方向和输出含义，而不是机械复制类名。

## 17. 边界、常见错误与调试观察点

| 层次 | 常见问题 | 具体后果 |
| --- | --- | --- |
| 建模错误 | 保存未来最大值而不是未结算日期 | 只能判断存在，无法保证最近位置 |
| 建模错误 | 栈中只保存温度 | 重复温度无法区分，也算不出日期差 |
| 条件错误 | 用 `<=` 判断旧温度可弹出 | 相等温度被错误视为升温 |
| 条件错误 | 用 `if` 代替 `while` | 一个高温日只能结算一个等待者，漏掉其余日期 |
| 条件错误 | 把栈描述为严格单调 | 相等温度实际会同时保留，描述与代码不一致 |
| 实现错误 | 把 `push(currentDay)` 放在 `else` 中 | 今天结算别人后，自己没有进入等待状态 |
| 实现错误 | 写成 `answer[settledDay] = temperatures[currentDay] - temperatures[settledDay]` | 算成温度差，而不是等待天数 |
| 实现错误 | 先 `peek()` 再检查空栈 | 初始状态或连续弹空时抛出异常 |
| 复杂度误判 | 看到 `for` 内有 `while` 就写 `O(n^2)` | 忽略每个下标最多出栈一次的生命周期 |

调试时不要只打印最终答案，建议每轮观察四项：当前下标和温度、弹栈前的等待栈、这一轮弹出了哪些下标、压栈后的温度序列。栈统一按“栈底到栈顶”打印，避免 `ArrayDeque.toString()` 的头部方向与脑内图不一致。

可以在纸上或日志中检查以下断言：

```text
1. 栈中下标从底到顶严格递增。
2. 对应温度从底到顶单调不升。
3. 每个已弹出下标只写答案一次，且答案大于 0。
4. 弹出时 currentDay 一定大于 settledDay。
5. 停止 while 时，栈空或栈顶温度大于等于当前温度。
```

针对条件错误，最有辨识度的用例是 `[70,70,71]`，期望 `[2,1,0]`；针对 `if/while` 错误，使用 `[75,71,69,72]`，`72` 必须同时结算 `69` 和 `71`；针对默认零，使用 `[80,70,60]`；针对下标差，使用跨度大的官方示例中 `75 -> 76`，必须得到 `4` 而不是 `1`。

若结果出错，可以先暂时用人工暴力模型与推荐模型对同一批小数组进行对拍。两者输出不同时，打印第一个不同位置和每轮栈快照，通常能迅速定位严格比较、压栈时机或栈方向问题。暴力虽然慢，却是小规模验证推荐模型的可靠事实基线。

## 18. 最终模型卡：脱离全文也能复习

| 模型卡项目 | 本题答案 |
| --- | --- |
| 识别指纹 | 一维顺序序列；对每个位置找右侧“第一个/最近”满足严格大小关系的位置；新元素可能一次确定多个旧位置答案 |
| 关系模型 | 每个旧日期等待右侧第一个严格更高温度，结果是两个下标的距离 |
| 实际保存 | 尚未遇到更高温度的日期下标，不重复保存温度 |
| 状态变化 | 当前温度严格高于栈顶对应温度时反复结算；随后当前日期入栈 |
| 答案时机 | 旧日期弹出的一刻，用当前下标减旧下标 |
| 核心不变量 | 栈底到栈顶下标递增、温度不升，所有元素在已扫描范围内都未结算 |
| 时间复杂度 | `O(n)`，每个下标入栈一次、最多出栈一次 |
| 辅助空间 | `O(n)`，递减或全相等时全部日期等待到结束 |

四句建模结论：

```text
我正在处理的对象是：按时间从左向右到来的日期下标。
我必须持续保存的是：已经出现但尚未遇到严格更高温度的日期下标。
当 当前温度严格高于栈顶等待日期的温度 发生时，我执行：弹出该日期并用下标差完成结算，直到不能继续。
答案在 等待日期被弹出的时刻 由 当前日期下标与被弹出日期下标 计算出来。
```

泛用控制模板：

```text
从事件发生的自然方向扫描：
    while 等待状态非空 且 当前事件能确定栈顶旧对象的答案：
        取出旧对象
        在状态从等待转为完成的瞬间写答案
    将当前对象加入等待状态
遍历结束：仍在等待的对象使用“不存在”的默认答案
```

迁移时不要只问“还是不是单调栈”，而要逐项比较条件、状态和结果时机：

- `496. 下一个更大元素 I`：触发条件仍是严格更大，状态仍是未结算元素，但结果从“距离”变为“目标元素值”，改变的是结果内容。
- `503. 下一个更大元素 II`：关系发生在循环数组中，需要模拟两轮扫描；改变的是序列边界和当前下标映射，通常只在第一轮压入待结算下标。
- `901. 股票价格跨度`：方向改为寻找左侧连续不大于当前价格的范围，栈中可保存“价格 + 已压缩跨度”；改变的是扫描关系和状态内容。
- `84. 柱状图中最大的矩形`：弹栈时当前元素提供右边界，弹出后的新栈顶提供左边界；改变的是一次结算所需状态和面积计算时机。

真正应记住的不是某个 `Deque` API，而是一条可以重新推出来的链。先定义“右侧第一个严格更大”的关系，再发现逐起点扫描存在重复，于是转为新事件结算旧对象。状态中只保留尚未结算的下标，用不变量保证只看栈顶已经足够。最后，在旧对象离开等待状态的那一刻写入答案。
