本篇重点解决五个学习困难。

第一，为什么“窗口移动一格”意味着可以增量维护，而不只是把双重循环换成一个陌生模板。第二，为什么不能只保存当前最大值，而要保存一组有先后次序的候选。第三，为什么删除队首和删除队尾是两种完全不同的业务事件：一个因为位置过期，一个因为竞争资格被永久取代。第四，为什么结构里必须保存下标，而不能只保存数值。第五，代码中虽然有嵌套的 `while`，总时间为什么仍是 `O(n)`。

文章会先建立一定正确的逐窗口扫描模型，再用具体窗口找出重复比较；随后才定义候选、支配关系、生命周期和不变量。等这些模型事实都成立后，再给相应的数据结构命名。

## 2. 完整题目

给定一个整数数组 `nums` 和一个正整数 `k`。把一个恰好包含 `k` 个连续元素的窗口放在数组最左侧，然后让窗口每次向右移动一个位置，直到窗口右端到达数组末尾。

对于窗口停留的每一个位置，都要找出窗口内部的最大元素。按窗口从左到右出现的顺序，返回这些最大值组成的数组。

若数组长度为 `n`，合法窗口的左端点从 `0` 逐一递增到 `n-k`，因此一共有 `n-k+1` 个结果。左端点为 `left` 的窗口覆盖闭区间 `[left, left+k-1]`。

**示例 1：经典输入**

```text
输入：nums = [1,3,-1,-3,5,3,6,7], k = 3
输出：[3,3,5,5,6,7]

窗口 [1, 3,-1]             最大值 3
窗口 [3,-1,-3]             最大值 3
窗口 [-1,-3, 5]            最大值 5
窗口 [-3, 5, 3]            最大值 5
窗口 [5, 3, 6]             最大值 6
窗口 [3, 6, 7]             最大值 7
```

第一个窗口覆盖下标 `0..2`，最后一个窗口覆盖下标 `5..7`。输出顺序与窗口出现顺序一致。

**示例 2：单元素数组**

```text
输入：nums = [1], k = 1
输出：[1]
解释：唯一窗口只包含唯一元素，最大值就是 1。
```

**示例 3：全部相等**

```text
输入：nums = [5,5,5,5], k = 3
输出：[5,5]
解释：两个窗口中的最大值都是 5。相等元素虽然数值相同，所在下标和离开窗口的时刻不同。
```

官方题面给出的全部约束为：

- `1 <= nums.length <= 10^5`；数组保证非空。
- `-10^4 <= nums[i] <= 10^4`；元素可以为负数、零或正数。
- `1 <= k <= nums.length`；窗口总能完整放入数组，因此结果至少有一个元素。

官方额外提示强调：可以考虑双端队列；队列大小不必等于窗口大小；应删除冗余元素，只保留仍需考虑的元素。这些提示用于核验最终模型，不作为本文推导起点。

Java 方法入口为：

```text
class Solution {
    public int[] maxSlidingWindow(int[] nums, int k)
}
```

约束直接给出性能信号。`n` 最多为十万，若 `k` 也接近十万，逐窗口扫描会达到约百亿次比较，无法接受。元素值范围较小，确实存在按值计数的专用方案，但那依赖固定值域；本篇选择不依赖值域、能迁移到一般可比较对象的模型。所有下标和结果长度都在 Java `int` 范围内。

## 3. 先把题目说成人话

**一句话生活化复述：** 用一个固定宽度的观察框从左向右扫过一排数字，每停一格就报告框里最高的数字。

**一句话关系化复述：** 对数组的每个长度恰好为 `k` 的连续区间，按顺序求区间最大值。

以 `nums = [4,1,3,2]`、`k = 3` 为例，先不要写公式：观察框第一次罩住 `4,1,3`，最大值是 `4`；右移后罩住 `1,3,2`，最大值是 `3`。移动过程中只发生两件事：旧下标 `0` 离开，新下标 `3` 进入。中间的 `1,3` 并没有变化。

```text
下标：      0   1   2   3
数值：      4   1   3   2
第一次：   [4   1   3]  2
第二次：    4  [1   3   2]
变化：      4 离开，2 进入，1 和 3 被两个窗口共享
```

| 要素 | 本题中的含义 |
| --- | --- |
| 对象 | 数组元素及其下标；真正移动的是窗口左右边界 |
| 关系 | 当前窗口内各元素之间的大小竞争，以及元素是否仍在窗口内 |
| 方向 | 窗口只从左向右移动；元素按下标从小到大到来 |
| 目标 | 每形成一个完整窗口，就得到该窗口的最大值 |
| 限制 | 窗口长度固定为 `k`；旧元素会从左侧离开；新元素从右侧进入；值可重复 |

这里的关键不是“连续”三个字本身，而是相邻问题高度重叠。每次从一个窗口变成下一个窗口，只删除一个最旧元素并加入一个最新元素。我们希望保留共享部分中仍对未来最大值有用的信息，而不是保留整个窗口后再全部扫描。

## 4. 第一切入点：读题时先看什么

读题第一分钟，先圈出四组真正决定模型的词。

1. **“大小固定为 `k`”**：任何下标的有效期都能由当前位置计算出来。处理右端下标 `right` 时，完整窗口左边界是 `right-k+1`。
2. **“每次向右移动一位”**：相邻窗口只发生一进一出，应该尝试复用状态。
3. **“每个窗口的最大值”**：不是求和。求和可以用一个数字加新值、减旧值；最大值在旧最大元素离开时无法直接反向恢复，所以可能需要保留后备候选。
4. **“按顺序返回所有窗口结果”**：窗口刚形成时就可以立即输出，不必等到遍历结束后回头处理。

可以暂时忽略“观察窗口”这层故事包装，把问题看成一串事件：

```text
新下标 right 到来
-> 当前合法范围的左边界向右推进
-> 清除已经不在范围中的旧对象
-> 用新对象更新最大值候选
-> 范围长度达到 k 时输出
```

数据范围 `n <= 10^5` 暗示目标应接近线性或 `O(n log n)`。`O(nk)` 在 `n=k=10^5` 时明显不可行。值域 `[-10^4,10^4]` 允许计数数组作为专用备选，但如果先依赖这个巧合，就很难迁移到更大整数、浮点权重或自定义对象，所以不把它当主线。

人工处理最小的非平凡样例 `[4,1,3,2]`、`k=3` 时，会记得第一个窗口最大值 `4`。窗口右移后，`4` 恰好离开，于是需要在留下的 `1,3` 和新来的 `2` 中找到后备最大值 `3`。这暴露了一个必要条件：状态不能只有“当前最大值是 4”，还必须能回答“4 失效后谁接班”。

## 5. 最直接的人工或暴力模型

最接近题意、也一定正确的做法是把每个窗口当成独立任务。

对每个左端点 `left = 0..n-k`：

1. 把本窗口的暂存最大值设为 `nums[left]`。
2. 从 `left+1` 扫描到 `left+k-1`。
3. 每看到一个元素，就与暂存最大值比较并保留较大者。
4. 扫描结束后，把暂存最大值写入答案中与 `left` 对应的位置。

用控制流程表示为：

```text
for 每个合法窗口左端 left:
    windowMaximum = nums[left]
    for current 从 left + 1 到 left + k - 1:
        windowMaximum = max(windowMaximum, nums[current])
    记录 windowMaximum
```

它一定正确，因为所有合法窗口都由唯一左端点表示，外层循环既不遗漏也不重复；对每个窗口，内层循环检查了其中每个元素，最终保存的值不小于任何已检查元素，同时又来自窗口本身，因此正好是窗口最大值。

若 `n` 是数组长度，窗口数是 `n-k+1`。每个窗口读取 `k` 个元素并做约 `k-1` 次比较，所以时间为 `O((n-k+1)k)`，通常简写为 `O(nk)`。除返回数组外，只需要循环下标和一个暂存最大值，额外空间为 `O(1)`；返回数组本身有 `n-k+1` 个元素，占 `O(n-k+1)`。

这个模型很有价值，因为它建立了正确性基线，也告诉我们优化不能改变什么。每个合法窗口必须恰好产生一个结果，而且结果必须来自该窗口。若要跳过某个元素，就必须先证明它以后不可能成为最大值。

## 6. 暴力到底浪费在哪里

用 `nums = [9,7,6,5,4]`、`k = 3` 看重复工作：

```text
窗口 0：[9,7,6] -> 比较 9 与 7，再比较 9 与 6，得到 9
窗口 1：[7,6,5] -> 又比较 7 与 6，再比较 7 与 5，得到 7
窗口 2：[6,5,4] -> 又比较 6 与 5，再比较 6 与 4，得到 6
```

元素 `7` 和 `6` 同时出现在前两个窗口中。第一个窗口已经知道 `7 > 6`，但这个关系在窗口右移后被丢弃，第二个窗口重新比较。类似地，`6 > 5` 的关系又在后两个窗口中重复建立。严格递减数组尤其能暴露“旧最大值离开后重新扫描整个窗口”的代价。

再看 `nums = [1,3,-1,-3,5]`、`k=3`：

```text
窗口 [1,3,-1] 的比较结论：3 胜过 1 和 -1
右移后 [3,-1,-3]：3 仍在，最大值仍是 3
再右移 [-1,-3,5]：5 新进入，并且同时胜过 -3、-1
```

当 `3` 到来时，左边的 `1` 不只是“当前输了”。在任何同时包含下标 `0` 和下标 `1` 的未来窗口里，值 `3` 更大，而且下标 `1` 更晚离开。因此下标 `0` 已经永久没有机会成为最大值。继续保存它没有意义。

同理，当 `5` 到来时，仍在候选中的 `-3` 和 `-1` 都比它小，并且都比它更早过期。这些旧元素不是暂时排在后面，而是被新元素从“当前及未来的最大值候选”中永久淘汰。

暴力还有一类浪费：已经知道某个下标离开窗口，却仍通过重新扫描隐式地把它排除。位置有效性可以直接由下标和当前左边界判断，不需要靠重算结果体现。

因此优化目标可以写成一句具体的话：

> 不要让每个窗口重新扫描全部 `k` 个元素，而要在新下标到来时，一次删除已经过期或已被永久支配的旧候选，只保存未来仍可能成为最大值的下标。

## 7. 容易想到但走不通的方向

### 方向一：只保存一个当前最大值

这个想法很自然，因为求窗口和只需要保存一个和。新元素进入时执行 `maximum = max(maximum, newValue)` 也确实能处理“加入”。问题出在“删除”：如果离开的元素就是最大值，仅凭最大值这个数字，不知道留下的元素中谁是第二大。

例如 `[9,7,6,5]`、`k=3`，第一个窗口最大值是 `9`。右移后 `9` 离开，仅保存 `9` 无法推出新窗口最大值是 `7`，只能重新扫描 `[7,6,5]`。这个方案可以做成正确算法，但最坏情况下会反复退化为 `O(nk)`。它给出的新条件是：状态需要保留按优先级排列的后备候选，而不是一个结果值。

### 方向二：每次把窗口排序

排序后最后一个元素就是最大值，因此逻辑正确，也容易实现。但每个窗口独立排序需要 `O(k log k)`，总时间达到 `O((n-k+1)k log k)`，而且相邻窗口的共享信息仍被丢弃。如果使用支持插入、删除和取最大值的有序多重集合，可以把每次移动降到 `O(log k)`，总时间 `O(n log k)`；这是可行方案，并非逻辑错误，只是没有利用“只关心最大值且元素按时间单向过期”这一更强条件。

### 方向三：大顶堆保存所有候选

把 `(数值, 下标)` 放入大顶堆，可以快速看到当前最大值。每个窗口输出前，不断弹出堆顶中已经过期的下标。这种延迟删除方案正确，代码也常见，时间通常写作 `O(n log n)`，空间最坏为 `O(n)`，因为已经过期但数值较小的元素可能长期埋在堆内部，无法立即删除。若另加索引结构支持任意删除，复杂度和实现成本又会上升。

堆的问题不是不能找最大值，而是只擅长操作堆顶。我们还希望新元素进入时，批量删除队列另一端那些“更早且不大于新元素”的候选。需要从优先级最低的一侧连续淘汰，堆并不直接提供这个操作。

### 方向四：利用固定值域做频次数组

由于本题值只在 `[-10^4,10^4]`，可以把值平移后计数，窗口移动时增减频次，再从最大值方向寻找非零桶。适当维护当前最大桶时可以很快，这在本题约束下并非错误。但模型绑定了小整数值域；值域很大或元素是一般对象时就失效。它也掩盖了本题更通用的支配关系，所以适合作为约束特化，不作为主要建模结论。

这些方向共同推动出三个要求：状态必须知道过期时间，必须保留最大值的后备顺序，并且最好能从一端清理过期对象、从另一端清理被新对象支配的对象。

## 8. 关键视角转换

原来的提问方式是：“对当前窗口的 `k` 个数，最大值是谁？”这个问题每移动一次就重新问一遍，自然得到重复扫描。

新的提问方式是：“当下标 `right` 到来时，哪些旧下标从此不再有资格参与当前或未来窗口的最大值竞争？”

| 原视角 | 新视角 |
| --- | --- |
| 每个窗口是一项独立查询 | 所有窗口是一条连续事件流 |
| 保存窗口中的全部元素，然后查最大值 | 只保存仍可能成为最大值的候选 |
| 最大值离开后重新扫描寻找接班者 | 候选按竞争力排列，队首后面天然就是后备者 |
| 旧元素统一等到离窗时删除 | 一旦被更晚且不小的元素支配，就提前永久删除 |
| 值只表示大小 | 下标同时表示到达顺序和过期时间 |

“支配”是视角转换的核心。若旧下标 `old < current` 且 `nums[old] <= nums[current]`，那么对从现在开始的任何窗口：

- 只要旧下标还在窗口，新下标也一定还在，因为新下标更靠右、离开得更晚。
- 新值不小于旧值，比较最大值时旧值不会胜过新值。

所以旧下标以后不可能成为某个窗口的唯一更优选择，可以永久丢弃。若某个旧值大于新值，则不能删：它可能先担任当前最大值，等它过期后，新值再接班。因此候选需要按从旧到新的顺序排列，同时对应值从大到小。

这次转换减少重复的原因不是“用了一个高级结构”，而是每个大小关系只在新元素到来时结算一次。被支配的旧下标立即退场；没有被支配的下标继续作为有意义的后备者。一个已经退场的下标再也不会被后续窗口重新比较。

> **小白追问：** 为什么不能把整个窗口都保存下来，只在需要时从中找最大值？
>
> **先给短答：** 保存整个窗口只解决了“元素还在不在”，没有解决“每次仍要重新比较谁最大”；候选压缩会提前删掉已经永远不可能获胜的元素。
>
> **最小例子：** 看 `[1,3]`。下标 `1` 的值 `3` 到来后，下标 `0` 的值 `1` 更小，而且下标更早。以后只要 `1` 仍在某个窗口，`3` 也一定在，并且更大。继续保存 `1` 不会改变任何尚未产生的窗口最大值。
>
> **回到模型/代码：** “只保存候选”对应队尾淘汰条件 `nums[old] <= nums[right]`。被这个条件删除的不是普通窗口成员，而是已经同时输掉数值和剩余有效期的成员；仍可能接班的成员继续留在 `candidateIndices` 中。

## 9. 正式建立模型

先定义处理时刻。按下标从左到右扫描，当前进入的下标为 `right`。当 `right >= k-1` 时，完整窗口左边界为 `windowLeft = right-k+1`，窗口覆盖 `[windowLeft,right]`。

| 建模项 | 本题结论 |
| --- | --- |
| 对象 | 已经到来的数组下标；下标关联一个数值和一个离开窗口的时刻 |
| 关系 | 更晚且数值不小的下标支配更早下标；窗口左边界决定下标是否过期 |
| 状态 | 按下标递增排列、按对应值严格递减排列的一组有效候选下标 |
| 事件 | 左边界右移导致队首过期；新下标到来导致队尾候选被支配；完整窗口形成导致输出 |
| 不变量 | 候选下标从前到后严格递增且都未过期，对应值严格递减，队首是当前窗口最大值下标 |
| 结果时机 | 当前下标加入并恢复不变量后，若 `right >= k-1`，由队首对应值产生一个答案 |

每轮处理分成四个动作，顺序表达各自职责：

1. **队首过期淘汰**：计算 `windowLeft = right-k+1`，只要队首下标 `< windowLeft`，它已经在当前范围左边，必须从队首删除。
2. **队尾支配淘汰**：只要队尾对应值 `<= nums[right]`，队尾更早过期且不比新值大，永久删除。
3. **加入当前下标**：把 `right` 放到队尾。下标顺序仍递增，值顺序也恢复为严格递减。
4. **窗口结算**：完整窗口形成后，队首是值最大的有效候选，写入答案。

必须区分两种删除：

```text
队首删除：位置条件触发，原因是 candidateIndex < windowLeft
队尾删除：大小与时间共同触发，原因是 candidateValue <= currentValue

队首回答“它还在不在窗口里”
队尾回答“它以后还有没有赢的可能”
```

> **小白追问：** 队首删除和队尾删除为什么不能合成一句“删掉没用的元素”？
>
> **先给短答：** 因为两者判定的是两个不同事实：队首元素已经不属于窗口，队尾元素仍属于窗口却已经不可能成为现在或未来的最大值。
>
> **最小例子：** 在 `[9,1,2]`、`k=2` 中处理下标 `2`。下标 `0` 的值 `9` 很强，却因 `0 < 1` 已经过期，要从队首删；下标 `1` 的值 `1` 仍在窗口 `[1,2]`，却被更晚的值 `2` 支配，要从队尾删。一个因位置失效，一个因竞争失效。
>
> **回到模型/代码：** 过期只看 `candidateIndex < windowLeft`，对应 `pollFirst()`；支配同时看新旧值和先后位置，对应 `nums[peekLast()] <= nums[right]` 与 `pollLast()`。日志和证明都应保留这两个原因。

> **小白追问：** 队尾淘汰为什么必须写成 `while`，弹出一个最弱候选还不够吗？
>
> **先给短答：** 一个新值可能连续支配多个旧候选，必须一直删除到队尾值严格大于新值，值序才重新成立。
>
> **最小例子：** 在 `[5,4,3,6]` 中，`6` 到来前候选是 `[5,4,3]`。若只弹出 `3`，队列会变成 `[5,4,6]`，队首 `5` 已经不是最大值；继续弹出 `4` 和 `5` 后，留下 `[6]` 才正确。
>
> **回到模型/代码：** 第二段 `while` 的停止条件意味着“队尾已经严格大于 `nums[right]`”。停止后再执行 `offerLast(right)`，才能恢复候选值严格递减的不变量。

状态是足够的。被保留的候选按值从大到小，队首直接给出最大值；队首过期后，下一个候选就是未被更强对象支配的最佳后备。状态也没有保存明显多余的信息：任何被删除对象都能给出永久安全的删除理由。

遍历必须从左到右，因为下标的到来顺序就是窗口移动顺序。只有这样，“新元素离开得更晚”才成立，支配关系才能把数值优势和生命周期优势结合起来。

> **小白追问：** 为什么本文先清队首过期项，再清队尾支配项？把两段 `while` 交换就一定错吗？
>
> **先给短答：** 先过期再支配最符合“先确定当前合法范围，再比较范围内竞争者”的建模顺序；在本题不变量完整时交换两段通常仍可正确，但不能交换它们的条件或删除方向。
>
> **最小例子：** 在 `[3,1,2]`、`k=2` 中处理下标 `2`，左边界为 `1`。先从队首删过期的 `0:3`，再从队尾删被 `2:2` 支配的 `1:1`，原因清楚。若先做支配，会先删 `1:1`，再删过期的 `0:3`，最终也得到 `[2:2]`，但日志中的业务阶段变得更难读。
>
> **回到模型/代码：** 本文固定第一段为 `peekFirst() < windowLeft` 加 `pollFirst()`，第二段为队尾值 `<= nums[right]` 加 `pollLast()`。顺序服务于解释和调试；正确性的硬约束是每次输出前两类无效候选都已清完，并且当前下标已经入队。

### 相等值策略

本文采用 `nums[tail] <= nums[right]` 时删除旧队尾，即相等时保留较新的下标。理由是新旧值相同，而新下标离开窗口更晚，旧下标不会提供额外答案。这样候选值保持**严格递减**。

另一种正确策略是只删除严格更小的队尾，即比较条件使用 `<`，同时保留多个相等下标；此时候选值只是**非递增**，旧相等值会先从队首过期。两种策略都正确，但证明、注释和代码必须一致。本文后续演算和 Java 实现全部使用“相等时删除旧下标”的策略，不能一处按严格递减解释，另一处却写成 `<`。

## 10. 所需数据结构详解

模型已经要求一种容器：候选按到达时间排列；最旧候选可能因过期从前端删除；新元素可能从后端连续淘汰弱候选；还要从后端加入新下标，并从前端读取当前最强候选。

能够在两端进行常数时间操作的线性容器称为**双端队列**，英文为 deque。加上“对应数值始终保持严格递减”这个业务不变量后，通常把本题中的用法称为**单调队列**。单调队列不是 Java 中另一种神秘容器，而是“双端队列 + 单调维护规则”。

### 结构内部保存什么

队列保存的是数组下标，不是单独的数值：

```text
队首 -> [indexA, indexB, indexC] <- 队尾
下标：       indexA < indexB < indexC
数值： nums[indexA] > nums[indexB] > nums[indexC]
```

保存下标同时提供两种信息：通过 `nums[index]` 比较竞争力；通过 `index < windowLeft` 判断生命周期。若只保存值，重复值出现时无法知道队首的那个值来自哪个位置、何时离开。可以额外维护频次补救，但下标已经是更直接的复合身份。

严格地说，某些专门写法可以只存数值：它们必须保留相等值，并把即将离窗的原数组值与队首同步比较。那是另一套状态契约。本文采用“相等时删除旧候选”的策略，因此单独的数值已经不能标明队列中的 `5` 究竟来自哪个下标；保存下标才让过期判断与相等值策略保持统一。

> **小白追问：** 数值已经能比较大小了，为什么这个模型还必须保存下标？
>
> **先给短答：** 最大值竞争需要数值，窗口过期需要身份和位置；下标同时携带这两类信息，而单独数值无法区分相等元素的生命周期。
>
> **最小例子：** 对 `[5,5,1]`、`k=2`，处理第二个 `5` 时，本文会删除旧下标 `0`，只保留新下标 `1`。处理 `1` 时，离窗的是下标 `0`，但队列中的 `5` 来自下标 `1`，仍然有效。若只看到数值 `5`，就无法直接判断该不该删除这个 `5`。
>
> **回到模型/代码：** `candidateIndices` 保存下标；`nums[candidateIndices.peekLast()]` 负责比大小，`candidateIndices.peekFirst() < windowLeft` 负责判过期。一个下标通过两种读取方式承担“值”和“有效期”两种职责。

### 本题使用的操作

| 操作 | Java `Deque` 方法 | 本题职责 | 单次成本 |
| --- | --- | --- | --- |
| 查看队首 | `peekFirst()` | 读取最强候选下标，或判断它是否过期 | `O(1)` |
| 删除队首 | `pollFirst()` | 淘汰已经移到窗口左侧的下标 | `O(1)` |
| 查看队尾 | `peekLast()` | 判断最弱候选是否被新元素支配 | `O(1)` |
| 删除队尾 | `pollLast()` | 永久淘汰更早且不大于新值的候选 | `O(1)` |
| 加入队尾 | `offerLast(right)` | 登记当前下标为最新候选 | `O(1)` |

Java 中使用 `ArrayDeque<Integer>`。它以可扩容循环数组实现双端操作，避免 `LinkedList` 为每个整数下标创建链表节点的额外对象开销。这里不需要线程安全，也不需要在中间位置随机插入。

### 为什么普通队列、栈和堆不完全匹配

- 普通先进先出队列只能从前端删除，无法从尾部连续删除被支配候选。
- 栈适合只处理最近对象，但本题还必须从另一端清除最旧的过期对象并读取最旧的最强候选。
- 大顶堆能读最大值，却不能高效删除埋在内部的任意过期元素，也不能从“最弱且最新”一端连续清理。
- 有序集合可行，但插入、删除通常是 `O(log k)`，没有利用候选天然按到达顺序排列的性质。

队列最多保存多少下标？所有候选都来自当前窗口，数量不超过 `k`。采用相等时删除旧下标后，全相等窗口甚至只保留一个下标；严格递减窗口中没有队尾支配删除，队列会保留完整的 `k` 个下标，这就是 `O(k)` 最坏额外空间。

## 11. 生活化类比及边界

可以把每个数组元素想成参加固定时长评选的候选人。候选人按下标顺序到场，分数是数组值。评委每一轮只考虑最近 `k` 位到场者，并报告其中最高分。

候选席不是把所有人都留下，而是维护一张“仍可能获胜的候选名单”。名单前面是当前最高分，后面依次是前面的人离场后可能接班的候选。

新候选到场时，如果他的分数不低于名单尾部的人，那么尾部旧候选可以提前离席：新候选分数至少一样高，而且到场更晚，也会更晚超过最近 `k` 人的有效范围。旧候选在任何未来评选中都不可能胜过他。另一方面，名单最前面的人即使分数最高，只要他的到场编号已经早于当前有效范围，也必须因“到期”离席。

| 生活对象或动作 | 算法中的对应物 |
| --- | --- |
| 候选人的到场编号 | 数组下标 `right` |
| 候选人的分数 | `nums[right]` |
| 最近 `k` 位的评选范围 | 当前固定长度窗口 `[windowLeft,right]` |
| 仍可能获胜的候选名单 | 双端队列中的候选下标 |
| 名单从前到后的分数顺序 | 对应数组值严格递减 |
| 最前候选因编号过早离席 | 队首过期淘汰 `index < windowLeft` |
| 新候选让尾部弱者提前离席 | 队尾支配淘汰 `oldValue <= newValue` |
| 新候选登记在名单尾部 | `offerLast(right)` |
| 每轮报告最高分 | 完整窗口形成后读取 `nums[peekFirst()]` |

这个类比最有价值的地方，是把两个删除方向解释成两种原因：名单前端处理“年龄到期”，名单后端处理“竞争资格消失”。两者不能混成一句“把没用的删掉”。

类比到这里为止。现实评选可能允许候选人主动退出、分数变化、并列多人共同获奖或跨轮回归，本题都没有这些规则。算法中的值固定、窗口严格右移、每轮只输出一个数值。类比也不是正确性证明；旧候选能安全删除，仍要依靠“新值不小且新下标离开更晚”这两个可验证条件。

## 12. 典型输入的完整数据变化图

完整演算官方经典输入：

```text
下标：  0   1   2   3   4   5   6   7
数值：  1   3  -1  -3   5   3   6   7
k = 3

队列表示统一为：队首 -> [下标:数值, 后续候选] -> 队尾
```

每轮先清队首过期项，再清队尾被支配项，最后加入当前下标。窗口未满时只维护状态，不输出。

| `right` | `windowLeft` | 处理前候选 | 队首过期淘汰 | 队尾支配淘汰 | 加入后候选 | 新增结果 |
| ---: | ---: | --- | --- | --- | --- | --- |
| 0 | -2 | `[]` | 无 | 无 | `[0:1]` | 窗口未满 |
| 1 | -1 | `[0:1]` | 无 | `0:1` 被 `1:3` 支配 | `[1:3]` | 窗口未满 |
| 2 | 0 | `[1:3]` | 无 | 无，`3 > -1` | `[1:3, 2:-1]` | `3` |
| 3 | 1 | `[1:3, 2:-1]` | 无，`1` 仍等于左边界 | 无，`-1 > -3` | `[1:3, 2:-1, 3:-3]` | `3` |
| 4 | 2 | `[1:3, 2:-1, 3:-3]` | 删除过期的 `1:3` | `3:-3`、`2:-1` 都被 `4:5` 支配 | `[4:5]` | `5` |
| 5 | 3 | `[4:5]` | 无 | 无，`5 > 3` | `[4:5, 5:3]` | `5` |
| 6 | 4 | `[4:5, 5:3]` | 无 | `5:3`、`4:5` 都被 `6:6` 支配 | `[6:6]` | `6` |
| 7 | 5 | `[6:6]` | 无 | `6:6` 被 `7:7` 支配 | `[7:7]` | `7` |

把关键转折拆成快照，更容易看到两类删除并不相同。

### 快照 A：`right = 3`，左边界恰好等于队首下标

```text
当前窗口：[1..3] = [3,-1,-3]
处理前：  队首 -> [1:3, 2:-1] -> 队尾
过期判断：1 < 1 为 false
队尾比较：nums[2] = -1 > -3，不删除
加入 3：  队首 -> [1:3, 2:-1, 3:-3] -> 队尾
输出：nums[1] = 3
```

下标等于左边界仍在窗口中，所以过期条件必须是 `< windowLeft`，不能写成 `<= windowLeft`。

### 快照 B：`right = 4`，先过期再支配

```text
当前窗口：[2..4] = [-1,-3,5]

处理前：       队首 -> [1:3, 2:-1, 3:-3] -> 队尾
队首过期：     1 < 2，删除 1:3
剩余：         队首 -> [2:-1, 3:-3] -> 队尾
队尾支配 1：   -3 <= 5，删除 3:-3
队尾支配 2：   -1 <= 5，删除 2:-1
加入当前下标： 队首 -> [4:5] -> 队尾
输出：         nums[4] = 5
```

这里同一轮同时触发两种删除。下标 `1` 是因为不在窗口内而删除；下标 `2、3` 仍在窗口内，但因为新值 `5` 更大且活得更久而删除。若日志只写“pop 了三个元素”，就会失去最重要的模型信息。

### 每轮统一检查清单

```text
当前输入：nums[right]
处理前状态：候选下标及其对应值
判断依据一：队首下标是否小于 windowLeft
执行动作一：从队首删除所有过期下标
判断依据二：队尾值是否小于等于当前值
执行动作二：从队尾删除所有被支配下标
执行动作三：当前下标加入队尾
处理后状态：下标递增、值严格递减、全部未过期
新增结果：窗口完整时读取队首对应值
```

最终依次输出 `[3,3,5,5,6,7]`。整个过程中，任何已从队尾删除的下标都没有重新进入；任何从队首删除的下标也不会因窗口继续右移而重新有效。

## 13. 边界场景的数据变化

### 边界一：`k = 1`

取 `nums = [4,-2,7]`、`k=1`。每个元素自己构成一个窗口，预期输出 `[4,-2,7]`。

| `right` | 左边界 | 处理前 | 过期删除 | 加入后 | 输出 |
| ---: | ---: | --- | --- | --- | ---: |
| 0 | 0 | `[]` | 无 | `[0:4]` | 4 |
| 1 | 1 | `[0:4]` | 删除 `0:4`，因为 `0 < 1` | `[1:-2]` | -2 |
| 2 | 2 | `[1:-2]` | 删除 `1:-2`，因为 `1 < 2` | `[2:7]` | 7 |

每轮过期删除后队列可能暂时为空，但当前下标随后一定加入，因此输出前队首存在。官方约束保证 `k>=1` 且数组非空，不需要为空输入定义额外返回语义。循环执行三次，答案也恰好写三次，不会越界。

### 边界二：全部相等，验证相等值策略

取 `nums = [5,5,5,5]`、`k=3`。本文选择相等时删除旧下标：

```text
right=0：加入 0        -> [0:5]
right=1：1:5 支配 0:5 -> 删除 0，加入 1 -> [1:5]
right=2：2:5 支配 1:5 -> 删除 1，加入 2 -> [2:5]，输出 5
right=3：左边界为 1，2 未过期；3:5 支配 2:5
         删除 2，加入 3 -> [3:5]，输出 5
```

队列始终只保留最新的那个 `5`。这不会漏掉答案，因为新 `5` 与旧 `5` 数值相同，却更晚离开窗口。若代码使用 `<` 而不是 `<=`，队列会保留多个相等下标，仍可得到正确输出，但队列值不再严格递减。文档中的不变量和代码条件必须选同一种口径。

### 边界三：严格递减，验证最大空间

取 `[9,8,7,6]`、`k=3`：新值从不支配队尾，所以第一个完整窗口形成时队列为 `[0:9,1:8,2:7]`。到 `right=3`，下标 `0` 从队首过期，加入 `3:6` 后得到 `[1:8,2:7,3:6]`，输出 `8`。队列最多保存 `k` 个下标，但不会超过窗口范围。

### 边界四：`k = n`

整个数组只有一个窗口。算法仍会逐个建立候选，但只在最后一个下标到来时输出一次。答案数组长度 `n-k+1` 等于 `1`。这说明结果时机由“窗口是否完整”控制，而不是每次加入都输出。

## 14. 正确性与不变量

要证明的不是“双端队列很快”，而是每个完整窗口输出的队首值恰好等于真实最大值。证明围绕三个不变量展开。

### 不变量一：候选下标严格递增且都没有过期

我们按 `right` 从小到大处理，每个新下标只从队尾加入，因此下标顺序天然递增。加入前先从队首删除所有 `< windowLeft` 的下标，剩余下标都位于当前窗口范围。新下标 `right` 当然也在范围内。于是每轮结束后，队列中的下标都有效。

### 不变量二：候选对应值严格递减

加入当前下标前，从队尾删除所有值小于等于当前值的候选。停止时，若队列非空，最后一个候选值必然严格大于当前值；把当前下标加到尾部后，整个值序列仍严格递减。若队列被清空，单元素序列也满足不变量。

### 不变量三：每个未入队的有效元素都被某个更晚且不小的候选代表

元素只会因两种原因离队。因过期离队的元素已经不属于当前及未来窗口，无需代表。因队尾支配离队的旧元素 `old`，存在新下标 `current > old` 且 `nums[current] >= nums[old]`。只要旧元素可能出现在某个未来窗口，新元素也会在同一窗口中，并且不比它小，所以旧元素不可能决定更大的答案。

若代表旧元素的新候选以后又被更晚元素支配，可以沿支配链继续找到一个仍在队列中的候选。链中下标不断增大，不会循环；最终候选至少与原元素一样大，并且更晚过期。因此删除不会遗漏未来最大值。

> **小白追问：** 新元素只是在当前这一刻更大，凭什么说它能永久支配旧元素？
>
> **先给短答：** 永久删除依赖两个优势同时成立：新值不小于旧值，并且新下标更靠右、离开得更晚；未来不会出现旧元素还有效而新元素已经过期的窗口。
>
> **最小例子：** `[2,3]` 中，旧下标 `0` 的值为 `2`，新下标 `1` 的值为 `3`。在下标 `1` 到来后的窗口里，只要下标 `0` 仍在范围中，下标 `1` 必然也在；比较最大值时 `3` 又不会输给 `2`。所以 `2` 没有任何未来翻盘时刻。
>
> **回到模型/代码：** “值不小”由 `nums[peekLast()] <= nums[right]` 检查，“更晚”由从左到右扫描和 `right` 总是最新下标保证。缺少任一前提都不能执行 `pollLast()`。

### 为什么队首就是当前窗口最大值

队首本身未过期，确实属于当前窗口。根据值严格递减，它不小于队列内其他候选。

当前窗口中不在队列里的元素，已经被某个更晚且不小的候选通过支配链覆盖。窗口中因此不存在比队首更大的未保存元素。队首既来自窗口，又不小于窗口内任何元素，所以正是窗口最大值。

> **小白追问：** 队列没有保存窗口里的所有数，为什么队首仍然一定是整个窗口的最大值？
>
> **先给短答：** 留在队列里的候选按值递减；没留在队列里的有效元素，都有一个更晚且不小的代表，因此不可能偷偷比队首更大。
>
> **最小例子：** 对窗口 `[4,2,3]`，`3` 到来时会删除 `2`，候选成为 `[0:4,2:3]`。虽然值 `2` 不在队列中，但它小于代表它的 `3`；而队首 `4` 又大于 `3`。删除 `2` 不会让真实最大值从队列外消失。
>
> **回到模型/代码：** `pollLast()` 建立“被删元素有不小的代表”，严格递减顺序建立“队首不小于所有代表”，第一段 `while` 保证队首仍有效。三条事实合起来，才允许用 `nums[candidateIndices.peekFirst()]` 输出。

### 为什么队首过期后不会失去正确接班者

队首后面的候选没有被队首删除，因为它们到来时值更小；它们之所以仍被保存，正是因为会比队首更晚离开。当队首从左侧过期，后续候选仍按值递减排列，新队首就是尚未过期候选中的最大者。无需重新扫描窗口寻找第二大。

### 为什么相等时删除旧下标安全

设旧值和新值相等。任何包含旧下标但不包含新下标的窗口只能发生在新下标到来之前，而那些窗口已经结算；从新下标到来以后，只要旧下标仍有效，新下标一定也有效。两者贡献值相同，新下标还更晚过期，所以保留新下标足以覆盖所有尚未产生的答案。

> **小白追问：** 两个值相等时，删掉旧下标真的不会在窗口边界处少算一次吗？
>
> **先给短答：** 不会；旧下标独自有效的窗口都已在新下标到来前输出，之后新下标与它同值并且活得更久，可以接管所有尚未输出的窗口。
>
> **最小例子：** 对 `[5,5,1]`、`k=2`，下标 `1` 到来时，第一个完整窗口 `[0,1]` 的最大值仍由新 `5` 输出。下一轮窗口变成 `[1,2]`，旧下标 `0` 已过期，新下标 `1` 仍在并继续提供最大值 `5`。没有一个未来窗口必须依赖旧 `5`。
>
> **回到模型/代码：** 条件使用 `<=`，所以新相等值会触发 `pollLast()` 并留下更新的下标。对应的不变量是“值严格递减”；若改成 `<` 保留旧相等值，就必须把不变量改成“值非递增”。

遍历结束时，每个右端点 `right = k-1..n-1` 都恰好形成一个合法窗口，并在恢复不变量后输出一次。这样的右端点共有 `n-k+1` 个，与所有合法窗口一一对应，因此没有漏窗口，也没有多输出。

## 15. 时间与空间复杂度推导

先定义变量：

- `n` 表示数组 `nums` 的长度。
- `k` 表示固定窗口长度，满足 `1 <= k <= n`。
- 合法窗口数量为 `w = n-k+1`。
- 返回数组不计入额外工作空间时单独说明；计入总占用时再加上其长度。

### 直接模型

直接模型处理 `w` 个窗口，每个窗口读取 `k` 个元素并做 `k-1` 次量级的比较，所以精确量级是 `w * k = (n-k+1)k`，时间复杂度为 `O((n-k+1)k)`，常写作 `O(nk)`。当 `k` 约为 `n/2` 时达到 `O(n^2)` 量级。

它只用一个暂存最大值和循环下标，排除返回数组后的额外空间是 `O(1)`；返回数组长度为 `w`，若计入则总空间为 `O(w)`。

### 推荐模型：为什么嵌套 `while` 仍是 `O(n)`

外层循环显然执行 `n` 次。每轮有两个 `while`，不能只因为它们写在循环里面就乘成 `O(nk)`，要按每个下标的完整生命周期计数。

一个下标的生命周期只有：

```text
尚未到来
-> 恰好一次从队尾入队
-> 留在队列若干轮，但停留本身不执行操作
-> 要么从队尾因被支配出队
   要么从队首因过期出队
-> 永久离开，绝不再次入队
```

每个下标恰好入队一次，因此总入队次数是 `n`。一个下标一旦从任一端出队就永久消失，不可能既从队尾出队又在未来从队首出队，所以两个 `while` 合计的成功删除次数最多为 `n`。每轮 `while` 最后还会做常数次失败判断，总共也是 `O(n)`。

因此所有入队、出队、查看队首队尾和答案写入的总操作数都与 `n` 成正比，均摊时间复杂度是 `O(n)`。这里“均摊”不表示随机平均，也不依赖输入分布；即使某一轮连续删除很多元素，那些元素以后再不会被删除，整段执行仍有确定的线性上界。

> **小白追问：** 外层 `for` 里面最多有两段 `while`，为什么不能直接判断成 `O(n^2)`？
>
> **先给短答：** 嵌套只说明某一轮可能做多次删除，不代表同一个下标会被每一轮重复删除；每个下标总共只会入队一次、出队一次。
>
> **最小例子：** 在 `[5,4,3,6]` 中，处理 `6` 时会连续弹出 `3、4、5`，这一轮确实做了三次删除。但这三个下标此前各入队一次，弹出后永久消失，后面不可能再为它们付第二次删除成本。四个元素的总入队次数是四，总出队次数最多也是四。
>
> **回到模型/代码：** 统计整个 `for` 期间的 `offerLast`、`pollFirst` 和 `pollLast`，而不是把单轮最坏删除数机械乘以 `n`。这种把偶尔昂贵的轮次分摊到元素完整生命周期上的计数，就是这里的“均摊”。

### 空间

队列只保存当前窗口中的候选下标，最多 `k` 个，所以额外工作空间为 `O(k)`。严格递减输入达到这个上界；递增或全相等输入使用本文策略时，队列通常只有一个下标。

答案数组长度是 `n-k+1`。按算法题惯例不把返回值计入额外空间时结论为 `O(k)`；若统计进程实际持有的全部新空间，则为 `O(k + n-k+1)`，可简化为 `O(n)`。算法没有递归，因此没有递归栈空间。

作为对比，大顶堆延迟删除通常需要 `O(n log n)` 时间和最坏 `O(n)` 空间；平衡树多重集合可做到 `O(n log k)` 时间与 `O(k)` 空间。推荐模型利用更强的支配不变量，把每个下标的结构操作压缩到常数次。

### 泛用模型骨架

下面骨架抽取的是“固定宽度范围内维护极值候选”的控制流程，不绑定最大值还是最小值。子类只定义“新值是否支配旧值”。最大值模型使用 `newValue >= oldValue`；最小值模型改为 `newValue <= oldValue`。相等时由新对象取代旧对象，使结构更精简。

```java
import java.util.ArrayDeque;
import java.util.Deque;

abstract class FixedWindowExtremeTemplate {
    public int[] collectExtremeValues(int[] values, int windowSize) {
        if (values == null || values.length == 0) {
            throw new IllegalArgumentException("values must not be empty");
        }
        if (windowSize < 1 || windowSize > values.length) {
            throw new IllegalArgumentException("invalid window size");
        }

        int[] results = new int[values.length - windowSize + 1];
        Deque<Integer> candidateIndices = new ArrayDeque<>();
        int resultIndex = 0;

        for (int currentIndex = 0;
                currentIndex < values.length;
                currentIndex++) {
            int leftBoundary = currentIndex - windowSize + 1;

            while (!candidateIndices.isEmpty()
                    && candidateIndices.peekFirst() < leftBoundary) {
                candidateIndices.pollFirst();
            }

            while (!candidateIndices.isEmpty()
                    && newCandidateDominates(
                            values[currentIndex],
                            values[candidateIndices.peekLast()])) {
                candidateIndices.pollLast();
            }

            candidateIndices.offerLast(currentIndex);

            if (currentIndex >= windowSize - 1) {
                results[resultIndex++] =
                        values[candidateIndices.peekFirst()];
            }
        }

        return results;
    }

    protected abstract boolean newCandidateDominates(
            int newValue,
            int oldValue);
}

class FixedWindowMaximum extends FixedWindowExtremeTemplate {
    @Override
    protected boolean newCandidateDominates(int newValue, int oldValue) {
        return newValue >= oldValue;
    }
}
```

骨架中的抽象判断有明确契约：只有当新对象的极值优先级不弱于旧对象，并且因到来更晚而拥有更长剩余有效期时，才返回 `true`。固定窗口最小值可以改变比较方向复用流程；若窗口不是单向移动、候选会重新有效或优先级会动态变化，这个骨架就不适用。

### LeetCode 可直接提交代码

```java
import java.util.ArrayDeque;
import java.util.Deque;

class Solution {
    public int[] maxSlidingWindow(int[] nums, int k) {
        int[] answers = new int[nums.length - k + 1];
        Deque<Integer> candidateIndices = new ArrayDeque<>();
        int answerIndex = 0;

        for (int right = 0; right < nums.length; right++) {
            int windowLeft = right - k + 1;

            while (!candidateIndices.isEmpty()
                    && candidateIndices.peekFirst() < windowLeft) {
                candidateIndices.pollFirst();
            }

            while (!candidateIndices.isEmpty()
                    && nums[candidateIndices.peekLast()] <= nums[right]) {
                candidateIndices.pollLast();
            }

            candidateIndices.offerLast(right);

            if (right >= k - 1) {
                answers[answerIndex++] =
                        nums[candidateIndices.peekFirst()];
            }
        }

        return answers;
    }
}
```

模型与代码的对应关系如下：

| 模型角色 | Java 变量或代码块 |
| --- | --- |
| 当前进入的对象 | `right` 与 `nums[right]` |
| 当前窗口左边界 | `windowLeft = right - k + 1` |
| 仍有资格的候选 | `candidateIndices` 中的数组下标 |
| 队首过期条件 | `candidateIndices.peekFirst() < windowLeft` |
| 队尾支配条件 | `nums[candidateIndices.peekLast()] <= nums[right]` |
| 状态变化 | 两端删除后执行 `offerLast(right)` |
| 结果时机 | `right >= k - 1`，窗口首次达到并持续保持完整 |
| 结果来源 | `nums[candidateIndices.peekFirst()]` |

> **小白追问：** 为什么必须先完成两段删除并加入 `right`，然后才能读取队首输出？
>
> **先给短答：** 输出必须基于“当前窗口”的完整候选；提前输出会遗漏刚进入的新元素，延后清理则可能读取已经过期的旧元素。
>
> **最小例子：** 对 `[1,3]`、`k=2`，处理下标 `1` 前，队首还是值 `1`。如果先输出再加入当前下标，会错误得到 `1`；先让 `3` 淘汰 `1` 并入队，队首才变为当前窗口真实最大值 `3`。
>
> **回到模型/代码：** 更新顺序是计算 `windowLeft`、执行 `pollFirst()`、执行 `pollLast()`、`offerLast(right)`，最后在 `right >= k - 1` 时读取 `peekFirst()`。这个顺序对应“清范围、清竞争、登记当前、结算答案”。

代码没有给 `k==1`、全相等或 `k==n` 写专门分支，因为统一不变量已经覆盖这些情况。两段 `while` 分开保留，虽然某些顺序变体也能正确，但这种写法最直接地对应“先清理范围，再处理竞争”的模型。

## 17. 边界、常见错误与调试观察点

### 边界清单

- `nums.length == 1` 且 `k == 1`：答案长度为一，当前下标加入后立即输出。
- `k == 1`：上一轮候选会在下一轮先过期，每个元素都是自己窗口的最大值。
- `k == nums.length`：只在最后一轮输出一次。
- 全部相等：本文采用 `<=` 删除旧相等下标，始终保留最新下标。
- 严格递增：每个新值会清空队尾旧候选，队列长度通常为一。
- 严格递减：没有支配删除，队列最多达到 `k`，靠队首过期推进。
- 包含负数：比较规则与正负无关，不能把最大值默认初始化为零；本实现直接从候选取值。
- 官方约束保证输入非空且 `k` 合法；泛用骨架额外做了参数校验，LeetCode 提交代码可依赖题目契约。

### 常见错误

| 层次 | 错误表现 | 后果与修正 |
| --- | --- | --- |
| 建模错误 | 只保存当前最大值 | 最大值过期时没有接班信息，必须重扫窗口 |
| 建模错误 | 队列保存所有窗口下标，却不做支配删除 | 仍可从中扫描最大值，但没有消除重复工作 |
| 建模错误 | 把队首删除和队尾删除都解释成“过期” | 无法证明提前删除的窗口内元素为何安全 |
| 条件错误 | 过期条件写成 `index <= windowLeft` | 恰好位于左边界的元素仍有效，却被提前删除 |
| 条件错误 | 相等时代码用 `<`，文档却声称值严格递减 | 算法可能仍正确，但不变量与实际状态不一致 |
| 条件错误 | 窗口未满就输出 | 结果数量变成 `n`，前 `k-1` 个不是合法窗口答案 |
| 代码错误 | 队列存值后用值判断过期 | 重复值无法区分来源位置和生命周期 |
| 代码错误 | 输出数组长度写成 `n-k` | 少一个窗口；合法左端点包含 `n-k` |
| 代码错误 | 直接调用 `peekFirst()` 而没有先保证加入当前下标 | 队列可能为空并发生拆箱异常 |
| 代码错误 | 使用 `ArrayDeque` 的 `push/pop` 混合首尾语义 | 容易把方向写反；本题显式使用 `First/Last` 方法 |

### 最值得打印的调试状态

不要只打印最终答案。每轮打印下面这些语义状态：

```text
right 与 nums[right]
windowLeft
处理前 candidateIndices（同时打印 index:value）
从队首删除了哪些下标，以及原因“expired”
从队尾删除了哪些下标，以及原因“dominated”
处理后 candidateIndices
本轮是否输出，输出来自哪个队首下标
```

可以在调试版本加入四项断言：

1. 队列下标从前到后严格递增。
2. 每个候选下标都满足 `index >= windowLeft`。
3. 对应值从前到后严格递减；若采用保留旧相等值策略，则改为非递增。
4. 完整窗口形成后，队首下标位于 `[windowLeft,right]`。

对经典输入重点观察 `right=4`：日志必须先显示 `1:3` 因过期从队首删除，再显示 `3:-3` 与 `2:-1` 因被 `4:5` 支配从队尾删除。若三个下标都从同一端删除，或删除原因相同，方向模型很可能写错。

对全相等输入，若比较使用 `<=`，每轮加入后队列应只剩最新下标。若队列不断增长，说明实际用了 `<`；这未必导致答案错误，但要同步修改严格递减不变量。对 `k=1`，若上一轮下标未在下一轮过期，检查是否把左边界误写成 `right-k`。

## 18. 最终模型卡

| 模型卡项目 | 结论 |
| --- | --- |
| 识别指纹 | 固定长度连续范围单向移动；每次一进一出；每个范围要极值；旧极值离开后需要后备者 |
| 一句话关系模型 | 更晚且不小的元素永久支配更早元素，只保留未过期、未被支配的下标 |
| 实际保存什么 | 双端队列保存候选下标；下标递增，对应值严格递减 |
| 状态何时变化 | 左边界推进时从队首删过期项，新元素到来时从队尾删被支配项并入队 |
| 答案何时产生 | 每个完整窗口状态恢复后，由队首对应值产生 |
| 核心不变量 | 候选全部有效；下标递增；值严格递减；被删元素都有更晚且不小的代表 |
| 时间复杂度 | `O(n)`，每个下标最多入队一次、出队一次 |
| 额外空间复杂度 | `O(k)`，不计返回数组 |

四句建模结论：

```text
我正在处理的对象是：按下标从左到右进入固定窗口的数组元素。
我必须持续保存的是：仍未过期且没有被更晚不小元素支配的候选下标。
当左边界推进或新元素到来时，我执行：从队首清理过期候选，从队尾清理被支配候选，再加入当前下标。
答案在每个完整窗口的不变量恢复后由队首下标对应的数组值计算出来。
```

泛用模板可以压缩为六步：

```text
1. 明确对象的有效区间和过期边界。
2. 定义什么样的新对象能永久支配旧对象。
3. 用一端按时间清理过期对象。
4. 用另一端按支配关系清理弱候选。
5. 加入新对象并恢复候选顺序不变量。
6. 在范围完整时从最强候选一端产生结果。
```

迁移变式：

- **固定窗口最小值**：变化的是支配条件和值顺序。新值不大于旧值时删除队尾，候选值保持严格递增，结果时机不变。
- **同时求窗口最大值和最小值**：条件和结果扩展。分别维护递减候选与递增候选，窗口完整时同时读取两个队首。
- **窗口左右边界都可按规则移动**：过期条件变化。只要下标一旦离开就不会重新进入，仍可用实际 `left` 清理队首；若边界会回退，生命周期单向性消失，模型不能直接套用。
- **1438. 绝对差不超过限制的最长连续子数组**：结果从“每个固定窗口的极值”变为“最长合法窗口”。维护最大与最小两个候选队列，右端加入后若差值超限就移动左端，答案在窗口恢复合法后更新。
- **862. 和至少为 K 的最短子数组**：仍有双端支配淘汰，但对象改为前缀和下标，支配条件和结果时机完全不同。不能因为都叫单调队列就照搬本题比较式。

最终应记住的不是一段 `Deque` 模板，而是两问：旧对象什么时候因位置过期，新对象在什么条件下能同时拥有“结果不差”和“寿命更长”两个优势。只有能证明这两类删除，候选压缩才成立。
