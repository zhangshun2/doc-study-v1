这道题真正值得学习的，不是记住“区间题先排序”，而是回答下面几个更基础的问题：输入为什么一乱序就很难做；排序究竟消除了哪一种不确定性；为什么扫描时只比较当前合并块，而不用回头检查全部结果；什么时候一个块已经确定，再也不会被未来区间改变；`[1,4]` 与 `[4,5]` 为什么必须合并；Java 中直接复用 `int[]` 又会带来什么对象共享问题。

本文不会把“排序 + 扫描”当作一个从天而降的模板。我们会先建立一个一定正确但反复比较的模型，看清浪费，再主动寻找一种顺序，使过去可以被永久封口。最后得到的模型不仅适用于本题，也适用于会议时间、日志时间段、道路施工里程、资源占用窗口等一维区间归并问题。

## 2. 完整题目

给定一个二维整数数组 `intervals`。每一行 `intervals[i] = [start_i, end_i]` 表示一个**闭区间**：它覆盖从 `start_i` 到 `end_i` 的全部位置，并且两个端点都包含在区间中。

需要把所有存在重叠的区间合并，返回一个新的区间数组。返回结果必须满足两个条件：

1. 结果中的区间两两不重叠。
2. 结果覆盖的位置与输入全部区间覆盖的位置完全相同，不能漏掉，也不能跨过空白区域多覆盖。

输入区间不保证有序，输出只要表达正确的合并结果即可。下面的推荐实现会按左端点升序返回结果。

### 示例 1：普通重叠与多个独立块

```text
输入：intervals = [[1,3],[2,6],[8,10],[15,18]]
输出：[[1,6],[8,10],[15,18]]
```

`[1,3]` 与 `[2,6]` 共同覆盖一段连续区域，因此合成 `[1,6]`。`[8,10]` 与前一块之间存在空白，`[15,18]` 也与其他区间分离，所以它们各自保留。

### 示例 2：端点相接也算重叠

```text
输入：intervals = [[1,4],[4,5]]
输出：[[1,5]]
```

两个闭区间都包含位置 `4`，交集不是空集，所以它们重叠。判断条件必须允许 `nextStart == currentEnd`。

### 示例 3：输入乱序

```text
输入：intervals = [[4,7],[1,4]]
输出：[[1,7]]
```

数组中的先后顺序不代表数轴上的左右顺序。虽然 `[4,7]` 先出现，仍要看实际端点；它与 `[1,4]` 在位置 `4` 相接。

### 示例 4：完全包含

```text
输入：intervals = [[1,10],[2,3],[4,8]]
输出：[[1,10]]
```

后两个区间都被 `[1,10]` 包含。合并时右端点不能无条件改成下一个区间的右端点，否则会把当前覆盖范围错误缩短。

### 约束、提示与 Java 入口

- `1 <= intervals.length <= 10^4`。
- `intervals[i].length == 2`。
- `0 <= start_i <= end_i <= 10^4`。
- 题目没有额外算法提示。
- Java 方法入口为：

```java
public int[][] merge(int[][] intervals)
```

`intervals.length` 最多为 `10^4`，说明平方级乃至立方级的反复配对不适合作为提交方案。端点上限也是 `10^4`，确实允许设计固定坐标轴标记法，但那会依赖值域；区间排序模型只依赖区间个数，更容易迁移到端点很大、为负数或为时间戳的场景。题目保证至少有一个区间，所以 LeetCode 入口可以直接用排序后的第一行初始化当前块。

## 3. 先把题目说成人话

### 一句话生活化复述

桌上有许多长短不一、摆放顺序混乱的透明胶带，它们贴在同一条刻度线上；把彼此接触或覆盖的胶带看成一整段，最后报告所有连续覆盖区域。

### 一句话关系化复述

把若干闭区间按“交集非空”连接起来，求每个重叠连通组的最小左端点和最大右端点。

先不用公式，看三个具体区间：

```text
数轴方向：从小到大  ------------------------------------------>

[1,4]：       1==========4
[3,7]：             3==============7
[9,10]：                                   9====10

前两段在 [3,4] 上共同覆盖，合并为：
[1,7]：       1======================7

[7,9] 之间有空白，所以 [9,10] 不能并入 [1,7]。
最终覆盖：    [1====================7]  [9====10]
```

对任意两个闭区间 `[a,b]` 与 `[c,d]`，它们重叠等价于较大的左端点不超过较小的右端点，也就是 `max(a,c) <= min(b,d)`。但是如果先按左端点排序，并且当前合并块是 `[currentStart,currentEnd]`，那么下一个区间的左端点 `nextStart` 已经不会小于 `currentStart`。此时判断可以简化为 `nextStart <= currentEnd`。这个简化不是背出来的技巧，而是排序替我们消除了一半方向的不确定性。

| 要素 | 本题中的含义 |
| --- | --- |
| 对象 | 一维数轴上的闭区间；扫描后真正维护的是若干输入区间的并集块 |
| 关系 | 两段是否有共同覆盖点；重叠关系还能通过区间链传递成同一个合并组 |
| 方向 | 原输入没有空间方向；按左端点排序后，从数轴左侧向右侧处理 |
| 目标 | 返回覆盖范围完全相同、彼此不重叠的最大连续块 |
| 限制 | 端点相接算重叠；不能跨过真实空白；输入行顺序不可信 |

这里还有一个容易忽略的“间接关系”：`[1,2]` 与 `[3,4]` 不重叠，但若中间还有 `[2,3]`，三者最终会合成 `[1,4]`。因此不能只记住输入中最初看到的两两关系；合并会扩大当前覆盖范围，扩大后的范围可能继续吸收后面的区间。

> **小白追问：** 第一段和第三段明明不重叠，为什么最后还能进入同一个结果？
>
> **先给短答：** 题目合并的是整组区间形成的连续覆盖，不要求组内任意两段都直接重叠。
>
> **最小例子：** `[1,2]` 先与 `[2,3]` 合成 `[1,3]`，扩大的 `[1,3]` 再与 `[3,4]` 相接，于是得到 `[1,4]`。
>
> **回到模型/代码：** `currentEnd` 保存整组目前能到达的最远终点。后续区间与更新后的 `currentEnd` 比较，而不是只与组内第一段的终点比较。

## 4. 第一切入点：读题时先看什么

第一次读题，先圈出四个真正决定模型的词。

1. **区间**：对象不是孤立数字，而是带左、右边界的一段连续覆盖。一次操作可能改变整段的边界。
2. **重叠**：核心关系是交集是否为空。由于区间是闭区间，相等端点也属于交集。
3. **合并所有**：重叠可能形成链，不能只做一轮固定配对；合并后的新区间仍可能与其他区间重叠。
4. **恰好覆盖**：不能为了减少区间数量跨过空白。例如 `[1,2]` 与 `[3,4]` 不能合成 `[1,4]`，因为那会新增 `(2,3)` 这段原本没有的覆盖。

“数组”“二维整数”先看成数据载体即可。第一分钟更重要的是问：这些区间在数轴上的先后是否与输入顺序一致？答案是否定的。只要顺序混乱，一个刚读到的区间既可能落在已有区间左边，也可能落在右边，还可能把两个旧块桥接起来。这正是难点来源。

用最小样例 `[[4,7],[1,4]]` 手工处理时，人通常不会忠于数组顺序，而会先在脑中把 `[1,4]` 放到左边：

```text
输入顺序： [4,7]  [1,4]
空间顺序： [1,4]  [4,7]
观察交点：          4
合并结果： [1,7]
```

这一步很有价值：人工已经自发地把“无序集合问题”改造成“从左到右扫描问题”。算法中的排序，就是把这个隐含动作显式化。

数据规模 `n <= 10^4` 给出的性能信号是：`O(n log n)` 通常合适，`O(n^2)` 在最坏情况下要做约一亿次比较，风险很高，反复重启扫描的 `O(n^3)` 更不可接受。端点值域较小是可利用条件，但不是必须依赖的条件。

## 5. 最直接的人工或暴力模型

先不考虑效率，可以严格照“看见任意一对重叠就揉成一段”的人工动作实现：

```text
把所有输入区间复制到一个可修改列表中

重复执行：
    从头检查列表中的每一对区间
    如果找到一对重叠区间：
        用两者较小的左端点和较大的右端点生成并集区间
        删除原来的两段，加入并集区间
        从头重新检查，因为新区间可能产生新的重叠
    如果完整检查一轮都没有找到重叠：
        停止

返回列表中的全部区间
```

判断任意两段是否重叠，可以先判断它们是否完全分离：`firstEnd < secondStart` 或 `secondEnd < firstStart`。只要两个“完全分离”条件都不成立，它们就重叠。注意这里使用严格小于，因为端点相等时不是分离。

这个模型虽然慢，但一定正确。每次替换都把两个有交集的闭区间换成它们的并集，覆盖范围没有增加也没有减少；列表长度减少一。当再也找不到重叠对时，列表已经两两不重叠，同时仍然覆盖输入原有的全部位置，所以满足题目要求。间接连接也不会漏掉，因为每次合成的新区间会重新参与下一轮比较。

设 `n` 为输入区间数。一次完整配对最多检查约 `n(n-1)/2` 对；最坏情况下每轮只发现一次合并，然后重启，最多发生 `n-1` 次合并。因此这个具体的“找到一对就重启”实现最坏可达 `O(n^3)`。使用列表保存当前区间，工作空间和结果规模都是 `O(n)`。动态数组删除产生的移动总成本至多再贡献平方级，不改变这里的立方级上界。

暴力模型的价值不在提交，而在建立正确性基线：优化后的方案仍必须完成同样的“发现重叠组并取边界”工作，只是要避免反复询问任意两段之间的关系。

## 6. 暴力到底浪费在哪里

观察这个刻意打乱的输入：

```text
[[1,4], [10,12], [3,8], [7,11]]
```

它们实际上通过重叠链连成一个块 `[1,12]`。暴力过程可能如下：

```text
第 1 轮：
    比较 [1,4] 与 [10,12] -> 不重叠
    比较 [1,4] 与 [3,8]   -> 重叠
    合成 [1,8]，旧结论全部放下，从头重启

第 2 轮：
    比较 [1,8] 与 [10,12] -> 仍不重叠
    比较 [1,8] 与 [7,11]  -> 重叠
    合成 [1,11]，再次从头重启

第 3 轮：
    比较 [1,11] 与 [10,12] -> 现在重叠
    合成 [1,12]，再次重启

第 4 轮：
    完整扫描，确认没有第二段后结束
```

浪费有三层：

- `[1,4]`、`[1,8]`、`[1,11]` 都是在描述同一个不断扩大的连通块，但每次扩张后，程序没有保留“数轴上哪些区间已经在左侧处理完”的秩序，只能重新询问。
- `[10,12]` 被反复比较。前两次“不重叠”并不是永久结论，因为另一侧的块还可能向右扩大。
- 中间结果 `[1,8]` 和 `[1,11]` 刚算完就被替换。它们真正有价值的信息只是当前块的最左端和最右端，不需要把合并历史保留下来。

如果输入预先按左端点排列，会变成：

```text
[1,4] -> [3,8] -> [7,11] -> [10,12]
```

这时当前块只会向右扩张：`[1,4] -> [1,8] -> [1,11] -> [1,12]`。一个区间不需要回头与任意旧区间比较，旧区间也不需要主动寻找未知未来。

因此本题的优化目标可以写成一句具体的话：

> 不要在每次合并后重新检查所有区间对；先建立从左到右的确定顺序，再让每个新区间只更新唯一一个尚未封口的合并块。

## 7. 容易想到但走不通的方向

### 方向一：按输入顺序，只与上一个区间比较

这是最自然的第一反应，因为许多相邻元素问题都能这样处理。它能保存“刚才看过的区间”，却没有保存数轴上的真实相邻关系。

```text
输入： [1,3]  [8,10]  [2,6]

按输入相邻比较：
[1,3] 与 [8,10] 不重叠
[8,10] 与 [2,6] 不重叠

但真实数轴：
[1,3] 与 [2,6] 重叠，应得到 [1,6]
```

如果只与结果列表最后一段比较，读到 `[2,6]` 时最后一段是 `[8,10]`，仍会漏掉它与更早 `[1,3]` 的关系。这个方向是逻辑错误，不只是慢。失败带来的新条件是：在做局部相邻比较以前，必须先让数组相邻关系反映数轴相邻关系。

> **小白追问：** 原输入也能用 `for` 从左到右走，为什么不能直接一遍合并？
>
> **先给短答：** `for` 的方向只是数组下标方向；乱序输入的下一行不一定是数轴上的下一段。
>
> **最小例子：** 对 `[1,3]、[8,10]、[2,6]`，第二段让程序以为 `[1,3]` 已经结束，第三段却从左侧回来并与 `[1,3]` 重叠。若旧块已经输出，一遍扫描无法安全补救。
>
> **回到模型/代码：** 只有执行按起点排序后，`index` 增大才同时表示“处理位置向右”。这时 `merged` 中的块才能一经输出就不再回查。

### 方向二：建立“区间重叠图”再找连通分量

把每个区间看作节点，任意两段重叠就连边，然后用 DFS、BFS 或并查集找到连通分量；每个分量取最小起点与最大终点。这个模型是正确的，也能自然表达重叠链。

问题在于它先检查所有区间对来建边，时间与边数量最坏都是 `O(n^2)`；还额外引入图、访问状态或并查集。它保存了“谁直接与谁重叠”的完整历史，但本题只需要每个连通覆盖块的两个边界。失败点不是正确性，而是状态过多、代价过高。它提醒我们：如果对象具有一维顺序，通常应先利用顺序压缩关系，而不是把所有关系显式建图。

### 方向三：按坐标逐点标记覆盖

本题端点都在 `0` 到 `10^4`，所以可以把数轴离散成固定数组，标出每段覆盖，再从左到右恢复连续区域。这在当前约束下有机会做成正确方案，但有两个陷阱。

第一，简单标记整数点会混淆 `[1,2]` 与 `[3,4]`：整数 `2` 和 `3` 相邻，不代表两个实数闭区间重叠。需要把坐标放大或同时表示点与点之间的缝隙。第二，若端点改成 `10^9`、负数、长整型时间戳或小数，固定坐标轴立即失去通用性。这个方向不是绝对错误，而是强依赖值域且表达更绕。它提示我们优先寻找只依赖区间数量 `n` 的模型。

### 为什么本文不按终点升序直接扫描

终点排序并非在所有区间算法中都无用。选择最多互不重叠区间时，较早结束很重要；从右向左建立对称模型时，也可以设计另一套边界状态。但若按终点升序后，仍照搬本文“遇到空隙就立刻输出当前块”的从左到右流程，结论并不安全。

> **小白追问：** 所有区间按终点也有顺序，为什么不能用相同代码一遍合并？
>
> **先给短答：** 终点递增只限制未来的右边界，不能阻止未来区间的起点重新回到左边并连接旧块。
>
> **最小例子：** 按终点升序为 `[1,2]、[4,5]、[2,10]`。看到 `[4,5]` 时若输出 `[1,2]`，之后的 `[2,10]` 又会同时连接 `[1,2]` 和 `[4,5]`，说明刚才封口过早。
>
> **回到模型/代码：** `nextStart > currentEnd` 能成为永久结论，依赖未来的 `start` 不再减小。因此当前状态机必须按起点排序；换排序键就必须重新推导不变量，不能只改比较器。

### 方向四：排序后把右端点直接改成 `nextEnd`

看到重叠后写 `currentEnd = nextEnd` 很顺手，但包含关系会让当前块缩短：

```text
当前块：[1,10]
下一段：[2,3]
错误更新后：[1,3]
```

后续 `[8,12]` 原本应该与 `[1,10]` 合并，却会被错误状态拒绝。这个方向缺少的建模条件是：当前块表示所有已吸收区间的**并集**，右边界只能保持或扩大，不能后退，因此必须取 `max(currentEnd, nextEnd)`。

## 8. 关键视角转换

优化并不是把双重循环机械换成排序，而是先改变“哪些结论能够永久确定”。

| 转换前 | 转换后 |
| --- | --- |
| 输入顺序与空间位置无关，新区间可能从左侧或右侧影响旧结果 | 按左端点排序后，未来区间的起点只会保持或向右移动 |
| 反复询问任意两个区间是否重叠 | 只询问下一段能否接入当前未封口块 |
| 每次合并后担心新区间又碰到任意旧区间 | 当前块吸收所有连续重叠；更早结果已经跨过空隙并永久封口 |
| 保存许多两两重叠关系 | 只保存当前块的 `currentStart` 和 `currentEnd` |
| “合并”是反复修改集合 | “合并”变成一次从左到右的状态机：扩张或封口 |

排序后的关键变化可以画成：

```text
未来方向： -------------------------------------------------->

已经封口的结果       当前未封口块             尚未处理区间
[1,3] [5,7]          [10,15]                  [nextStart,nextEnd] ...
                        ^
                        未来唯一可能继续改变的块
```

为什么未来只可能影响当前块？因为下一个区间以及它后面的所有区间，左端点都不小于 `nextStart`。如果 `nextStart > currentEnd`，已经出现一个确定空隙；更未来的起点只会更大，不可能跨回空隙左侧。当前块就可以永久输出。如果 `nextStart <= currentEnd`，下一段与当前块有共同点，吸收它并把右端扩到两者最大值即可。

排序付出 `O(n log n)`，换来的是一种**可封口性**：扫描过某个正空隙后，左边的答案不再受未来影响。线性扫描之所以成立，真正依赖的不是“数组有序”这四个字，而是有序带来的永久结论。

> **小白追问：** 为什么按起点排序以后，只看相邻到来的区间就足以发现所有潜在重叠？
>
> **先给短答：** 排序把所有可能向左连接当前块的区间提前了；当前块右侧第一次出现空隙后，剩余起点只会更大。
>
> **最小例子：** 排序后为 `[1,4]、[3,8]、[7,9]`。第二段先把当前块扩成 `[1,8]`，第三段虽然不与最初的 `[1,4]` 重叠，却与当前块相交并被继续吸收。
>
> **回到模型/代码：** 循环每次比较 `nextStart` 与不断更新的 `currentEnd`。这里的“相邻事件”是下一段与整个当前块相邻，不是只比较两条原始数组行。

## 9. 正式建立模型

| 建模项 | 本题结论 |
| --- | --- |
| 对象 | 按左端点排序后的闭区间，以及它们形成的当前连续覆盖块 |
| 关系 | `nextStart <= currentEnd` 时，下一段与当前块重叠或端点相接 |
| 状态 | 已永久封口的结果列表，加上唯一未封口块的 `currentStart`、`currentEnd` |
| 事件 | 读取排序后的下一个区间 `[nextStart,nextEnd]` |
| 不变量 | 已输出块正确、有序、互不重叠；当前块精确覆盖已处理区间最右侧的重叠连通组，并且是唯一可能被未来扩张的块 |
| 结果时机 | 遇到 `nextStart > currentEnd` 时输出当前块；遍历结束后再输出最后一个当前块 |

### 为什么两个整数就是足够的最小状态

当前块可能由十几个原区间合并而来，但未来只会问两个问题：下一区间的起点是否落在当前覆盖终点以内；若能接入，合并后的最右端在哪里。回答它们只需要 `currentStart` 与 `currentEnd`。原区间是谁、按什么顺序被吸收、两两交集各有多长，都不会改变未来决策。

`currentStart` 也不会在扫描中改变。排序保证当前块从该重叠组最小的左端点开始，后来的 `nextStart` 不会更小。`currentEnd` 则必须表示已吸收区间右端点的最大值，所以它单调不减。两个整数没有保存多余历史，但完整保留了未来决策所需的信息。

> **小白追问：** `currentStart/currentEnd` 到底代表刚读过的一个区间，还是代表已经合并出的结果？
>
> **先给短答：** 它们代表所有已处理且仍与最右侧连续覆盖相连的区间的并集，还不是已经输出的最终结果。
>
> **最小例子：** 依次读 `[1,4]` 和 `[2,8]` 后，`current` 是 `[1,8]`。它既不等于第一段，也不等于第二段，而是两段共同形成的覆盖块。
>
> **回到模型/代码：** 每轮开始前，`currentStart` 是这一组最小起点，`currentEnd` 是这一组最大终点。只有进入 `else` 或遍历结束时，这两个值才被复制进 `merged`。

### 为什么旧结果可以永久丢出候选集

假设当前块 `[L,R]` 因 `nextStart > R` 被封口。排序保证所有未来区间的起点都大于等于 `nextStart`，于是也都大于 `R`。它们与 `[L,R]` 之间永远存在空隙，之后无论右端点多大，都不能向左跨过自己的起点来覆盖该空隙。因此 `[L,R]` 以后不需要再参与任何判断。

更早输出的块更不需要比较：它们在此前就已经遇到过空隙，右端点比当前块的左端点还小。扫描时只比较当前块，实际上是在利用一串已经证明过的永久分离关系。

> **小白追问：** 为什么重叠条件是 `nextStart <= currentEnd`，等号也要进入合并分支？
>
> **先给短答：** 本题给的是闭区间，左右端点都属于区间；两个边界相等时，它们共享这个点。
>
> **最小例子：** `[1,4]` 包含点 `4`，`[4,5]` 也包含点 `4`。若使用严格小于，它们会被错误输出成两个仍然重叠的结果。
>
> **回到模型/代码：** `if (nextStart <= currentEnd)` 中的等号来自题目语义，不是代码习惯。若题目改为开区间，是否保留等号必须重新判断。

> **小白追问：** 已经知道两段重叠，为什么不能直接把 `currentEnd` 赋成 `nextEnd`？
>
> **先给短答：** 下一段可能完全藏在当前块里面，直接赋值会把已经覆盖的右侧错误删掉。
>
> **最小例子：** 当前块 `[1,10]` 吸收 `[2,3]` 后仍应是 `[1,10]`；若写成 `currentEnd=3`，后来的 `[8,12]` 会被误判为不重叠。
>
> **回到模型/代码：** `currentEnd = Math.max(currentEnd, nextEnd)` 保证它始终是已吸收区间的最大终点，也保证同一块内部的右边界只保持或扩大。

### 相等端点、相同起点与重复区间

- `nextStart == currentEnd`：两个闭区间共享该端点，进入合并分支。
- 多个区间起点相同：它们排序后的相对顺序不影响正确性，`max` 最终保留最大的右端点。
- 完全重复区间：第二段被当前块吸收，边界不变。
- 被包含区间：`nextEnd <= currentEnd`，当前块不变化，但该区间已经被覆盖，不需要另存。
- 零长度区间 `[x,x]`：它表示单个点。若当前块包含 `x` 就合并，否则形成独立块。

遍历方向选择从左到右，是因为左端点排序使“未来不会回头”成立。也可以设计按右端点排序的其他状态，但需要重新维护左边界，无法直接沿用当前块左端已确定的简单不变量。

## 10. 所需数据结构详解

本题不需要栈、队列、哈希表或树。真正需要的是排序后的二维数组、两个边界变量和一个只在尾部追加的结果列表。结构简单不代表无需理解；尤其在 Java 中，`int[][]` 的对象关系会直接决定是否修改输入。

### 10.1 `int[][]`：外层数组保存的是行引用

Java 的 `int[][] intervals` 可以理解为：外层数组的每个位置保存一个 `int[]` 引用，每个内部 `int[]` 再保存起点和终点。

```text
intervals 外层数组
下标 0  ----->  int[] {8, 10}
下标 1  ----->  int[] {1,  3}
下标 2  ----->  int[] {2,  6}
```

执行 `Arrays.sort(intervals, comparator)` 时，主要变化是外层数组中的行引用顺序：

```text
排序后
下标 0  ----->  原来的 int[] {1,  3}
下标 1  ----->  原来的 int[] {2,  6}
下标 2  ----->  原来的 int[] {8, 10}
```

因此，排序会改变调用方看到的输入行顺序，但不会自动复制或修改每行的两个端点。本题用 `interval[0]` 和 `interval[1]` 进行 `O(1)` 随机访问。外层数组最坏保存 `n` 个行引用，每行固定保存两个整数。

### 10.2 排序：把空间先后变成数组先后

本题使用 `Arrays.sort(intervals, (a, b) -> Integer.compare(a[0], b[0]))`，比较键是每行的左端点。一次比较读取两个起点，成本为 `O(1)`；比较排序总体需要 `O(n log n)` 时间。

只按左端点排序已经足够。起点相同的区间无论谁在前，连续执行 `currentEnd = max(currentEnd, nextEnd)` 都得到相同最大右端点。也可以再按右端点排序，但那不是正确性必需条件。

使用 `Integer.compare(a[0], b[0])` 比 `a[0] - b[0]` 更稳妥，因为后者在一般大整数场景可能溢出。本题端点范围不会触发该溢出，但可迁移骨架不应依赖这个偶然约束。

Oracle Java 17 文档说明对象数组的比较器排序是稳定的，并提供 `O(n log n)` 级别性能；具体实现可以使用临时引用数组。因此“对输入外层数组原地排序”不等于“排序额外空间必然是 `O(1)`”。复杂度一节会分别说明抽象模型与这份 Java 实现。

### 10.3 两个整数：唯一未封口块

`currentStart` 和 `currentEnd` 不是随手写的临时变量，而是算法最核心的状态容器：

| 状态 | 含义 | 允许的变化 |
| --- | --- | --- |
| `currentStart` | 当前重叠连通组的最小左端点 | 初始化或开始新区块时改变；块内合并时不变 |
| `currentEnd` | 当前组所有已处理区间右端点的最大值 | 重叠时保持或增大；开始新区块时重置 |

每次读取下一区间只做常数次比较与赋值，时间 `O(1)`，额外空间 `O(1)`。

### 10.4 `ArrayList<int[]>`：只追加已经确定的答案

结果块数量事先未知，最少可能是 `1`，最多可能是 `n`，所以使用动态数组 `ArrayList`。本题只需要尾部 `add`，单次追加均摊 `O(1)`；不在列表中间插入、删除，也不需要按键查询。扫描结束后用 `toArray` 生成题目要求的 `int[][]`。

最坏情况下所有区间互不重叠，列表保存 `n` 个行引用和 `n` 个新建的二元素数组。链表也能尾部追加，但每个节点有额外对象和指针，连续遍历的局部性也较差；栈、队列不能提供额外价值；平衡树或优先队列会重复承担已经由排序完成的有序化工作。

### 10.5 为什么输出时新建 `int[]`

有些短实现会让 `current` 直接引用 `intervals[0]`，重叠时执行 `current[1] = max(...)`，最后把该引用加入结果。这能通过题目，但有两个副作用：

1. 修改 `current[1]` 会改动输入中的某个内部数组。
2. 返回结果与输入共享内部 `int[]`；调用方之后修改任一方，另一方也可能变化。

本文实现用两个整数维护当前块，在封口时执行 `new int[] {currentStart, currentEnd}`。这样返回的每个内部数组都是新对象，不与输入行共享。`merged.toArray(...)` 只复制这些新对象的引用到新的外层数组，并不会再次深复制；由于这些行本来就是本方法创建且之后不再修改的，这种共享位于方法自己的结果结构内部，是可控的。

需要诚实说明：本文 LeetCode 实现仍会通过 `Arrays.sort` 改变输入的**行顺序**。若业务接口要求输入在任何层面都不变，应先复制外层数组再排序；因为算法不修改内部端点，只需复制外层引用即可阻止行顺序变化。如果后续实现准备修改内部行，则必须进一步深复制每个 `int[]`。

> **小白追问：** `Arrays.copyOf(intervals, intervals.length)` 已经复制了数组，为什么还说它不是深复制？
>
> **先给短答：** 它只新建外层引用数组，里面每个位置仍指向原来的 `int[]` 行对象。
>
> **最小例子：** 复制后交换两行，只改变副本的行顺序；但执行 `copy[0][1]=99` 会修改那一行对象，原数组中指向同一行的位置也会看到 `99`。
>
> **回到模型/代码：** 泛用骨架只排序并读取端点，所以浅复制足够保护输入顺序。若改成通过 `current[1]` 写端点，就要逐行复制，或像本文一样用两个整数并在输出时新建行。

## 11. 生活化类比及边界

把问题想成“整理一条公路上的施工封闭通知”。每张通知写着封闭里程 `[start,end]`。管理人员要发布一份简洁清单：连续封闭的路段只发布一次，中间确实开放的路段不能被误报为封闭。

一开始，通知按到达办公室的时间堆放，无法直接逐张合并，因为晚收到的通知可能属于公路更左侧。先按起始里程排序，管理人员就能从公路左端向右走，并在手里维护一张“尚未盖章”的当前通知。

| 生活对象或动作 | 算法中的对应物 |
| --- | --- |
| 一张施工通知 `[起点,终点]` | 一个输入闭区间 `[start,end]` |
| 按起始里程排列通知 | 按区间左端点升序排序 |
| 手里尚未盖章的通知 | `currentStart`、`currentEnd` 表示的当前合并块 |
| 新通知在当前封闭终点之前或恰好从终点开始 | `nextStart <= currentEnd`，与当前块有共同覆盖点 |
| 延长手中通知的终点 | `currentEnd = max(currentEnd, nextEnd)` |
| 新通知从更远处开始，中间存在开放路段 | `nextStart > currentEnd`，当前块可以封口 |
| 盖章并放入发布清单 | 新建 `int[]` 并追加到 `merged` |
| 全部通知看完后盖最后一章 | 循环结束后补充输出当前块 |

这个类比最有用的地方，是说明“为什么只拿一张未盖章通知”：排序以后，已经盖章的路段都在左边，并且盖章前确认过它与下一段之间有空隙；后来的通知起点只会更靠右，所以不可能要求拆章重做。

### 类比到哪里为止

现实中的道路通知可能还包含方向、车道、日期、施工类型和开闭端点。两张里程相同但日期不同的通知未必能合并；现实里“恰好相接”也可能因测量精度有特殊规则。本题只有一维整数闭区间，没有其他属性，端点相等明确算重叠。这个故事帮助理解状态变化，但正确性仍由“左端点有序”和“不变量”保证，不能用现实经验替代题目契约。

## 12. 典型输入的完整数据变化图

选择一个同时包含乱序、普通重叠、端点相接、空隙和后段扩张的输入：

```text
输入：[[8,10],[1,3],[17,20],[2,6],[15,18],[6,7]]
```

### 第一步：排序建立方向

```text
原下标：       0       1        2        3         4       5
原区间：    [8,10]  [1,3]  [17,20]   [2,6]   [15,18]  [6,7]

按 start 升序
扫描下标：     0       1       2       3         4         5
排序区间：   [1,3]   [2,6]   [6,7]  [8,10]   [15,18]   [17,20]
扫描方向：     ------------------------------------------------>
```

数轴上的覆盖关系是：

```text
[1,3] 与 [2,6] 重叠，[2,6] 与 [6,7] 在 6 相接
    [1================7]

                         [8====10]

                                         [15=========20]
```

### 第二步：逐个维护当前块

| 步骤 | 当前输入 | 处理前状态 | 判断依据 | 执行动作 | 处理后状态 | 新增结果 |
| ---: | --- | --- | --- | --- | --- | --- |
| 初始化 | `[1,3]` | 当前块为空 | 第一段一定属于第一个块 | 用它初始化 | 当前块 `[1,3]` | `[]` |
| 1 | `[2,6]` | 当前块 `[1,3]` | `2 <= 3`，重叠 | 右端取 `max(3,6)` | 当前块 `[1,6]` | `[]` |
| 2 | `[6,7]` | 当前块 `[1,6]` | `6 <= 6`，端点相接 | 右端取 `max(6,7)` | 当前块 `[1,7]` | `[]` |
| 3 | `[8,10]` | 当前块 `[1,7]` | `8 > 7`，出现空隙 | 输出旧块，以新区间重置 | 当前块 `[8,10]` | `[[1,7]]` |
| 4 | `[15,18]` | 当前块 `[8,10]` | `15 > 10`，出现空隙 | 输出旧块，以新区间重置 | 当前块 `[15,18]` | `[[1,7],[8,10]]` |
| 5 | `[17,20]` | 当前块 `[15,18]` | `17 <= 18`，重叠 | 右端取 `max(18,20)` | 当前块 `[15,20]` | `[[1,7],[8,10]]` |
| 收尾 | 无 | 当前块 `[15,20]` | 没有下一区间触发封口 | 主动输出最后一块 | 无未封口块 | `[[1,7],[8,10],[15,20]]` |

把最关键的三次状态变化展开来看：

```text
快照 A：普通重叠
当前输入：    [2,6]
处理前状态：  current = [1,3]
判断依据：    nextStart=2 <= currentEnd=3
执行动作：    currentEnd = max(3,6) = 6
处理后状态：  current = [1,6]
新增结果：    无；当前块未来仍可能扩张

数轴：        [1-----3]
                 [2----------6]
合并：        [1-------------6]

快照 B：端点相接
当前输入：    [6,7]
处理前状态：  current = [1,6]
判断依据：    nextStart=6 <= currentEnd=6
执行动作：    currentEnd = max(6,7) = 7
处理后状态：  current = [1,7]
新增结果：    无

数轴：        [1-------------6]
                             [6--7]
共同点：                      6

快照 C：遇到空隙
当前输入：    [8,10]
处理前状态：  current = [1,7]
判断依据：    nextStart=8 > currentEnd=7
执行动作：    输出 [1,7]；current 重置为 [8,10]
处理后状态：  current = [8,10]
新增结果：    [1,7]

数轴：        [1-------------7]   [8----10]
                                     ^
               未来起点都 >= 8，不可能再连接回 7 左侧
```

注意输出不是在每次重叠时产生。重叠只会更新“未封口状态”；看见确定空隙时，才把旧状态变成答案。循环结束没有新的空隙来触发最后一次输出，所以必须显式收尾。

> **小白追问：** 能不能只用三个区间，把“吸收”和“结算”各走一次？
>
> **先给短答：** 前两段制造一次吸收，第三段制造一个不可跨回的空隙，就能看到完整状态机。
>
> **最小例子：** `[1,4] -> [2,8] -> [10,12]`。先令 `current=[1,4]`；因 `2<=4` 吸收成 `[1,8]`；再因 `10>8` 输出 `[1,8]`，并把 `current` 重置为 `[10,12]`；遍历结束再输出它。
>
> **回到模型/代码：** `if` 分支只更新 `currentEnd`，`else` 分支先向 `merged` 追加旧块再重置两个边界，循环后的一次 `add` 负责最后残留块。

## 13. 边界场景的数据变化

### 场景一：端点相接

```text
输入并排序： [1,4] -> [4,5]

初始化：current = [1,4]
读取：  next = [4,5]
判断：  4 <= 4 为 true
更新：  current = [1,max(4,5)] = [1,5]
收尾：  result = [[1,5]]
```

若条件误写为 `nextStart < currentEnd`，这里会输出 `[[1,4],[4,5]]`。两个结果区间仍共享点 `4`，违反“返回不重叠区间”的要求。

### 场景二：完全包含，右端不能后退

```text
排序区间： [1,10] -> [2,3] -> [4,8]

初始化：current = [1,10]
读取 [2,3]：2 <= 10，currentEnd = max(10,3) = 10
读取 [4,8]：4 <= 10，currentEnd = max(10,8) = 10
收尾：result = [[1,10]]
```

两个被包含区间都被处理，但状态无需变化。它们的生命周期到比较完成即结束，因为当前块已经完整覆盖它们。

> **小白追问：** 被完全包含的区间没有让变量变化，算法是不是等于没处理它？
>
> **先给短答：** “处理”不等于必须改值；确认它的覆盖已经包含在当前状态中，就是这一步的结论。
>
> **最小例子：** `current=[1,10]`，下一段 `[2,3]` 满足重叠，但 `max(10,3)=10`。当前块不变，却已经完整代表两段的并集。
>
> **回到模型/代码：** 该区间仍执行了条件判断和 `Math.max`。它不单独加入 `merged`，因为那会制造一个与当前块重叠的冗余结果。

### 场景三：只有一个零长度区间

```text
输入：[[5,5]]
排序后：[[5,5]]
初始化：current = [5,5]
for 循环：不执行，因为没有下一个区间
收尾：加入 [5,5]
结果：[[5,5]]
```

题目保证 `n >= 1`，所以访问 `intervals[0]` 不会越界。即使循环完全不执行，收尾动作仍会产生唯一答案。`[5,5]` 不是空区间，而是包含点 `5` 的闭区间。

### 场景四：全部互不重叠

```text
排序区间： [1,2] -> [3,4] -> [7,8]

[1,2] 遇到 [3,4]：3 > 2，输出 [1,2]
[3,4] 遇到 [7,8]：7 > 4，输出 [3,4]
遍历结束：输出 [7,8]

最终没有未处理区间，当前块也已在收尾时输出。
```

注意 `[1,2]` 与 `[3,4]` 在整数点集合上看似“相邻”，仍然没有共同点；闭区间相接要求前一终点与后一开端相等，而不是相差 `1`。

## 14. 正确性与不变量

要证明的不是“代码看起来会合并”，而是：输出恰好是输入覆盖集合的所有最大连续块，没有漏合并，也没有跨空隙误合并。

### 循环不变量

在开始处理每个下一区间以前，始终保持：

1. `merged` 中的区间按左端点有序、两两分离，并且已经永久确定。
2. `merged` 与当前块一起，恰好覆盖所有已经读取的输入区间。
3. 当前块是已读取区间中最右侧的重叠连通组，等于这个组的最小起点到最大终点。
4. 在所有已读取状态中，只有当前块还有可能与尚未读取的区间重叠。

初始化时只读取排序后的第一段。结果列表为空，当前块恰好覆盖该段，也显然是唯一可能被未来改变的块，所以不变量成立。

### 情况一：下一段与当前块重叠

若 `nextStart <= currentEnd`，由于排序还保证 `nextStart >= currentStart`，下一段与当前块至少共享一个点。把右端更新为 `max(currentEnd,nextEnd)`，得到的正是两个闭区间的并集：左端仍是较小的 `currentStart`，右端是较大的终点，中间没有空白。

这个动作不会漏掉更大范围。若下一段伸得更远，`max` 扩大当前块；若下一段被包含，`max` 保留原右端。新区间已经被当前块完整表示，以后不需要单独保存。结果列表没有变化，当前块仍是最右侧唯一开放块，所以不变量继续成立。

### 情况二：下一段与当前块分离

若 `nextStart > currentEnd`，两者之间存在空白。排序保证任何未来区间的起点 `futureStart >= nextStart > currentEnd`。因此未来区间不可能与当前块重叠，也不可能填回这个空隙。现在输出当前块不会过早，之后再无信息能够改变它。

> **小白追问：** 当前区间右端可能很长，未来区间会不会从右边绕回来，把已经输出的旧块重新连接上？
>
> **先给短答：** 区间只能从自己的起点向右覆盖；未来起点已经在空隙右侧，再长的右端也只能继续向右，不能向左补空隙。
>
> **最小例子：** 当前块 `[1,4]`，下一段 `[6,7]`，以后即使出现 `[6,100]`，它也从 `6` 开始，仍不覆盖 `(4,6)`，所以无法连接 `[1,4]`。
>
> **回到模型/代码：** 排序给出 `futureStart >= nextStart`。当 `nextStart > currentEnd` 时，`merged.add([currentStart,currentEnd])` 才安全，随后旧块永远退出候选状态。

为什么不用把下一段与更早结果逐个比较？更早结果早在之前遇到更靠左的空隙时就被封口，它们的右端小于当前块的起点，而 `nextStart` 又不小于当前块的起点。下一段离它们只会更远。把下一段设为新当前块后，已处理覆盖仍然完整，不变量恢复。

### 为什么不会错误跨过空隙

算法只在 `nextStart <= currentEnd` 时合并。这个条件保证两段交集非空；只要 `nextStart > currentEnd` 就立即分块。因此每次合并都不会新增输入未覆盖的间隙，每次分块又保留了真实空隙，输出覆盖与输入覆盖完全一致。

### 为什么不会漏掉间接重叠

设 `[1,2]` 与 `[2,4]` 合并成 `[1,4]`，后面的 `[4,6]` 会与扩大后的 `currentEnd=4` 比较并继续合并。算法比较的不是下一段与“最初那一段”，而是与整个连通组的最远边界。因此任意长度的重叠链都会被逐段吸收。

### 遍历结束为什么完整

每个输入区间恰好被读取一次：它要么扩张当前块，要么触发旧块输出并成为新块。循环中只有“看见下一段前有空隙”才能封口，因此最后一个当前块不会在循环内自然输出；收尾把它加入 `merged` 后，所有输入覆盖都进入结果，且不存在未处理状态。由不变量可知最终结果有序、互不重叠并恰好覆盖输入。

从集合角度看，每个输出都是一个最大的重叠连通块。跨空隙继续合并会多覆盖，拆开同一连通块又会留下仍然重叠或相接的结果，因此该分块正是题目需要的规范化结果。

## 15. 时间与空间复杂度推导

定义：

- `n` 表示输入区间数量。
- `k` 表示最终合并后的区间数量，满足 `1 <= k <= n`。
- 一次区间重叠判断、一次 `min` 或 `max`、一次边界赋值都视为 `O(1)`。
- 返回的 `int[][]` 及其 `k` 个二元素数组属于输出空间；是否把输出空间计入“额外空间”会分别说明。

### 直接模型

“找到一对重叠就合并并重启”的直接模型，在列表还有 `m` 段时，一轮最多检查 `m(m-1)/2 = O(m^2)` 对。一次合并让列表长度减少一，最多进行 `n-1` 次；最后还可能有一轮用于确认已经没有重叠。把这些上界相乘得到 `O(n^3)` 时间。

这不是说所有输入都会达到立方级：全部互不重叠时，只需一轮 `O(n^2)` 检查；许多重叠对很早被发现时，每轮也不会扫描完整列表。但最坏情况可以让程序反复在扫描很久之后才找到下一对，因此提交时必须按 `O(n^3)` 风险评估。

列表最多保存 `n` 段。若复制输入并为并集创建新数组，工作空间为 `O(n)`；最终结果也最多 `O(n)`。元素生命周期上，一段可能在多轮中被重复拿来与许多其他段比较，中间并集也会被删除和重建，这正是时间无法压到线性的原因。

### 排序后维护当前块

1. 排序 `n` 个行引用，需要 `O(n log n)` 时间。
2. 扫描从下标 `1` 到 `n-1`，恰好读取 `n-1` 个区间。每段只做一次起点比较、至多一次 `max` 和一次结果追加，扫描为 `O(n)`。
3. 把 `k` 个结果行引用转换为外层数组需要 `O(k)`。

总时间为：

```text
O(n log n) + O(n) + O(k) = O(n log n)
```

> **小白追问：** 排序后明明还要再扫描，为什么总时间不是 `O(n log n + n)`，甚至更大？
>
> **先给短答：** `O(n log n + n)` 是正确中间式；当 `n` 增大时，`n log n` 不小于同数量级的 `n`，所以总量级写成 `O(n log n)`。
>
> **最小例子：** 把工作看成“约 `n log n` 次排序操作，再做 `n-1` 次扫描判断”。扫描没有套在排序的每一步里面，两者相加而不是相乘。
>
> **回到模型/代码：** `Arrays.sort` 先完整执行，随后只有一个 `for`。因此排序贡献 `O(n log n)`，循环贡献 `O(n)`，不是 `O(n^2)`。

这里没有隐藏的内层循环。每个输入区间的生命周期很清楚：排序后被扫描一次，随后要么被当前块吸收并结束，要么封口旧块后成为新当前块；每个最终块也只被追加一次。`ArrayList.add` 偶尔会扩容并复制已有引用，但按动态数组增长规律，`k` 次尾部追加的总搬移量是 `O(k)`，所以单次追加按均摊 `O(1)` 计算。

> **小白追问：** `ArrayList.add` 有时会搬动很多元素，为什么还能说均摊 `O(1)`？
>
> **先给短答：** 均摊表示把少数扩容的较大成本分摊到许多无需扩容的追加上，不是说每一次都严格是常数成本。
>
> **最小例子：** 容量按倍数增长时，扩到 `2、4、8` 会分别搬 `1、2、4` 个引用；完成约 `8` 次追加，总搬移不到 `8` 的常数倍，而不是每次都搬全部元素。
>
> **回到模型/代码：** `merged` 只在尾部追加，且一个最终块只追加一次，所以全部 `add` 的总成本是 `O(k)`，不会改变总体 `O(n log n)`。

空间要区分三个口径：

- **仅看扫描状态**：两个边界整数和循环变量是 `O(1)`。
- **计入必要输出**：`k` 个二元素数组、结果列表的引用以及返回外层数组为 `O(k)`，最坏 `O(n)`。
- **计入这份 Java 17 排序实现的辅助空间**：`int[][]` 对 Java 来说是对象引用数组，`Arrays.sort(T[], Comparator)` 可以使用线性数量的临时引用，最坏按 `O(n)` 计。因此这份实现的总体额外空间上界写作 `O(n)` 更准确；不能因为它重排了输入外层数组就声称严格 `O(1)`。

若抽象讨论一种具有 `O(1)` 辅助空间的原地比较排序，并且排除返回结果，扫描本身确实只需常数空间；但那不是本文 Java 代码所调用排序库的完整空间画像。

### 泛用模型骨架

下面先给闭区间归并的可迁移骨架。它额外允许空输入，并复制外层数组后再排序，因此不会改变调用方看到的行顺序；它只读取内部端点，不修改输入行。

```java
import java.util.ArrayList;
import java.util.Arrays;
import java.util.List;

class OrderedClosedRangeMerger {
    public static int[][] mergeClosedRanges(int[][] ranges) {
        if (ranges.length == 0) {
            return new int[0][2];
        }

        int[][] orderedRanges = Arrays.copyOf(ranges, ranges.length);
        Arrays.sort(
                orderedRanges,
                (first, second) -> Integer.compare(first[0], second[0]));

        List<int[]> finalizedBlocks = new ArrayList<>();
        int currentStart = orderedRanges[0][0];
        int currentEnd = orderedRanges[0][1];

        for (int index = 1; index < orderedRanges.length; index++) {
            int nextStart = orderedRanges[index][0];
            int nextEnd = orderedRanges[index][1];

            boolean touchesOrOverlaps = nextStart <= currentEnd;
            if (touchesOrOverlaps) {
                currentEnd = Math.max(currentEnd, nextEnd);
            } else {
                finalizedBlocks.add(new int[] {currentStart, currentEnd});
                currentStart = nextStart;
                currentEnd = nextEnd;
            }
        }

        finalizedBlocks.add(new int[] {currentStart, currentEnd});
        return finalizedBlocks.toArray(new int[finalizedBlocks.size()][]);
    }
}
```

这个骨架稳定的语义角色是：`orderedRanges` 提供单向未来，`currentStart/currentEnd` 保存唯一未封口块，`touchesOrOverlaps` 表示“继续扩张还是永久封口”的事件条件，`finalizedBlocks` 只保存以后再也不会改变的块。若题目改成开区间或“不把端点相接视为重叠”，改变的是触发条件；若输入已经按左端有序，则可以省掉排序，但状态机不变。

> **小白追问：** `else` 中为什么必须先保存旧块，再把 `currentStart/currentEnd` 改成新区间？
>
> **先给短答：** 两个变量同一时刻只容纳一个块；若先重置，旧块的边界会被覆盖并永久丢失。
>
> **最小例子：** `current=[1,8]`，`next=[10,12]`。先重置会让变量立刻变成 `[10,12]`，此时再 `add` 只能重复保存新区间，答案 `[1,8]` 消失。
>
> **回到模型/代码：** `else` 的动作顺序是“`finalizedBlocks.add` 结算旧状态，再赋值开启新状态”。这不是语法细节，而是状态交接顺序。

> **小白追问：** 为什么泛用骨架复制输入，而提交版直接排序输入？两份代码的模型不一致吗？
>
> **先给短答：** 合并模型完全一致，区别只是接口副作用：提交版利用题目未要求保留输入顺序，泛用骨架选择更保守的调用约定。
>
> **最小例子：** 输入行顺序是 `[8,10]、[1,3]`。提交版调用后，原外层数组会变成 `[1,3]、[8,10]`；骨架对副本排序，调用方仍看到原顺序，但两者返回结果相同。

### 模型与 Java 代码映射

| 模型角色 | Java 变量或代码块 |
| --- | --- |
| 建立从左到右的单向未来 | `Arrays.sort(... Integer.compare(first[0], second[0]))` |
| 当前输入对象 | `nextStart`、`nextEnd` |
| 唯一未封口状态 | `currentStart`、`currentEnd` |
| 继续吸收的触发条件 | `nextStart <= currentEnd` |
| 扩张当前块 | `currentEnd = Math.max(currentEnd, nextEnd)` |
| 永久封口的触发条件 | `nextStart > currentEnd`，即 `else` 分支 |
| 输出已确定结果 | `merged.add(new int[] {currentStart, currentEnd})` |
| 开始新的未封口块 | 把 `nextStart`、`nextEnd` 赋给当前边界 |
| 最后一个块的结果时机 | 循环后的最后一次 `merged.add` |
| 转换为题目接口 | `merged.toArray(new int[merged.size()][])` |

读代码时不要把重点放在 `for` 循环语法上。真正的控制流程只有两个状态转移：有交集就扩大同一块；出现空隙就封口旧块并开启新块。

## 17. 边界、常见错误与调试观察点

| 层次 | 常见错误 | 具体后果 | 应观察的状态 |
| --- | --- | --- | --- |
| 建模错误 | 不排序，只按输入相邻关系合并 | 乱序输入会漏掉空间上相邻的区间 | 同时打印输入顺序与按起点排序后的顺序 |
| 建模错误 | 每个新区间与所有已输出块继续比较 | 失去“封口后永久确定”的不变量，代码复杂且重复 | 检查输出块是否在 `nextStart > currentEnd` 时才加入 |
| 条件错误 | 使用 `nextStart < currentEnd` | `[1,4]` 与 `[4,5]` 被错误分开 | 打印 `nextStart`、`currentEnd` 和布尔判断 |
| 条件错误 | 用 `nextStart <= nextEnd` 判断 | 这个条件只说明下一段自身合法，不能说明两段重叠 | 判断式左边必须来自下一段起点，右边必须来自当前块终点 |
| 条件错误 | 重叠时直接写 `currentEnd = nextEnd` | 包含区间会让当前块缩短，后续关系判断错误 | 观察 `currentEnd` 是否始终单调不减 |
| 实现错误 | 忘记循环后的最后一次追加 | 最右侧区间或合并块永远丢失 | 循环结束前后分别打印 `current` 与 `merged` |
| 实现错误 | 比较器写成 `first[0] - second[0]` | 通用大整数场景可能溢出并破坏顺序 | 使用 `Integer.compare`，必要时打印排序结果 |
| 实现错误 | 直接修改并返回输入行引用 | 调用方输入端点被改，输出与输入发生别名共享 | 测试合并后再打印原二维数组及引用相等关系 |
| 实现错误 | 误以为 `toArray` 深复制所有行 | 后续修改列表中的内部数组时，返回值也会变化 | 理解外层复制与内部引用复制的区别 |

### 推荐的调试日志

不要只打印最终结果。最有效的是每轮打印一个稳定快照：

```text
index=2, next=[6,7], before=[1,6], action=EXTEND, after=[1,7], merged=[]
index=3, next=[8,10], before=[1,7], action=FINALIZE, after=[8,10], merged=[[1,7]]
```

建议逐项检查：

1. 排序后所有相邻行是否满足 `intervals[i-1][0] <= intervals[i][0]`。
2. 进入每轮前，`currentStart <= currentEnd` 是否成立。
3. 同一个当前块内部，`currentEnd` 是否只增不减。
4. 每当追加结果时，追加块的右端是否严格小于新当前块左端。
5. 循环结束时，最后当前块是否恰好追加一次。

专门准备四类测试最容易定位错误：乱序桥接 `[[1,3],[8,10],[2,6]]`；端点相接 `[[1,4],[4,5]]`；完全包含 `[[1,10],[2,3]]`；单元素 `[[5,5]]`。如果它们分别失败，通常能直接对应到排序、比较符号、`max` 和收尾四个位置。

## 18. 最终模型卡

| 复习项 | 结论 |
| --- | --- |
| 题型识别指纹 | 一组无序一维区间；要求消除重叠并保持覆盖集合不变 |
| 一句话关系模型 | 左端有序后，下一段起点不超过当前块终点就属于同一连续覆盖组 |
| 实际保存什么 | 已封口结果列表，以及唯一未封口块的左右端点 |
| 状态何时变化 | 重叠时扩大右端；出现空隙时输出旧块并用下一段重置 |
| 答案何时产生 | 看到确定空隙时产生一个结果，遍历结束时补最后一个结果 |
| 核心不变量 | 已输出块永久确定；当前块精确表示已处理区间最右侧的重叠连通组 |
| 时间复杂度 | 排序 `O(n log n)`，扫描 `O(n)`，总体 `O(n log n)` |
| 空间复杂度 | 扫描状态 `O(1)`；计输出与 Java 排序辅助空间后最坏 `O(n)` |

### 四句建模结论

```text
我正在处理的对象是：按左端点排序后，从左到右到来的闭区间。
我必须持续保存的是：已经永久封口的结果，以及唯一未封口块的左右端点。
当下一区间到来时，我执行：若起点不超过当前终点就扩张右端，否则封口旧块并开启新块。
答案在遇到确定空隙以及遍历结束时，由当前合并块的左右端点计算出来。
```

### 泛用模板

```text
先寻找一种顺序，使未来对象只能从一个方向到来
用最小边界状态表示唯一仍可能变化的对象
新对象若仍属于当前连续组，就增量更新边界
新对象若跨过不可逆边界，就永久输出旧状态并重置
遍历结束后，处理没有后继事件触发的残留状态
```

### 迁移变式

| 题目 | 与本题相比变化在哪里 | 建模迁移 |
| --- | --- | --- |
| 57. 插入区间 | 输入已按左端点有序且原区间互不重叠，新增一个区间 | 省去全量排序；状态仍是当前待合并块，但事件分成左侧直接输出、重叠吸收、右侧收尾 |
| 986. 区间列表的交集 | 目标从“求并集块”变成“输出两个列表的共同覆盖” | 状态变为两个有序列表的指针；答案在交集非空时立即产生，移动右端较小的一方 |
| 435. 无重叠区间 | 目标从合并覆盖变成删除最少区间 | 排序键和状态改变：通常按右端点排序，持续保存最早结束的可兼容选择 |
| 253. 会议室 II | 结果从合并块改为任意时刻的最大并发数量 | 单个当前块不足以表示所有活跃会议；事件改成起点占用、终点释放，需要最小堆或分离的事件序列 |

识别迁移时不要只问“是不是区间题”。更有效的问题是：排序后，未来是否只从一个方向到来；我是在维护覆盖并集、寻找交集、选择兼容区间，还是统计同时活跃对象。目标关系不同，最小状态和结果时机也会随之改变。
