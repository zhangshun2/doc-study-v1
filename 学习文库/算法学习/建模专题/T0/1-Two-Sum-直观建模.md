# 1. 两数之和：从两数关系到补数查询

本篇要解决的并不是“怎样背出一段 `HashMap` 代码”，而是三个更基础的困难：为什么一个两层枚举问题可以变成一次扫描；为什么表里保存的是“值到下标”而不是只保存值；为什么顺序必须是**先查后存**。如果这三个问题能从题目关系中推出来，`HashMap` 只是承载模型的工具，而不再是需要死记的答案。

## 2. 完整题目

给定一个整数数组 `nums` 和一个整数目标值 `target`，从数组中找到两个**不同位置**的整数，使它们的和等于 `target`，返回这两个整数的数组下标。

题目保证每个输入恰好存在一个有效答案。不能把同一个数组元素使用两次；也就是说，即使 `2 * nums[i] == target`，也不能返回 `[i, i]`。两个下标的返回顺序不受限制。

### 输入与输出

- 输入：整数数组 `nums`，以及整数 `target`。
- 输出：长度为 2 的整数数组，内容是满足条件的两个不同下标。
- 关系要求：若返回 `[i, j]`，必须同时满足 `i != j` 和 `nums[i] + nums[j] == target`。

### 示例 1

```text
输入：nums = [2, 7, 11, 15], target = 9
输出：[0, 1]
解释：nums[0] + nums[1] = 2 + 7 = 9。
```

### 示例 2

```text
输入：nums = [3, 2, 4], target = 6
输出：[1, 2]
解释：nums[1] + nums[2] = 2 + 4 = 6。
```

### 示例 3

```text
输入：nums = [3, 3], target = 6
输出：[0, 1]
解释：两个 3 的值相同，但下标不同，所以可以组成答案。
```

### 约束与提示

- `2 <= nums.length <= 10^4`
- `-10^9 <= nums[i] <= 10^9`
- `-10^9 <= target <= 10^9`
- 每个输入只存在一个有效答案。
- 进阶目标是得到时间复杂度低于 `O(n^2)` 的算法。
- Java 方法入口为：

```java
public int[] twoSum(int[] nums, int target)
```

长度上限 `10^4` 并非大到完全不能运行双重循环，但题目明确要求思考低于平方级的模型。数值范围却非常大，不能创建一个从 `-10^9` 到 `10^9` 的直接寻址数组。当前约束下，`target - nums[i]` 的范围是 `[-2 * 10^9, 2 * 10^9]`，仍在 Java `int` 范围内。

## 3. 先把题目说成人话

**一句话生活化复述：**手里依次拿到一张张写着数字的卡片，每拿到一张新卡片，都要判断以前是否见过一张能与它凑成目标数的卡片；如果见过，就报出两张卡片的位置。

**一句话关系化复述：**寻找两个不同下标 `i`、`j`，使 `nums[i] + nums[j] = target`。

题目最重要的变化来自一次简单移项。假设当前数字是 `4`，目标是 `6`，另一个数字就不再是任意候选，而被唯一确定为 `2`：

```text
两个未知数的关系：leftValue + currentValue = target
固定当前值 4：       leftValue + 4 = 6
改写为一次查询：     leftValue = 6 - 4 = 2
```

这就是本题的关系图：

```text
                       target = 6
                           |
              需要满足两数相加等于目标
                           |
          earlierValue + currentValue = target
                           |
                           v
          earlierValue = target - currentValue
                           |
                           v
       “枚举任意两数”变成“查询唯一需要的补数”
```

> **小白追问：** 为什么枚举当前数时，查询的必须是 `target - currentValue`？
>
> **先给短答：** 因为当前值已经固定，等式中唯一还未知的搭档只能通过移项得到。
>
> **最小例子：** 目标是 `9`，当前值是 `7`。搭档若是 `2`，有 `2 + 7 = 9`；搭档若是 `3`，和就会变成 `10`。所以当前 `7` 只需要询问“以前有没有 `9 - 7 = 2`”，不必询问其他数。
>
> **回到模型/代码：** 这一步对应 `neededValue = target - currentValue`。`neededValue` 是由关系反解出的查询键，不是凭题型标签猜出的变量。

> **小白追问：** 固定当前值以后只查一个补数，会不会漏掉别的数对？
>
> **先给短答：** 不会；数组中的每个位置都会轮流成为当前位置，而每个合法数对总有一个较晚出现的位置。
>
> **最小例子：** 对 `[4, 1, 5]`、目标 `6`，扫描到 `4` 时查 `2`，扫描到 `1` 时查 `5`，扫描到 `5` 时查 `1`。合法对 `(1, 5)` 会在较晚的 `5` 到来时被检查到。
>
> **回到模型/代码：** `for` 循环让每个下标都成为一次 `currentIndex`；哈希查询只替代“怎样找搭档”，没有删掉任何当前位置。

| 要素 | 本题中的含义 |
| --- | --- |
| 对象 | 数组元素及其下标；返回的是下标，不只是数值 |
| 关系 | 两个不同下标上的值相加等于 `target` |
| 方向 | 从左到右扫描，把当前下标当作较晚出现的那个位置 |
| 目标 | 找到一对满足关系的下标 |
| 限制 | 不能重复使用同一下标；允许两个位置上的值相等；保证唯一解 |

## 4. 第一切入点：读题时先看什么

第一次读题，先圈出四个真正决定模型的词：**两个整数**、**和为目标值**、**数组下标**、**不能使用同一元素两次**。

- “两个整数”说明答案是一个配对关系，而不是单个元素的性质。
- “和为目标值”说明固定其中一个值后，另一个值可以由减法唯一算出。
- “返回下标”说明不能只记“某个值出现过”，还要找回它出现的位置。
- “不能使用同一元素两次”说明查询历史和记录当前值的先后顺序会影响正确性。

> **小白追问：** 为什么“返回下标”会反过来决定历史状态保存什么？
>
> **先给短答：** 查询命中只证明数值关系成立；要构造输出，还必须从命中的数值找回它原来的位置。
>
> **最小例子：** `[2, 7]`、目标 `9` 中，只记录“见过 `2`”可以判断 `7` 有搭档，却无法回答这个 `2` 位于下标 `0`。若数组更长，同一个值还可能出现在多个位置。
>
> **回到模型/代码：** 因此状态不是布尔集合，而是 `indexByValue`，其中键保存数值，映射值保存一个可返回的历史下标。

“买东西凑价格”“数组里找数字”一类故事都可以暂时拿掉。数组是否有序、是否连续、是否要求最短距离，题目都没有给出，因此也不要提前引入双指针、滑动窗口或距离最优化。

数据范围给出两个信号：`n` 最多是 `10^4`，平方级比较次数在最坏情况下接近五千万；而数值跨度约为二十亿，无法按数值大小直接开普通计数数组。我们需要的是一种“按任意整数值快速查询”的状态容器。

用最小例子 `[2, 7]`、`target = 9` 人工求解时，实际动作不是理解某个复杂结构，而是：看见 `2` 后知道它需要 `7`；再看见 `7` 时知道它需要 `2`，而 `2` 已经见过。这个“见过什么”的问题正是后面需要保存的最小历史状态。

## 5. 最直接的人工或暴力模型

最稳妥的直接模型是枚举所有合法下标对：先选择左下标 `i`，再从 `i + 1` 开始选择右下标 `j`，逐对检查两数之和。

```text
for i 从 0 到 n - 2：
    for j 从 i + 1 到 n - 1：
        如果 nums[i] + nums[j] == target：
            返回 [i, j]
```

`j` 从 `i + 1` 开始有两层含义：不会用同一下标两次，也不会把 `[i, j]` 和 `[j, i]` 当成两个新候选重复检查。

> **小白追问：** `j` 不从 `0` 开始，凭什么仍然检查了所有合法答案？
>
> **先给短答：** 任意两个不同下标都能唯一写成“小下标在前、大下标在后”。
>
> **最小例子：** 长度为 `3` 时，所有不同位置组合只有 `(0,1)`、`(0,2)`、`(1,2)`。循环不再检查 `(1,0)`，因为它使用的仍是下标 `0` 和 `1`，只不过顺序反了。
>
> **回到模型/代码：** 暴力循环的范围 `j = i + 1` 同时实现 `i != j` 和去除对称重复，为后面证明“优化没有漏解”提供完整基线。

这个方法一定正确，因为任意两个不同下标都能按较小者、较大者唯一写成 `i < j`。双重循环会检查所有这样的组合，所以有效答案不可能被漏掉；只有两数之和真的等于目标时才返回，也不会返回无效答案。

若 `n` 是数组长度，候选下标对共有：

```text
(n - 1) + (n - 2) + 依次递减 + 2 + 1
= n(n - 1) / 2
```

因此最坏时间复杂度是 `O(n^2)`，除返回结果外只使用两个下标和少量变量，额外空间复杂度是 `O(1)`。暴力模型的价值很高：它先准确界定了完整搜索空间，后续优化是在保持“不遗漏”的前提下减少寻找搭档的成本。

## 6. 暴力到底浪费在哪里

观察 `nums = [8, 1, 5, 3, 12]`、`target = 15`。唯一答案是下标 `[3, 4]`，即 `3 + 12 = 15`。

```text
i = 0，固定 8，需要 7：依次查看 1、5、3、12
i = 1，固定 1，需要 14：   依次查看 5、3、12
i = 2，固定 5，需要 10：      依次查看 3、12
i = 3，固定 3，需要 12：         查看 12，找到答案
```

从“数组元素被读取”的角度看，`12` 被四个不同起点反复查看，`3` 被前三个起点反复查看，`5` 也先后被查看。更关键的是，处理 `i = 0` 时我们已经知道“到目前看到的候选中没有 7”，但这段历史没有被组织成可复用状态；换一个 `i` 后又从头做线性寻找。

固定 `nums[i]` 以后，需要找的数其实已经唯一确定为 `target - nums[i]`。暴力模型仍然用 `O(n)` 扫描去回答一个“某个确定值是否出现”的问题。真正的优化目标因此可以写成：

> 不要让每个位置重新线性寻找它的搭档；让数组只扫描一次，并把已经见过的值组织成可快速查询、还能取回原下标的历史索引。

> **小白追问：** 补数已经算出来了，为什么还不能直接得到答案？
>
> **先给短答：** 算出“需要谁”和知道“这个数是否出现、出现在哪里”是两个不同问题。
>
> **最小例子：** 对 `[8, 1, 7]`、目标 `15`，看到 `8` 可以立刻算出需要 `7`，但此时还不知道数组后面有没有 `7`。等扫描到 `7`，又需要快速知道左边的 `8` 位于下标 `0`。
>
> **回到模型/代码：** 减法负责生成查询键，`indexByValue.get(neededValue)` 负责回答存在性并恢复位置；两步共同替代暴力的内层扫描。

这不是减少必须考虑的数学关系。每个元素仍会被当作一次当前对象；减少的是为它寻找补数时反复扫描其他元素的工作。

## 7. 容易想到但走不通的方向

### 7.1 只用 `HashSet` 记录出现过的值

想到集合很自然，因为它可以回答“补数是否出现过”。但题目要求返回下标，集合只能告诉我们 `2` 存在，不能告诉我们 `2` 在下标 `1`。如果再额外扫描数组找下标，就重新引入了线性工作；如果给集合另配一张值到下标的表，本质上已经回到映射结构。这个方向不是判断关系错误，而是保存的信息不够。

> **小白追问：** 用 `HashSet` 再返回当前下标，为什么还不够？
>
> **先给短答：** 当前下标只对应数对中的一端，集合没有保存另一端的下标。
>
> **最小例子：** `[4, 2]`、目标 `6` 中，处理下标 `1` 的 `2` 时，集合能回答“`4` 出现过”。但输出必须是 `[0,1]`，集合无法给出其中的 `0`。
>
> **回到模型/代码：** `HashMap<Integer, Integer>` 的映射值就是缺失的 `previousIndex`。这是输出需求造成的信息下限，不是偏爱某个 Java 容器。

### 7.2 先排序，再使用左右指针

有序数组中，左右指针确实能根据当前和偏大或偏小排除一侧，因此逻辑上可行。但是排序会改变元素位置，而本题要求原下标。为了保留下标，需要把每个元素包装成“值 + 原下标”再排序，整体时间为 `O(n log n)`，代码和状态都比一次哈希查询更重。这个方向是正确的备选模型，适合输入本来有序或额外空间限制更强的变式，不是当前最直观的首选。

### 7.3 先把当前值存入表，再查询补数

这看起来只是交换两行代码，却破坏了“历史只包含当前下标左侧元素”的含义。对 `[3, 2, 4]`、`target = 6`，处理第一个 `3` 时若先存 `3 -> 0`，再查询补数 `3`，会错误得到 `[0, 0]`。表里确实有值，但它来自当前元素自己。

可以通过记录次数、维护下标列表等方式修补“先存后查”，但那是在制造额外状态解决由顺序引入的问题。新的建模条件是：查询阶段只能看到严格早于当前位置的元素，这样两个下标天然不同。

> **小白追问：** “先存再查”只是交换两行，为什么会复用同一个元素？
>
> **先给短答：** 写入以后，当前下标立即变成了查询可见的候选；当补数恰好等于当前值时，它会匹配自己。
>
> **最小例子：** 数组开头只有一个 `3`，目标是 `6`。若先写入 `{3 -> 0}`，再查询补数 `3`，会取回下标 `0`，从而返回 `[0,0]`。数组里明明只有一个位置，却被使用了两次。
>
> **回到模型/代码：** `get(neededValue)` 必须位于 `put(currentValue, currentIndex)` 之前。这个更新顺序让映射在查询时严格代表左侧前缀。

## 8. 关键视角转换

暴力模型把每个左端点当作发起者：“我选中了 `8`，现在去未来寻找 `7`。”这种视角要求反复扫描尚未处理的后缀。

新的视角把正在到来的元素当作事件：“当前来了 `7`，它需要的 `8` 是否已经在历史中？”每一对答案总有一个较早下标和一个较晚下标。当扫描到较晚下标时，较早元素已经可以被查询。因此，不必让旧元素主动搜索未来，只需让新元素检查过去。

> **小白追问：** 只查过去而不查未来，为什么不会错过答案？
>
> **先给短答：** 一对下标不可能同时到来；等较晚位置被扫描时，较早位置已经属于过去。
>
> **最小例子：** `[5, 1]`、目标 `6` 中，扫描 `5` 时没有找到过去的 `1`，这不代表永久失败。下一轮扫描 `1` 时，`5` 已在历史中，查询补数 `5` 就会命中。
>
> **回到模型/代码：** 一次从左到右的循环规定当前下标是数对的较晚端，`indexByValue` 只负责较早端；方向明确后不需要再扫描右侧。

| 转换前 | 转换后 |
| --- | --- |
| 枚举两个自由变化的下标 | 固定当前下标，补数被唯一确定 |
| 每个旧元素反复扫描未来 | 每个新元素对历史做一次查询 |
| 搜索的是一个完整数对 | 查询的是 `target - currentValue` |
| 中间观察算完即丢弃 | 已见值被保存成可复用索引 |

新视角减少重复的原因是：历史集合只增量维护一次。一个元素到来时被记录，之后任何当前元素都可以直接按值查询它，不需要再从数组起点寻找。关系式没有改变，改变的是谁在什么时候负责完成配对。

### 8.1 把切换过程写成一串可以复用的自问

如果事先不知道答案，可以按下面的顺序向自己提问，而不是直接猜数据结构。

**第一问：答案中的两个对象都是自由的吗？** 暴力枚举时两个下标都在变化，看起来是两个自由对象。但一旦固定当前值 `currentValue`，另一个值就只能是 `target - currentValue`。因此真正需要寻找的不是“任意第二个数”，而是一个确定的键。

**第二问：这个确定的键为什么还找得慢？** 因为数组擅长按下标取值，不擅长按值反查下标。若仍在数组中逐个比较，关系虽然已经简化，查询手段却没有改变，时间仍会浪费在线性寻找上。

**第三问：应该查询未来还是历史？** 查询未来需要为每个当前值扫描后缀；查询历史则可以把所有已经扫描过的信息维护成同一份可复用索引。每个答案都有一个较晚出现的元素，所以等它到来时查历史不会漏解。

**第四问：历史中究竟要记什么？** 只记“出现过”不足以返回下标；记下所有元素的完整对象又没有必要。题目最终需要一个历史下标，因此状态应是“数值 -> 一个下标”。输出要求反过来决定了状态的内容。

**第五问：当前元素何时进入历史？** 当前元素必须先作为查询者，查询失败后才能成为后来元素的历史。如果先登记，它就同时扮演当前对象和历史搭档，违反两个下标必须不同的限制。

**第六问：找到以后还要继续吗？** 题目保证唯一答案，命中时两数关系已经成立，继续扫描不会改善结果。因此答案产生事件也是算法终止事件。

这六问形成了一条可迁移路径：先看关系能否反解，再看反查为何昂贵，然后决定查询方向，最后让输出内容和合法性限制共同决定状态及更新时机。`HashMap` 是回答完这些问题之后才出现的名字。

## 9. 正式建立模型

| 建模项 | 本题结论 |
| --- | --- |
| 对象 | 当前元素 `nums[i]`，以及位于它左侧的历史元素 |
| 关系 | `earlierValue + nums[i] == target` |
| 状态 | 历史中每个已见数值到某个对应下标的映射 |
| 事件 | 从左到右读到一个新的当前元素 |
| 不变量 | 开始处理 `i` 时，映射只含 `[0, i)` 内出现过的值及其有效下标 |
| 结果时机 | 查询到 `target - nums[i]` 已在历史映射中时 |

处理当前下标 `i` 只需要两个动作：先计算 `neededValue = target - nums[i]` 并查询历史；若没有匹配，再把 `nums[i] -> i` 放入历史。状态足够的原因是，判断当前元素能否完成答案只依赖“所需值以前是否出现”及“它的一个下标”，不依赖这些元素之间的顺序、距离或所有出现位置。

> **小白追问：** 开始处理下标 `i` 时，Map 里到底允许有哪些位置？
>
> **先给短答：** 只允许下标小于 `i` 的已处理位置，当前位置和右侧位置都不在其中。
>
> **最小例子：** 处理 `[4, 1, 5]` 的下标 `1` 时，Map 只能是 `{4 -> 0}`。下标 `1` 的值 `1` 要等查询失败后才写入，下标 `2` 的 `5` 还没有被读到。
>
> **回到模型/代码：** 区间写成 `[0, i)`，右侧圆括号表示不包含 `i`。这就是 `get` 在 `put` 之前所维护的循环不变量。

映射对同一个键只能保存一个下标，因此后来的相同值可能覆盖较早下标。对本题仍然安全：只要任务是返回任意一个有效数对，一个值保留任意一个历史下标都能组成有效答案；在题目“唯一有效答案”的保证下，也不会因覆盖而错过必须返回的唯一关系。更重要的重复值场景 `[3, 3]` 会在第二个 `3` 覆盖之前完成查询，所以第一个下标仍然可见。

> **小白追问：** 同一个数值出现多次时，只保留一个下标为什么够用？
>
> **先给短答：** 对未来某个当前值来说，所有同值历史位置在“两数之和”关系中作用相同，而题目只要求返回一对位置。
>
> **最小例子：** 历史里先后出现两个 `2`，未来来了 `5`，目标是 `7`。无论 Map 保存第一个还是第二个 `2` 的下标，它与当前 `5` 相加都等于 `7`，都能构造一对合法答案。
>
> **回到模型/代码：** `put` 覆盖同键时只替换代表位置，不会改变键 `2` 的存在性。若题目改为返回全部数对，映射值才必须升级为下标列表。

> **小白追问：** “唯一答案”这个条件究竟帮了模型什么？
>
> **先给短答：** 它让命中后立即返回没有选择歧义，也让调用方不必规定多组答案的优先级；补数查询本身并不依赖唯一性才成立。
>
> **最小例子：** `[1, 3, 3, 5]`、目标 `6` 有 `(1,5)` 和 `(3,3)` 两类答案。当前算法会返回扫描中先完成的那一对；若题目允许任意一对，这仍正确，但若要求全部答案，一个下标映射就不够。
>
> **回到模型/代码：** 本题的唯一解保证支持 `return` 立即终止。状态是否要保存全部下标，仍由“返回一对还是返回全部”决定。

遍历必须从左到右，因为这让“历史”和“当前”有清晰边界，自动保证两个下标不同。相等值并不需要特殊分支：先查后存会让第一个值只负责进入历史，第二个值负责完成关系。

本模型唯一会永久停止考虑候选的时刻是找到答案并返回。若重复键被覆盖，旧下标可以丢弃，因为题目不要求输出所有下标对；一个同值的新下标已足以代表这个数值参与未来查询。

### 9.1 对最小状态做一次审计

可以从“删掉某项信息后还能不能作答”来检查状态是否最小。

- 删掉数值，只留一组历史下标：无法知道哪个下标对应所需补数，必须回数组逐个读取，退化成扫描。
- 删掉下标，只留已见数值：能判断关系成立，却无法生成题目要求的输出。
- 不保存出现次数：本题仍能完成，因为只需构造一对答案，而不是统计答案数量。
- 不保存所有重复位置：本题仍能完成，因为任意一个具有所需值的历史下标都合法。
- 不保存历史顺序：本题仍能完成，因为只要求任意顺序返回，不要求最近、最早或距离最小。

所以“一个数值对应一个历史下标”既不缺信息，也没有为了本题保存无用细节。如果题目改成“返回全部下标对”，这个状态就不再足够，需要把映射值改成下标列表；如果改成“数对数量”，映射值应改成出现次数。由此可见，数据结构内保存什么不是固定模板，而是由结果形态决定。

模型还有一个适用边界：固定当前对象后，目标搭档必须能被直接反解或转换为一个可查询条件。两数之和满足等式移项；若关系是“两个数的乘积最接近目标”或“任意两数差的绝对值最小”，仅查一个确定补数就不够，还需要有序性、邻近查询或全局最优维护。

## 10. 所需数据结构详解

正式模型要求一种容器同时提供两项能力：按一个任意整数值快速判断是否出现过；出现过时取回一个原数组下标。Java 中最直接的选择是 `HashMap<Integer, Integer>`。

### 10.1 它是什么

`HashMap` 保存键值映射。本题中，键是数组中的数值，值是该数值已经出现过的下标：

```text
indexByValue
键 key：     earlierValue
值 value：   earlierIndex

例如：{3 -> 0, 2 -> 1}
含义：值 3 在下标 0 出现过，值 2 在下标 1 出现过。
```

概念上，哈希表先通过键的哈希值定位桶，再在桶内通过相等性确认具体键。不同键可能落入同一桶，这叫哈希冲突；实现必须处理冲突，所以“哈希地址相同”不等于“两个键相同”。`Integer` 的值语义让本题可以直接用数值作为键。

### 10.2 本题实际使用的操作

| 操作 | 本题含义 | 期望或平均时间 |
| --- | --- | --- |
| `get(neededValue)` | 查询补数并取回历史下标 | `O(1)` |
| `put(currentValue, i)` | 记录当前值及其下标 | `O(1)` |

Oracle Java 17 文档对 `HashMap` 的表述带有前提：当哈希函数能把元素适当地分散到桶中时，基本 `get`、`put` 操作提供常数时间性能。因此本文把整体 `O(n)` 明确写成平均或期望复杂度，而不是无条件的最坏情况承诺。极端冲突、扩容和具体实现细节都提醒我们：哈希表的“快”来自良好的分散和受控桶长度，不是数学上的直接数组寻址。

### 10.3 为什么保存“值到下标”

- 只保存值：能判断答案存在，却无法返回题目要求的下标。
- 保存“下标到值”：数组本身已经能做这件事，却不能按补数快速反查。
- 保存“值到所有下标列表”：信息足够，但本题只需任意唯一答案，保存全部位置是多余状态。
- 保存“值到一个下标”：恰好满足查询和返回要求，是最小状态。

> **小白追问：** 为什么键是数值、映射值是下标，不能反过来？
>
> **先给短答：** 查询条件是补数这个“数值”，返回结果才是“下标”，所以数值必须放在可直接查询的键位置。
>
> **最小例子：** 当前值为 `7`、目标为 `9` 时，要直接询问键 `2`。若表保存 `{0 -> 2}`，我们只知道下标 `0` 对应 `2`，仍得逐个检查所有键才能找到值 `2`。
>
> **回到模型/代码：** `indexByValue.get(neededValue)` 同时表达查询方向和返回内容：传入补数，取回 `previousIndex`。

### 10.4 为什么常见替代结构不如它合适

| 结构 | 问题 |
| --- | --- |
| 普通数组或链表 | 按补数查询仍需 `O(n)` 扫描 |
| 直接寻址计数数组 | 数值范围约为二十亿，空间不可接受，还要处理负数偏移 |
| `HashSet<Integer>` | 没有从值到原下标的映射 |
| `TreeMap<Integer, Integer>` | 可以完成任务，但查询和写入是 `O(log n)`，本题不需要有序性 |

最坏情况下，答案出现在最后或直到最后才匹配，表中会保存至多 `n - 1` 个不同键，因此额外空间上界为 `O(n)`。如果有重复值，实际键数是不同数值数量 `u`，空间可更精确写成 `O(u)`，其中 `u <= n`。

### 10.5 用一次冲突理解“平均常数时间”

把哈希值想成先给键选择一个较小范围的桶。两个不同整数经过容量换算后可能落进同一桶，例如在某个容量下，键 `2` 和另一个键可能拥有相同的桶位置。实现不会因为桶位置相同就认定键相同，而会继续比较桶内记录的键；因此查询成本取决于桶内候选有多少。

分散良好时，`n` 个键落到许多桶里，每次只检查很少记录，`get`、`put` 的平均成本接近常数。若大量键集中到少数桶，每次桶内确认就会变重，还可能触发扩容或桶结构调整。Java 的实现会缓解严重冲突，但调用者不应据此把单次操作描述成绝对的最坏 `O(1)`。

> **小白追问：** “平均 `O(1)`”是不是说每次 `get` 都只做一步？
>
> **先给短答：** 不是；它表示在键分散正常的一系列操作中，每次查询平均只检查常数数量的候选。
>
> **最小例子：** 若四个键分散在四个桶，查询通常只核对一个键；若两个键碰巧落在同一桶，查询其中一个可能要核对两个键。只要桶没有随着 `n` 持续变长，平均工作量仍不随 `n` 成比例增长。
>
> **回到模型/代码：** 因而 `get`、`put` 的复杂度要写“平均或期望 `O(1)`”。算法总共发起线性次操作，才得到平均总时间 `O(n)`。

> **小白追问：** 那最坏情况应该怎样理解，为什么不能直接说总时间永远是 `O(n)`？
>
> **先给短答：** 哈希查询还依赖冲突处理；若大量键集中在少数位置，单次查询就可能检查更多候选。
>
> **最小例子：** 把三个不同键都放进同一条桶内记录时，查询最后一个键不能只看第一项。理论哈希表在极端冲突下，单次操作可退化到随元素数增长，而不再是常数。
>
> **回到模型/代码：** 本文采用容器契约层面的保守表述：平均总时间 `O(n)`；不承诺无条件最坏 `O(n)`。Java 17 会用扩容和树化缓解冲突，但那是实现措施，不应改写成接口保证。

这也解释了为什么本题复杂度分析要分两层：算法层面一共只发起至多 `2n` 次映射操作；容器层面在正常哈希假设下，每次操作平均 `O(1)`。两层合起来才得到平均 `O(n)`。如果把 `HashMap` 换成保证对数查询的平衡搜索树，算法动作数不变，但单次查询与写入变成 `O(log n)`，总时间便是 `O(n log n)`。

## 11. 生活化类比及边界

可以把哈希表想成办事大厅的一套“编号登记卡”。每位已经进入大厅的人拿着一个数值牌，登记员按牌面数值建立一张能快速找到座位号的卡片。新来的人不必逐排寻找搭档，只需先算出自己需要哪个牌面，再查登记卡。

| 生活对象或动作 | 算法中的对应物 |
| --- | --- |
| 新进入大厅的人 | 当前元素 `nums[i]` |
| 人手中的数值牌 | 数组元素值 |
| 座位号 | 数组下标 `i` |
| 目标配对规则 | 两张牌的数值之和为 `target` |
| 登记卡“牌面 -> 座位号” | `HashMap<Integer, Integer>` |
| 先查询所需牌面 | `get(target - nums[i])` |
| 查询失败后登记新人 | `put(nums[i], i)` |
| 查到搭档并报出座位号 | 返回 `[previousIndex, i]` |

“先查后登记”对应一个严格规则：新来的人查询时，登记卡上只有比他早到的人，所以绝不可能把自己当搭档。两个拿相同牌面的人仍是两个人，只要座位号不同就能合法配对。

类比到这里为止。真实登记卡可能按顺序摆放、可能允许一张牌对应多人，也可能由工作人员肉眼寻找；Java `HashMap` 不保证遍历顺序，同一个键默认只保留一个映射，查找成本也依赖哈希分布。这个故事只帮助理解“按值快速反查下标”和“历史边界”，不能替代哈希冲突分析或正确性证明。

## 12. 典型输入的完整数据变化图

完整演算 `nums = [3, 2, 4]`、`target = 6`。图中数组向右扫描；映射按插入顺序展示只是为了便于阅读，不表示 `HashMap` 保证顺序。

```text
下标：       0     1     2
数值：      [3,    2,    4]
扫描方向：   ---------------->
```

### 快照 A：处理下标 0

```text
当前输入：nums[0] = 3
处理前状态：indexByValue = {}
判断依据：neededValue = 6 - 3 = 3；历史中没有键 3
执行动作：记录 3 -> 0
处理后状态：indexByValue = {3 -> 0}
新增结果：无
```

注意：虽然当前值本身正好是目标的一半，但查询发生在记录之前，因此不能拿下标 0 与自己配对。

> **小白追问：** 第一轮没有找到补数，为什么还必须把当前值放进 Map？
>
> **先给短答：** 当前值这轮没有历史搭档，不代表它不能成为后续元素的历史搭档。
>
> **最小例子：** `[3, 3]`、目标 `6` 的第一轮查不到历史 `3`。若因此不保存下标 `0`，第二轮的 `3` 仍会面对空 Map，答案就会被漏掉。
>
> **回到模型/代码：** 查询失败后的 `put(currentValue, currentIndex)` 把当前对象的角色从“查询者”转换为“下一轮可见的历史候选”。

### 快照 B：处理下标 1

```text
当前输入：nums[1] = 2
处理前状态：indexByValue = {3 -> 0}
判断依据：neededValue = 6 - 2 = 4；历史中没有键 4
执行动作：记录 2 -> 1
处理后状态：indexByValue = {3 -> 0, 2 -> 1}
新增结果：无
```

### 快照 C：处理下标 2

```text
当前输入：nums[2] = 4
处理前状态：indexByValue = {3 -> 0, 2 -> 1}
判断依据：neededValue = 6 - 4 = 2；历史中有 2 -> 1
执行动作：直接返回历史下标 1 和当前下标 2
处理后状态：无需再写入 4，方法已经结束
新增结果：[1, 2]
```

把三步压缩成状态表：

| `i` | 当前值 | 需要的补数 | 查询前映射 | 查询结果 | 动作 |
| ---: | ---: | ---: | --- | --- | --- |
| 0 | 3 | 3 | `{}` | 未找到 | 写入 `3 -> 0` |
| 1 | 2 | 4 | `{3 -> 0}` | 未找到 | 写入 `2 -> 1` |
| 2 | 4 | 2 | `{3 -> 0, 2 -> 1}` | 找到下标 1 | 返回 `[1, 2]` |

每一行开始时，映射都只代表当前下标左侧。每一行结束时，若尚未返回，当前元素才进入历史。这个边界就是代码正确性的核心。

## 13. 边界场景的数据变化

### 13.1 重复值 `[3, 3]`

这是检验“值相等但元素不能相同”最关键的用例。

```text
下标：       0     1
数值：      [3,    3]
扫描方向：   -------->

i = 0：
  当前值 3，需要 3
  查询前映射 {}
  查询失败，写入 3 -> 0
  稳定状态 {3 -> 0}

i = 1：
  当前值 3，需要 3
  查询前映射 {3 -> 0}
  查询成功，取出历史下标 0
  返回 [0, 1]
```

重复的是**值**，不是**下标**。先查后存让第二个 `3` 看见第一个 `3`，同时保证不会看见自己。若顺序颠倒，第二轮会先把 `3 -> 0` 覆盖成 `3 -> 1`，随后错误返回 `[1, 1]`。

> **小白追问：** `[3,3]` 两个值完全一样，算法怎样确认它们不是同一个元素？
>
> **先给短答：** 身份由下标区分；第二轮取出的 `0` 来自历史，当前下标是 `1`，所以两者天然不同。
>
> **最小例子：** 空前缀处理第一个 `3`：先查 `{}`，再得到 `{3 -> 0}`。前缀扩展到两个元素后处理第二个 `3`：先查 `{3 -> 0}`，命中下标 `0`，与当前下标 `1` 组成 `[0,1]`，不再执行覆盖。
>
> **回到模型/代码：** `previousIndex` 来自 `[0,i)`，`currentIndex` 等于 `i`。即使 `nums[previousIndex] == nums[currentIndex]`，仍有 `previousIndex < currentIndex`。

> **小白追问：** 为什么第二个 `3` 命中后不再执行 `put(3, 1)`？
>
> **先给短答：** 题目只要求一组唯一答案，命中时任务已经完成，后续状态不再会被读取。
>
> **最小例子：** `[3,3]` 的第二轮已经得到 `[0,1]`。再把映射改成 `{3 -> 1}` 既不会改善这组答案，还可能掩盖“返回发生在查询时”这个关键时机。
>
> **回到模型/代码：** `return new int[]{previousIndex, currentIndex}` 位于 `put` 之前；命中分支结束整个方法，写入只属于未命中分支。

### 13.2 工程环境中的无解输入

题目保证有解，所以正常提交一定会在循环中返回。若把方法复用到不保证有解的系统中，例如 `[1, 2]`、`target = 10`：

```text
i = 0：查 9 失败，状态变为 {1 -> 0}
i = 1：查 8 失败，状态变为 {1 -> 0, 2 -> 1}
遍历结束：映射残留两个键，没有结果
```

本篇实现选择抛出 `IllegalArgumentException`，使违反方法前置条件的问题显式暴露。也可以在工程接口中约定空数组或 `Optional`，但不能静默返回一个看似有效的默认下标对。

## 14. 正确性与不变量

要证明的对象是：方法返回时两个下标一定合法；若题目中的唯一答案存在，方法一定能找到它。

**循环不变量：**开始处理下标 `i` 时，`indexByValue` 中的每个映射都来自区间 `[0, i)`；对这个区间内已经出现的每种数值，表中保存一个具有该值的有效历史下标。

> **小白追问：** “不变量”听起来很抽象，它在这里具体帮我们保证什么？
>
> **先给短答：** 它是一条每轮查询前都成立的状态说明，同时保证查到的搭档真实存在且下标不同。
>
> **最小例子：** 处理下标 `2` 前，若 Map 是 `{3 -> 0, 2 -> 1}`，每条记录都指向左侧真实位置。查询到键 `2` 时，可以立刻确认值来自下标 `1`，而不是当前下标 `2`。
>
> **回到模型/代码：** 空 Map 建立初始状态；未命中后的 `put` 把当前元素加入下一轮前缀；命中时 `previousIndex < currentIndex` 直接来自这条不变量。

1. **初始成立。**处理 `i = 0` 前，左侧区间为空，映射也是空表，二者一致。
2. **保持成立。**若当前没有找到补数，才执行 `nums[i] -> i`。进入下一轮 `i + 1` 时，新历史区间是 `[0, i + 1)`，刚才的当前元素正好成为历史，映射仍只包含左侧元素。
3. **返回结果一定有效。**若查询得到 `previousIndex`，它严格小于 `i`，所以两个下标不同；查询键是 `target - nums[i]`，因此 `nums[previousIndex] + nums[i] == target`。
4. **不会漏掉答案。**设唯一答案的两个下标为 `p < q`。扫描到 `p` 时如果尚未返回，`nums[p]` 会进入映射。扫描到 `q` 时，需要的补数正是 `target - nums[q] = nums[p]`，查询必然成功。
5. **覆盖旧的重复值是安全的。**模型只要求返回一对下标。同值历史下标中的任意一个与当前补数关系相同；保留一个就足以证明存在并构造结果。`[3, 3]` 还会在第二个值写入前完成返回。

> **小白追问：** 证明“不会漏掉答案”时，为什么总把答案下标写成 `p < q`？
>
> **先给短答：** 这是为了给两个位置分配稳定角色：`p` 是历史端，`q` 是触发查询的当前端。
>
> **最小例子：** 答案位于下标 `0` 和 `2` 时，扫描到 `0` 只能先登记；扫描到 `2` 时，下标 `0` 已经进入历史。无论题目允许返回 `[0,2]` 还是 `[2,0]`，发现事件都发生在 `q = 2`。
>
> **回到模型/代码：** 循环方向使较小下标先经过 `put`，较大下标再通过 `get` 找到它。证明顺序与代码更新顺序完全一致。

遍历结束的情况在题目契约下不会发生，因为上面的第 4 点说明存在的答案必在较晚下标到来时被发现。工程版末尾抛异常不是算法缺口，而是对“不满足题目保证”的输入给出明确行为。

## 15. 时间与空间复杂度推导

设 `n = nums.length`，设 `u` 为扫描过程中出现的不同数值数量，始终有 `u <= n`。复杂度只统计算法额外使用的空间，不把输入数组和最终返回的两个下标计入额外空间。

### 15.1 直接模型

双重循环最多检查所有 `i < j` 的下标对，总数是 `n(n - 1) / 2`。每次检查只做数组读取、加法和比较，成本为 `O(1)`，所以总时间为 `O(n^2)`。循环变量和临时和不随 `n` 增长，额外空间为 `O(1)`。

### 15.2 补数查询模型

数组最多扫描 `n` 次。每轮执行一次减法、一次 `HashMap.get`；查询失败时再执行一次 `HashMap.put`。因此哈希操作总数不超过 `2n`，不存在隐藏的数组内层扫描。

在键哈希分布合理的通常假设下，`get` 和 `put` 的平均或期望成本均为 `O(1)`，总平均时间为 `O(n)`。这不是“内层循环的均摊抵消”，而是每个元素生命周期内只承担一次查询和至多一次写入：

```text
一个元素的生命周期：成为 current -> 查询自己的补数 -> 未命中则登记一次
所有 n 个元素合计：  n 次查询 + 至多 n 次登记
```

> **小白追问：** 这里为什么是“至多 `2n` 次哈希操作”，不是又形成一个隐藏的平方级过程？
>
> **先给短答：** 每个数组位置只触发一次查询，并且最多触发一次写入，没有任何位置会让代码重新扫描整个 Map。
>
> **最小例子：** 三个元素都未在前两轮命中时，动作最多是“查、存；查、存；查、返回”，共五次哈希操作，而不是检查三对以后再做额外扫描。
>
> **回到模型/代码：** `for` 每轮只有一个 `get` 和条件性的一个 `put`。`HashMap` 的内部冲突成本另行分析，不能把容器内部成本误认成代码里的第二重数组循环。

若哈希冲突极端严重，哈希操作的最坏成本不能笼统承诺为常数；Java 17 的实现会对冲突桶采取额外措施，但公开契约强调的仍是满足散列前提时的常数性能。因此面试和题解中应写“平均 `O(n)`”，不要把它误写成无条件最坏 `O(n)`。

> **小白追问：** 平均复杂度已经够快，为什么文章还要单独提醒最坏情况？
>
> **先给短答：** 因为 `O(n)` 结论包含“哈希分散正常”这个前提，说明前提才能分清算法动作数和容器单次成本。
>
> **最小例子：** 同样做三次 `get`，若每次只核对一个桶内键，成本接近三步；若桶内候选逐渐变多，每次核对的工作也会增加。外层仍是三轮，但单轮不再等价于固定一步。
>
> **回到模型/代码：** 面试结论写“平均时间 `O(n)`、空间 `O(n)`”最准确。若业务必须要确定的上界，可考虑 `TreeMap`，代价是总时间稳定在 `O(n log n)`。

映射最多保存 `u` 个键值对，空间是 `O(u)`，最坏 `u = n`，所以通常写作 `O(n)`。返回数组固定长度为 2，即使计入也只是 `O(1)`。

### 16.1 泛用的“固定当前对象 + 查询互补历史”骨架

下面的类表达一类稳定模型：二元关系可以在固定当前值后反解出唯一搭档；从左到右处理；历史状态既支持查询又能恢复结果位置。这里没有未定义的抽象调用，代码本身可独立编译。

```java
import java.util.HashMap;
import java.util.Map;

final class ComplementLookupModel {
    private ComplementLookupModel() {
    }

    static int[] findPairIndices(int[] values, int desiredSum) {
        Map<Integer, Integer> earlierIndexByValue = new HashMap<>();

        for (int currentIndex = 0; currentIndex < values.length; currentIndex++) {
            int currentValue = values[currentIndex];
            int requiredEarlierValue = desiredSum - currentValue;
            Integer earlierIndex = earlierIndexByValue.get(requiredEarlierValue);

            if (earlierIndex != null) {
                return new int[]{earlierIndex, currentIndex};
            }

            // 查询完成后，当前对象才进入下一轮可见的历史状态。
            earlierIndexByValue.put(currentValue, currentIndex);
        }

        throw new IllegalArgumentException("No pair satisfies the required relation");
    }
}
```

这个骨架可迁移的不是方法名，而是控制流程：**反解需要的历史值 -> 查询历史 -> 命中时产生答案 -> 未命中时登记当前对象**。如果另一道题需要的不只是“是否存在”，状态值可能从一个下标变成次数、最早位置或一组位置，但推导顺序不变。

> **小白追问：** 读 Java 代码时，最应该盯住哪条顺序，而不是逐行背语法？
>
> **先给短答：** 盯住“反解、查询、命中返回、未命中登记”这四个模型动作，以及查询必须先于登记。
>
> **最小例子：** 当前值是 `4`、目标是 `6` 时，先得到需要值 `2`；Map 有 `2` 就返回其下标，没有才登记 `4`。若把登记提前，当前 `4` 在目标为 `8` 时就可能匹配自己。
>
> **回到模型/代码：** 四个动作依次对应 `neededValue`、`get`、`if (previousIndex != null) return` 和 `put`。变量名改变时，这条状态时序仍可迁移。

### LeetCode 可直接提交代码

下面只保留题目要求的 `Solution` 入口。它和泛用骨架使用同一条控制流程，但方法签名与返回类型严格对应本题。

```java
import java.util.HashMap;
import java.util.Map;

public class Solution {
    public int[] twoSum(int[] nums, int target) {
        Map<Integer, Integer> indexByValue = new HashMap<>();

        for (int currentIndex = 0; currentIndex < nums.length; currentIndex++) {
            int currentValue = nums[currentIndex];
            int neededValue = target - currentValue;
            Integer previousIndex = indexByValue.get(neededValue);

            if (previousIndex != null) {
                return new int[]{previousIndex, currentIndex};
            }

            // 先查后存，使表中只包含当前下标左侧的元素。
            indexByValue.put(currentValue, currentIndex);
        }

        throw new IllegalArgumentException("Input does not contain a valid pair");
    }
}
```

> **小白追问：** 为什么 `previousIndex` 使用 `Integer` 并判断 `null`，不能用基本类型 `int` 的默认值 `0` 表示没找到？
>
> **先给短答：** 因为 `0` 是合法下标；把它同时当作“缺失标记”，会混淆“补数在数组开头”和“补数不存在”。
>
> **最小例子：** `[2, 7]`、目标 `9` 中，处理 `7` 时应该取回历史下标 `0`。若程序约定返回 `0` 就算没找到，它会把这次真实命中误判成缺失，继续扫描并最终丢掉正确答案。
>
> **回到模型/代码：** `HashMap.get` 在键不存在时返回 `null`，存在键 `2` 时返回装箱后的下标 `0`。所以 `previousIndex != null` 检查的是“映射是否存在”，不会把任何合法下标误当成哨兵值。

## 17. 边界、常见错误与调试观察点

| 层次 | 常见问题 | 结果与修正 |
| --- | --- | --- |
| 建模错误 | 保存“见过哪些值”，却没有保存下标 | 能判断存在，不能构造输出；改为值到下标映射 |
| 建模错误 | 排序后忘记原下标已经变化 | 返回的是排序位置；排序元素必须携带原下标，或改用哈希模型 |
| 条件错误 | 先 `put` 再 `get` | 目标为当前值两倍时可能返回同一下标；坚持先查后存 |
| 条件错误 | 把重复值理解成非法 | `[3,3]` 的两个下标不同，合法；限制的是元素位置，不是数值 |
| 实现错误 | 映射写成 `下标 -> 值` | 无法按补数快速查找；键必须是数值，映射值才是下标 |
| 实现错误 | 返回 `{neededValue, currentValue}` | 题目要求下标，不是数值 |
| 实现错误 | 用 `0` 表示“没找到” | 下标 0 本身有效；使用 `null` 或 `containsKey` 判断 |

调试时不要只打印最终结果。每轮输出下面四项，模型边界会非常清楚：

```text
currentIndex
currentValue
neededValue
查询前的 indexByValue
```

对 `[3,3]` 应特别观察：第一轮查询前映射为空，第二轮查询前映射是 `{3=0}`。如果第一轮查询时已经能看到 `{3=0}`，说明写入时机错了。若查询命中却返回数值 `3`，说明“键是数值、值是下标”的角色发生了混淆。

还要区分题目契约和工程契约。LeetCode 保证数组非空、至少两个元素且存在唯一答案；若方法在业务代码中对外开放，应再明确 `nums == null`、无解、多解时的行为，而不是假设平台保证自动延伸到所有调用环境。

## 18. 最终模型卡

| 项目 | 复习结论 |
| --- | --- |
| 题型识别指纹 | 在一组对象中找两个对象满足可反解的关系，并且需要恢复原位置 |
| 一句话关系模型 | 固定当前值后，另一个值唯一等于 `target - currentValue` |
| 实际保存什么 | 已扫描数值到一个历史下标的映射 |
| 状态何时变化 | 当前补数查询失败后，才把当前值和下标加入历史 |
| 答案何时产生 | 当前值所需的补数已经在历史映射中时 |
| 核心不变量 | 处理下标 `i` 前，映射只代表 `[0, i)` 中的历史元素 |
| 时间复杂度 | 平均 `O(n)` |
| 空间复杂度 | `O(u)`，最坏 `O(n)` |

四句建模结论：

```text
我正在处理的对象是：从左到右到来的当前数组元素及其下标。
我必须持续保存的是：已见数值到一个历史下标的映射。
当 当前值的补数已出现在历史映射中 发生时，我执行：取出历史下标并与当前下标组成答案。
答案在 补数查询命中时 由 历史下标和当前下标 计算出来。
```

泛用模板：

```text
二元关系 relation(earlier, current) = target
-> 固定 current
-> 反解 requiredEarlier
-> 在历史索引中查询 requiredEarlier
-> 命中则构造结果
-> 未命中则把 current 登记为后续对象的历史
```

迁移变式：

| 变式 | 变化点 |
| --- | --- |
| 167. 两数之和 II（有序数组） | 条件增加“有序”，状态可改为左右边界，利用和的单调变化淘汰候选 |
| 15. 三数之和 | 关系多一个对象；先固定一个值，把剩余关系降成两数之和，并额外处理去重 |
| 560. 和为 K 的子数组 | 对象从元素变为前缀状态；查询的是前缀差，映射值从下标变为出现次数 |
| 653. 两数之和 IV（BST） | 数据载体变成树；关系仍是补数查询，但遍历方式和历史产生顺序改变 |

真正应该记住的不是“Two Sum 等于 `HashMap`”，而是：当二元关系在固定一个对象后能唯一反解另一个对象时，可以把组合枚举改造成查询；查询需要什么结果，就在历史状态中保存什么信息。

闭卷复述时，按“固定当前值、反解补数、查询左侧历史、命中即返回、未命中再登记”的顺序讲。只要还能说明为什么查询早于登记，就已经抓住了本题最关键的合法性边界，而不是只记住容器名称。
