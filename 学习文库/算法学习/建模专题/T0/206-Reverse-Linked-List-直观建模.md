# 206. 反转链表：在改写方向之前保住下一站

这道题的代码很短，真正值得学习的却不是“背四行赋值”。困难在于：单链表只能沿 `next` 向前；一旦把当前节点的 `next` 改向前一个节点，原来的下一站就会从当前节点上消失。如何在修改结构的同时不丢节点，如何知道哪些边已经正确、哪些边还没处理，才是本题的建模核心。

本篇希望解决几个常见困惑：为什么反转节点不是交换节点值；为什么一定要先保存 `next`；`previous`、`current`、`next` 三个引用各自代表什么业务状态；为什么原地修改不会制造环；迭代和递归看似完全不同的代码，其实各自在表达什么稳定语义。阅读完后，应当能从“单向可达关系发生重建”独立推导出状态，而不是仅在看到题号 206 时默写模板。

## 2. 完整题目

给定一个单链表的头节点 `head`。链表中的每个节点保存一个整数值和一个指向下一节点的引用 `next`；最后一个节点的 `next` 为 `null`。需要把整条链表的连接方向反转，并返回反转后的新头节点。

输入不是一个真正的 Java 数组。题面使用 `[1,2,3]` 只是为了展示链表沿 `next` 依次可见的节点值。算法实际收到的是第一个节点的引用，之后只能从某个节点的 `next` 找到下一节点。

### 输入与输出

- 输入：单链表头节点 `head`，也可能为 `null`。
- 输出：同一批节点重新连接后的新头节点。
- 结构要求：原来的相邻关系 `A -> B` 在结果中应变成 `B -> A`。
- 节点身份：推荐解法不新建结果节点，而是修改原节点的 `next`。

### 示例 1

```text
输入：head = [1,2,3,4,5]
输出：[5,4,3,2,1]
```

原头节点 `1` 最终成为尾节点，所以 `1.next` 必须为 `null`；原尾节点 `5` 最终成为新头节点。不是把值 `1` 和 `5` 交换，而是把节点之间的每一条有向连接翻转。

### 示例 2

```text
输入：head = [1,2]
输出：[2,1]
```

唯一一条有效连接 `1 -> 2` 被改成 `2 -> 1`，同时 `1 -> null`。若只建立 `2 -> 1` 却没有断开 `1 -> 2`，就会形成 `1 <-> 2` 的环。

### 示例 3

```text
输入：head = []
输出：[]
```

空链表没有节点和连接需要修改，新头仍然是 `null`。

### 约束、进阶与方法入口

- 链表节点数 `n` 的范围为 `[0, 5000]`。
- 每个节点值 `Node.val` 的范围为 `[-5000, 5000]`。
- 题目进阶要求分别思考迭代方式和递归方式。
- Java 方法签名为：

```text
public ListNode reverseList(ListNode head)
```

节点值范围不会决定模型，因为反转只关心节点身份和连接方向，不比较数值。节点数上限则提醒我们：`O(n)` 扫描是合理目标；递归虽然也是 `O(n)` 时间，但需要深度为 `n` 的调用栈，在 Java 中比固定引用的迭代写法更容易受到栈空间限制。

## 3. 先把题目说成人话

**一句话生活化复述：**有一条路线，每一站只记录“下一站在哪里”；现在要把整条路线的指示牌全部掉头，并让原来的终点成为新起点。

**一句话关系化复述：**对一条无环的单向节点链，把每条原始边 `node -> originalNext` 改成 `originalNext -> node`，并返回原尾节点。

| 要素 | 本题含义 |
| --- | --- |
| 对象 | 有身份的链表节点，不只是节点中的整数值 |
| 关系 | 每个节点通过 `next` 指向至多一个后继节点 |
| 方向 | 输入只能从头沿原 `next` 向后访问；结果的边方向与原方向相反 |
| 目标 | 所有节点恰好保留一次，所有相邻连接反向，原尾成为新头 |
| 限制 | 没有数组下标、没有直接前驱引用；改边后原后继可能失去入口 |

题目关系图如下。字母表示节点身份，括号中的数字表示值；箭头表示 `next`，而不是数组中的相邻位置。

```text
原关系，访问方向从左到右：

head
 |
 v
A(1) -> B(2) -> C(3) -> D(4) -> null

目标关系，访问方向仍沿 next，但连接已经反向：

newHead
   |
   v
D(4) -> C(3) -> B(2) -> A(1) -> null
```

把问题说成“输出值倒序”会隐藏结构要求。即使两个节点都保存值 `7`，它们仍然是两个不同对象；反转要改变的是对象之间的边。值是否相同，不影响任何一步。

## 4. 第一切入点：读题时先看什么

第一分钟不要先问“这是双指针还是递归”，先盯住三个事实。

第一，关键词是“单链表”和“反转”。“单”意味着节点只给出后继，没有前驱；“反转”意味着要修改边的方向，而不是重新排序数值。真正的任务单位是边 `current.next`。

第二，问自己修改一条边会破坏什么信息。对最小非空链表 `1 -> 2 -> null`，如果直接执行 `1.next = null`，节点 `1` 已经正确成为尾部，但从 `1` 再也找不到节点 `2`。因此第一条自然结论不是“需要三个指针”，而是：**改写当前出口前，必须另存原出口。**

第三，观察人工动作是否依赖整条链。反转当前节点 `1` 时，只需要知道它应当指向谁，以及之后从哪里继续：它应指向已经处理好的前一个区域，之后应从刚保存的原下一节点继续。无需提前知道链表总长度，也无需随机访问第 `i` 个节点。

用三节点最小样例手工尝试：

```text
开始：null <- [已处理为空]    1 -> 2 -> 3 -> null

处理 1：先记住 2，再令 1 -> null
处理 2：先记住 3，再令 2 -> 1
处理 3：先记住 null，再令 3 -> 2

结束：3 -> 2 -> 1 -> null
```

数据规模 `n <= 5000` 不要求比 `O(n)` 更激进，因为每个节点的边至少要检查或改写一次，时间下界已经是 `O(n)`。优化空间更有价值：能否不保存全部节点，只保留当前边两侧的必要入口。

## 5. 最直接的人工或暴力模型

在不知道原地模型时，一个一定正确且容易验证的方案是先把所有节点引用放进数组列表，再按相反方向重新连接。它不是坏答案，而是一座很好的推导桥梁。

自然步骤如下：

1. 从 `head` 出发沿 `next` 遍历，把遇到的每个节点对象加入列表。
2. 若列表为空，返回 `null`。
3. 从列表最后一个节点开始，让它的 `next` 指向前一个节点。
4. 持续向前连接，直到列表第一个节点。
5. 把原头节点，也就是列表第一个节点的 `next` 设置为 `null`。
6. 返回列表最后一个节点。

对应的完整逻辑可以写成：

```text
nodes = 空列表
current = head
while current != null:
    nodes 加入 current
    current = current.next

if nodes 为空:
    return null

for i 从 nodes.length - 1 递减到 1:
    nodes[i].next = nodes[i - 1]

nodes[0].next = null
return nodes[nodes.length - 1]
```

这个方案不会漏节点，因为第一次遍历按输入的唯一前进路线收集全部可达节点；第二次遍历对每对原相邻节点建立反向边；最后显式封住新尾。它的时间复杂度是 `O(n)`，额外空间复杂度是 `O(n)`，因为列表保存了 `n` 个节点引用。

这个直接模型还帮助我们排除一种伪解法：把值依次放入数组，再按逆序写回链表。这样从值序列上看可能一致，但节点的连接和身份完全没变。如果外部还持有某个节点引用，或后续题目要求反转局部区间、拼接链表，这种做法表达的不是同一个结构操作。

## 6. 暴力到底浪费在哪里

数组列表方案的时间已经是线性的，所以这里的“浪费”不是一个隐藏的三重循环，而是保存了远超当前决策所需的信息，并对同一批节点做了两轮结构性处理。

以 `1 -> 2 -> 3 -> 4 -> null` 为例：

```text
第一轮：沿 next 读取

读 1：nodes = [1]
读 2：nodes = [1, 2]
读 3：nodes = [1, 2, 3]
读 4：nodes = [1, 2, 3, 4]

第二轮：再次取出相同节点引用并改边

取 4、3：4.next = 3
取 3、2：3.next = 2
取 2、1：2.next = 1
取 1：   1.next = null
```

第一轮读取 `1.next` 得到 `2` 后，这条原始边的唯一剩余价值只是告诉算法“下一步去 2”。如果当时把节点 `2` 的引用临时保存起来，就可以立刻把 `1.next` 改向已经完成的区域；没有必要把 `1` 留在一个长度最终达到 `n` 的列表中。节点 `2`、`3` 也完全相同。

进一步看，列表中真正被第二轮使用的信息是局部相邻关系：处理节点 `3` 时，需要知道它前面已经反转好的入口是 `2`；要继续原路线，需要知道原下一站是 `4`。全量列表提供了这些信息，但提供得过多。任意时刻只需要两个长期状态和一个改边前的短期快照。

本题的优化目标可以准确写成：

> 不再先保存整条链后重建，而是在原方向只经过每个节点一次；改写当前 `next` 前只保存一个原下一站，同时维护已经反转好的入口。

这个优化把额外空间从随 `n` 增长的 `O(n)` 降到 `O(1)`。时间仍是 `O(n)`，因为读取并改写每个节点一次已经达到本题必要的线性下界。

## 7. 容易想到但走不通的方向

### 方向一：从原尾节点不断寻找前驱

看到目标从 `5` 开始，容易产生“先找到尾节点，再从尾往前走”的想法。问题是单链表节点没有 `previous`。找到原尾 `5` 需要从头扫描一次；想找 `5` 的前驱 `4`，又要从头扫描；再找 `4` 的前驱 `3`，仍要从头扫描。

它能在 `O(1)` 额外空间下找到正确顺序，但第一个前驱查找约扫描 `n` 个节点，之后约扫描 `n-1`、`n-2` 个节点，总量是等差数列，因此时间为 `O(n^2)`。失败中得到的新条件是：不能围绕“谁是当前节点的前驱”反复查询，而要在正向经过节点时持续保存已经形成的新前驱关系。

### 方向二：只交换节点值

链表值可读写，于是可以收集值或用前后两组指针交换值。它能让题面展示出的数值序列倒过来，在只比较值的简单判题中甚至可能通过。然而它没有反转任何连接，外部持有的节点身份与关系没有改变；遇到节点还带有其他业务字段、要求保持对象整体移动，或者反转局部链时就会暴露语义错误。

这个方向不是时间上必然失败，而是模型对象选错了：题目操作对象是节点和边，`val` 只是节点携带的数据。新的建模条件是，状态必须保存节点引用，动作必须落在 `next` 上。

> **小白追问：** 最终打印出来都是 `[2,1]`，交换两个节点的值为什么还不算反转？
>
> **先给短答：** 因为题目要求改变节点之间的连接，值相同只是输出表面相同，节点身份和边仍可能完全错误。
>
> **最小例子：** 设外部变量 `first` 一直引用节点 A，原链是 `A(1) -> B(2)`。只交换值后得到 `A(2) -> B(1)`，`first` 仍是头节点 A，A 仍指向 B；真正反转后应是 `B(2) -> A(1)`，此时 A 是尾节点且 `A.next == null`。
>
> **回到模型/代码：** 推荐模型的对象是节点引用和 `next` 边，核心写操作是 `current.next = previous`；整个算法从不读取 `val` 来决定流程。

### 方向三：先改边，再从改后的边继续

最危险的写法是：

```text
current.next = previous
current = current.next
```

第二行读到的已经不是原下一站，而是刚写进去的 `previous`。第一次循环中 `previous` 为 `null`，所以算法立刻结束，节点 `2` 以及后面整段都丢失。若更新顺序换成某些其他组合，还可能让一个节点指向自己，产生无限循环。

这个方向逻辑错误，不是性能不足。失败给出的条件极其明确：任何破坏导航信息的写操作之前，都要先取得之后仍需使用的引用。数据库迁移、树旋转、数组原地覆盖也有同类“先备份即将覆盖的信息”问题。

### 递归不是走不通，而是空间契约不同

递归可以正确完成本题。它把“怎样到达原尾”交给调用栈：先递归反转 `head.next` 的后缀，再把当前头接到后缀尾部。代码很凝练，但每个节点对应一个未返回的调用帧，额外空间为 `O(n)`。在 Java 中，题目给出的 5000 个节点不保证任何运行环境都能安全承受对应递归深度，因此本篇选择迭代作为推荐落地，递归作为理解“返回值语义”和“后序处理”的重要对照。

## 8. 关键视角转换

### 转换一：从倒序取节点，变成逐条改变边

原视角关注最终顺序：“我要先拿到 5，再拿到 4。”这会诱导我们从尾部找前驱。新视角关注局部关系：“原边 `1 -> 2` 最终必须变成 `2 -> 1`。”每条边都能在正向经过其起点时处理，无需具备反向访问能力。

### 转换二：从保存整条未来，变成保护一个后缀入口

修改 `current.next` 会切断当前节点通往未处理区域的唯一路径。但为了以后处理后缀，并不需要保存后缀中所有节点，只需保存它的入口 `next = current.next`。因为后缀内部仍保持原连接，从这个入口仍可到达余下全部节点。

```text
修改前：previous 区域    current -> next -> 其余后缀
                       唯一会被覆盖的出口

临时保存：savedNext ----------------^ 

修改后：previous <- current    savedNext -> 其余后缀
```

> **小白追问：** 只保存一个 `next` 引用，真的能保护后面整段链吗？
>
> **先给短答：** 能，因为尚未处理的后缀内部还没有被改动，拿到后缀第一个节点就等于保住了进入整段后缀的入口。
>
> **最小例子：** 在 `1 -> 2 -> 3 -> null` 中处理节点 1 时，只保存 `next = 2`。即使随后把 `1.next` 改成 `null`，仍可以从变量 `next` 到达 `2 -> 3 -> null`，不需要再分别保存节点 2 和节点 3。
>
> **回到模型/代码：** `ListNode next = current.next` 保存的是后缀入口；一轮末的 `current = next` 把这个入口交给下一轮，后缀内部继续通过原 `next` 串联。

### 转换三：从“同时反转整条链”变成边界迁移

任何稳定时刻都把链表看成两个区域：左侧是已经反转好的前缀，右侧是仍按原方向连接的后缀。`current` 是后缀入口。一次循环只把 `current` 从右侧迁移到左侧，新边指向 `previous`，随后边界向后移动一个节点。

```text
循环前： [已反转前缀]    [current 开始的原序后缀]
循环后： [扩大一节点的已反转前缀]    [缩小一节点的原序后缀]
```

重复工作的减少来自“增量维护”：已经反转好的区域以后不再扫描、不再修改；未处理区域只通过一个入口继续。每个节点只经历一次从“待处理”到“已处理”的状态迁移。

> **小白追问：** 一轮结束时，怎样确认链表没有变成几段互相找不到的碎片？
>
> **先给短答：** 稳定时刻始终只有两个有入口的区域：`previous` 能到达全部已反转节点，`current` 能到达全部未处理节点。
>
> **最小例子：** 对 `1 -> 2 -> 3` 完成第一轮后，状态是 `previous -> 1 -> null` 与 `current -> 2 -> 3 -> null`。旧边 `1 -> 2` 虽然已经断开，但变量 `current` 已接管节点 2，因此三个节点仍分别落在左右两区，既没有丢失也没有重复。
>
> **回到模型/代码：** 每轮最后两句 `previous = current` 和 `current = next` 分别更新两个区域的入口；调试时应检查“从两个入口可达的节点并集仍是全部原节点”。

## 9. 正式建立模型

| 建模项 | 本题结论 |
| --- | --- |
| 对象 | 节点身份以及节点上的单向 `next` 边 |
| 关系 | 当前节点的原后继最终应指回当前节点；等价地，当前节点应指向已反转前缀入口 |
| 状态 | `previous` 指向已反转前缀的新头；`current` 指向原序后缀入口；改边前用 `next` 暂存原后继 |
| 事件 | 当 `current != null` 时，把当前节点从未处理后缀迁移到已反转前缀 |
| 不变量 | 两个区域无重无漏；前缀已完全反转且以 `null` 结束；后缀保持原顺序；`current` 是后缀唯一入口 |
| 结果时机 | 当 `current == null` 时后缀为空，`previous` 指向包含全部节点的反转链，因此成为答案 |

一次状态转移必须按下面的因果顺序发生：

```text
next = current.next        // 保住尚未处理后缀的入口
current.next = previous    // 当前节点接到已反转前缀之前
previous = current         // 已反转前缀扩大一个节点
current = next             // 从保存的原后继继续
```

这里的顺序不是代码风格。第一行之后，`next` 是对“改写前世界”的快照；第二行正式改变图结构；第三、四行再把两个区域的入口更新到下一稳定时刻。若第二行先执行，原后缀入口无法从当前节点恢复。

> **小白追问：** `previous`、`current`、`next` 都是节点引用，为什么要给它们三个不同角色？
>
> **先给短答：** 它们分别回答三个不同问题：完成部分从哪里进入、这轮处理谁、覆盖当前边后下一轮从哪里继续。
>
> **最小例子：** 处理 `1 -> 2 -> 3` 的节点 2 前，`previous` 指向 `1 -> null`，`current` 指向节点 2，读取出的 `next` 指向 `3 -> null`。若少了 `previous`，节点 2 不知道应接向谁；少了 `current`，不知道改哪条边；少了 `next`，改边后无法继续到节点 3。
>
> **回到模型/代码：** 三个角色依次对应 `previous`、`current` 和循环内的 `ListNode next`。不要按“几个指针”的数量背模板，要按三个问题检查状态是否齐全。

> **小白追问：** 为什么必须先保存 `next`，不能先反转 `current.next` 再补救？
>
> **先给短答：** 因为写入会覆盖当前节点中唯一的原后继引用，覆盖后没有信息可以推回原下一站。
>
> **最小例子：** 初始 `previous = null`、`current = 1 -> 2`。若先做 `current.next = previous`，节点 1 立即变成 `1 -> null`；此时再读 `current.next` 只能得到 `null`，节点 2 的入口已经无法从现有变量恢复。
>
> **回到模型/代码：** 写前快照必须是第一句 `ListNode next = current.next`。它是破坏性更新 `current.next = previous` 的前置条件，不是可随意调整的编码风格。

### 状态为什么足够

`previous` 不需要保存已反转前缀的所有节点，因为沿它的 `next` 已能到达整个前缀。`current` 不需要保存整个后缀，因为后缀尚未被改动，沿它的 `next` 已能到达全部待处理节点。`next` 只在一轮内部保护即将被覆盖的原出口；一轮结束后，新的 `current` 已接管这个职责，旧快照即可丢弃。

因此长期状态其实只有 `previous` 与 `current` 两个区域入口，`next` 是事务式临时状态。所谓“迭代双指针”若只按数量记忆，会忽略最重要的语义差别：这不是两个指针夹逼区间，而是两个链表区域的所有权边界，加一个写操作前的快照。

### 哪些信息可以永久丢弃

当前边改成 `current -> previous` 后，原边 `current -> next` 可以永久丢弃，因为它已经通过局部变量 `next` 完成最后一次导航用途；之后目标结构中也不再需要这条正向边。已反转前缀内部的边不会再次改变，因为它们的方向已经符合最终答案。节点值从未参与决策，也无需进入辅助状态。

> **小白追问：** 删除旧边 `current -> next` 为什么是安全的，后面不会再需要它吗？
>
> **先给短答：** 旧边只承担“找到下一待处理节点”的导航任务，这个任务已交给局部变量 `next`；最终反转链本来就不应保留这条正向边。
>
> **最小例子：** 处理节点 2 时，旧边是 `2 -> 3`。保存 `next = 3` 后，把边改成 `2 -> 1`；下一轮直接由 `current = 3` 开始。最终需要的是 `3 -> 2`，所以旧边 `2 -> 3` 不但无需恢复，恢复反而会形成错误方向甚至环。
>
> **回到模型/代码：** 安全删除由两处共同保证：`next` 保证后续遍历，`current.next = previous` 建立最终方向。二者缺一不可。

### 相等值、方向与无环前提

遍历必须沿原链表从头到尾，因为输入只提供这个方向的导航。值相等不会合并节点；两个值都为 `7` 的节点仍会各迁移一次。模型依赖输入是一条以 `null` 结束的无环单链表，这是题目默认结构契约。若输入本身有环，`current` 不会自然到达 `null`，需要先检测环并另行定义结果，不能直接套用本算法。

### 递归模型只作替代对比

递归版的函数契约是：反转 `head` 开始的整段链，并返回这段链的新头。它先让调用栈走到原尾，再在返回阶段执行 `head.next.next = head` 把当前节点接到后缀尾部，同时用 `head.next = null` 封住新尾。它同样是 `O(n)` 时间，但调用栈为 `O(n)`；迭代版只保留三个引用，额外空间为 `O(1)`。本篇主线采用迭代状态机，递归只用于说明“后序返回可以提供逆向处理次序”，不再展开成第二套完整推导。

## 10. 所需数据结构详解

### 单链表节点：值与一条有向边

典型节点由 `int val` 和 `ListNode next` 组成。`val` 是载荷，`next` 是结构。单链表的关键特征不是“数据排成一行”，而是每个节点只保存后继入口，不保存前驱，也不支持按下标随机访问。访问第 `k` 个节点必须从某个已知入口沿边走过去。

本题使用的核心操作只有三种：读取 `current.next`、写入 `current.next`、比较引用是否为 `null`。在通常的算法成本模型里，这些都是 `O(1)`。每次写入改变的是节点对象中的引用字段，而不是复制整个节点。

### Java 引用：保存入口，不复制节点

`ListNode previous = current` 只复制一个引用值，使两个变量暂时指向同一个节点；它不会复制节点对象。随后给变量 `current` 重新赋值，也不会移动或销毁节点。理解这一点才能看懂“变量更新”和“结构更新”的区别：

```text
变量更新：previous = current
含义：previous 改为指向 current 所指的节点

结构更新：current.next = previous
含义：修改 current 节点内部保存的有向边
```

`null` 表示没有任何节点。初始化 `previous = null`，不仅代表已反转前缀为空，还保证第一个被迁移的原头节点会指向 `null`，自然成为新尾。

### 三个引用各自保存什么

| 引用 | 保存内容 | 生命周期 | 最坏数量 |
| --- | --- | --- | ---: |
| `previous` | 已反转前缀的新头节点 | 整个循环持续更新 | 1 个引用 |
| `current` | 尚未处理后缀的入口节点 | 整个循环持续更新 | 1 个引用 |
| `next` | 本轮改边前的原后继 | 单轮内部有效 | 1 个引用 |

最坏情况下链表有 5000 个节点，这三个变量仍只保存三个引用，空间不会随 `n` 增长。它们保存节点，不保存值、下标或节点集合。

### 为什么数组、栈和双向链表不是推荐容器

数组或栈能保存所有节点，并容易按逆序取出，时间仍是 `O(n)`，但需要 `O(n)` 额外空间。栈的后进先出特征确实匹配倒序输出，却掩盖了链表自身的边已经足以承载“已反转前缀”。

把输入转换为双向链表会提供前驱引用，但转换本身需要新增或维护额外字段，也改变了问题给定的数据结构。推荐模型所需的不是一个更强容器，而是三个具有清晰职责的引用。

> **小白追问：** 既然目标顺序是倒着的，为什么不使用栈来保存所有节点？
>
> **先给短答：** 栈当然能做，但当前节点改写后的 `next` 已经能把全部已处理节点串起来，相当于链表本身就在保存反向结果，无需再复制一份节点引用到栈中。
>
> **最小例子：** 处理 `1 -> 2` 后，`previous` 指向 `2 -> 1 -> null`。从这个入口已经能按目标顺序访问两个节点；再维护栈 `[1,2]` 只会重复保存相同节点身份。
>
> **回到模型/代码：** 本题真正需要的是三个固定引用，而不是一个随 `n` 增长的容器。`previous` 所指链承担结果存储，`current` 和 `next` 承担遍历导航。

### 递归调用栈保存了什么

递归版隐式保存每一层的 `head`、返回位置和局部执行状态，返回时自然得到从尾到头的处理顺序。这个便利以深度为 `n` 的调用栈为代价，所以额外空间是 `O(n)`；迭代版把未完成历史压缩成两个区域入口和一个单轮快照，额外空间才是 `O(1)`。

## 11. 生活化类比及边界

把单链表想成一条接力路线。每个站点的卡片只写着下一站地址，没有上一站地址。工作人员从起点出发，要把路线改成反向路线。到达当前站后，他必须先把原下一站地址抄到手中的临时便签，再把当前站卡片改写为“去刚刚处理过的站”。最后拿着便签前往原下一站。

| 生活对象或动作 | 算法中的对应物 |
| --- | --- |
| 每个接力站 | 一个有独立身份的 `ListNode` 节点 |
| 站点卡片上的下一站地址 | 节点的 `next` 引用 |
| 已经完成掉头的路线入口 | `previous` |
| 工作人员当前所在站 | `current` |
| 改牌前抄下的原下一站地址 | 临时变量 `next` |
| 先抄地址再改指示牌 | 先读 `current.next`，再写 `current.next = previous` |
| 按便签前往下一工作点 | `current = next` |
| 走出原终点后发现没有下一站 | `current == null` |
| 手中最后的反向路线入口 | 返回 `previous` |

这个类比最重要的地方是“改牌会破坏导航信息”。如果先把当前牌改成指向上一站，再照牌前进，工作人员会走回已处理区域，永远到不了尚未处理的站。

类比到这里为止。现实路线可以有分叉、双向道路、多个工作人员和备用地图，而题目中的节点只有一个 `next`，输入是一条无环链。临时引用也不是纸张的物理复制，而是 Java 中指向同一节点对象的引用值。类比帮助记住状态职责，正确性仍要依靠“不丢节点、两区覆盖全部节点、每轮缩短后缀”的不变量。

## 12. 典型输入的完整数据变化图

完整演算 `1 -> 2 -> 3 -> 4 -> 5 -> null`。下面每个快照都处于一轮结束后的稳定状态。`previous` 一侧的箭头已经是目标方向，`current` 一侧仍保持输入方向。

### 初始状态

```text
当前输入：current 指向节点 1
处理前状态：previous = null
判断依据：current != null，仍有节点待迁移
执行动作：尚未执行
处理后状态：尚未执行
新增结果：没有最终输出；已反转前缀为空

previous
   |
   v
 null        current
                |
                v
              1 -> 2 -> 3 -> 4 -> 5 -> null
              -------- 原方向 -------->
```

### 第 1 轮：迁移节点 1

```text
当前输入：节点 1
处理前状态：previous = null，current = 1
判断依据：1 的目标后继应是已反转前缀入口 null
执行动作：next = 2；1.next = null；previous = 1；current = 2
处理后状态：1 已成为正确的新尾；2 仍是完整后缀入口
新增结果：已反转前缀为 [1]

       previous             current
           |                   |
           v                   v
         1 -> null            2 -> 3 -> 4 -> 5 -> null
                              ----- 原方向 ----->

本轮临时快照 next 曾指向 2；current 接管后，该快照可释放。
```

### 第 2 轮：迁移节点 2

```text
当前输入：节点 2
处理前状态：previous 链为 1 -> null；current 链从 2 开始
判断依据：节点 2 应接到已反转前缀入口 1 之前
执行动作：next = 3；2.next = 1；previous = 2；current = 3
处理后状态：2 -> 1 已正确反转；3 仍能到达所有未处理节点
新增结果：已反转前缀扩大为 [2,1]

       previous             current
           |                   |
           v                   v
         2 -> 1 -> null       3 -> 4 -> 5 -> null
         <-- 目标方向         --- 原方向 --->
```

### 第 3 轮：迁移节点 3

```text
当前输入：节点 3
处理前状态：previous = 2，current = 3
判断依据：先保存 4，才能安全覆盖 3.next
执行动作：next = 4；3.next = 2；previous = 3；current = 4
处理后状态：左侧包含原前 3 个节点，右侧包含原后 2 个节点
新增结果：已反转前缀扩大为 [3,2,1]

       previous             current
           |                   |
           v                   v
         3 -> 2 -> 1 -> null  4 -> 5 -> null
```

### 第 4 轮：迁移节点 4

```text
当前输入：节点 4
处理前状态：previous 链为 3 -> 2 -> 1；current 链为 4 -> 5
判断依据：原后继 5 是最后一个尚未处理入口
执行动作：next = 5；4.next = 3；previous = 4；current = 5
处理后状态：只剩节点 5 尚未迁移
新增结果：已反转前缀扩大为 [4,3,2,1]

       previous             current
           |                   |
           v                   v
         4 -> 3 -> 2 -> 1 -> null    5 -> null
```

### 第 5 轮：迁移节点 5

```text
当前输入：节点 5
处理前状态：previous = 4，current = 5
判断依据：5 的原后继是 null，迁移后后缀将为空
执行动作：next = null；5.next = 4；previous = 5；current = null
处理后状态：全部节点都位于已反转前缀，未处理后缀为空
新增结果：previous 指向完整答案 [5,4,3,2,1]

       previous                         current
           |                               |
           v                               v
         5 -> 4 -> 3 -> 2 -> 1 -> null    null
```

循环条件再次检查时 `current == null`，不再进入。返回 `previous`，而不是返回已经走到链外的 `current`。整个过程中没有单独“寻找新头”的动作；新头就是最后一次迁移后保存于 `previous` 的原尾节点。

## 13. 边界场景的数据变化

### 空链表

```text
head = null
previous = null
current = null

while (current != null) 为 false
没有读取 current.next，因此不会出现空引用访问
返回 previous = null
```

循环一次都不执行，结构中没有残留节点，也不需要专门创建空链表对象。

### 单节点链表 `[7]`

```text
初始：previous = null，current = 7 -> null

next = current.next = null
current.next = previous = null
previous = current = 7
current = next = null

结束：返回 7 -> null
```

虽然节点的边看起来没有变化，循环仍完成一次标准迁移。统一状态转移不需要为单节点增加特殊分支。两个值相同的节点也不能按此场景合并，例如 `7a -> 7b` 仍会得到 `7b -> 7a`，因为算法判断引用和 `null`，不判断 `val`。

> **小白追问：** 空链和单节点看起来完全不同，为什么可以共用同一套循环而不写特殊分支？
>
> **先给短答：** 因为循环只问“当前是否还有节点可迁移”；空链迁移零次，单节点迁移一次，两者结束时都满足后缀为空、`previous` 指向完整答案。
>
> **最小例子：** 空链初始化为 `previous = null, current = null`，直接返回 `null`。单节点 A 初始化为 `previous = null, current = A`，一轮后得到 `previous = A, current = null`，并且 `A.next` 仍是 `null`。
>
> **回到模型/代码：** 统一边界由 `while (current != null)` 控制，返回值始终是 `previous`；无需在 `reverseList` 开头分别判断 `head == null` 或 `head.next == null`。

### 更新顺序错误导致断链

对 `1 -> 2 -> 3`，若先执行 `1.next = previous`，初始 `previous` 为 `null`：

```text
错误改写后：1 -> null

变量 current 仍指向 1，但从 current.next 只能读到 null
节点 2 -> 3 虽然对象仍可能存在于内存中，算法已经没有任何入口能到达它们
```

这叫断链：不是节点立刻被删除，而是从算法持有的入口无法再访问。正确模型用 `next = 2` 在改写前保住后缀入口。

### 错误连接导致环

若在两节点链 `1 -> 2` 上只做 `2.next = 1`，却没有让 `1.next = null`，结果是：

```text
1 -> 2
^    |
|____|
```

沿 `next` 打印会无限重复 `1,2,1,2`。正确迭代模型在第一轮就让原头 `1.next = previous`，而初始 `previous` 恰好为 `null`，所以新尾自动封口。递归模型则必须显式执行 `head.next = null`。

### 输入本身有环

题目保证的是普通单链表。如果调用方私自传入 `1 -> 2 -> 3 -> 2`，`current` 沿原连接不会按有限步骤稳定到达 `null`；边在修改过程中还会改变环形关系，结果不属于本题定义。生产代码若允许这种输入，应先用快慢指针检测环，再选择报错、断环或定义特殊反转规则，不能把“算法没停”归咎于空链边界。

## 14. 正确性与不变量

证明对象是迭代推荐模型。我们要证明：返回链包含原链全部节点且各出现一次；相邻关系全部反向；算法一定终止；不会因为原地改边而丢失后缀或制造环。

### 初始化成立

循环开始前，`previous = null` 表示已处理前缀包含零个节点。空链当然已经正确反转，并以 `null` 结束。`current = head` 指向完整的原序链，所以未处理后缀包含全部节点。两个区域没有重复，合起来正好是原链全部节点。

### 一轮迁移保持不变量

假设一轮开始时不变量成立。`current` 是后缀第一个节点。读取 `next = current.next` 后，`next` 保存除当前节点之外的剩余后缀入口，因此后续即使覆盖 `current.next`，剩余节点也没有丢失。

执行 `current.next = previous`，当前节点接到已经正确反转的前缀头部。由于 `previous` 区域只包含原链中位于 `current` 之前的节点，并且内部以 `null` 结束，加入当前节点后仍是一条无环链。随后 `previous = current` 让它成为扩大后前缀的新入口，`current = next` 让保存的原后继成为缩小后缀的新入口。

这次迁移没有复制、删除或跳过节点，只把当前节点从右侧集合移动到左侧集合，所以两个区域仍无重无漏。后缀内部没有被改动，仍保持原顺序；前缀新增的边方向符合最终反转关系。因此不变量继续成立。

### 为什么不会漏节点

唯一可能造成遗漏的时刻是覆盖 `current.next`。但覆盖前已经把原后继保存到 `next`，一轮末又赋给 `current`。只要后缀非空，算法始终持有它的入口；沿后缀原连接仍可到达所有剩余节点。没有任何节点需要通过已经删除的正向边再次访问。

### 为什么不会制造环

迁移前，`current` 属于后缀，不属于 `previous` 链。新边只从 `current` 指向已处理前缀；前缀的所有边沿原下标严格向前回退并最终到达 `null`，不可能再走回 `current`。因此添加这条边不会闭合成环。第一轮把原头指向 `null`，为整个前缀建立了永久尾端。

> **小白追问：** 每轮都把箭头改向前面，为什么不会不小心连成环？
>
> **先给短答：** 因为当前节点尚在后缀中，已反转前缀不包含它；新边进入前缀后只能一路走到 `null`，没有边能返回当前节点。
>
> **最小例子：** 处理节点 2 前，前缀是 `1 -> null`，后缀是 `2 -> 3 -> null`。改成 `2 -> 1 -> null` 后，从节点 1 不存在回到节点 2 的边，所以无法闭环；节点 3 仍单独位于未处理后缀。
>
> **回到模型/代码：** `current.next = previous` 之所以安全，依赖循环不变量中的“两区不重叠”和“`previous` 链以 `null` 结束”。若输入原本有环，这两个前提就不再自动成立。

### 终止与最终答案

输入有 `n` 个节点且无环。每轮都让 `current` 沿保存的原始 `next` 前进一个节点，一个节点不会第二次成为待处理入口。因此恰好执行 `n` 轮后，`current == null`，算法终止。

根据不变量，此时未处理后缀为空，全部原节点都位于已反转前缀；前缀连接方向全部正确且以 `null` 结束。`previous` 是该完整链的入口，也就是原尾节点，所以返回它得到正确答案。空链时初始化已经是终止状态，同一结论仍成立。

> **小白追问：** `current` 走到 `null` 时，为什么 `previous` 恰好是新头，而不只是最后处理过的一个孤立节点？
>
> **先给短答：** 因为每次更新 `previous` 前，当前节点都已经接到旧 `previous` 所代表的完整前缀上；它保存的始终是整段已反转链的入口。
>
> **最小例子：** 在 `1 -> 2 -> 3` 中，三轮结束后的 `previous` 依次指向 `1`、`2 -> 1`、`3 -> 2 -> 1`。当 `current = null` 时，最后一个入口 3 已能到达全部节点，不是只指向节点 3 自身。
>
> **回到模型/代码：** `previous = current` 必须发生在 `current.next = previous` 之后；循环退出后 `return previous`，不能返回已经用于表示空后缀的 `current`。

### 递归正确性的压缩对比

递归版依赖另一条契约：较短后缀返回时已经正确反转，当前层只负责把 `head` 接到该后缀尾部并封住新尾。基线是空链或单节点，递归每层减少一个节点，因此最终会到达基线。这个模型正确但需要保存全部未返回调用层；它不改变本文推荐的迭代不变量，也不作为第二条主线展开。

## 15. 时间与空间复杂度推导

定义 `n` 为从输入 `head` 沿 `next` 可达的节点数量，题目中 `0 <= n <= 5000`。一次引用读取、引用写入、赋值和空值比较按 `O(1)` 计算。返回的是原有节点入口，不把输入节点本身当作算法新申请的输出空间。

### 数组列表直接模型

第一遍访问 `n` 个节点并存入列表，发生 `n` 次加入；第二遍按逆序改写约 `n` 条边。两段操作相加是 `2n` 量级，所以时间复杂度为 `O(n)`，不是 `O(n^2)`。列表同时保留 `n` 个节点引用，额外空间为 `O(n)`。结果链复用原节点，返回值本身只占一个引用。

### 从尾反复找前驱的方向

找原尾最多查看 `n` 个节点，找它的前驱最多再查看 `n-1` 个，随后依次递减到 `1`。这个等差数列的总访问次数为 `n(n+1)/2`，时间复杂度为 `O(n^2)`。若不使用集合，它可以保持 `O(1)` 额外空间，但时间代价没有必要。

### 原地迭代推荐模型

每个节点只经历一个生命周期：

```text
未处理后缀中的节点
-> 一次成为 current
-> 读取一次原 next
-> 改写一次 next
-> 永久进入已反转前缀
```

一个节点不会退回后缀，也不会被重新扫描。总共 `n` 次循环，每轮是固定数量的 `O(1)` 操作，所以时间复杂度为 `O(n)`。`previous`、`current`、`next` 的数量不随 `n` 变化，额外空间复杂度为 `O(1)`。

这里不需要用“内层循环均摊”掩盖成本；元素生命周期可以直接给出严格总次数：`n` 次保存原后继、`n` 次改边、`n` 次边界迁移。链表有 5000 个节点时，循环也只是约 5000 轮。

> **小白追问：** 每轮有四条核心赋值，为什么时间复杂度仍是 `O(n)`，不是 `O(4n)` 或更高？
>
> **先给短答：** 大 O 关注输入变大时操作次数的增长级别；每个节点承担固定数量的操作，四这个常数不会随 `n` 增长。
>
> **最小例子：** 两个节点执行两轮，约做两次保存、两次改边和四次边界赋值；四个节点执行四轮，各类操作也只是同步翻倍，没有任何节点被重新扫描。
>
> **回到模型/代码：** 循环条件使每个节点恰好一次成为 `current`。总成本可以写成 `n * O(1) = O(n)`，不需要均摊分析，也不存在隐藏的内层遍历。

> **小白追问：** 结果链明明有 `n` 个节点，为什么额外空间还能写成 `O(1)`？
>
> **先给短答：** 因为这些节点原本就在输入中，算法只是改写它们的边；额外申请并随 `n` 增长的状态只有零个。
>
> **最小例子：** 无论输入是 `1 -> 2` 还是 5000 个节点，迭代过程始终只有 `previous`、`current`、`next` 三个引用。结果复用原节点，没有新建长度为 `n` 的数组、栈或节点副本。
>
> **回到模型/代码：** 空间分析统计辅助状态，不重复计算输入节点和返回的一个头引用。三个引用数量固定，所以迭代额外空间为 `O(1)`；递归调用帧数量随 `n` 增长，才是 `O(n)`。

### 递归模型

每层处理一个节点，递推式可写为 `T(n) = T(n-1) + O(1)`，所以时间复杂度是 `O(n)`。调用栈最深保存 `n` 层，每层包含参数、返回地址和局部状态，额外空间复杂度为 `O(n)`。Java 语言和虚拟机并不保证把这种尾部之外仍有操作的递归优化成常量栈；实际还可能在到达 5000 层前后受具体线程栈配置影响而抛出 `StackOverflowError`。因此不能把递归空间写成 `O(1)`。

| 方案 | 时间复杂度 | 额外空间 | 主要代价 |
| --- | --- | --- | --- |
| 数组保存节点后倒连 | `O(n)` | `O(n)` | 保存全部节点引用并处理两轮 |
| 从尾反复找前驱 | `O(n^2)` | `O(1)` | 单链表缺少前驱导致重复扫描 |
| 原地迭代 | `O(n)` | `O(1)` | 三个引用，逐节点迁移 |
| 递归后序接回 | `O(n)` | `O(n)` | 深度为 `n` 的调用栈 |

### 泛用 Java 建模骨架

下面是面向任意载荷类型的单向链反转骨架。它不依赖 LeetCode 的 `ListNode`，强调三个稳定角色：`reversedPrefixHead`、`unprocessedSuffixHead` 和写前快照 `savedSuffixHead`。节点载荷完全不参与控制流程。

```java
final class ChainLink<T> {
    final T payload;
    ChainLink<T> next;

    ChainLink(T payload) {
        this.payload = payload;
    }
}

final class ForwardOnlyChainModel {
    static <T> ChainLink<T> reverse(ChainLink<T> first) {
        ChainLink<T> reversedPrefixHead = null;
        ChainLink<T> unprocessedSuffixHead = first;

        while (unprocessedSuffixHead != null) {
            ChainLink<T> savedSuffixHead = unprocessedSuffixHead.next;

            unprocessedSuffixHead.next = reversedPrefixHead;
            reversedPrefixHead = unprocessedSuffixHead;
            unprocessedSuffixHead = savedSuffixHead;
        }

        return reversedPrefixHead;
    }
}
```

这个骨架可迁移到“只给下一项入口的单向结构”。它要求输入从 `first` 出发最终到达 `null`。`savedSuffixHead` 不是第三个长期区域，而是覆盖 `next` 之前的短期保护；循环结束后，完整结果已经由 `reversedPrefixHead` 表示。

### LeetCode 可直接提交代码

```java
class Solution {
    public ListNode reverseList(ListNode head) {
        ListNode previous = null;
        ListNode current = head;

        while (current != null) {
            ListNode next = current.next;
            current.next = previous;
            previous = current;
            current = next;
        }

        return previous;
    }
}
```

### 本地可运行示例

```java
class ListNode {
    int val;
    ListNode next;

    ListNode(int val) {
        this.val = val;
    }
}

public class Solution {
    public ListNode reverseList(ListNode head) {
        ListNode previous = null;
        ListNode current = head;

        while (current != null) {
            ListNode next = current.next;
            current.next = previous;
            previous = current;
            current = next;
        }

        return previous;
    }

    public ListNode reverseListRecursively(ListNode head) {
        if (head == null || head.next == null) {
            return head;
        }

        ListNode newHead = reverseListRecursively(head.next);
        head.next.next = head;
        head.next = null;
        return newHead;
    }

    private static ListNode build(int[] values) {
        ListNode dummy = new ListNode(0);
        ListNode tail = dummy;
        for (int value : values) {
            tail.next = new ListNode(value);
            tail = tail.next;
        }
        return dummy.next;
    }

    private static String toText(ListNode head) {
        StringBuilder text = new StringBuilder("[");
        ListNode current = head;
        while (current != null) {
            if (text.length() > 1) {
                text.append(", ");
            }
            text.append(current.val);
            current = current.next;
        }
        return text.append(']').toString();
    }

    private static void check(String expected, ListNode actualHead) {
        String actual = toText(actualHead);
        System.out.println(actual);
        if (!expected.equals(actual)) {
            throw new AssertionError(
                    "expected=" + expected + ", actual=" + actual);
        }
    }

    public static void main(String[] args) {
        Solution solution = new Solution();

        check("[5, 4, 3, 2, 1]",
                solution.reverseList(build(new int[]{1, 2, 3, 4, 5})));
        check("[2, 1]", solution.reverseList(build(new int[]{1, 2})));
        check("[]", solution.reverseList(null));
        check("[7]", solution.reverseList(build(new int[]{7})));
        check("[4, 3, 2, 1]",
                solution.reverseListRecursively(build(new int[]{1, 2, 3, 4})));

        System.out.println("all cases passed");
    }
}
```

预期输出：

```text
[5, 4, 3, 2, 1]
[2, 1]
[]
[7]
[4, 3, 2, 1]
all cases passed
```

### 代码与模型角色映射

| 模型角色 | Java 变量或代码块 |
| --- | --- |
| 已反转前缀入口 | `previous` |
| 未处理后缀入口，也就是当前对象 | `current` |
| 改边前保存的原后缀入口 | `ListNode next = current.next` |
| 触发条件 | `while (current != null)` |
| 反向连接事件 | `current.next = previous` |
| 前缀边界前移 | `previous = current` |
| 后缀边界前移 | `current = next` |
| 结果产生时机 | 循环结束后 `return previous` |
| 递归后缀结果 | `newHead = reverseListRecursively(head.next)` |
| 递归接回当前头并封尾 | `head.next.next = head` 与 `head.next = null` |

代码中的 `next` 可以命名为 `savedNext`，但不能为了短而删除这个角色。四条核心赋值的书写顺序直接对应信息保护、改边、扩大前缀、缩小后缀四个模型动作。

> **小白追问：** 不背这四行代码，怎样在面试或调试时自己重新写出正确顺序？
>
> **先给短答：** 按“先保护将被覆盖的信息，再改结构，最后更新两个区域入口”的因果顺序写，而不是按变量名记忆。
>
> **最小例子：** 处理 `1 -> 2` 时，先把 2 保存为下一工作点；再把 1 接到空前缀；随后让完成区入口指向 1，最后让待处理区入口指向 2。若把第一步移到改边之后，读到的下一工作点会变成 `null`。
>
> **回到模型/代码：** 四个动作依次映射为 `next = current.next`、`current.next = previous`、`previous = current`、`current = next`。代码评审时逐项核对这四个职责即可。

## 17. 边界、常见错误与调试观察点

| 层次 | 常见错误 | 后果 | 应观察的状态 |
| --- | --- | --- | --- |
| 建模错误 | 把反转理解为值倒序 | 数值表面正确，但节点关系和身份未反转 | 调用前后同一节点对象的 `next` 指向 |
| 建模错误 | 试图从尾部找前驱 | 单链表没有反向入口，出现重复扫描 | 每次寻找前驱从头经过了多少节点 |
| 建模错误 | 没有明确输入必须无环 | 非法环形输入无法以 `current == null` 终止 | 节点身份是否重复出现 |
| 条件错误 | 循环写成 `current.next != null` | 原尾节点不被迁移，返回链缺少新头 | 最后一轮 `current` 是否仍被处理 |
| 条件错误 | 递归基线只判断 `head.next == null` | 空链表访问 `head.next` 时抛出异常 | 先检查 `head == null` |
| 实现错误 | 覆盖 `current.next` 后才保存下一站 | 未处理后缀失去入口，结果常只有原头 | 改边前的 `next` 是否仍指向原后继 |
| 实现错误 | 返回 `current` | 循环结束时它必为 `null` | 结束快照中的两个区域入口 |
| 实现错误 | 忘记初始化 `previous = null` | 原头不能稳定成为新尾，可能保留旧边 | 第一轮后原头的 `next` |
| 实现错误 | 递归缺少 `head.next = null` | 当前头与原后继形成环 | 回溯一层后从节点连续走若干步 |
| 实现错误 | 错误交换赋值顺序 | 自环、回到已处理区或节点丢失 | 每条赋值前后的三个引用身份 |

调试时不要只打印最终值序列。若出现断链或环，值可能重复，单看值无法判断节点身份。应在每轮改边前后记录：

```text
before: previous=<节点身份或 null>, current=<节点身份>, savedNext=<原后继身份>
after:  previous=<新前缀头>, current=<新后缀头>
edge:   刚处理节点.next=<应等于旧 previous>
```

本地可以临时打印 `System.identityHashCode(node)` 区分值相同的节点。打印整条链时应设置最大步数，例如超过 `n + 1` 步立即报告疑似环，否则错误实现可能让调试程序本身无限输出。

推荐逐项核对四个断点：保存 `next` 后，它是否仍能到达完整后缀；改写 `current.next` 后，它是否等于旧 `previous`；更新 `previous` 后，它是否等于刚处理节点；更新 `current` 后，它是否等于旧 `next`。只要某一步不满足，就能直接定位状态机在哪个转换上失真。

测试集至少包括：空链、单节点、双节点、五节点典型链、多个节点值相同、节点值达到 `-5000` 或 `5000`。数值边界不会改变流程，但能验证实现没有错误地把值当作哨兵。递归版还应在目标运行环境中谨慎评估长链栈深度，不应仅凭小样例通过就认为不存在资源风险。

## 18. 最终模型卡

| 项目 | 复习结论 |
| --- | --- |
| 题型识别指纹 | 单向结构只能沿下一项前进；要求原地改变连接方向；写当前边会破坏后续导航 |
| 一句话关系模型 | 把当前节点从原序后缀摘到已反转前缀头部，并在改边前保住原后继 |
| 实际保存什么 | 已反转前缀入口 `previous`、未处理后缀入口 `current`、本轮原后继 `next` |
| 状态何时变化 | `current != null` 时执行一次节点迁移 |
| 答案何时产生 | 后缀为空时，`previous` 成为包含全部节点的新头 |
| 核心不变量 | 前缀已正确反转，后缀仍保持原序，两区无重无漏且都能由各自入口到达 |
| 时间复杂度 | 迭代 `O(n)`；递归 `O(n)` |
| 空间复杂度 | 迭代 `O(1)`；递归调用栈 `O(n)` |

### 四句建模结论

```text
我正在处理的对象是：未处理后缀入口处的当前节点及其 next 有向边。
我必须持续保存的是：已反转前缀入口、未处理后缀入口和改边前的原下一站。
当 当前节点仍然存在 发生时，我执行：先保存原后继，再让当前节点指向已反转前缀，并把两个区域边界各向前迁移一步。
答案在 未处理后缀变为空时 由 previous 所指向的完整反转链计算出来。
```

### 泛用迁移模板

```text
1. 明确输入结构允许沿哪个方向导航，以及哪些写操作会覆盖导航信息。
2. 把全过程切成“已经处理正确的区域”和“尚未处理但仍保持原结构的区域”。
3. 为每个区域只保存一个足以到达全部内容的入口。
4. 在破坏性写入前，先保存写入后仍需使用的最小信息。
5. 一次只迁移一个最小处理单位，并验证两区无重无漏。
6. 当待处理区域为空时，从已完成区域入口取得结果。
```

### 后续变式

- **92. 反转链表 II：**只反转 `[left, right]` 区间。变化的是区域边界：除了反转状态，还要保存区间前驱和区间后继，以便局部反转后重新接回整链。
- **25. K 个一组翻转链表：**每轮先确认剩余节点至少有 `k` 个，再复用局部反转状态机。变化的是触发条件和结果连接时机，核心“改边前保存下一站”不变。
- **234. 回文链表：**先找中点，再反转后半链进行比较，必要时恢复。变化的是反转结果的用途；它成为比较状态，而不是最终输出。
- **138. 随机链表的复制：**节点不只有一条关系。变化的是状态维度：只保存 `next` 不再足够，还必须保持 `random` 指向的身份映射，提醒我们最小状态取决于所有会被破坏的关系。
