这道题真正难的地方通常不是写出一个队列，而是完成前面的几次翻译：`[1,0]` 到底应该画成哪一个方向的箭头？为什么“能否完成所有课程”会变成“有没有环”？为什么一个整数就足以概括一门课当前还差多少条件？队列为空为什么有时表示全部完成，有时却表示互相等待？

本篇不把“拓扑排序”当作开场答案。我们会先模拟人怎样安排课程，看见反复检查依赖的浪费，再逐步得到“剩余前置数量”和“当前可执行前沿”。等模型已经成立后，再给这种过程命名。

## 2. 完整题目

有 `numCourses` 门课程，编号为 `0` 到 `numCourses - 1`。二维数组 `prerequisites` 描述先修要求。每一项 `prerequisites[i] = [course, required]` 表示：只有先完成课程 `required`，才可以学习课程 `course`。

需要判断是否存在一种安排，使全部课程最终都能完成。存在就返回 `true`；如果某些课程无论如何都无法开始，则返回 `false`。题目只要求判断可行性，不要求返回具体学习顺序。

**示例 1：一条单向依赖**

```text
输入：numCourses = 2, prerequisites = [[1,0]]
输出：true

解释：先完成课程 0，再完成课程 1，全部课程都能结束。
关系方向：0 -> 1
```

**示例 2：两门课互相等待**

```text
输入：numCourses = 2, prerequisites = [[1,0],[0,1]]
输出：false

解释：课程 1 等课程 0，课程 0 又等课程 1，没有任何一门能够先开始。
关系方向：0 -> 1 -> 0
```

**示例 3：多条依赖汇合**

```text
输入：numCourses = 4,
      prerequisites = [[1,0],[2,0],[3,1],[3,2]]
输出：true

解释：课程 0 完成后，课程 1 和 2 都可以学习；
      两者都完成后，课程 3 才能学习。一种顺序是 0,1,2,3，
      另一种顺序是 0,2,1,3。
```

官方约束如下：

- `1 <= numCourses <= 2000`。
- `0 <= prerequisites.length <= 5000`。
- 每个依赖项长度都是 `2`。
- 课程编号都在 `[0, numCourses - 1]` 范围内。
- `prerequisites` 中的课程对互不相同，即不会重复出现完全一样的 `[course, required]`。

官方额外提示把问题指向“有向图中是否存在环”，并指出可以分别从 DFS 和 BFS 两条路线完成拓扑判断。这里先记住这是核验结论，后文仍从课程安排的动作推导出来。

Java 入口类为 `Solution`，方法签名为
`public boolean canFinish(int numCourses, int[][] prerequisites)`。

`numCourses` 最多为 `2000`，依赖最多为 `5000`。枚举所有课程顺序的阶乘级方法肯定不可行；对每门课反复扫描全部依赖也可能造成大量重复。这个规模提示我们应争取让每门课和每条依赖只被处理常数次。

### 2.1 从题目到拓扑排序：一步步的建模主线

这一节先给出本题的主线。后面的章节会分别展开暴力过程、数据结构、正确性、复杂度和 Java 代码。

#### 第一步：只保留题目动作和最终目标

```text
题目动作：上一门课程
最终目标：判断所有课程能不能都上完
```

先不要想到 `Queue`、`Map`、图或 `foreach`。这些是实现工具，不能替代对过程的理解。

#### 第二步：把一条输入关系翻译成完整句子

```text
prerequisites[i] = [course, required]
```

它的完整含义是：

```text
课程 course 必须等待课程 required 完成
```

因此关系方向是：

```text
required -> course
```

箭头表示“完成左边后，会让右边更接近可学习”，不是照抄数组的左右顺序。

#### 第三步：先写一个笨但正确的人工过程

人会这样安排课程：

```text
1. 找一门所有前置课程都已经完成的课程
2. 上完它
3. 看看哪些后续课程因此少等了一门课
4. 如果某门后续课程已经不再等待任何前置课，就把它作为下一批候选
5. 重复处理
```

如果某一轮找不到可以上的课程，但仍有课程没有完成，过程就被卡住；如果所有课程都完成，答案就是 `true`。

#### 第四步：描述一次动作造成的变化

假设课程 `1` 已经上完：

```text
事件：课程 1 完成
受影响者：所有等待课程 1 的后续课程
状态变化：每个受影响课程的剩余前置数量减一
触发条件：剩余前置数量变成 0
后续动作：该课程加入当前可处理列表
```

注意三个概念不要混在一起：

```text
固定关系：课程 3 的前置课程包含 1
变化状态：课程 3 还剩几个前置课程没有完成
完成事件：课程 1 被真正处理完
```

固定关系来自题目，不会因为处理过程改变；变化状态会随着课程完成而改变；完成事件触发状态更新。

#### 第五步：从过程推导出需要保存的信息

为了执行上面的动作，需要回答四个问题：

```text
问题 1：一门课程完成后，要更新谁？
保存：dependents，完成当前课程后需要更新的后续课程列表

问题 2：一门课程还差多少个前置条件？
保存：remainingPrerequisites，每门课程剩余的前置数量

问题 3：当前有哪些课程可以上但还没有处理？
保存：readyCourses，当前可执行前沿

问题 4：总共已经完成多少门课程？
保存：completedCourses，全局完成数量
```

它们不是从题目中一次猜出来的，而是从人工过程逐个推导出来的：

```text
先保存每门课的等待列表
-> 发现每轮都在寻找“当前能上的课”，保存 readyCourses
-> 发现每次都在扫描“谁等待刚完成的课”，反向保存 dependents
-> 发现后续只需要知道还剩几项等待，把等待列表压缩成数量
-> 最后统计完成数量，判断是否覆盖全部课程
```

#### 第六步：确定待处理列表的规则

当前可学课程可能同时有多门。本题只判断能否全部完成，因此可以任选一门：

```text
取任意一门：普通队列、栈或集合都可以
取最小编号：使用小根堆
取最大编号：使用大根堆
```

本题使用普通队列只是实现选择，因为题目不要求特定学习顺序。

#### 第七步：把过程命名为拓扑排序

到这里，过程已经完整：

```text
不断取出当前没有未完成前置的课程
-> 完成它
-> 解除它对直接后继课程的一项等待
-> 把等待数量变成 0 的后继课程加入待处理列表
-> 直到待处理列表为空
```

这个过程的标准名称是**拓扑排序**；使用剩余前置数量和队列实现时，通常称为 **Kahn 算法**。

本题不要求输出排序结果，只需要判断排序过程是否覆盖全部课程：

```text
completedCourses == numCourses -> 全部课程都能完成，返回 true
completedCourses <  numCourses -> 还有课程被依赖关系困住，返回 false
```

因此，成环不是另一个凭空增加的检测步骤。环的实际表现是：环中的课程都在等待别的课程，无法产生第一门可处理课程；或者处理完独立分支后，待处理列表耗尽，但完成数量仍小于总课程数。

#### 这条主线的可迁移版本

遇到任务依赖、构建依赖、审批前置等题目时，可以依次问：

```text
题目允许我执行什么动作？
有哪些参与对象？
对象之间是谁必须等待谁？
一次动作会影响谁？
被影响者的状态从什么变成什么？
什么状态允许下一步？
为了快速找到下一步，需要保存哪些关系和状态？
过程结束后，什么条件代表成功？
```

## 3. 先把题目说成人话

**一句话生活化复述：**有一批任务，每个任务可能有若干前置任务；要判断这些任务能否从“不需要等待的任务”开始，一个接一个全部办完。

**一句话关系化复述：**给定若干有方向的先后约束，判断所有对象能否排成一个满足每条约束的先后顺序。

先看一项具体数据 `prerequisites[i] = [3,1]`。自然语言是“课程 3 需要课程 1”。若箭头表达“完成左端后会释放右端”，那么应该画成：

```text
前置课程 1  ----完成后允许---->  后继课程 3
```

不要按数组书写顺序直接画 `3 -> 1`。数组中的第一项是“被依赖者”，第二项才是“前置者”。

> **小白追问：** `prerequisites` 写的是 `[course, required]`，为什么箭头却从第二项指向第一项？
>
> **先给短答：** 箭头表达的是“谁完成后会让谁更接近可学习”，不是照抄二元组的书写顺序；完成 `required` 会释放 `course`，所以方向是 `required -> course`。
>
> **最小例子：** 只有 `[1,0]` 时，课程 0 可以先学，课程 1 必须后学。若画成 `1 -> 0`，算法会把课程 1 当成无需等待的起点，得到的学习动作与题意正好相反。画成 `0 -> 1` 后，完成 0 才能沿箭头通知 1。
>
> **回到模型/代码：** 建图语句是 `dependents.get(required).add(course)`。外层下标保存“刚完成谁”，列表元素保存“接下来通知谁”；入度则加在被依赖的 `course` 上。

| 要素 | 本题翻译 |
| --- | --- |
| 对象 | 每一门课程，也就是编号为 `0..numCourses-1` 的节点 |
| 关系 | “必须先完成”这一先后依赖；`required -> course` |
| 方向 | 从已完成的前置课程流向被它释放的后继课程 |
| 目标 | 判断是否存在覆盖全部课程的合法完成顺序 |
| 限制 | 一门课必须等它的所有直接前置课程都完成，而不是满足其中任意一门 |
| 危险结构 | 一圈课程首尾相接地互相等待，也就是有向环 |

这里的“图”并不是额外创造出来的高深概念。课程是点，先修关系是带方向的线，题目本来就在描述一个有向关系网络。建图只是把自然语言中隐含的对象和关系显式保存下来。

## 4. 第一切入点：读题时先看什么

第一次读题，先圈出四组真正有建模价值的词：

1. **“之前”“必须先”**：关系有方向，顺序不能交换。
2. **“某些课程”**：一门课程可能没有前置，也可能有一个或多个前置。
3. **“完成所有”**：只完成大部分不算成功；最后必须核对处理数量。
4. **“是否可能”**：答案虽然是布尔值，但本质是在问一个合法顺序是否存在。

“学期”“选修”“学习”只是故事包装。把它替换成 Maven 模块构建、工单前置审批、流水线步骤或项目任务，关系完全不变。真正需要保留的是“谁必须在谁之前”。

最小样例 `[[1,0]]` 中，人工会先找当前不用等待的课程 0，完成它，再完成课程 1。第二个样例 `[[1,0],[0,1]]` 中，人工一开始就找不到任何不用等待的课程。这给出第一个可操作问题：

> 不要直接猜整条顺序，先问“此刻有哪些课程已经满足全部前置条件？”

数据范围继续提供信号。`V <= 2000`、`E <= 5000`，其中 `V` 是课程数，`E` 是依赖数。`V!` 不可能接受；即便每完成一门课都重新检查整个网络，也会重复阅读同一条关系。理想状态是课程只完成一次，依赖只解除一次。

还要留意一个容易被布尔返回值掩盖的问题：若把所有边都反过来，有向环依然是有向环，所以某些错误方向的实现可能仍然碰巧返回正确的 `true/false`。但“当前可以学什么”的语义已经完全错误，也无法正确扩展到输出课程顺序、学期数等问题。因此边方向必须按业务关系建模，不能只靠两个布尔样例碰运气。

## 5. 最直接的人工或暴力模型

最贴近人工安排的模型是“每轮从全部未完成课程中找一门现在能学的课”。为了判断课程是否能学，先为每门课保存它的前置课程列表。

完整步骤如下：

1. 标记所有课程为未完成。
2. 从课程 0 扫到课程 `V-1`。
3. 对每门未完成课程，逐个查看它的前置课程是否已经完成。
4. 找到一门全部条件都满足的课程，就完成它并开始下一轮全局扫描。
5. 若一轮找不到可完成课程，但仍有未完成课程，返回 `false`。
6. 若累计完成 `V` 门课程，返回 `true`。

伪代码可以写成：

```text
completed[V] = false
repeat at most V rounds:
    chosen = -1
    for every unfinished course:
        if every prerequisite of course is completed:
            chosen = course
            break
    if chosen == -1:
        return false
    completed[chosen] = true
return true
```

这个模型一定正确。每次只有在全部前置课程已完成时才选择课程，所以不会产生非法顺序；只要存在合法顺序，当前剩余课程中至少有一门可以作为下一门，否则合法顺序自己的下一项也不存在。它并不“笨”，反而已经抓住了可执行前沿，只是每轮都重新寻找前沿。

若预先按课程组织前置列表，一轮完整检查最多读取 `V` 个课程和 `E` 条依赖，最多进行 `V` 轮，所以时间为 `O(V(V+E))`。保存依赖列表和完成标记需要 `O(V+E)` 额外空间。若更原始地对每门课程都扫描整个二维数组，成本还会更高。

另一种绝对直接的方法是枚举 `V!` 种课程排列，再验证每条依赖的先后位置，时间达到 `O(V! * (V+E))`。它适合说明“存在一个合法顺序”的定义，却不适合本题规模。后文以更接近人工的重复扫描模型作为主要优化对象。

## 6. 暴力到底浪费在哪里

考虑下面这组依赖：

```text
0 -> 1 -> 2 -> 3 -> 4

对应 prerequisites：
[[1,0],[2,1],[3,2],[4,3]]
```

如果每轮按编号从大到小扫描未完成课程，会看到重复特别清楚：

```text
第 1 轮：检查 4，发现 3 未完成；
          检查 3，发现 2 未完成；
          检查 2，发现 1 未完成；
          检查 1，发现 0 未完成；
          检查 0，终于可以完成。

第 2 轮：再次检查 4、3、2；
          再次读取“4 等 3、3 等 2、2 等 1”；
          到课程 1 才发现它刚刚被课程 0 释放。

第 3 轮：又读取“4 等 3、3 等 2”，再完成课程 2。
```

一条依赖如 `3 -> 4` 在前几轮中被反复问：“3 完成了吗？”答案多次为否。这些否定结论本轮算完就丢弃；下一轮仍从头检查。更关键的是，课程 0 完成时，我们明明已经知道**只有依赖 0 的课程**可能因此改变状态，却仍去扫描所有课程。

于是可以把优化目标写得很具体：

> 不要每轮重新询问所有课程的全部前置；应在某门课完成时，只通知直接依赖它的后继，并把刚好解除最后一项等待的后继加入当前可执行前沿。

这意味着我们需要两类增量信息：第一，完成当前课程后应该通知谁；第二，每个后继还剩多少项前置没有满足。只要这两类信息存在，就不必重新读取已经确认过的条件。

## 7. 容易想到但走不通的方向

### 7.1 直接按课程编号或输入顺序学习

编号看起来像天然顺序，但编号不承载先后语义。`[[0,1]]` 明确要求课程 1 在课程 0 之前，按 `0,1` 学习立即违反条件。输入数组的先后也只是数据排列，不代表依赖层级。

这个方向保存了一个现成顺序，却没有保存“这个顺序是否满足每条边”。失败告诉我们：顺序必须由依赖状态动态产生，不能从编号或输入位置猜测。

### 7.2 用并查集判断环

在无向图中，加入一条边时发现两端已经连通，常用并查集判断环。因此看到“图中有环”容易联想到并查集。但本题的方向不可忽略：`0 -> 1` 与 `1 -> 0` 含义不同，而普通并查集只保存“属于同一个连通集合”，不保存谁必须在谁之前。

例如 `0 -> 1、0 -> 2、1 -> 2` 是合法的有向无环图；忽略方向后却形成一个三角形，无向意义下有环。普通并查集会误判。这不是性能问题，而是模型丢失了方向信息。

### 7.3 从每门课单独做一次可达搜索

可以从每个节点出发，沿依赖不断搜索，看能否回到起点。它在逻辑上可以判断环，但如果每个起点都建立一套全新访问状态，同一条边会被许多次搜索重复经过，最坏接近 `O(V(V+E))`。

搜索本身不是错误方向，错误在于没有跨起点复用结论。后面介绍的 DFS 三色模型正是修正版本：白色表示没检查，灰色表示在当前路径，黑色表示整片后继已经确认无环。黑色结论可以被所有后续起点复用，因而总时间降到 `O(V+E)`。

### 7.4 把边建成 `course -> required`

看到数组 `[course, required]` 后顺手从第一项连向第二项很自然。对于本题只判断有没有环，反转全部边不会改变“是否存在有向环”，所以错误方向甚至可能通过所有布尔测试。这正是它危险的地方。

如果入度被解释为“仍未满足的前置数量”，边就必须是 `required -> course`。否则初始入度 0 的是“没有后继依赖自己的课程”，并不是“无需前置的课程”。一旦题目扩展为输出课程顺序、计算最少学期或记录释放过程，反向模型立刻给出错误答案。建模不能只追求当前返回值碰巧相同，还要让状态语义与题意一致。

## 8. 关键视角转换

优化前，我们不断站在未完成课程的角度发问：

```text
课程 3：我的前置 1 完成了吗？前置 2 完成了吗？
下一轮课程 3：我的前置 1 完成了吗？前置 2 完成了吗？
```

优化后，站在“刚完成的课程”一侧主动释放：

```text
课程 1 完成：通知课程 3，它少等一项。
课程 2 完成：再通知课程 3，它已不再等待，可以进入前沿。
```

| 原视角 | 新视角 |
| --- | --- |
| 未完成课程反复查询全部前置 | 已完成课程只通知自己的直接后继 |
| 每轮重新判断“条件是否全满足” | 用一个剩余数量增量记录未满足条件 |
| 反复扫描全体寻找下一门课 | 用容器保存已经发现的当前可执行前沿 |
| 试图一次猜出完整顺序 | 每次只做一个现在必然合法的局部动作 |

一门课原来有 `k` 项前置，就把它的状态压缩为整数 `k`。每完成一个直接前置，该整数减一；从 1 变为 0 的瞬间，就是这门课第一次满足全部条件的事件。这是本题最关键的状态压缩：我们不再反复保存和询问每项前置的真假，只维护尚未满足的总数。

> **小白追问：** “入度”到底在数什么？它是这门课总共有多少前置，还是现在还没完成的前置？
>
> **先给短答：** 建图刚结束时，两种说法相同；处理开始后，代码维护的是“仍未完成的直接前置数量”，所以它会随着前置课程完成而递减。
>
> **最小例子：** 课程 3 依赖课程 1 和 2，初始计数是 2。完成 1 后，原始依赖仍有两条，但未满足的只剩课程 2，因此计数变为 1；完成 2 后变为 0。这个动态计数回答的是“现在还差几项”，不是在修改题目历史。
>
> **回到模型/代码：** `remainingPrerequisites[course]++` 建立初始计数，`remainingPrerequisites[nextCourse]--` 消耗一项已经满足的前置。不变量要求数组值始终等于尚未解除的入边数。

> **小白追问：** 为什么只有剩余前置数量为 0 的课程才能先学？计数为 1 时先放进队列，等那项前置稍后完成不行吗？
>
> **先给短答：** 队列表示“现在立刻执行也合法”的课程，不是预约名单；计数大于 0 就代表至少有一条先修条件尚未满足，提前执行会直接违反题意。
>
> **最小例子：** 课程 2 依赖课程 0 和 1。若只完成 0 时就把计数为 1 的课程 2 入队，下一次可能先学 2、后学 1，关系 `1 -> 2` 被破坏。等计数从 1 降到 0 再入队，才说明 0 和 1 都已经完成。
>
> **回到模型/代码：** 初始化和后续释放都使用同一资格条件 `remainingPrerequisites[course] == 0`。因此 `readyCourses` 的队列不变量是：其中每门课在入队时全部前置均已满足。

为什么这样减少重复？每条有向边只负责一次“通知”。前置课程只会完成一次，因此它发出的每条通知也只发生一次。每门课程只在剩余数量第一次变成 0 时进入前沿，并且只会完成一次。于是工作量由“轮数乘网络大小”变成“节点数加边数”。

## 9. 正式建立模型

先把推导结论固定下来，此时才准备选择实现结构：

| 建模项 | 本题结论 |
| --- | --- |
| 对象 | 课程节点，以及表示先修要求的有向边 |
| 关系 | `[course, required]` 建模为 `required -> course` |
| 状态 | 每门课尚未满足的直接前置数量；已经发现但尚未处理的可执行课程；每门课的直接后继 |
| 事件 | 一门可执行课程被完成，它的每条出边随之被解除 |
| 不变量 | 剩余数量始终等于“指向该课程、但前置节点尚未完成”的边数；前沿中的课程剩余数量均为 0 |
| 结果时机 | 前沿耗尽后，用已完成课程数是否等于总课程数判断答案 |

### 9.1 为什么这些状态足够

判断一门课现在能不能学，只关心它是否还有未满足前置，不关心这些前置过去按什么顺序完成，所以一个计数足够。完成一门课后，只需要知道哪些课程直接依赖它，所以保存出边邻接关系足够。已经可以学习但尚未处理的课程需要被保留，这就是“前沿”。

无需保存完整的课程排列来判断布尔结果。`completedCourses` 只计数即可；如果题目要求输出顺序，才额外把每次处理的课程追加到列表。

### 9.2 哪些信息可以永久丢弃

课程出前沿并被完成后，不会再次变成未完成，可以永久丢弃该课程本身。它的一条出边被解除后，也不会恢复，可以永久不再考虑。某门后继的剩余数量降为 0 后，只入前沿一次；由于计数只会递减，不会再次从正数变为 0。

> **小白追问：** 一门课到底什么时候入队，为什么不会因为多个前置陆续完成而重复入队？
>
> **先给短答：** 它只在“最后一项未满足前置刚被解除”的瞬间入队，也就是计数第一次从 1 变成 0；计数之后不会增加，所以这个瞬间只可能发生一次。
>
> **最小例子：** 课程 3 依赖 1 和 2，计数变化为 `2 -> 1 -> 0`。完成 1 时没有入队，完成 2 时入队一次。课程 3 以后即使被取出并处理，计数也不会回到 1，更不会再次发生 `1 -> 0`。
>
> **回到模型/代码：** 代码先执行 `remainingPrerequisites[nextCourse]--`，随后只在 `== 0` 时 `offer`。不能写成“每次减一都入队”，也不应使用可能掩盖错误递减的 `<= 0`。

### 9.3 遍历方向

遍历沿 `required -> course` 方向进行，因为事件是“required 已完成”，需要找到所有因此少等一项的 `course`。如果只保存反向列表 `course -> required`，每完成一门课时就无法直接定位应该通知谁，只能重新扫描全图。

> **小白追问：** 出队一门课后，为什么只减少它的直接后继入度，不能顺便减少所有间接后继？
>
> **先给短答：** 一次出队只证明“当前课程”完成了，因此只能解除以它为直接前置的边；间接后继等待的是中间课程，必须等中间课程也真正完成后再解除。
>
> **最小例子：** 有 `0 -> 1 -> 2`。完成 0 时，只能把课程 1 的计数从 1 减到 0。若同时把课程 2 也减到 0，课程 2 会在课程 1 尚未完成时入队，越过了依赖 `1 -> 2`。
>
> **回到模型/代码：** `for (int nextCourse : dependents.get(completedCourse))` 只遍历当前节点邻接表中的直接后继。课程 1 日后出队时，才由它自己的邻接表释放课程 2。

### 9.4 相同课程、重复依赖和自依赖

同一门课程出现在多条不同依赖中完全正常，例如 `[3,1]` 与 `[3,2]` 表示课程 3 要等两门课，初始剩余数量是 2。官方约束保证完全相同的课程对不会重复，因此不需要用集合去重。

在更一般的业务数据中，如果 `[3,1]` 重复两次，有两种一致做法：要么邻接表保留两条边且计数加二，完成 1 时也沿两条边减二；要么先把重复边去重，并且计数只加一。最危险的是只对一边去重，导致邻接表和计数不一致。本题按官方唯一性约束直接存储即可。

若出现 `[0,0]`，课程 0 的剩余数量为 1，初始不会进入前沿，也没有别的课程能解除它；最终处理数不足，正确识别为自环。

## 10. 所需数据结构详解

模型先要求三项能力：按前置课程快速找到直接后继；按课程编号快速读写剩余数量；按发现顺序保存当前可执行前沿。与这些能力匹配的结构分别是邻接表、数组和队列。这个“不断取出入度为 0 的节点并删除其出边”的过程，通常称为 **Kahn 拓扑排序**。

### 10.1 邻接表：保存“完成我会释放谁”

Java 中用 `List<List<Integer>> dependents`。外层下标是前置课程，`dependents.get(required)` 保存所有直接依赖它的课程。

```text
依赖 [[1,0],[2,0],[3,1],[3,2]]

dependents[0] = [1, 2]
dependents[1] = [3]
dependents[2] = [3]
dependents[3] = []
```

建立时每条边追加一次，遍历时每条边读取一次，总成本 `O(E)`；连同 `V` 个空列表，空间为 `O(V+E)`。邻接矩阵也能表达方向，但需要 `O(V^2)` 空间，并且处理一个节点时要扫描全部 `V` 个可能后继。本题最多只有 5000 条边，相对 2000² 个位置较稀疏，邻接表更贴合“只访问真实依赖”。

邻接表里保存的是**后继课程编号**，不是边的布尔值，也不是前置课程编号。课程编号足以定位它的剩余计数。

### 10.2 入度数组：保存“我还差几项前置”

`int[] remainingPrerequisites` 以课程编号随机访问。每读取一条 `required -> course`，执行 `remainingPrerequisites[course]++`。数组查询和增减都是 `O(1)`，空间为 `O(V)`。

图论把“指向某节点的边数”称为入度。随着前置课程完成，我们在逻辑上删除对应入边，因此数组中的值不是永远不变的原始入度，而是**尚未解除的入度**。用 `remainingPrerequisites` 比简写 `degree` 更容易在代码中保留业务语义。

布尔数组无法替代这个计数。若课程 3 同时依赖 1 和 2，完成 1 后只能说明“已满足一项”，不能把课程 3 直接标为可执行；必须知道它还差一项。

> **小白追问：** 已经有邻接表记录依赖，为什么还要入度数组？这不是把同一份关系保存了两遍吗？
>
> **先给短答：** 两者来自同一批边，却回答两个不同方向的问题：邻接表回答“我完成后影响谁”，入度数组回答“某门课现在还差几项”；缺少任意一个，更新都要重新扫描依赖。
>
> **最小例子：** 三门课有 `0 -> 1、0 -> 2、1 -> 2`。完成 0 时，邻接表立刻给出后继 `[1,2]`；此时入度数组说明课程 1 从 1 降到 0，而课程 2 从 2 降到 1。只看邻接表，不知道 2 是否还等 1；只看入度数组，又不知道完成 0 应该修改 1 和 2，而不是修改所有课程。
>
> **回到模型/代码：** `dependents.get(completedCourse)` 确定更新目标，`remainingPrerequisites[nextCourse]--` 更新目标的资格状态。它们形成“定位谁变化”和“变化后还剩多少”的配合，不是意义重复的两份答案。

### 10.3 队列：保存当前可执行前沿

当前所有剩余数量为 0、但还没有完成的课程构成前沿。实现使用 `ArrayDeque<Integer>`：

- `offer(course)` 把刚刚被释放的课程放到队尾，均摊 `O(1)`。
- `poll()` 从队头取出下一门课程，`O(1)`。
- `isEmpty()` 判断前沿是否耗尽，`O(1)`。
- 最坏情况下所有课程都没有依赖，队列同时保存 `V` 个编号，空间 `O(V)`。

为什么用队列？前沿中任意课程都合法，先进先出提供稳定、直观的处理过程，也方便扩展到按层计算最少学期。若只判断能否完成，使用栈同样正确，因为选择哪个零入度节点不影响“是否最终能删除全部节点”；优先队列也正确，但会多出 `O(log V)` 排序成本，除非题目要求字典序最小顺序。`LinkedList` 可以当队列，却有额外节点对象；`ArrayDeque` 是 Java 中更直接的双端队列实现，并且不允许 `null`，这里课程编号本来也不会是 `null`。

> **小白追问：** 入度数组已经能找出计数为 0 的课程，为什么还要专门维护队列？
>
> **先给短答：** 数组保存所有课程的资格状态，队列保存“已经发现、接下来待处理”的前沿；没有队列，就得在每完成一门课后重新扫描整个数组寻找新的 0。
>
> **最小例子：** `0 -> 1 -> 2` 中，初始扫描发现 0 并入队。完成 0 后，代码已经准确知道刚变化的是课程 1，便直接把新变成 0 的 1 入队。若不保存队列，就要再次检查 `[0,1,2]` 三个位置；完成 1 后还要再扫一次，重复检查没有变化的课程。
>
> **回到模型/代码：** 入度数组是资格的事实来源，`readyCourses` 是待处理工作清单。只有计数从 1 变 0 的事件才向队列追加课程，`poll()` 则消费这个已确认合法的前沿对象。

### 10.4 DFS 三色替代法：只看取舍

DFS 三色是同一问题的替代模型：白色表示尚未检查，灰色表示仍在当前递归路径，黑色表示该区域已经确认无环。沿边再次遇到灰色节点就发现环。本文不展开第二套实现，因为它不会帮助理解当前“前置完成后释放后继”的主线。

| 选择 | 适用条件 | 时间与空间 | 局限 |
| --- | --- | --- | --- |
| Kahn 入度释放 | 想得到可执行顺序、分层学期数，或希望全程迭代 | 时间 `O(V+E)`，空间 `O(V+E)` | 若要恢复具体环路径，需要额外设计 |
| DFS 三色 | 重点是沿依赖路径找环，或需要恢复一条环 | 时间 `O(V+E)`，空间 `O(V+E)`，其中递归栈最坏 `O(V)` | JVM 深递归有栈溢出风险，也不如队列模型直观展示“现在能学谁” |

本题只返回布尔值，两者都正确。这里选择 Kahn，不是因为 DFS 错误，而是因为队列、剩余前置数和课程安排的业务动作可以逐项对应。

## 11. 生活化类比及边界

把课程想成公司里的审批任务。每个任务桌上有一张“尚缺签字数”卡片；某项前置任务办结后，工作人员只去通知直接依赖它的任务，把对应卡片减一。卡片变成 0 的任务进入叫号队列，等待办理。

| 生活对象或动作 | 算法中的对应物 |
| --- | --- |
| 一项审批任务 | 一门课程节点 `course` |
| “任务 B 完成后才能做任务 A” | 有向边 `B -> A` |
| 尚缺签字数卡片 | `remainingPrerequisites[course]` |
| 办结后查看要通知的任务清单 | `dependents.get(completedCourse)` |
| 当前可以办理的叫号队列 | `readyCourses` |
| 办结一项并通知后继 | 出队，然后将每个后继计数减一 |
| 卡片从 1 变成 0 | 后继首次满足全部条件并入队 |
| 柜台无人可叫但仍有未办任务 | 剩余任务互相等待，依赖中存在环 |
| 全部任务办结 | `completedCourses == numCourses` |

这个类比解释了状态如何变化，却不是完整证明。现实审批可能被撤回、增加临时条件、允许人工跳过，算法模型都不允许这些变化；输入关系在运行期间固定，课程完成后也不会撤销。现实中两个无依赖任务可以真正并行，当前代码只是依次出队，但这不会改变“能否全部完成”的答案。队列的先后也不是课程唯一顺序，只是众多合法选择中的一种。

## 12. 典型输入的完整数据变化图

使用一个既有分叉又有汇合的输入：

```text
numCourses = 6
prerequisites = [[1,0],[2,0],[3,1],[3,2],[4,2],[5,3],[5,4]]

关系方向：
              +----> 1 ----+
              |            v
0 ------------+            3 ----+
              |            ^     |
              +----> 2 ----+     v
                     |            5
                     v            ^
                     4 -----------+
```

邻接表和初始剩余数量：

```text
dependents[0] = [1, 2]      remaining = [0, 1, 1, 2, 1, 2]
dependents[1] = [3]
dependents[2] = [3, 4]
dependents[3] = [5]
dependents[4] = [5]
dependents[5] = []

队列方向始终写作：队头 [较早入队元素, 较晚入队元素] 队尾
初始只有课程 0 的剩余数量为 0：队头 [0] 队尾
```

完整稳定状态如下。表中的 `remaining` 是本轮所有通知完成后的状态：

| 步骤 | 当前输入 | 处理前队列 | 判断依据与执行动作 | 处理后 `remaining` | 处理后队列 | 新增结果 |
| ---: | --- | --- | --- | --- | --- | --- |
| 初始化 | 扫描所有课程 | `[]` | 只有课程 0 的计数为 0，将 0 入队 | `[0,1,1,2,1,2]` | `[0]` | 已发现首个可执行课程 |
| 1 | 出队课程 0 | `[0]` | 0 合法完成；通知 1 和 2，它们都从 1 降到 0并入队 | `[0,0,0,2,1,2]` | `[1,2]` | `completed=1` |
| 2 | 出队课程 1 | `[1,2]` | 通知 3；3 从 2 降到 1，仍需等待课程 2 | `[0,0,0,1,1,2]` | `[2]` | `completed=2`，本步无人新入队 |
| 3 | 出队课程 2 | `[2]` | 通知 3 和 4；两者都从 1 降到 0并入队 | `[0,0,0,0,0,2]` | `[3,4]` | `completed=3` |
| 4 | 出队课程 3 | `[3,4]` | 通知 5；5 从 2 降到 1，仍需等待课程 4 | `[0,0,0,0,0,1]` | `[4]` | `completed=4` |
| 5 | 出队课程 4 | `[4]` | 通知 5；5 从 1 降到 0并入队 | `[0,0,0,0,0,0]` | `[5]` | `completed=5` |
| 6 | 出队课程 5 | `[5]` | 5 没有后继，完成后无需通知 | `[0,0,0,0,0,0]` | `[]` | `completed=6` |

把第 2、3 步放大看，最能说明“全部前置”与结果时机：

```text
课程 3 初始还差 2 项：{1, 2}

完成 1：2 -> 1
        课程 3 仍不能入队，不产生可执行结果

完成 2：1 -> 0
        课程 3 第一次满足全部条件，现在才入队
```

> **小白追问：** 课程 3 在完成课程 1 后已经少等一项，为什么不能先放进队列，等轮到它时课程 2 也许已经完成了？
>
> **先给短答：** 队列没有“轮到时再复查”的约定；进入队列就是算法对合法性的承诺，所以必须在入队当下已经满足全部条件。
>
> **最小例子：** 处理前队列是 `[1,2]`，课程 3 同时依赖二者。课程 1 出队后，队列只剩 `[2]`。若此时错误加入 3，队列变成 `[2,3]`，这个样例碰巧仍先处理 2；但若容器换成栈，3 会先于 2 被处理。正确性不能依赖容器碰巧给出的顺序。
>
> **回到模型/代码：** 入队资格由状态本身决定，而不是由 FIFO 偶然兜底。`remainingPrerequisites[3]` 从 2 降到 1 时不操作，从 1 降到 0 时才执行 `readyCourses.offer(3)`。

循环结束时队列为空并不单独代表失败。这里队列为空时 `completed=6`，等于总课程数，所以返回 `true`。判断必须同时看“前沿是否耗尽”和“是否覆盖全部对象”。

## 13. 边界场景的数据变化

### 13.1 有独立分支，但另一部分存在环

```text
numCourses = 5
prerequisites = [[1,0],[2,1],[0,2],[4,3]]

环形分支：0 -> 1 -> 2 -> 0
可完成分支：3 -> 4
初始 remaining = [1,1,1,0,1]
初始队列：队头 [3] 队尾
```

状态变化：

| 步骤 | 出队 | 动作 | 队列 | 已完成数 |
| ---: | ---: | --- | --- | ---: |
| 初始化 | 无 | 只有 3 的计数为 0 | `[3]` | 0 |
| 1 | 3 | 4 从 1 降到 0，4 入队 | `[4]` | 1 |
| 2 | 4 | 没有后继 | `[]` | 2 |

此时课程 0、1、2 的剩余数量仍是 `[1,1,1]`。队列为空，但 `completed=2 < 5`，返回 `false`。这说明算法不会因为完成了一部分合法课程就误判成功；环以外的节点可以正常处理，环内节点最终全部残留。

### 13.2 没有任何依赖

`numCourses=3, prerequisites=[]` 时，初始计数为 `[0,0,0]`，三门课全部进入队列。循环各处理一次，邻接列表都是空，最终 `completed=3`，返回 `true`。边循环不执行，不会越界，也不需要特殊分支。

### 13.3 自己依赖自己

`numCourses=1, prerequisites=[[0,0]]` 时，计数为 `[1]`，初始队列为空，主循环一次都不执行，`completed=0`，返回 `false`。默认计数和统一返回条件已经覆盖自环。

### 13.4 完全相同的依赖对

官方保证课程对互不相同，所以实现不做去重。若把非官方输入 `[[1,0],[1,0]]` 交给当前实现，邻接表中有两个 `1`，其计数也是 2；完成 0 时连续减两次，1 仍会正确入队一次。虽然可行性结果不受影响，但业务上重复边通常应在输入层规范化。绝不能只对邻接表去重却仍累计两次计数，或者反过来，否则“计数等于剩余边数”的不变量会被破坏。

## 14. 正确性与不变量

要证明的不是“代码看起来像拓扑排序”，而是下面这个充要关系：算法处理全部课程，当且仅当题目存在合法完成顺序。

### 14.1 循环开始前

建图时，每条 `required -> course` 都让 `course` 的计数加一，因此初始 `remainingPrerequisites[course]` 正好等于它的全部直接前置数量。所有计数为 0 的课程进入队列，所以队列中每门课都无需等待；任何初始可执行课程也没有被漏掉。

### 14.2 一次处理为什么始终合法

课程只有在计数为 0 时入队。计数为 0 表示所有指向它的依赖边都已经随着前置课程完成而解除。因此从队头取出的课程满足题目条件，完成它不会违反任何先修约束。

通知后继时，每条出边恰好对应“当前课程是后继的一项直接前置”。当前课程刚刚完成，所以将后继计数减一有确切业务含义。计数从 1 变 0 时，最后一项未满足条件刚刚消失，此时入队既不早也不晚。

### 14.3 为什么不会漏掉可执行课程

一门课程如果最终满足全部前置，那么它的每个直接前置都必然在某一步被处理。每个前置被处理时，算法都会沿对应出边将它的计数减一。最后一个前置完成时，计数必然降到 0并入队，因此不会漏掉。

一门课程也不会重复入队。计数只递减；只有从正数第一次到 0 的时刻满足 `== 0`，之后不存在第二次到 0。官方边唯一性确保每条关系只被建立一次；即使概念上有多条不同前置，每条也只解除一次。

> **小白追问：** `completedCourses` 只是一个数量，没有保存具体完成了谁，为什么足以判断“所有课程都能完成”？
>
> **先给短答：** 具体身份已经由“每门课最多入队、出队一次”保证不重复；因此计数每增加一，就代表新增完成了一门不同课程，达到总数就等价于覆盖全部课程。
>
> **最小例子：** 总共 3 门课，若实际出队顺序是 `0,1,2`，计数从 0 变成 3，覆盖全部。它不可能通过重复出队 `0,0,0` 凑到 3，因为课程 0 只会在计数第一次降到 0 时入队一次。
>
> **回到模型/代码：** `completedCourses++` 紧跟在唯一的 `poll()` 后，最终比较 `completedCourses == numCourses`。若无法证明入队唯一性，这个全局计数就不能可靠使用。

### 14.4 被处理的边为什么可以永久删除

课程完成后不会撤销，对应先修条件永久满足。它的出边被计数消费后，不再影响任何未来判断。删除这条候选关系不会漏掉后续答案，因为它能造成的唯一状态变化已经发生。

### 14.5 为什么处理数不足就一定有环

如果队列耗尽但仍有未处理课程，那么剩余课程中没有入度为 0 的节点；每个剩余节点至少还有一条来自剩余集合的前置边。任选一个剩余节点，沿它尚未完成的前置向后追，再从那个前置继续追。剩余节点数量有限，却可以一直追下去，所以必然再次遇到某个已经经过的节点，形成有向环。

环中每门课都要求环里的另一门先完成，不可能选出第一门，因此不存在覆盖全部课程的合法顺序。反过来，如果处理数等于 `V`，实际出队顺序本身就是一条合法顺序，所以一定可以完成。两边合起来，返回条件既充分又必要。

> **小白追问：** 队列空了、还有课程没处理，为什么剩余部分一定包含环？会不会只是算法漏放了一门本来能学的课？
>
> **先给短答：** 在入度计数和释放规则保持不变量的前提下，可学课程必然在最后一个前置完成时入队；所以队列空意味着每个剩余节点都仍指向另一个剩余前置。有限个节点一直沿前置追下去，只能重复遇到节点，从而形成环。
>
> **最小例子：** 剩余课程只有 0、1、2，且三者计数都大于 0。假设 0 还等 2，2 还等 1，1 还等 0；追踪链是 `0 <- 2 <- 1 <- 0`，回到了 0。即使依赖更多，剩余集合有限，追踪也迟早重复某个节点。
>
> **回到模型/代码：** `while` 结束时先得到“没有 `remainingPrerequisites == 0` 的待处理课程”，再用 `completedCourses < numCourses` 确认确实有残留。两项同时成立才推出残留环；单看队列为空不能判断失败。

> **小白追问：** 为什么不能在队列第一次变空时直接返回 `false`，还要比较 `processedCount` 或 `completedCourses`？
>
> **先给短答：** 成功时队列最终也会为空；队列只描述“还有没有待处理前沿”，处理计数才描述“全局对象是否已经覆盖”。
>
> **最小例子：** `0 -> 1` 中，先处理 0，再处理 1，队列同样变空，但此时 `completedCourses=2` 等于课程总数，应返回 `true`。在 `0 -> 1 -> 0` 中，队列从一开始就空，`completedCourses=0<2`，才应返回 `false`。
>
> **回到模型/代码：** 循环条件只控制何时停止，最终结果由 `return completedCourses == numCourses` 产生。泛用骨架中的同一角色叫 `processedItems`，两者都承担全局覆盖证明。

### 14.6 多个零入度选择为什么不影响可行性

队列中两门课程都已经不依赖任何未完成课程，先处理哪一门都合法。处理其中一门只会解除更多条件，不会给另一门新增前置，也不会使任何计数增加。因此任意选择零入度节点都不会把原本可行的图“选坏”；这也是普通队列、栈都能判断可行性的原因。

## 15. 时间与空间复杂度推导

定义：

- `V = numCourses`，表示课程节点数。
- `E = prerequisites.length`，表示有向依赖边数。
- 额外空间不包含输入数组和布尔返回值，但包含为计算建立的邻接表、计数数组和队列。

### 15.1 直接重复扫描模型

预先构建每门课的前置列表需要 `O(V+E)` 时间和空间。一次全局扫描最多查看 `V` 门课程，并在所有课程之间合计读取至多 `E` 项前置，所以一轮为 `O(V+E)`。最不利时每轮只完成一门课程，共进行 `V` 轮：

```text
时间：O(V * (V + E))
空间：O(V + E)
```

如果枚举全部排列，则有 `V!` 个候选，每个候选验证位置与依赖需要 `O(V+E)`，时间为 `O(V! * (V+E))`，空间根据生成方式至少为 `O(V)`。

### 15.2 入度释放模型

初始化 `V` 个邻接列表和扫描初始零计数课程各为 `O(V)`。读取每条依赖，追加邻接表并增加一次计数，共 `O(E)`。

主循环中每门课程最多入队一次、出队一次，所以节点操作合计 `O(V)`。虽然循环里还有一层遍历后继，但不是每次都扫描全部边：一条边只属于一个前置节点的邻接列表，而该节点只出队一次，因此每条边只导致一次减计数，合计 `O(E)`。总时间为：

```text
O(V) + O(E) + O(V) + O(E) = O(V + E)
```

> **小白追问：** 代码明明是 `while` 里面套 `for`，为什么不是 `O(V * E)`？
>
> **先给短答：** 内层循环每次访问的是当前课程自己的后继，不是重新扫描全部 `E` 条边；把所有外层轮次的内层访问加起来，每条边恰好只出现一次。
>
> **最小例子：** 三条边 `0 -> 1、0 -> 2、2 -> 3` 中，出队 0 时访问前两条，出队 2 时访问第三条，出队 1 和 3 时访问零条。总访问数是 `2+0+1+0=3=E`，不是四门课各访问三条边。
>
> **回到模型/代码：** 成本要按 `dependents.get(completedCourse)` 中元素的总生命周期求和。每个 `completedCourse` 只出队一次，所以所有邻接列表长度之和为 `E`，节点操作再加 `V`，得到 `O(V+E)`。

空间方面，邻接表外层和全部边为 `O(V+E)`，计数数组为 `O(V)`，队列最坏保存 `V` 门课程。合并后为 `O(V+E)`。返回值只有一个布尔量；本实现不保存完整拓扑顺序。Kahn 模型没有递归调用栈。

### 15.3 DFS 三色替代的复杂度

每个节点从白变灰、再从灰变黑，各发生一次；每条边在其起点 DFS 时检查一次，所以时间也是 `O(V+E)`。邻接表和颜色数组使用 `O(V+E)`，递归栈最坏深度 `O(V)`，总体仍为 `O(V+E)`，但递归深度必须明确计入额外空间。

### 第一层：泛用依赖释放骨架

下面的骨架不使用“课程”作为唯一场景。`dependencies[i] = [dependent, prerequisite]` 可表示构建任务、审批步骤或作业流水线。核心角色保持不变：后继表、剩余前置数、可执行前沿、已处理数。

```java
import java.util.ArrayDeque;
import java.util.ArrayList;
import java.util.Deque;
import java.util.List;

class DependencyFrontier {
    boolean canProcessAll(int itemCount, int[][] dependencies) {
        // 固定关系：dependents.get(x) 表示“完成 x 后，需要被更新的对象”。
        // 例如 [3, 1] 表示 3 等待 1；完成 1 后要更新 3。
        List<List<Integer>> dependents = new ArrayList<>(itemCount);
        for (int item = 0; item < itemCount; item++) {
            // 一门课可能影响多门后续课程，因此每个对象对应一个列表。
            dependents.add(new ArrayList<>());
        }

        // 变化状态：每个对象还剩多少个前置条件没有完成。
        // 数量为 0，表示当前可以处理。
        int[] remainingPrerequisites = new int[itemCount];
        for (int[] dependency : dependencies) {
            int dependent = dependency[0];
            int prerequisite = dependency[1];

            // dependent 等待 prerequisite：把 dependent 放入 prerequisite 的影响范围。
            dependents.get(prerequisite).add(dependent);

            // dependent 多了一个尚未完成的前置条件。
            remainingPrerequisites[dependent]++;
        }

        // 当前可执行前沿：可以处理、但还没有处理的对象。
        // 处理顺序不影响本题的 true/false 结果。
        Deque<Integer> readyItems = new ArrayDeque<>();
        for (int item = 0; item < itemCount; item++) {
            if (remainingPrerequisites[item] == 0) {
                // 没有前置等待，可以作为过程的起点。
                readyItems.offer(item);
            }
        }

        // 全局统计：已经真正处理完成的对象数量。
        int processedItems = 0;
        while (!readyItems.isEmpty()) {
            // 从“可以处理”变成“现在处理”，这代表一次完成事件。
            int completedItem = readyItems.poll();

            // 当前对象已完成，无论它是否影响其他对象，都要计入总数。
            processedItems++;

            // 只遍历当前对象的影响范围，不扫描全部依赖关系。
            for (int dependent : dependents.get(completedItem)) {
                // completedItem 已完成，dependent 少等待一个前置条件。
                remainingPrerequisites[dependent]--;

                // 只有最后一个前置条件被解除时，dependent 才能进入待处理列表。
                if (remainingPrerequisites[dependent] == 0) {
                    readyItems.offer(dependent);
                }
            }
        }

        // 列表为空只表示过程无法继续；还要比较数量，才能判断是否全部完成。
        return processedItems == itemCount;
    }
}
```

这个骨架的抽象判断没有隐藏调用：`remainingPrerequisites[dependent] == 0` 就是“全部前置已处理”的完整定义；`processedItems == itemCount` 就是“处理覆盖全部对象”的完整定义。若业务允许动态新增依赖、撤销任务或失败重试，这个静态骨架便不够，需要重新定义状态变化规则。

> **小白追问：** Java 循环里为什么必须先减计数，再判断是否等于 0；能不能先判断原值是不是 0？
>
> **先给短答：** 当前完成事件要先被记到账上，判断的才是“解除这项前置之后还剩多少”；若先判断，最后一项前置尚未反映到状态里，课程会晚一拍甚至永远不入队。
>
> **最小例子：** 后继课程原计数为 1。当前前置完成后，它应立刻可学。正确顺序得到 `1 -> 0`，随后入队；若先检查 `1 == 0`，结果为假，再减到 0，却已经错过本次唯一的入队时机。
>
> **回到模型/代码：** 更新顺序固定为 `remainingPrerequisites[dependent]--`，再执行 `if (... == 0) offer(...)`。这两行共同表达“事件先改变状态，改变后的状态触发结果”。

```java
import java.util.ArrayDeque;
import java.util.ArrayList;
import java.util.Deque;
import java.util.List;

class Solution {
    public boolean canFinish(int numCourses, int[][] prerequisites) {
        List<List<Integer>> dependents = new ArrayList<>(numCourses);
        for (int course = 0; course < numCourses; course++) {
            dependents.add(new ArrayList<>());
        }

        int[] remainingPrerequisites = new int[numCourses];
        for (int[] prerequisite : prerequisites) {
            int course = prerequisite[0];
            int required = prerequisite[1];
            dependents.get(required).add(course);
            remainingPrerequisites[course]++;
        }

        Deque<Integer> readyCourses = new ArrayDeque<>();
        for (int course = 0; course < numCourses; course++) {
            if (remainingPrerequisites[course] == 0) {
                readyCourses.offer(course);
            }
        }

        int completedCourses = 0;
        while (!readyCourses.isEmpty()) {
            int completedCourse = readyCourses.poll();
            completedCourses++;

            for (int nextCourse : dependents.get(completedCourse)) {
                remainingPrerequisites[nextCourse]--;
                if (remainingPrerequisites[nextCourse] == 0) {
                    readyCourses.offer(nextCourse);
                }
            }
        }
        return completedCourses == numCourses;
    }
}
```

## 17. 边界、常见错误与调试观察点

| 层次 | 常见错误 | 直接后果 |
| --- | --- | --- |
| 建模错误 | 把“依赖谁”和“释放谁”混成同一方向 | 入度失去“剩余前置”的业务含义 |
| 建模错误 | 只要完成部分节点就返回成功 | 图中独立分支可完成、环形分支残留时误判 |
| 建模错误 | 用普通并查集忽略方向判断环 | 把合法的有向汇合结构当成无向环 |
| 条件错误 | 后继计数减一次就立刻入队 | 多前置课程尚未全部完成便被提前学习 |
| 条件错误 | 用 `<= 0` 掩盖重复减计数 | 数据不一致时可能让同一课程重复入队 |
| 实现错误 | 建立 `course -> required` 后仍把入度解释成前置数 | 布尔答案可能碰巧正确，但输出顺序语义错误 |
| 实现错误 | 外层列表创建后未为每个课程添加空列表 | `get(required)` 越界或得到缺失容器 |
| 实现错误 | 只看循环结束时队列为空 | 成功和环阻塞两种结束状态无法区分 |
| 实现错误 | 邻接表去重但入度不去重 | 计数永远无法降到 0 |

调试时不要只打印最终布尔值。对小图打印下面四项，几乎可以定位全部核心错误：

```text
1. 建图后：required -> dependents[required]
2. 初始化后：remainingPrerequisites 全数组
3. 每次循环前：队头到队尾的 readyCourses
4. 每次释放：completedCourse -> nextCourse，计数 old -> new
5. 循环结束：completedCourses / numCourses
```

可以建立三条人工断言：队列里的课程计数必须为 0；计数不能小于 0；一门课程只能在计数从 1 变 0 时入队。对于示例 3，若初始化队列不是 `[0]`，优先检查边方向和计数加在了哪个下标；若课程 3 在只完成课程 1 后就入队，检查是否错误地把“满足任一前置”当成“满足全部前置”。

检查 DFS 三色版本时，应打印 `current`、进入前的颜色、当前递归路径和退出后的颜色。遇到灰色节点才代表当前路径成环；遇到已经访问过的黑色节点不是环，而是复用了已验证区域。

### 17.1 从题目到过程建模：本题的完整推导

这道题不应该从“能不能套队列、Map 或图”开始。先把题目的动作翻译成人能够执行的过程：

```text
题目动作：上一门课程
目标结果：判断所有课程能不能都上完
直接关系：[course, prerequisite] 表示 course 必须等待 prerequisite
```

继续扩写一次真实事件：

```text
找到当前可以上的课程
-> 上完这门课程
-> 找到所有等待它的后续课程
-> 后续课程的未完成前置数量减一
-> 数量变成 0 的课程，现在也可以上
-> 把这些课程放入待处理列表
-> 重复上述过程
```

从这段过程里，不是先猜数据结构，而是先看需要回答哪些问题：

```text
1. 每门课程前面还有多少门课没上？
2. 上完当前课程后，哪些课程需要被更新？
3. 哪些课程已经可以上但还没有处理？
4. 整个过程一共上完了多少门课？
```

这四个问题分别产生四份信息：

```text
remainingPrerequisites：每门课程剩余的前置数量
dependents：完成当前课程后，需要更新的后续课程列表
readyItems：当前可以处理但还没有处理的课程
processedItems：全局已经完成的课程数量
```

它们不是四份凭空想到的容器，而是从一个“笨但正确”的过程逐步优化出来的：

```text
先为每门课程保存等待列表
-> 每轮扫描全部课程，寻找等待列表为空的课程
-> 发现“当前可学课程”被反复寻找，保存 readyItems
-> 发现“谁在等待刚完成课程”被反复寻找，反向保存 dependents
-> 发现后续只需要知道还剩几项等待，把等待列表压缩成 remainingPrerequisites
-> 最后用 processedItems 判断是否覆盖全部课程
```

因此，`foreach` 只是执行已经建模好的动作，不负责发现题目的逻辑：

```text
遍历对象：当前课程的直接后续课程
遍历原因：当前课程刚刚完成，需要解除它造成的等待
每次变化：后续课程的剩余前置数量减一
触发条件：数量变成 0，后续课程加入待处理列表
```

这条推导链可以迁移到其他依赖题：

```text
题目动作
-> 参与对象
-> 对象之间的方向关系
-> 一次动作会影响谁
-> 被影响对象的状态如何变化
-> 什么状态允许下一步
-> 如何保存待处理对象
-> 如何判断最终成功
```

本题的最终判断是：待处理列表耗尽后，已完成课程数是否等于课程总数。若相等，所有课程都能上完；若小于总数，说明仍有课程被依赖关系困住，过程无法完成。

### 17.2 算法名称与可迁移模板

### 这道题叫什么

这道题使用的是**拓扑排序**。当前代码采用的是“入度 + 后继列表 + 待处理队列”的实现方式，通常称为 **Kahn 算法**。

名称只是给已经推导出的过程命名：

```text
不断选择当前没有未完成前置的对象
-> 处理这个对象
-> 解除它对直接后继的影响
-> 产生新一批没有未完成前置的对象
```

本题只要求判断能否全部完成，因此不必保存完整顺序，只统计处理数量：

```text
处理数量 == 对象总数 -> 全部完成，返回 true
处理数量 < 对象总数  -> 仍有对象被依赖关系困住，返回 false
```

### 过程建模模板

遇到“任务依赖、课程先修、构建依赖、审批前置”等题目时，先用自然语言回答：

```text
1. 正在处理的对象是什么？
2. [A, B] 表示谁必须等待谁？
3. 一个对象完成后，会直接影响哪些对象？
4. 每个对象还剩多少个前置条件没有完成？
5. 剩余前置数量变成什么值时，可以继续处理？
6. 当前可以处理但还没有处理的对象放在哪里？
7. 过程结束后，如何判断所有对象是否都完成？
```

对应的通用模型是：

```text
前置对象 -> 后继对象
后继对象的剩余前置数：初始化时增加，前置完成时减少
剩余前置数为 0：进入当前可执行前沿
处理一个前沿对象：释放它的所有直接后继
前沿为空：过程结束
处理数量是否覆盖全部对象：得到最终答案
```

### Kahn 算法伪代码模板

```text
创建 successorList：每个对象完成后要更新哪些后继
创建 remaining：每个对象还剩多少个前置条件

遍历每条依赖 [dependent, prerequisite]：
    successorList[prerequisite] 加入 dependent
    remaining[dependent] 加一

把所有 remaining 等于 0 的对象加入 ready

processed = 0
只要 ready 不为空：
    取出一个当前可处理对象 current
    processed 加一

    遍历 successorList[current] 中的每个后继 next：
        remaining[next] 减一
        如果 remaining[next] == 0：
            把 next 加入 ready

返回 processed == 对象总数
```

### Java 泛用模板

下面的模板只适用于静态依赖关系、目标为“能否全部完成”的场景。变量名可以替换成课程、任务、模块或审批节点，但关系方向不能随意交换。

```java
import java.util.ArrayDeque;
import java.util.ArrayList;
import java.util.List;
import java.util.Queue;

class DependencyTemplate {
    boolean canProcessAll(int itemCount, int[][] dependencies) {
        // successorList[prerequisite]：完成 prerequisite 后，需要更新哪些对象
        List<List<Integer>> successorList = new ArrayList<>(itemCount);
        for (int item = 0; item < itemCount; item++) {
            successorList.add(new ArrayList<>());
        }

        // remaining[item]：item 还剩多少个前置条件没有完成
        int[] remaining = new int[itemCount];

        for (int[] dependency : dependencies) {
            int dependent = dependency[0];
            int prerequisite = dependency[1];

            // dependent 等待 prerequisite
            successorList.get(prerequisite).add(dependent);
            remaining[dependent]++;
        }

        // 当前可以处理、但还没有处理的对象
        Queue<Integer> ready = new ArrayDeque<>();
        for (int item = 0; item < itemCount; item++) {
            if (remaining[item] == 0) {
                ready.offer(item);
            }
        }

        int processed = 0;
        while (!ready.isEmpty()) {
            int current = ready.poll();
            processed++;

            // 当前对象完成，解除它对所有直接后继的一项等待
            for (int next : successorList.get(current)) {
                remaining[next]--;
                if (remaining[next] == 0) {
                    ready.offer(next);
                }
            }
        }

        // ready 为空后，只有全部对象都处理过才算成功
        return processed == itemCount;
    }
}
```

### 模板不能直接套用的情况

先确认题目目标，再决定保留哪一部分：

| 题目目标 | 需要的调整 |
| --- | --- |
| 判断能否全部完成 | 保留 `processed == itemCount` |
| 输出一个合法顺序 | 保存每次取出的 `current`，最后返回顺序；处理数量不足时返回空结果 |
| 计算分几轮/几学期完成 | 按当前队列大小分层处理，每层代表一轮 |
| 要求字典序最小的合法顺序 | 把 `Queue` 换成按编号取最小值的优先队列 |
| 找出具体的环 | 通常改用 DFS 三色标记，并保存当前路径 |
| 依赖会动态新增或撤销 | 重新定义状态变化，静态入度模板不再直接适用 |

### 17.3 优先队列：小根堆与大根堆

一个直观记忆方式是：

```text
大根堆：优先取大的根
小根堆：优先取小的根
```

这里的“根”就是堆顶，也就是下一次从优先队列中取出的元素。名称描述的是“谁优先出队”，不是说所有元素已经整体排好序。

普通队列只回答：

```text
现在有哪些对象可以处理？取出其中最早进入的一个。
```

但有些题目会额外要求：

```text
每次必须取编号最小的对象
```

这时不能继续使用普通队列，因为普通队列保证的是先进先出，不保证编号顺序。需要一种“每次取出当前最优对象”的待处理结构：优先队列。

优先队列通常用堆实现。堆不保证所有元素整体有序，只保证堆顶是当前应该优先取出的元素；这正好满足“加入对象、取出当前最优对象”的需求。

#### 小根堆

小根堆的堆顶是当前最小值：

```text
加入：[3, 1, 4, 2]
每次取出：1 -> 2 -> 3 -> 4
```

它适合：

```text
每次取最小编号
每次取最短距离
每次取最早时间
```

在“字典序最小的合法拓扑顺序”中，当前有多门课程可以学习时，要选择编号最小的课程，因此使用小根堆。

Java 的 `PriorityQueue` 默认就是小根堆：

```java
PriorityQueue<Integer> ready = new PriorityQueue<>();
ready.offer(course); // 加入候选课程
int current = ready.poll(); // 取出当前编号最小的课程
```

#### 大根堆

大根堆的堆顶是当前最大值：

```text
加入：[3, 1, 4, 2]
每次取出：4 -> 3 -> 2 -> 1
```

它适合：

```text
每次取最大编号
每次取最高优先级
每次取最大收益
```

Java 的 `PriorityQueue` 默认不是大根堆，需要传入反向比较器：

```java
PriorityQueue<Integer> ready =
        new PriorityQueue<>(Comparator.reverseOrder());
```

或者写成：

```java
PriorityQueue<Integer> ready =
        new PriorityQueue<>((a, b) -> b - a);
```

通常更推荐 `Comparator.reverseOrder()`，因为它直接表达“按默认顺序反向排列”，也避免数值相减在极端整数值下发生溢出。

#### 小根堆和大根堆的选择

不要先背“某题用小根堆”。先看题目要求每次取什么：

```text
取任意一个：普通队列、栈或集合都可以
取最小值：小根堆
取最大值：大根堆
取最早进入的：普通队列
取最近一次加入的：栈
```

因此，在拓扑排序中：

```text
只判断能否完成：普通队列即可
输出任意合法顺序：普通队列即可
输出字典序最小顺序：小根堆
输出字典序最大顺序：大根堆
```

把普通队列换成堆，只改变“当前多个可执行对象中的选择规则”，不改变入度减少、后继释放和成环判断的核心过程。

所以真正可迁移的不是某一段 Java 代码，而是这条顺序：

```text
先写实际处理过程
-> 明确固定关系
-> 明确会变化的状态
-> 明确状态变化的触发事件
-> 明确当前可执行前沿
-> 明确成功/失败条件
-> 最后选择容器和代码 API
```

## 18. 最终模型卡

| 模型卡项目 | 结论 |
| --- | --- |
| 题型识别指纹 | 对象之间有“必须先于”的有向依赖，要求判断能否全部完成或输出合法顺序 |
| 一句话关系模型 | `[course, required]` 是 `required -> course`，课程可执行当且仅当所有入边都已解除 |
| 实际保存什么 | 邻接表保存完成当前课程会释放谁；入度数组保存每门课还差几项前置；队列保存当前可执行前沿 |
| 状态何时变化 | 一门课完成时，它的每个直接后继剩余计数减一 |
| 答案何时产生 | 前沿耗尽后比较已处理课程数与总课程数 |
| 核心不变量 | 剩余计数等于尚未完成前置对应的入边数，队列中的课程计数均为 0 |
| 时间复杂度 | Kahn 与三色 DFS 都是 `O(V+E)` |
| 空间复杂度 | `O(V+E)`；DFS 还包含最坏 `O(V)` 递归栈 |

四句建模结论：

```text
我正在处理的对象是：由先修关系连接起来的课程节点。
我必须持续保存的是：每门课尚未满足的前置数量、它能释放的后继，以及当前可执行前沿。
当一门前沿课程完成时，我执行：解除它的每条出边，并把剩余前置数量降到 0 的后继加入前沿。
答案在可执行前沿耗尽后由已完成课程数是否等于课程总数计算出来。
```

可迁移的泛用模板：

```text
把“前置 -> 后继”建成有向边
-> 统计每个对象尚未满足的前置数量
-> 收集所有数量为 0 的对象作为当前前沿
-> 每处理一个前沿对象，只释放它的直接后继
-> 用处理覆盖数判断是否存在无法消除的循环依赖
```

迁移变式：

| 题目 | 主要变化 | 模型如何调整 |
| --- | --- | --- |
| 210. 课程表 II | 结果从布尔值变为具体顺序 | 保存每次出队课程；数量不足时返回空数组 |
| 1136. 平行课程 | 结果时机变为完成所需轮数 | 按队列层处理，同层课程视为同一学期 |
| 1203. 项目管理 | 状态增加组内与组间两级依赖 | 分别建图并保持两层拓扑约束一致 |
| Maven/Gradle 构建顺序 | 对象变为模块，边变为构建依赖 | 模板不变；若需稳定顺序可把队列换成优先队列 |
| 查找一条具体环 | 结果从“是否残留”变为环路径 | 更适合 DFS 三色，并额外保存父节点恢复路径 |

看到新题时，不要先背“拓扑排序”四个字。先问：每个对象还差哪些前置？某个对象完成时会释放谁？能否把“所有前置是否完成”压缩成一个只减不增的计数？如果答案都是肯定的，可执行前沿模型就自然出现了。
