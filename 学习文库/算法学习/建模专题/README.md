# T0 算法直观建模专题：生成规范与进度

## 1. 文档定位

本目录用于维护 T0 经典算法题的“直观建模专题”。专题的重点不是更快地给出标准答案，而是完整保留下面这条思考链：

```text
读懂题目
-> 找到第一切入点
-> 建立一定正确的直接模型
-> 看见重复工作或无效状态
-> 转换观察视角
-> 定义最小状态和变化事件
-> 写出不变量
-> 选择数据结构
-> 得到可运行代码
-> 证明正确性和复杂度
-> 提炼可迁移模型
```

### 目标读者

- 已经具备 Java 业务开发经验，能读懂循环、集合、类和方法。
- 对常见数据结构有零散认识，但还不能从题目自然推导出结构。
- 容易看懂题解，却难以独立找到切入点或解释代码为什么成立。
- 希望建立可迁移的建模能力，而不是继续积累互不关联的模板。

### 单篇目标

- 不设置固定字数或一级章节数量；篇幅由题型复杂度和真实知识断点决定。
- 必须完整覆盖题意、暴力基线、浪费点、视角转换、状态、不变量、结构选择、演算、正确性、复杂度和迁移。
- 优先保证因果关系、例子可验证和代码映射清楚，不为了篇幅重复解释。

## 2. 与标准题解的职责边界

每道题仍然只有一篇标准主文档，位于 `../题目/<主题型>`。建模专题是学习推导层，不声明为第二篇标准题解。

| 文档类型 | 主要职责 | 不承担的职责 |
| --- | --- | --- |
| 核心模型 | 一句话本质、生活类比、状态事件表、最小演算和识别信号 | 完整试错史和权威代码 |
| 标准题解 | 准确题意、标准解法、唯一权威代码、边界和复杂度 | 完整记录学习者如何从零走到模型 |
| 建模专题 | 切入点、试错、视角转换、证明和迁移方法 | 替代标准题解或维护第二份实现 |

双向关联规则：

1. 每篇建模专题必须链接对应的标准题解和核心模型。
2. 标准题解、核心模型和深挖专题使用稳定相对链接双向关联。
3. 事实冲突时以题目来源、`problems.json` 哈希和本地测试重新核验，不能机械认定任意一篇天然正确。
4. 题意、约束、方法入口等事实允许在专题中完整转述，但专题叙事必须围绕建模过程重新组织。

## 3. 目录和命名约定

规划后的目录结构：

```text

├─ README.md
├─ 核心模型/
│  └─ <主题型>/
│     └─ 题号-English-Title-核心模型.md
├─ 题目/
│  └─ <主题型>/
│     └─ 题号-English-Title.md
└─ 建模专题/
   ├─ README.md
   └─ T0/

```

专题文件名示例：

```text
T0/1-Two-Sum-直观建模.md
T0/3-Longest-Substring-Without-Repeating-Characters-直观建模.md

```

文件要求：

- 使用 UTF-8 无 BOM。
- 英文题名与标准题解保持一致，使用连字符分词。
- 不在 `题目` 目录中创建第二份同题文档。
- 专题尚未生成时，进度表只写预期路径，不创建无内容占位文件。

## 4. 总体写作原则

### 4.1 先建模，后命名结构

不能以“这是一道滑动窗口题”作为推导起点。正确顺序是先得到要维护的区间、状态和变化规则，再说明这种规则适合由滑动窗口实现。

```text
不推荐：题目有连续子串，所以使用滑动窗口。

推荐：答案对应连续区间；右端加入字符可能破坏合法性；
      左端只需单向收缩就能恢复合法性；
      因而只要维护一个不断右移、必要时左移的区间。
      这类状态维护方式通常称为滑动窗口。
```

### 4.2 题目故事必须翻译成关系

每篇文章都要从自然语言中提取：

| 要素 | 要回答的问题 |
| --- | --- |
| 对象 | 算法真正处理的是元素、下标、节点、区间还是状态？ |
| 关系 | 要寻找的是配对、先后、包含、可达、最值还是计数？ |
| 方向 | 信息来自左边、右边、父节点、子节点还是邻接节点？ |
| 状态 | 在任意时刻，哪些信息必须继续保留？ |
| 事件 | 什么变化会让状态更新或让答案产生？ |
| 不变量 | 每一步结束后，必须继续成立的性质是什么？ |
| 结果 | 答案在什么时候、由哪些状态计算出来？ |

### 4.3 允许出现真实的错误方向

文章可以记录双重循环、排序、双指针、Map、递归等第一反应，但必须满足：

- 说明这个方向为什么自然，而不是把它嘲讽成“错误思路”。
- 用具体输入找到失败点、重复工作或无法维护的信息。
- 说明失败结论的适用范围。例如某方法可能正确但太慢，而不是逻辑错误。
- 错误方向的作用是推动下一次建模，不是堆积无关解法。

### 4.4 官方资料用于校验，不控制叙事顺序

- 题意、约束、方法签名和示例需要回到题目来源核验。
- 官方题解可以作为正确性和复杂度的交叉参考。
- 推荐模型不必与官方方法顺序一致；优先选择更容易推导、更容易解释且更可迁移的路径。
- 当本题约束允许一个更直白的专用解法时，应诚实介绍，并与通用模型比较，不能为了套模板而隐藏更简单的思路。

### 4.5 解释动作，不翻译语法

不要逐行解释 `i++`、`push` 或 `get` 的字面含义。重点解释：

- 这一步改变了哪个状态。
- 为什么现在可以改变。
- 改变后保持了什么性质。
- 哪个动作产生了答案。

### 4.6 用小白反问降低经验密度

默认读者会读 Java 循环、数组、集合和方法，但不预设其理解题型标签、状态、不变量、均摊、剪枝、支配关系或候选淘汰。文章中的每个解释句都要接受一次内部质询：

1. 这句话处理的对象到底是谁？
2. 是否使用了尚未解释的概念？
3. 结论依赖什么前提，凭什么成立？
4. 如果不这样做，最小反例是什么？
5. 能否用 2 至 5 个元素完整走一步？
6. 它最终对应哪个变量、条件、状态变化或代码动作？

逐句质询是审稿方法，不要求把每句话都改写成对话。只有暴露出前置知识、因果跳步、边界误解或代码映射困难的地方，才在原知识断点附近加入可见问答：

```markdown
> **小白追问：** 为什么这里可以……
>
> **先给短答：** 用一句话直接回答。
>
> **最小例子：** 用 2 至 5 个元素演算一次。
>
> **回到模型/代码：** 指向对应状态、不变量、变量或判断条件。
```

问答写作规则：

- 新术语首次出现时，先用生活语言说明它解决什么问题，再给正式名称。
- 出现“只需”“可以删除”“不会遗漏”“一定”“最优”“均摊”“不变量”等结论时，必须给出依据。
- 每个关键条件都要回答“不这样会怎样”，优先给最小反例。
- 一个段落只推进一个主要推理；过长句要拆成前提、动作和结论。
- 不逐行翻译 Java 语法，但必须解释变量角色、判断条件和更新顺序。
- 问答必须解决真实认知断点，不能把上一句改成疑问句后原样重复。
- 每篇只完整讲透一条推荐模型；暴力负责建立基线，其他正确方法压缩为适用条件、复杂度和局限对比。
- 逐句审稿结论统一记录在 [小白逐句审稿台账](小白逐句审稿台账.md)，不得只靠作者口头声明完成。

## 5. 单篇专题的职责覆盖

下面各节说明必须覆盖的语义职责，不要求一级标题数量固定，也不要求逐字使用标题。机器门禁检查语义关键词，审稿检查因果关系；两者都通过后才算完整。

### 5.1 题目档案

必须列出：

- 题号、中文题名、英文题名和难度。
- LeetCode 来源链接。
- 对应标准题解的相对链接。
- 原清单标签、P0/P1/P2 优先级和本专题中的核心模型。
- 本篇希望解决的具体学习困难。

这一节只建立上下文，不提前公布“看到这题就用什么结构”。

### 5.2 完整题目

采用完整、忠实的中文转述，不直接复制来源页面的长段落。至少包含：

- 输入是什么。
- 输出是什么。
- 至少两个编号示例，复杂模型建议三个。
- 每个示例的必要解释。
- 全部约束和题目提示。
- Java 方法入口签名。

约束不能放在文末当作附属信息。正文后面必须说明哪些约束会影响复杂度或模型选择。

### 5.3 先把题目说成人话

暂时移除题目背景，只保留生活动作和目标。要求分别写出：

1. 一句话生活化复述。
2. 一句话关系化复述。
3. 对象、关系、方向、目标和限制表。

如果使用公式，必须先用具体数据解释变量，再给公式；不能让公式代替理解。

### 5.4 第一切入点：读题时先看什么

明确指出：

- 哪些关键词真正决定模型，例如“连续”“第一个”“恰好”“最多”“依赖”。
- 哪些故事词只是包装，可以暂时忽略。
- 数据范围提供了什么性能信号。
- 最小样例中，人工是怎样得到答案的。

这一节的目标是让读者知道下次遇到陌生题时，第一分钟应该观察什么。

### 5.5 最直接的人工或暴力模型

先给出一定正确、最接近人工操作的方案：

- 用自然语言写完整步骤。
- 必要时给朴素 Java 或伪代码。
- 说明它为什么不会漏掉答案。
- 推导时间和空间复杂度。
- 不以“这是暴力，所以没价值”一笔带过。

### 5.6 暴力到底浪费在哪里

必须选择一个具体输入，逐步展示重复工作：

```text
第 1 次处理重复看了哪些数据
第 2 次处理又看了哪些相同数据
哪些中间结论算完后被丢弃
哪些候选其实已经永久不可能成为答案
```

优化目标必须写成一个具体句子，例如：

> 不要让每个起点重新扫描未来，而要让新元素到来时一次结算所有能够确定答案的旧起点。

### 5.7 容易想到但走不通的方向

选择一至三个最自然的偏差方向，每个方向回答：

1. 为什么会想到它。
2. 它能保存什么信息。
3. 它缺少什么信息，或在哪里产生重复。
4. 它是错误、超时，还是仅仅不够通用。
5. 从失败中得到什么新的建模条件。

不要为了数量罗列与题目无关的算法。

### 5.8 关键视角转换

用转换前后对照说明优化的真正来源。常见转换包括但不限于：

| 原视角 | 新视角 |
| --- | --- |
| 每个旧对象主动寻找未来 | 新事件到来时结算旧对象 |
| 枚举完整答案 | 枚举答案的最后一步 |
| 反复判断整个区间 | 增量维护区间是否合法 |
| 记录走过的全部过程 | 只记录决定未来的最小状态 |
| 从起点尝试所有路线 | 从终点状态反推前驱 |
| 把矩阵当表格 | 把格子当节点、相邻移动当边 |

必须说明为什么新视角减少了重复，而不只写“换个思路”。

### 5.9 正式建立模型

使用统一模型表：

| 建模项 | 本题结论 |
| --- | --- |
| 对象 | 待填写本题的实际对象 |
| 关系 | 待填写目标关系 |
| 状态 | 待填写必须保留的信息 |
| 事件 | 待填写触发更新的动作 |
| 不变量 | 待填写每一步后的稳定性质 |
| 结果时机 | 待填写答案何时产生 |

生成正式专题时必须把“待填写”全部替换为题目事实，不得保留模板文字。

这一节还要回答：

- 状态为什么足够，是否保存了多余信息。
- 哪些候选可以永久丢弃，以及丢弃为什么安全。
- 遍历方向为什么是当前方向。
- 相等值、重复值或边界状态如何处理。

### 5.10 所需数据结构详解

只讲本题真正用到的数据结构。每种结构必须覆盖：

1. 结构是什么，内部如何组织数据。
2. 本题使用哪些操作。
3. 每个操作的时间复杂度。
4. 结构的关键特征，例如后进先出、先进先出、随机访问或有序性。
5. 为什么这些特征正好匹配刚才得到的状态变化。
6. 为什么常见替代结构不如它合适。
7. 数据结构中保存值、下标、节点还是复合状态。
8. 最坏情况下会保存多少数据。

如果题目只需要数组或几个变量，也要解释这些状态容器的职责，但不能为了凑章节强行引入复杂结构。

### 5.11 生活化类比及边界

类比必须服务于状态变化，至少包含一张映射表：

| 生活对象或动作 | 算法中的对应物 |
| --- | --- |
| 现实中的对象 | 变量、下标、节点或状态 |
| 现实中的等待或移动 | 入栈、出队、指针移动或状态转移 |
| 现实中的规则 | 不变量或触发条件 |
| 现实中的结果 | 算法输出 |

类比之后必须补充“类比到哪里为止”，指出现实故事中哪些细节不属于算法，避免读者把类比误当成完整证明。

推荐类比方向：

- 栈：一摞待处理便签、盘子或撤销记录。
- 队列：排队叫号和分层扩散。
- 滑动窗口：可伸缩检查框或进出受控的房间。
- 哈希表：按唯一编号直接查找的储物柜。
- 链表：只知道下一站地址的接力路线。
- 堆：只保证最紧急事项位于最前面的任务池。
- 回溯：岔路口做选择、走不通后恢复现场。
- 动态规划：保存已经结算的小问题账本。

这些只是候选类比，必须根据题目重新组织，不得机械复制。

### 5.12 典型输入的完整数据变化图

至少完整演算一个能触发核心变化的输入。优先使用简单文本图和 Markdown 表，不依赖图片才能理解。

统一快照字段：

```text
当前输入：正在处理什么
处理前状态：结构中已有内容
判断依据：为什么执行当前动作
执行动作：移动、加入、删除、更新或回退
处理后状态：不变量如何恢复
新增结果：本步产生了什么答案
```

不同模型优先采用以下形式：

```text
数组/双指针：下标行 + 数值行 + 指针箭头
滑动窗口：left/right 边界 + 窗口内容 + 计数状态
栈/队列：栈底到栈顶或队头到队尾的连续快照
链表：A -> B -> C 与 prev/current/next 指针位置
树：ASCII 树 + 当前节点返回值
图：邻接关系 + visited + 队列/递归栈
回溯：选择树 + path + used + 撤销动作
动态规划：状态表 + 当前格来源 + 更新前后数值
```

图中必须标出方向。不能只给最终数组而省略中间状态。

### 5.13 边界场景的数据变化

从下面类型中至少选一个单独演算，题目风险较高时选多个：

- 空状态或只有一个元素。
- 全部相等。
- 严格递增或严格递减。
- 没有可行答案。
- 答案位于第一个或最后一个位置。
- 图不连通、存在环或节点重复访问。
- 数值达到约束边界。

边界演算要说明默认值、循环是否执行、结构最终是否残留数据，以及为什么不会越界。

### 5.14 正确性与不变量

证明使用普通语言优先，至少回答：

1. 当前动作产生的结果为什么满足题目条件。
2. 为什么不会漏掉更早、更近或更优的答案。
3. 被删除、跳过或合并的候选为什么以后也不需要。
4. 当前状态为什么足以支持下一步。
5. 遍历结束时，为什么所有应该得到答案的对象都已处理。

可根据模型采用循环不变量、归纳、交换论证、反证或状态转移证明，但必须先说明证明对象，不堆砌术语。

### 5.15 时间与空间复杂度推导

必须同时分析直接模型和推荐模型，并定义变量：

```text
n 表示什么
m、k、V、E 等其他变量表示什么
一次操作的成本是什么
操作总共发生多少次
额外空间是否包含返回结果
递归深度是否计入空间
```

禁止只写结论。对于带内层 `while` 的线性算法，要按元素生命周期解释均摊复杂度；对于固定值域，要分别说明理论参数复杂度和本题固定范围下的实际含义。

### 5.16 Java：泛用骨架与权威实现引用

专题只负责说明模型如何落到代码，不再维护第二份题目实现。

#### 第一层：泛用模型骨架

- 展示可迁移的控制流程和语义角色。
- 使用 `current`、`pending`、`leftBoundary`、`state` 等有含义的名字。
- 可以省略 `main`，但必须保持 Java 语法完整，不允许使用 `...` 代替逻辑。
- 模型中的抽象判断必须在文字中解释，不能留下未定义调用让读者猜测。

#### 第二层：本题变量映射与权威实现入口

- 用变量映射表连接模型角色与标准题解代码，不复制完整实现。
- 需要展示关键片段时明确标注“非权威片段”，保持 Java 8 兼容。
- 题目可提交代码、本地运行代码和复杂度的唯一权威副本位于标准题解。
- 专题正文必须链接对应标准题解，避免多份实现失同步。

### 5.17 边界、常见错误与调试观察点

至少从三层总结：

| 层次 | 示例 |
| --- | --- |
| 建模错误 | 保存了错误状态、遗漏方向、把局部最优当成全局最优 |
| 条件错误 | `<` 写成 `<=`、边界移动时机错误、重复元素处理错误 |
| 实现错误 | 下标和值混淆、先覆盖再保存、忘记撤销、队列层数计算错误 |

调试建议必须指向可观察状态，例如打印窗口边界、栈中下标、队列当前层、递归返回值或 DP 表，而不是只说“多打日志”。

### 5.18 最终模型卡

结尾必须提供一张可脱离全文复习的模型卡，包含：

1. 题型识别指纹。
2. 一句话关系模型。
3. 栈、队列、窗口、递归或 DP 中实际保存什么。
4. 状态何时变化。
5. 答案何时产生。
6. 核心不变量。
7. 时间和空间复杂度。
8. 四句建模结论。
9. 两至四道迁移变式，并说明变化的是条件、状态还是结果时机。

固定的四句建模结论格式：

```text
我正在处理的对象是：<本题对象>。
我必须持续保存的是：<最小状态>。
当 <关键事件> 发生时，我执行：<状态变化>。
答案在 <结果时机> 由 <相关状态> 计算出来。
```

生成正式专题时必须替换尖括号中的模板内容。

### 5.19 参考资料与交叉核验

每篇至少核对三类来源：

1. 题目原页：确认题意、示例、约束和方法签名。
2. 官方题解或可靠实现：确认复杂度、边界和正确性。
3. 一篇高质量模式讲解或可视化资料：比较不同直觉和术语。

资料规则：

- 文末列出标题、链接和检索日期。
- 清楚区分“来源中的事实”和“本文重新组织的建模结论”。
- 不复制来源中的大段表述、代码或图。
- 多个来源说法冲突时，回到可运行示例和题目约束验证。
- 无法打开或无法核验的页面不能作为关键结论的唯一依据。

## 6. 图示和文字表达标准

### 6.1 图示的最低要求

每篇至少包含：

- 一张题目关系图。
- 一张典型输入的完整状态变化图或表。
- 一张边界场景图或状态快照。
- 一张最终模型卡。

### 6.2 文本图的可读性

- 所有下标、值和方向分别成行，不把多个含义挤在一行。
- 每次状态变化使用同一种栈底/栈顶、队头/队尾方向。
- 动态状态较长时拆成多个快照，不用一张巨图表达全部步骤。
- 表格中的每一行代表一个稳定时刻，避免在同一行混合更新前后状态。
- 文字图必须配解释，不能假设读者能自动看懂箭头。

### 6.3 禁止的图示方式

- 只有最终结果，没有中间变化。
- 用“显然”“同理”跳过模型最关键的状态转折。
- 依赖颜色表达唯一含义，导致纯文本环境无法阅读。
- 图中下标和值混用却不标注。

## 7. 数据结构讲解标准

数据结构章节不是百科全书。讲解范围由本题模型决定，并遵守下面的顺序：

```text
模型需要什么操作
-> 候选结构能否高效提供这些操作
-> 结构要保存什么内容
-> 如何维护结构性质
-> 结构性质如何保证正确性
```

每个核心结构至少回答五问：

1. 为什么是它？
2. 里面存什么？
3. 什么时候加入？
4. 什么时候删除或更新？
5. 删除或更新时是否产生答案？

若使用多个结构，例如“哈希表 + 双向链表”，必须分别说明职责以及它们之间的数据一致性。

## 8. Java 建模表达标准

### 8.1 变量名保留模型语义

推荐：

```text
pendingDays
windowCounts
farthestReachable
remainingPrerequisites
bestEndingHere
```

谨慎使用只有模板作者知道含义的 `a`、`b`、`tmp`、`cur2`。常规循环下标 `i`、`j` 可以使用，但首次出现时要说明角色。

### 8.2 注释解释不变量和原因

注释适合解释：

- 为什么现在可以删除候选。
- 为什么这个方向遍历。
- 为什么先保存 `next` 再改指针。
- 为什么某个默认值无需额外处理。

注释不应重复代码字面动作。

### 8.3 模型骨架与题目代码的映射

完整实现后必须增加一张映射表：

| 模型角色 | Java 变量或代码块 |
| --- | --- |
| 当前对象 | 具体变量 |
| 待处理状态 | 具体集合、数组或指针 |
| 触发条件 | 具体判断表达式 |
| 状态变化 | 具体语句 |
| 结果时机 | 写入答案的位置 |

这样读者看到的不只是“代码能跑”，还知道每行代码在模型中的职责。

## 9. 单篇生成工作流

每次生成一题，严格按以下顺序执行：

1. 读取本规范、对应标准题解、清单标签和根索引。
2. 打开题目原页，核对题意、示例、约束和方法签名。
3. 检索至少两类补充资料，记录不同的直觉、模型和术语。
4. 先写“关系、直接模型、重复工作、视角转换、状态、不变量”的提纲。
5. 对代码块外的解释句逐句质询，标出新术语、因果跳步、删除依据、边界和代码映射问题。
6. 在真实知识断点附近加入“小白追问、先给短答、最小例子、回到模型/代码”四段问答。
7. 完成数据结构、生活类比、文本图、证明和复杂度，并压缩非主线替代解法。
8. 写泛用 Java 骨架和模型到标准题解的变量映射。
9. 运行根目录 Python 门禁，核对标准题解权威代码和官方示例。
10. 创建专题文件，补齐专题、核心模型和标准题解的双向链接。
11. 更新小白逐句审稿台账、本页状态表和根目录专题进度。
12. 完成质量清单后，才开始下一题。

## 13. 质量红线

出现下面任一情况，专题不能标记为完成：

- 一开头就公布数据结构，没有从题目关系推导状态。
- 只有推荐解法，没有直接模型、重复工作或视角转换。
- 生活类比没有映射到变量和动作。
- 文本图只展示最终结果，没有中间状态。
- 正确性只写“显然”“根据定义可知”，没有回答为什么不遗漏。
- 复杂度只有 `O(...)` 结论，没有定义变量和统计操作次数。
- 泛用骨架只是把题目代码换了变量名，没有提炼稳定角色。
- 标准题解的权威代码不能编译、本地示例没有 `main` 或官方示例不能通过。
- 大段照搬官方题解，缺少重新组织后的建模过程。
- 为了显得高级而隐藏更简单、在本题约束下完全成立的模型。

这套规范的最终目标不是让每篇文章看起来相同，而是让每篇文章都能回答同一个核心问题：

> 如果我事先不知道答案，如何从题目事实一步步建立出这个模型？
