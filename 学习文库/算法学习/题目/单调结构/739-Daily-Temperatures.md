### 官方题面原句

> 给定一个整数数组 `temperatures` ，表示每天的温度，返回一个数组 `answer` ，其中 `answer[i]` 是指对于第 `i` 天，下一个更高温度出现在几天后。如果气温在这之后都不会升高，请在该位置用 `0` 来代替。

### 合成后的人话过程

```text
我手里有每天的按顺序温度。
我先把当前天定为第 0 天。
我从当前天的下一天开始向右看。
如果看到严格更高的温度，就记下两个日期的下标差，并停止这一天的寻找。
如果一直看到最后都没有更高温度，就给这一天记 0。
当前天处理完后，移动到下一天，重复同样的过程。
所有天都处理完以后，交回答案数组。
```

### 七列对象表

| 题目对象 | 值和状态 | 身份由什么决定 | 位置或时间 | 从何时有效到何时失效 | 和谁发生关系 | 最终要得到什么 |
| --- | --- | --- | --- | --- | --- | --- |
| 日期 | 第 `i` 天的温度由这个日期持有 | 原始下标 `i` | 时间顺序中的第 i 天 | 从读取原题到交回结果都保持同一身份 | 与未来日期比较温度，并把结果放回自己 | 第一次严格更高日期与它的距离 |
| 绑定在日期上的温度 | 当天数值，例如 `70` | 不能脱离具体日期单独判断 | 跟随该日期的位置 | 只在该日期存在时用于比较 | 与未来日期的温度比较 | 判断未来温度是否严格更高 |
| 每天自己的答案位置 | 未写入或已写入 | 结果下标 `i` | `answer[i]` | 从读取原题到交回结果都属于该日期 | 接收该日期自己的结果 | 日期差，找不到时为 `0` |

`[70,70,71]` 中位置 0 和位置 1 是不同对象。若只保存一个 `70`，结果就无法确定应该写回 `answer[0]` 还是 `answer[1]`。

### 用一次升温捕捉连续结算

取 `[75,71,69,72]`：

```text
75 到来：没有可结算日期，75 等待。
71 到来：71 不高于 75，71 等待。
69 到来：69 不高于 71，69 等待。
72 到来：72 高于 69，结算 69；72 高于 71，结算 71；72 不高于 75，75 继续等待。
```

这里有三件事同时出现：

1. 一个未来温度可以结算多个旧日期；
2. 结算必须从最近加入的日期开始；
3. 一旦遇到仍不低于今天的旧日期，前面的日期也不会被今天结算。

最后一条来自等待日期的温度顺序。若较早的 75 仍在等待，而较晚的 71 也仍在等待，那么 71 到 75 之间的温度关系保证了这种排列；更晚的日期都还没有遇到比自身更高的温度。

### 状态和初始条件

```text
answer[i]：第 i 天第一次遇到严格更高温还要等几天，默认 0
waiting：已经出现、仍未结算的日期下标
```

`waiting` 初始为空。每处理一天，先在 `waiting` 中结算能被今天解决的日期，再把今天加入。

### 一次转移

```text
读取今天 today
当 waiting 非空，且 temperatures[today] > temperatures[waiting 最近项]：
    弹出最近的等待日期 previous
    answer[previous] = today - previous
重复上述结算
把 today 加入 waiting
```

### 不变量

```text
waiting 中只有已经出现、尚未遇到严格更高温的日期。
waiting 中日期下标从旧到新递增。
waiting 中温度从旧到新不增。
```

温度不增的原因是：如果较早日期 i 比较晚日期 j 更冷，那么 j 到来时已经严格高于 i，i 会被结算，不可能继续留在等待集合中。

### 为什么最近项可以先处理

如果今天能结算较早的日期，却先遇到一个仍不低于今天的最近日期，那么这个最近日期和更早日期之间的温度顺序说明：更早日期也不会低于这个最近日期，所以今天同样不能结算它们。于是遇到第一个不满足严格更高的日期就可以停止。

### 最小反例

```text
最小输入：temperatures = [70,70]
原本应保持的不变量或更新顺序：只有严格更高才能结算
如果破坏它，具体哪一步先算错：第 1 天等于第 0 天，如果使用 >=，第 0 天会被错误结算为 1
错误输出：[1,0]
正确输出：[0,0]
修复动作：比较条件必须是 temperatures[today] > temperatures[waiting 最近项]
```

另一个顺序反例：

```text
最小输入：temperatures = [75]
若先把今天加入等待集合，再查询今天是否高于最近等待项，就会用自己和自己比较。
正确顺序是先用今天结算旧日期，再把今天加入等待集合。
```

### 伪代码

```text
answer = 长度为 n 的 0 数组
waiting = 空集合

for today from 0 to n - 1:
    while waiting 非空
          且 temperatures[today] > temperatures[waiting 最近项]:
        previous = waiting 弹出最近项
        answer[previous] = today - previous
    waiting 加入 today

return answer
```

### LeetCode 可直接提交代码

> 入口类与方法已根据 2026-08-30 的官方 Java 模板核验。本代码不包含本地 `main`。

```java
import java.util.ArrayDeque;
import java.util.Arrays;
import java.util.Deque;

class Solution {
    public int[] dailyTemperatures(int[] temperatures) {
        int[] answer = new int[temperatures.length];
        Deque<Integer> stack = new ArrayDeque<>();

        for (int today = 0; today < temperatures.length; today++) {
            while (!stack.isEmpty()
                    && temperatures[today] > temperatures[stack.peek()]) {
                int previous = stack.pop();
                answer[previous] = today - previous;
            }
            stack.push(today);
        }
        return answer;
    }
}
```

### 复杂度和正确性

- 时间复杂度：`O(n)`。每个日期最多加入等待集合一次、被删除一次。
- 空间复杂度：`O(n)`。温度持续不升时，所有日期都可能同时等待。
- 不丢解：某个日期被今天删除时，今天严格更高，且它此前一直没有被更早日期删除，因此今天就是首次严格更高。
- 不漏结算：今天能结算的最近等待日期会被连续删除，直到最近项不再更低。
- 不误结算：相等温度不满足严格 `>`，答案保持等待或默认 0。

## 边界与易错点

- 比较条件必须是严格 `>`；相等温度不是更高。
- 等待容器保存下标而不是温度，否则无法计算天数差。
- 新温度到来时可能连续结算多个旧日期，因此需要循环而不是只判断一次。
- 结果数组默认是 0，末尾仍未结算的日期不需要额外处理。
- 必须先把今天能结算的旧日期全部处理，再加入今天，避免当前日期与自己比较。
- 栈底到栈顶温度保持不增，是删除顺序和安全停止的依据。

## 复习闭环

- **本次主分析法：** 从逐日重扫出发，发现一次高温会连续结算最近一批等待日期，再把“等待日期”保存成按时间排列的状态。
- **闭卷过程链：** 读题确认严格更高 -> 逐日扫描 -> 记第一次答案 -> 数平方预算 -> 发现同一天结算多个旧日期 -> 比较候选 -> 写先结算后加入。
- **最早断点：** 为什么新温度可以从最近等待日期连续删除，又为什么遇到不更低的日期就停止。
- **下次第一步：** 关掉本页，用 `[75,71,69,72]` 写出每一步谁在等待、谁被删除、答案写入哪里。
