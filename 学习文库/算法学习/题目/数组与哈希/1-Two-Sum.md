## 阶段 1：只读题，先确认题目到底给了什么

官方题面原句：

> 给定一个整数数组 `nums` 和一个整数目标值 `target`，请你在该数组中找出 **和为目标值** `target` 的那 **两个** 整数，并返回它们的数组下标。
>
> 你可以假设每种输入只会对应一个答案，并且你不能使用两次相同的元素。
>
> 你可以按任意顺序返回答案。

我先只把能指回原句的内容抄下来，不先猜方法。

| 原句 | 我现在能确认的事实 | 来源 | 我不能自行补上的假设 |
| --- | --- | --- | --- |
| 给定一个整数数组 `nums` 和一个整数目标值 `target` | 输入有两个对象：一个整数数组和一个目标整数 | 事实 | 数组是否有序、是否没有重复值 |
| 找出和为目标值 `target` 的那两个整数 | 要找到两个数值，它们相加必须恰好等于 `target` | 事实 | 是否只需要考虑相邻位置 |
| 返回它们的数组下标 | 输出不是两个数值，而是这两个元素原来所在的位置 | 事实 | 返回顺序是否有大小要求 |
| 每种输入只会对应一个答案 | 在题目保证下，不需要处理多个答案，也不需要选“最左”或“最优”答案 | 事实 | 整数范围内是否还存在无解输入 |
| 你不能使用两次相同的元素 | 两个输出下标必须不同；值相同但位置不同可以组成一对 | 事实 | 两个值相同的元素是否一定出现在相邻位置 |
| 可以按任意顺序返回答案 | `[i, j]` 和 `[j, i]` 都表示同一对位置 | 事实 | 当前扫描方向可以先固定哪一种顺序 |

此刻真实候选：没有形成候选。更准确地说，我只知道“要比较两个不同位置上的值”，但还不知道一个普通人应该按什么顺序把位置拿出来比较。题目没有保证数组有序或没有重复值，因此这里没有形成额外假设。此时想到任何容器名，都只能标成：

```text
记忆候选，不是题目事实
```

### 官方示例

```text
示例 1
输入：nums = [2,7,11,15], target = 9
输出：[0,1]
解释：nums[0] + nums[1] = 2 + 7 = 9

示例 2
输入：nums = [3,2,4], target = 6
输出：[1,2]

示例 3
输入：nums = [3,3], target = 6
输出：[0,1]
```

示例 3 特别重要：两个 `3` 的值相同，但下标 `0` 和 `1` 不同。它提醒我，后面不能把“值相同”误当成“位置相同”。

```text
我刚得到：输入是 nums 和 target，输出是两个不同下标，且每个输入只有一个答案。
但它还不能说明：一个人应该先拿哪个位置、再和哪个位置比较、什么时候停止。
所以现在只问：一个完全不懂算法的人，拿着 nums 和 target 在纸上会怎样开始找？
```

能回答这个问题的是逐句扩写，不是算法名称。

## 阶段 2：把题干扩写成可执行的人话过程

逐句扩写时，我只新增动作、顺序、停止条件和防错作用。

| 原句事实 | 它在人的过程里新增什么 | 如果忽略会错在哪 | 来源 |
| --- | --- | --- | --- |
| 数组 `nums` 有多个位置 | 每个位置上的值都有自己的位置身份 | 只记两个数值，最后不知道要返回哪两个下标 | 推导 |
| 选两个整数 | 一次要拿出一对位置，而不是只看一个元素 | 可能把单个元素当成答案 | 事实 |
| 它们的和等于 `target` | 拿到两个数后，先计算和，再与目标值比较 | 可能只因为两个数都出现过就返回 | 事实 |
| 返回两个下标 | 一旦找到满足条件的两个位置，要保留这两个位置的身份 | 只返回数值或不完整的下标 | 事实 |
| 不能使用两次相同的元素 | 第二个位置必须与第一个位置不同 | 可能把同一个下标拿两次 | 事实 |
| 每种输入只有一个答案 | 第一次找到合法的一对后，不需要继续挑选 | 可能在唯一答案之后继续处理并覆盖它 | 事实 |

把动作连起来，我得到下面这段人话过程：

```text
我手里有 nums 和 target。
先从位置 0 开始，把它当作第一个位置。
再从第一个位置后面找一个不同的位置，当作第二个位置。
把两个位置上的数相加。
如果和等于 target，就把这两个位置交回去，并停止。
如果不等于 target，就换下一个第二个位置。
第一个位置的所有后续位置都试完，再把第一个位置向后移动一格。
直到找到那一对为止。
```

这段过程里有两个容易混淆的动作：

- “两个数”不是“两个值必须不同”；题目允许值和值相同，只禁止同一个位置被使用两次。
- “按任意顺序返回”不代表可以按任意顺序取同一个元素；两个下标仍然必须不同。

## 阶段 3：先留困惑和新增证据，再分清对象并走人工过程

我此刻具体卡在：题目说“两个整数”，但示例 `[3,3]` 里两个数看起来一样，我不知道它们算一个对象还是两个对象。

我现在实际做的纸面动作：圈出“返回它们的数组下标”和“不能使用两次相同的元素”，再在纸上并排写出 `nums[0] = 3`、`nums[1] = 3`。

做完以后新增的证据：两个 `3` 的值相同，但下标不同，因此它们是两个不同位置；答案需要交回位置，而不能只交回一个数值。

这份证据还不够，因为：现在只知道位置不同，还不知道一个人应按什么顺序检查两个位置，以及哪一步会让答案真正确定。

### 3.1 当前困惑、实际纸面动作和新增证据

这里保留上面的真实卡点、实际动作和新增证据。扩写已经能执行，但仍分不清数值和位置的身份；只有圈出返回要求并写出两个位置后，才知道“值相同”和“对象相同”不是一回事。

### 3.2 六列对象表

新增证据已经能区分数值和位置，但还没有完整关系表；现在把对象、值和状态、身份、位置、关系和结果并排写清。

| 题目对象 | 值和状态 | 身份由什么决定 | 位置或时间 | 和谁发生关系 | 最终要得到什么 |
| --- | --- | --- | --- | --- | --- |
| 数值 | `nums[index]` 的取值，例如 `3` | 值本身不能单独决定身份 | 跟随所在位置 | 与另一个数值相加，和 `target` 比较 | 本身不是答案 |
| 位置 | 当前是待检查、已检查还是答案位置 | 数组下标 `index` | 数组中的原始位置 | 两个不同位置组成一个待检查的对 | 输出中的两个整数 |
| 目标值 | 固定的 `target` | 由这一次输入确定 | 不随数组位置移动 | 约束两个位置上的数值之和 | 用来判断一对是否合法 |
| 一对位置 | 待检查或已经合法 | 由两个不同的下标共同决定 | 两个原始位置 | 共同产生一次和 | 合法时成为答案 |

值相同的两个位置仍然是两个不同对象。比如 `[3,3]` 中两个 `3` 有相同的值，但位置分别是 `0` 和 `1`，所以不能返回 `[0,0]`。

### 3.3 人工过程

对象已经分清，但还不知道按什么时间顺序检查位置对；现在用最小完整例子逐步走最直接、可能很慢的过程。

取 `nums = [3,2,4]`，`target = 6`：

| 当前第一位置 | 当前第二位置 | 两数之和 | 和是否等于 6 | 接下来做什么 |
| --- | --- | --- | --- | --- |
| `0`，值 `3` | `1`，值 `2` | `5` | 否 | 保持第一位置不变，移动第二位置 |
| `0`，值 `3` | `2`，值 `4` | `7` | 否 | 第一位置向后移动 |
| `1`，值 `2` | `2`，值 `4` | `6` | 是 | 输出 `[1,2]`，停止 |

这一步只说明过程怎样走，不说明应该用什么结构。

### 3.4 第一次变化

完整过程已经能走，但还不知道哪个对象因为哪个事件改变；这里只记录第一次变化和答案产生时刻。

```text
变化前：已经检查过的位置对都不能组成目标值，我还没有答案。
触发事件：当前两个位置上的数相加，第一次等于 target。
变化后：这两个位置被确定为答案。
答案产生时刻：合法数对第一次被比较出来的那一步。
```

因为题目保证只有一个有效答案，一旦这个变化发生，就不需要比较后面的位置。这里我仍然只得到一个过程事实：答案不是由“某个数出现过”产生的，而是由“两个不同位置的数共同满足关系”产生的。

### 阶段 3 -> 阶段 4 的交接

```text
我刚得到：对象身份、完整的人工比较过程，以及答案产生时刻。
但它还不能说明：这种逐对比较在最大输入上是否会变得太慢。
所以现在只问：官方范围有多大，最坏情况要做多少次核心比较？
```

## 阶段 4：读范围，先估算慢过程，再缩小方向

### 官方约束

- `2 <= nums.length <= 10^4`
- `-10^9 <= nums[i] <= 10^9`
- `-10^9 <= target <= 10^9`
- 每种输入只会存在一个有效答案
- 进阶目标：思考一个时间复杂度小于 `O(n^2)` 的算法

### 4.1 先数最慢的人工过程

固定第一个位置后，第二位置只检查它后面的位置。最坏情况下，每一对位置都要比较一次。

```text
第一位置取 0 时，最多比较 n - 1 次
第一位置取 1 时，最多比较 n - 2 次
...
总比较次数最多为 n(n - 1) / 2
```

当 `n = 10^4` 时：

```text
10000 * 9999 / 2 = 49,995,000
```

接近五千万次比较。这里我只得到一个预算结论：逐对比较的平方级过程不能作为最终方向；我还没有资格从 `n` 直接点名某个算法。

### 4.2 值域还能排除什么

`nums[i]` 和 `target` 都可以到 `±10^9`，数值跨度约为二十亿。因此不能依赖“与整个值域成正比”的额外空间；但这也意味着不能用一个固定大小的小数组把任意值当作连续位置。

### 4.3 从关系产生功能候选

在已经固定一个当前值时，题目关系可以改写成：

```text
另一个值 = target - 当前值
```

例如 `target = 9`，当前值是 `7`，那么另一个值只能是 `2`。这不是新规则，而是原关系移项后的结果。

| 官方约束 | 限制了什么 | 慢过程预算 | 排除哪些复杂度家族 | 排除哪些功能候选 | 保留哪些功能候选 | 仍不能确定什么 |
| --- | --- | --- | --- | --- | --- | --- |
| `n <= 10^4`，元素和 `target` 都可到 `±10^9`，输出要求原下标 | 最多一万个位置，不能用与整个数值跨度成正比的额外空间，也不能丢失原位置 | 最坏逐对比较约 `n(n-1)/2`，即约五千万次 | 排除每个当前位置都完整重扫未来位置的平方级过程 | 排除“每来到一个位置都重新检查所有潜在搭档”这一功能路径 | 保留“当前值确定唯一搭档值后，查询该搭档是否已出现并取回位置”的功能方向 | 仍不知道历史信息需要哪些精确操作、何时加入，以及顺序为何不能交换 |

目前仍然只能列出功能候选：

1. 继续检查所有位置对，代价约五千万次比较。
2. 对一个当前值，先算出唯一需要的搭档值，再问“这个值有没有在我已经看过的位置里出现”。

第二种候选还没有说明历史信息怎样保存、查询时要取回什么，也没有说明什么时候加入，因此它不是最终方向。

### 阶段 4 -> 阶段 5 的交接

```text
我刚得到：平方级比较的成本，以及“当前值只能对应一个搭档值”的功能候选。
但它还不能说明：历史信息会在哪些位置被再次使用，是否真的值得保留，以及需要哪些操作。
所以现在只问：带着这个代价重看过程，哪份信息会被重复询问，什么时候可以复用？
```

## 阶段 5：第二次变化，找到重复查询和所需操作

### 5.1 用最小例子捕捉重复

取 `nums = [2,7,11,15]`，`target = 9`。

当当前值来到 `7` 时，需要的搭档是 `2`。这个 `2` 已经在当前值之前出现过。如果每次来到一个新位置都重新向左找，那么过去的元素会被未来的多个位置反复检查。

这里真正重复的不是“把和算一遍”，而是：

```text
反复询问：某个需要的值，是否已经在历史位置出现过？
```

### 5.2 为什么可以把当前值当成较晚的位置

对任意一个合法数对，两个下标总有一个较小、一个较大：

```text
若 i < j，且 nums[i] + nums[j] = target
那么处理到 j 时，i 已经处理过了。
```

返回顺序任意，所以我完全可以把 `j` 当作当前值，把 `i` 当作之前出现过的搭档。这样每个合法数对至少会在较晚的那个位置被检查一次，不会因为固定扫描方向漏掉。

### 5.3 历史需要支持什么

仅仅知道“某个搭档值存在”还不够。题目要求返回下标，所以历史必须能回答：

```text
需要的值有没有出现过？
如果出现过，它原来的位置是哪一个？
```

处理每个新位置时，还需要把当前值和当前位置加入历史，供未来位置查询。历史不会因为某个当前值处理完就整批失效，因为更晚的位置仍可能使用它。

### 5.4 顺序要求从哪里来

题目说不能使用两次相同的元素。因此，查询当前值的搭档时必须只查看“当前值之前”的历史；不能让当前元素参与自己的答案。

用 `[3,3]`、`target = 6` 检查：

- 处理第一个 `3` 时，如果把自己先加入历史，马上就会把自己当成搭档，得到 `[0,0]`。
- 先查询、后加入时，处理第二个 `3` 才能找到第一个 `3`，得到 `[0,1]`。

所以第二次变化给出的是操作需求和顺序要求，不是某个容器名称：

```text
按值查询历史
如果命中，取回历史位置
把当前值和当前位置加入历史
查询必须发生在加入当前值之前
```

### 5.5 四类第二次变化逐项确认

| 现象 | 本次是否发生 | 最小例子 | 未来会读取、失效、复用或必须保序什么 | 翻译出的操作动词 |
| --- | --- | --- | --- | --- |
| 重复查询 | 发生 | 当前值是 `7` 时只需要补数 `2`；未来每个位置都会再次问“我的补数以前出现过吗” | 需要保留已经处理过的值和原位置，供未来按值回查 | 按值查询、命中后取回位置 |
| 候选失效 | 没有形成该现象 | 当前题目没有会整批排除的候选范围；每个历史位置都可能成为未来位置的搭档 | 不把“已经检查过”错误理解成“以后永远不需要” | 不产生删除或淘汰操作 |
| 子问题复用 | 没有形成该现象 | 当前过程没有从不同路径反复到达同一个更小问题 | 不借用其他题型的状态复用理由 | 不产生子问题状态或转移 |
| 顺序约束 | 发生 | `[3,3]`、`target = 6`：处理第一个 `3` 时若先写入自己，会查到同一个位置 | 查询只能看当前下标之前的历史，当前值必须稍后加入 | 先查询、后加入 |

只有前两行标记为“发生”的机制在本题形成真实需求；“候选失效”和“子问题复用”没有被硬凑成候选。

## 阶段 6：比较候选，确认算法方向

现在才允许具体方法名进入比较。

| 候选 | 支持什么 | 缺少什么 | 何时失效 | 代价 |
| --- | --- | --- | --- | --- |
| 继续逐对比较 | 能完整覆盖所有不同位置对，不需要额外结构 | 不能减少未来位置的重复回扫 | 在最大输入上仍保留约五千万次比较，达不到题目进阶目标 | 时间平方级；空间常数级，但重复工作最多 |
| 先排序位置，再从两端收缩 | 能在有序序列上通过移动一端改变和 | 不能直接保留原始位置作为返回值 | 本题要求返回原下标，单独排序会破坏位置身份 | 时间 `O(n log n)`；还要额外维护值与原下标的关系 |
| 用哈希表保存“历史值 -> 原下标” | 支持按补数精确查询，并在命中时取回历史位置 | 仍然依赖先查询后加入的顺序 | 若先写入当前值，会在 `[3,3]` 上把当前元素当成自己的搭档 | 平均时间 `O(n)`；额外空间 `O(n)`，保存值和位置 |

这里的取舍不是“哈希表比较熟悉”，而是过程已经给出了明确的点查询操作：给定一个补数，问它是否出现，并取回它的位置。排序能支持范围比较，但本过程不需要先获得大小顺序；逐对比较虽然不占额外结构，却保留了最坏的重复工作。

完整方向确认句：

> 当前过程会反复询问“某个补数是否已经在历史位置出现过，并且它的原下标是什么”；继续逐对比较最坏约五千万次，不能稳定满足进阶目标；排序虽然可行，但需要额外的重排和原位置恢复；哈希表能直接按值查询并取回下标，平均一次查询和插入为 `O(1)`，额外空间为 `O(n)`。因此选择从左到右处理位置，用哈希表保存已经处理过的“值 -> 下标”，并保证先查询补数、再加入当前值。

方向到这里才确认。下一段才进入状态、更新顺序、不变量和代码。

## 阶段 7：方向确认后的思维链

### 7.1 状态和初始条件

```text
indexByValue：已经处理过的值 -> 该值最近一次出现的位置
```

初始时还没有处理任何位置，所以 `indexByValue` 为空。

处理下标 `i` 之前，必须满足不变量：

```text
indexByValue 中的每个位置都属于 [0, i)，
并且每个值都能找回它对应的历史下标。
```

### 7.2 一次转移

```text
读取当前值 nums[i]
计算 need = target - nums[i]
查询 need 的历史位置
如果找到，返回 [历史位置, i]
如果没有找到，把 nums[i] -> i 加入历史
```

### 7.3 为什么更新顺序不能交换

如果先把当前值加入历史，再查询 `need`，当前下标可能被自己查询到。最小反例是 `[3,3]`、`target = 6`：处理下标 `0` 时，当前值本身就会满足 `need`，得到错误的 `[0,0]`。

因此必须：

```text
先查询历史
后加入当前值
```

### 7.4 为什么不会漏

对任意合法答案，两个下标中总有一个较晚出现。扫描到较晚的那个下标时，较早的下标已经在哈希表中；此时计算它的补数，就一定查询到较早位置。题目保证只有一个合法答案，所以第一次命中就是答案。

### 7.5 题目对象到代码的逐段映射

| 题目对象 | 人工过程里的动作 | 第二次变化提出的操作要求 | 状态或变量 | 伪代码 | Java 代码位置 | 更新顺序或不变量 | 对应反例 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 当前值及其下标 | 当前值需要唯一的搭档值 | 计算补数 | `i`、`need` | 计算 `target - nums[i]` | `for` 循环前两行 | 当前位置尚未加入历史 | `[2,7,11,15]`、`9` 中 `7` 的补数是 `2` |
| 历史值和原位置 | 查询补数是否出现过并取回位置 | 按值查询、返回历史下标 | `indexByValue`、`previousIndex` | 查询补数 | `indexByValue.get(need)` | 查询只能看到当前下标的左侧 | 第一次处理 `[3,3]` 时不能看到第二个 `3` |
| 当前值和当前位置 | 把当前值留给未来位置 | 加入当前值和原下标 | `indexByValue.put(nums[i], i)` | 写入历史 | `put` 所在行 | 查询结束后才写入 | 先写入会让当前值匹配自己 |
| 最终答案 | 两个不同位置共同满足关系 | 返回历史下标和当前下标 | `new int[]{previousIndex, i}` | 返回两个下标 | `return` 所在行 | 返回时下标天然不同 | 返回同一个下标会违反“不能使用两次” |

最小反例可以实际打破“历史表只覆盖 `[0, i)`”这条不变量：

```text
最小输入：nums = [3,3]，target = 6
原本应保持的不变量或更新顺序：处理下标 i 前，历史表里的位置都属于 [0, i)
如果破坏它，具体哪一步先算错：如果处理 i = 0 时先加入当前值，历史表就包含位置 0，下一步查询补数会命中当前位置自身
错误输出：[0,0]，同一个元素被使用两次
修复动作：先查询 need，再把 nums[i] 和 i 加入历史
```

### 7.7 Java 实现

### LeetCode 可直接提交代码

> 入口类与方法已根据 2026-08-30 的官方 Java 模板核验。本代码不包含本地 `main`。

```java
import java.util.Arrays;
import java.util.HashMap;
import java.util.Map;

class Solution {
    public int[] twoSum(int[] nums, int target) {
        Map<Integer, Integer> indexByValue = new HashMap<>();
        for (int i = 0; i < nums.length; i++) {
            int need = target - nums[i];
            Integer previousIndex = indexByValue.get(need);
            if (previousIndex != null) {
                return new int[]{previousIndex, i};
            }
            indexByValue.put(nums[i], i);
        }
        throw new IllegalArgumentException("No valid pair");
    }

    
}
```

## 复杂度和正确性

- 时间复杂度：平均 `O(n)`。每个位置最多查询一次、写入一次；哈希表的平均查询和写入为 `O(1)`。
- 空间复杂度：`O(n)`。最坏情况下要保存已经处理过的全部值到下标。
- 不变量：处理下标 `i` 前，表里只保存 `[0, i)` 中的位置。
- 不多用：查询发生在写入之前，当前元素不能成为自己的搭档。
- 不漏解：每个合法数对都有较晚出现的下标，处理到它时，较早下标已经在表里。

## 边界与易错点

- `[3,3]`、`target = 6`：两个值相同但位置不同，必须返回 `[0,1]`。
- 无解输入：LeetCode 题面保证有解；当前代码在没有保证的工程环境里抛出异常，并把这一点明确写出来。
- 只存“值是否存在”：能判断补数出现过，却不能取回原下标，输出不完整。
- `Map.get` 返回 `null` 表示没有命中；不能用返回的默认值 `0` 判断未命中，因为下标 `0` 是合法答案。
- 数值范围内 `target - nums[i]` 仍在 `int` 范围内；两数和可能达到 `±2 * 10^9`，也不会越过当前 `int` 范围。
